# Создание и upsert отдают представление, как команда; удаление — `{id, version}`

Исход `:projected` у создания и upsert event-sourced агрегата — представление, прочитанное после
commit запросом актора, как у любой команды; `:accepted` — `{id, version}`. Удаление отдаёт
`{:projected | :accepted, id, version}` в обоих исходах. Удалением считается операция, после
которой запрос актора объект не отдаёт; операция, после которой объект читается (архивирование,
деактивация), — команда. Заменяет ADR-0027 в пункте «создание отвечает `{id, version}` на 200»,
ADR-0039 в пункте «создание — `{id, version}` при `:projected`» и ADR-0047 в пункте «upsert —
`{id, version}`». Норма — `docs/rules/app/10-architecture.md`, «Usecases»;
`docs/rules/22-projections.md`, «Read-after-write»; `docs/rules/app/15-web-api.md`, «Ожидание
проекции».

## Контекст

Факты на 2026-10-06:

- команда event-sourced агрегата отвечает представлением на 200 и `{id, version}` схемой `Written`
  на 202 — две формы по статусу, и это норма для всех команд;
- ADR-0027 отверг представление у создания доводом «ответ создания распадается на две формы по
  статусу», ADR-0039 — доводом «представление usecase читал бы зря»; оба довода относятся к любой
  команде одинаково;
- после создания объект читается всегда: ради этого `:projected` и ждёт проекцию;
- после удаления — в зависимости от проекции: строку она удаляет или оставляет с признаком. У
  event-sourced агрегата soft-delete нет, удаление — доменное событие (`app/11-domain.md`);
- чтение после commit, которое не нашло объект, — исход `:accepted` (ADR-0047): удаление с
  представлением отвечало бы 202 при готовой проекции;
- upsert — создание или команда в зависимости от состояния; после него объект читается всегда.

## Рассмотренные варианты

- **Оставить `{id, version}` у создания (ADR-0027).** Отвергнут: исключение без собственного
  довода, клиент после каждого создания читает представление вторым запросом.
- **`{id, version}` у всех команд, представление — `GET`.** Отвергнут: снимает исключение из CQS,
  но откатывает ADR-0039 и добавляет второй запрос каждой команде.
- **Удаление тоже отдаёт представление.** Отвергнут: при проекции, которая удаляет строку, чтение
  после commit даёт `:not_found` и исход `:accepted` — 202 при готовой read-модели; форма ответа
  зависела бы от устройства проекции.
- **`:projected` с `nil` у удаления.** Отвергнут ADR-0047: тип представления стал бы опциональным
  у всех команд ради одной.

## Решение

- создание и upsert — `{:ok, {:projected, View.t()}} | {:ok, {:accepted, ID.t(), Version.t()}}`,
  как команда; HTTP — `MyAppWeb.Accepted.respond/3`: представление на 200, `Written` на 202;
- удаление — `{:ok, {:projected | :accepted, ID.t(), Version.t()}}`; HTTP —
  `MyAppWeb.Accepted.written/2`, `Written` на 200 и на 202;
- граница «удаление» — объект перестаёт читаться запросом актора; иначе операция — команда;
- создание state-stored агрегата — по-прежнему `{id}` схемой `Created`.

## Цена

- **Ломающее изменение для потребителей:** usecase создания и upsert читает представление после
  ожидания, экшен создания переходит с `written/2` на `respond/3`, операция создания объявляет
  схему представления в `ok:`.
- **Актор без права чтения** получает на создание 202, хотя проекция готова: отказ чтения после
  commit — `:accepted` (ADR-0047), как у любой команды.
- **Граница удаления держится ревью:** сборка не знает, отдаёт ли запрос объект после операции.
