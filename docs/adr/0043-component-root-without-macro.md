# Корень компонента — модуль приложения, макроса `use Core.Component` нет

Корень компонента `<Component>.Supervisor` остаётся модулем приложения, написанным по
`docs/rules/app/17-otp-concurrency.md`, «Компонент»: макроса `use Core.Component` библиотека не
даёт. Повтор в корнях библиотека забирает функцией или готовым деревом, когда за повтором стоит
порядок или проверка, которые можно держать построением. Скелет корня — чтение тумблера, `:ignore`
с `info`, `start_link` с именем модуля, `watch_list/0` и списки читателей с фильтром по тому же
тумблеру — остаётся у потребителя. Решает вариант «Макрос `use Core.Component`», который ADR-0024
отложил; остальное решение ADR-0024 в силе. Норма не меняется.

## Контекст

Факты на 2026-10-03 (обзор корней —
`.scratch/consumer-architecture/research/03-component-roots.md`, снятие отсрочки —
`.scratch/consumer-architecture/decisions.md`, Q31):

- ADR-0024 отложил макрос: он закрепил бы API раньше, чем переезд компонентов покажет общую
  форму корня. Q31 снял отсрочку и назначил порядок: обзор корней, затем ADR и макрос;
- корни по ADR-0024 есть только у потребителя A — 5 корней. У B, C, D, F — 9 корней на версиях
  библиотеки до ADR-0024: у B, C, F реестр `watch_list` повторяет тумблеры, у B и F деревья
  подписчиков свои, у всех четырёх своя проверка единственности очереди. У E компонентов нет.
  Эти корни переписываются при переезде на вертикаль после выпуска core-ex;
- скелет корня у A занимает 11–32 строки кода, всего 117 из 495 (24 %), и у пяти корней четыре
  варианта: тумблер корня над деревом подписчика; кеш без тумблера корня, с подчинённым тумблером
  инвалидатора; тумблер с третьим случаем «нечего запускать» и двумя деревьями под клиентом
  брокера; проверка единственности перед веткой тумблера, ключ под `:core`;
- два корня подписчиков A совпадают почти целиком (92 % строк): из 88 строк кода каждого 50 —
  сборка опций дерева подписчика, 21 — скелет. Те же 50 строк повторяет третий корень с деревом
  подписчика на Stream при другом скелете. Общая трём корням часть — сборка опций, её параметры —
  ключи конфигурации, соединение, фабрика контекста, модуль обработчика, имена процессов;
- корень очереди — единственный вид компонента у нескольких потребителей: у всех пяти с
  компонентами один состав детей в одном порядке (writer → поллер → cleaner, `rest_for_one`) и
  одни ключи `Core.Outbox` в опциях, 31–63 строки опций на корень;
- повторы корней до ADR-0024 библиотека уже забрала функцией и готовым деревом. Своя проверка
  единственности очереди (четыре копии по 15–27 строк) ушла в `Core.Outbox.check_singleton!/1`,
  своё дерево подписчика с процессом-bootstrap (три копии) — в
  `Core.PubSub.MqSubscriberReliable.Supervisor`;
- у A один тумблер для старта и `watch_list/0` держат рукописные корни. Реестр, который повторяет
  тумблеры, остался только в коде B, C, F, написанном до ADR-0024. Тумблер у всех 14 корней,
  включая A, читается с дефолтом `false` в модуле — против `app/17`, «Опции процессов».

## Рассмотренные варианты

- **Макрос `use Core.Component` над скелетом корня** — опции `component:` и `strategy:`, колбэки
  `opts/0`, `children/1`, `watch/1`; генерирует `start_link/1`, `init/1`, `watch_list/0`,
  `readers/0`, `kafka_readers/0`. Отвергнут:
  - он заменяет 11–32 строки, но каждый вариант скелета у A — ещё одна опция или колбэк: корень
    без тумблера, «нечего запускать», проверка перед тумблером с ключом `:core`, своя работа в
    `init/1`. Интерфейс выходит не уже кода, который он прячет;
  - повтор, общий трём корням подписчиков, — сборку опций — макрос не убирает; скелет совпадает
    только у двух корней одного потребителя;
  - построением макрос держал бы одну норму, которую сейчас не держит никто, — тумблер без дефолта
    в модуле (`Keyword.fetch!`). Ради неё одной вводить генерируемые функции не стоит: они у
    потребителя — граница типов (ADR-0014) и требуют сужения результата, сценариев фикстуры и
    проверки опций `use` при компиляции;
  - API скелета подгонялся бы под корни одного потребителя. Форма, которая повторяется у пяти, —
    корень очереди — это кандидат на готовое дерево, а не на макрос.
- **Behaviour `Core.Component` без генерации.** Отвергнут: функции корня (`start_link/1`,
  `watch_list/0`) уже требует норма, а нужны ли `readers/0` и `kafka_readers/0`, решает вид
  компонента. Behaviour добавил бы модуль библиотеки, который ничего не исполняет.
- **Сохранить отсрочку до переезда второго потребителя.** Отвергнут: вопрос «переписывать ли
  корень второй раз» остался бы открытым как раз на время переезда, а переезд B–F предписан
  ADR-0037 и ADR-0040 и пройдёт по `app/17`. Второй потребитель на форме ADR-0024 — условие
  пересмотра, а не причина держать вопрос открытым.
- **Общий корень подписчика модулем библиотеки** — вместо одного параметризуемого модуля у
  потребителя (Q11). Отвергнут: корни подписчиков различаются данными потребителя. Деревья
  библиотеки config и env не читают, опции собирает приложение (`app/17`, «Опции процессов»), а
  само дерево подписчика уже параметризуется опциями.

## Решение

- макроса `use Core.Component` нет: корень компонента — модуль приложения по `app/17`,
  «Компонент». Переезд на вертикаль идёт по `app/17`, и формы макроса, под которую корень
  пришлось бы переписать, нет;
- повтор в корнях библиотека забирает функцией или готовым деревом, если за повтором стоит порядок
  или проверка, которые можно держать построением (дерево подписчика, `check_singleton!/1`).
  Скелет корня она не генерирует;
- корень очереди — кандидат на готовое дерево библиотеки: решение отдельным тикетом
  (`.scratch/consumer-architecture/issues/11-outbox-ready-tree.md`);
- параметризуемый корень подписчика у потребителя (Q11) — его собственная функция сборки опций
  дерева; где ей лежать, свод не нормирует: повтор измерен у одного потребителя;
- пересмотр — новым ADR, если у двух потребителей с корнями по ADR-0024 найдётся общая часть
  корня, которую не забирает функция или готовое дерево библиотеки. Перевод корней на новую форму
  — цена того ADR.

## Цена

- скелет корня повторяется в каждом корне — 11–32 строки. Один тумблер для старта и наблюдения
  держит норма и ратчет `watch_list/0` (`app/19`, «Ратчеты»), а не построение;
- тумблер без дефолта в модуле держит только ревью: дефолт `false` сейчас у всех 14 корней;
- у A сборка опций дерева подписчика повторяется в трёх корнях, пока потребитель не вынесет её в
  свою функцию;
- кандидаты в функции библиотеки остаются без тикета: проверка единственности для компонента,
  который не очередь (`check_singleton!/1` назван по outbox), и сборка опций дерева из общих
  опций топика. Оба ждут подтверждения у второго потребителя с корнями по ADR-0024.
