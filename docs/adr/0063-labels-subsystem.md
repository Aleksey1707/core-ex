# Подписи событий — подсистема `Core.Labels`, а не опции существующих макросов

Частично заменён ADR-0066 (`0066-event-page-event-absorbs-details-wire.md`): wire сведений — не
публичный `Core.Web.Labels`, а часть `Core.Web.Event`, и wire ответа потребителя A меняется. Ниже —
решение в редакции 2026-10-13; устаревшие фразы помечены ссылкой на ADR-0066, при расхождении верен
он.

Название события, подписи полей и значений и вид id в сведениях объявляются отдельными
`use Core.Labels.*` после основного `use` модуля — события, struct'а нагрузки, Enum, Prim, — а не
опциями `Core.Es.Event`, `Core.Enum`, `Core.Prim.*` и плагинов по полям. Из объявлений библиотека
строит сведения события, собирает словарь ссылок страницы событий и отдаёт оба на wire. Тексты —
по-русски, без локализации. Подсистема переносится из потребителя A.

## Контекст

Факты на 2026-10-13:

- потребитель A отдаёт у каждого события на странице событий агрегата название и сведения. Без них
  клиент держит копию знания обо всех событиях — подписи полей и значений, разбор вложенных
  нагрузок, — и копия расходится с доменом молча, при каждом новом событии и поле;
- его ADR называл объявления в библиотеке чище и откладывал их только из-за цикла выпуска core-ex;
- страницу событий агрегата отдаёт ещё один потребитель, подписей у него нет; у остальных
  подписей нет тоже. (Исправлено ADR-0066, «Контекст»: страницу событий отдают три потребителя из
  шести — A, B, F; подписи — только у A.)

## Рассмотренные варианты

- **Опции существующих макросов** (`title:` у `Core.Es.Event`, `labels:` у `Core.Enum`, подписи
  полей у `Es.Event.Payload` и плагинов по полям, вид id у `Prim.UUID`). Отвергнут: подписи
  расходятся по шести-семи макросам, общим для всех потребителей, а построению сведений и ратчету
  полноты знание всё равно нужно собрать в одном месте.
- **В библиотеке только объявления**, сведения, словарь ссылок и wire — у потребителя. Отвергнут:
  ни одно из них не зависит от предметной области, второй потребитель повторил бы их.
- **Локализация (gettext).** Отвергнута: тексты библиотеки уже по-русски (сообщения ошибок), второго
  языка не просил ни один потребитель. «Да» / «Нет» у `boolean` — текст библиотеки.
- **Учётная запись как ссылка на запись** с особым видом записи. Отвергнут: автор есть у каждого
  события, и презентер отличал бы учётную запись по строке вида записи.

## Решение

- Объявления — `Core.Labels.Event`, `Fields`, `Values`, `ID`, `Text`; полнота каждого и порядок
  «после основного `use`» проверяются сборкой. Подключение — по желанию: модуль без них
  собирается как прежде.
- Вид id в сведениях — ссылка на запись (вид записи атомом и резолвер), ссылка на учётную запись
  (резолвер) или только id.
- Сведения — чистая функция «событие → название и сведения» из Prim-значений. Словарь ссылок
  собирается пачкой по резолверу типа id.
- Подписи полей по типу, без значения, — для описания формы — даёт тот же модуль полей.
- Ратчет полноты — один case-модуль на приложение (`otp_app:`): кодеки событий и семейства он находит
  сам среди модулей приложения, поэтому новый кодек ловится без новой строки теста; пустой обход —
  провал. Case на агрегат, как у golden-фикстур, отвергнут: агрегат, которому тест не завели,
  прошёл бы молча.
- Домен — `Core.Labels.*`, JSON он не знает. Wire сведений — дамп и OpenAPI-схемы — в
  `Core.Web.Labels`, вместе (ADR-0064). Форму ссылки на учётную запись на wire задаёт потребитель.
  (Заменено ADR-0066: `Core.Web.Labels` нет, wire сведений — `use Core.Web.Event, labels: true`.)

## Следствия

- Потребитель A переходит на `Core.Labels.*` переименованием модулей; отличия объявлений
  перечисляет CHANGELOG. Первый релиз у него не состоялся, но wire его ответа без причины не
  меняется. (Заменено ADR-0066, «Цена»: у A меняются `payload` и OpenAPI-документ страницы
  событий.)
