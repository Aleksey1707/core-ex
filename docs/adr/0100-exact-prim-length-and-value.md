# Точная длина и точное значение Prim вместо вырожденных границ

`Core.Prim.String` получает `len:` — точную длину строки, `Core.Prim.Integer` и
`Core.Prim.Decimal` — `exact:` — точное значение числа. Обе опции — выражения, на компиляции
раскрываются в `min_len == max_len` / `min == max` и не сочетаются с явными границами.
Вырожденный диапазон, заданный парой, становится `CompileError`; код ошибки точной границы
остаётся `:bounds`, меняется только текст для человека.

## Контекст

- Точную длину строки задавали парой `min_len: n, max_len: n`, точное число — парой
  `min: n, max: n`. Это единственный способ выразить «ровно n»; пара читается как диапазон и
  провоцирует ошибку конфигурации (забыли поправить вторую границу).
- Валидатор вырожденную пару не отличал от диапазона: сообщение было
  `"от 3 до 3 символа(ов)"`, у чисел — `"от 5 до 5"`. Текст уходит клиенту в ответе
  (`code: prim/bounds`), и «от N до N» читается как дефект.
- `__domain_type_opts__/0` — задокументированный контракт типа: по нему `Core.Validator.*`
  проверяет значение, `Core.Prim.Integer` / `Decimal` выводят `sec_max_len`, `Web.Params.Schema`
  читает границы. Новый ключ в нём расширил бы контракт для всех читателей.
- `Prim.String` и `Prim.Decimal` вычисляют опции типа в теле модуля и потому принимают
  выражения (`max_len: @max`, `min: @min`). `Prim.Integer` — единственная обёртка, которая
  считала их на `use` и принимала только литералы.

## Рассмотренные варианты

- **Оставить `min == max` допустимым, чинить только текст.** Отвергнуто: у одного смысла
  остаются два синтаксиса, а вырожденный диапазон продолжает жить в коде потребителей;
  различие «ровно» и «диапазон» нигде не видно.
- **Новый код ошибки `prim/len`.** Отвергнуто: код — часть контракта ответов; точная граница —
  частный случай `:bounds`, и новый код заставил бы потребителей расширять маппинг без выгоды.
- **Хранить `len:` / `exact:` отдельными ключами `__domain_type_opts__/0`.** Отвергнуто:
  задокументированный вид опций типа изменился бы, а `sec_max_len` и `fits_bounds!` получили бы
  новые ветки. Раскрытие в канонические границы сохраняет и контракт, и существующий код.
- **`exact:` только литералом, как `min:` / `max:` у `Integer`.** Отвергнуто: `len:` —
  выражение (рядом с `max_len:`), и одинаковое имя с разной семантикой в двух обёртках хуже,
  чем перевод `Prim.Integer` на body-вычисление, уже принятое у `Decimal` и `String`.
- **Склонять только сообщение точной длины.** Отвергнуто: соседние сообщения остались бы с
  `символа(ов)`, и стиль разъехался бы внутри одного валидатора.

## Решение

- `Core.Prim.String`: `len:` — литерал или выражение, целое ≥ 1, не сочетается с `min_len:` /
  `max_len:`. Раскрывается в `min_len: n, max_len: n`; `min_len == max_len`, заданные парой, —
  `CompileError` с подсказкой `len: n`; равенство нулей и `len: 0` — `CompileError`
  (нулевая длина недопустима).
- `Core.Prim.Integer` и `Core.Prim.Decimal`: `exact:` — литерал или выражение, не сочетается с
  `min:` / `max:`. Раскрывается в `min: n, max: n`; `min == max`, заданные парой, —
  `CompileError` с подсказкой `exact: n`. `exact: 0` разрешён. У `Decimal` значение обязано быть
  конечным и укладываться в `scale:`; иначе `CompileError`.
- `Core.Prim.Integer` переведён на body-вычисление опций типа: `type_opts!` и `sec_max_len`
  считаются в теле модуля, как у `Decimal` и `String`; `min:` / `max:` остаются литералами.
- `__domain_type_opts__/0` отдаёт канонические `min_len` / `max_len` и `min` / `max` — сахар
  раскрыт на компиляции. У `Decimal` раскрытый `exact:` нормализуется в `%Decimal{}`.
- Код ошибки точной границы — `:bounds` (`prim/bounds`). Тексты строк склоняются по-русски:
  «ровно 1 символ / 3 символа / 5 символов», «минимум 3 символа», «максимум 1 символ», диапазон —
  «от 3 до 10 символов». Числа — «ровно N».

## Цена

- **Ломающее изменение контракта.** Потребитель с `min_len == max_len` или `min == max` больше не
  соберётся; миграция — `len:` / `exact:`, записана в CHANGELOG.
- **`Prim.Integer` проверяет опции позже.** Ошибка конфигурации остаётся `CompileError`, но
  возникает в теле модуля, а не на `use`; расположение ошибки в отчёте компилятора меняется.
- **Текст сообщений о длине изменился.** Это «текст для человека», не контракт, но тесты
  потребителей, сверяющие сообщение целиком, потребуют правки.
- **Склонения захардкожены по-русски.** Локализация сообщений в библиотеке не поддерживается;
  третьего места с русской грамматикой не появилось — она уточнена в одном валидаторе.
- **Явный `sec_max_len` у `String` по-прежнему не сверяется с `max_len` / `len`.** Известный
  пробел вне этой правки: такая конфигурация отвергает валидные значения, а не падает сборкой.
