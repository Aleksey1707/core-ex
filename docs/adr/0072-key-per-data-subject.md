# Единица ключа — субъект данных

Персональные данные в событиях лежат под ключом субъекта данных — физического лица, а не агрегата, потока или
поля. Ключ у субъекта один и уничтожается только целиком. Субъекта называет UUID внутри самого события —
`aggregate_id` или явно объявленное поле нагрузки; идентификатор лежит открыто. Термины — `CONTEXT.md`,
«Персональные данные».

## Контекст

Факты на 2026-10-18:

- потребителю нужны ПДн в событиях event-sourced агрегата; решение «ПДн шифруются, при уничтожении удаляется
  ключ» принято потребителем; история неизменяема (ADR-0010), поэтому стереть данные можно, только сделав их
  невосстановимыми;
- 152-ФЗ определяет уничтожение невосстановимостью содержания ПДн во всей ИСПДн (ст. 3 п. 8); уничтожать
  требуется по достижении цели обработки (ст. 21 ч. 4), а при отзыве согласия — если данные не нужны по
  договору (ст. 21 ч. 5); акт и выгрузка из журнала (приказ РКН № 179) называют субъекта и перечень категорий;
- ПДн одного лица встречаются не только в его потоке: контакт, получатель перевода, имя счёта его владельца
  лежат в потоках других агрегатов;
- готовые решения (Axon Data Protection, akka-gdpr, пример Kurrent, паттерн Verraes) держат ключ на субъекта;
  Akka допускает id субъекта от `persistenceId`, но тогда ПДн лица в чужих потоках не достать; Axon даёт
  несколько ключей на субъекта (`group`) для выборочного стирания;
- кодек события видит событие целиком: заголовок с `aggregate_id` и нагрузку, при `load` заголовок
  разбирается до нагрузки; `%Context{}` и метаданных кодек не видит;
- автор события (`by`) — тот, кто действовал, а не тот, чьи данные: оператор вносит ФИО клиента;
- пилота нет, требования задаёт синтетический агрегат тестов.

## Рассмотренные варианты

### Единица ключа

- **Поток агрегата, ключ от `aggregate_id`.** Отвергнут: ПДн лица в потоках других агрегатов под его
  уничтожение не попадают. Остаётся частным случаем: когда агрегат и есть субъект, идентификатор субъекта —
  `aggregate_id`.
- **Поле или значение.** Отвергнут: уничтожение лица требует перечня всех его ключей, то есть того же ключа на
  субъекта плюс индекса.
- **Пара «субъект + цель обработки».** Отвергнут для первого выпуска механизма: даёт частичное уничтожение по
  ст. 21 ч. 4, но у события появляется несколько ключей одного лица, у операции — аргумент цели, а требований
  к нему нет. Путь оставлен: шифротекст называет свой ключ, и ключи по целям добавятся без переписывания
  истории.

### Источник идентификатора

- **`%Context{}` записи.** Отвергнут: кодек контекста не видит, а в одном событии бывает несколько субъектов.
- **Метаданные события.** Отвергнут: кодек их не видит, а копия id в метаданных (Kurrent) — второй источник
  рядом с полем.
- **`by` по умолчанию.** Отвергнут: автор действия — не владелец данных.

### Различение субъектов

- **Пара «вид + значение»** со стабильным строковым видом у типа идентификатора. Отвергнут: допускает
  целочисленные id, но вид становится ещё одной неизменяемой строкой, как wire-тег события, а роль через
  `Prim.Compose` обязана его наследовать. UUID уникален сам.

## Решение

- субъект данных — физическое лицо; ключ субъекта — один на субъекта и уничтожается целиком; операция —
  «уничтожение ключа субъекта», слово из 152-ФЗ;
- идентификатор субъекта — значение `Prim.UUID` или `Prim.Compose` над ним, тип проверяет сборка; субъекта
  различает значение UUID, а не тип Prim: `Approver.ID` поверх `User.ID` — тот же субъект;
- идентификатор берётся из самого события — `aggregate_id` или явно объявленное поле нагрузки, не
  `%Context{}`, не метаданные и не `by`; лежит открыто и сам ПДн не является;
- привязка — на событие, а не на поток: смена владельца не перешифровывает историю, прежние события остаются
  под ключом прежнего;
- в событии допускается несколько субъектов, у каждого ПДн-значения — ровно один;
- ПДн-значение при `nil` в поле-субъекте не пишется: это ошибка программиста; `nil` в ПДн-значении шифровать не
  нужно;
- шифротекст называет ключ, под которым лежит.

## Цена

- **Нет частичного уничтожения.** Данные субъекта с разными сроками (рассылка и договор) уничтожаются только
  вместе; ПДн с коротким сроком потребитель в события не кладёт.
- **Два идентификатора — два субъекта.** Лицо под несвязанными `User.ID` и `Client.ID` потребитель уничтожает
  дважды; свести их в одного субъекта — его модельное решение.
- **Только UUID.** Целочисленный идентификатор субъектом быть не может.
- **Открытый идентификатор остаётся.** После уничтожения событие по-прежнему ссылается на субъекта; ни на кого
  он не указывает, только когда потребитель удалит то, что связывает UUID с лицом. Идентификатор, вычисленный
  из ПДн, их выдаёт.
- **Смешанное значение не делится.** Свободный текст с данными двух лиц ложится под ключ одного, субъекта
  выбирает автор события.
