# Write-путь возвращает входной агрегат, а не строку из БД

`insert` / `update` / `save` возвращают `{:ok, entity}`, где `entity` — тот агрегат, который
передали на вход (у агрегата с событиями — с очищенными `events`), и он же уходит эталоном в
`Repo.Sc` регистрацией после commit. Возврат означает ровно одно: состояние, от которого мутируют
дальше.

## Контекст

Под одной сигнатурой жили три разных смысла: `Repo.Pg.insert/4` отдавал декодированную строку из
БД, `update/4` — то же, но на `:unchanged` входной агрегат, `Repo.Pg.Es` — входной агрегат с
очищенными событиями. Из-за этого call site не мог понять, обязан он связать результат или вправе
выбросить, а сам decode был вредным: сразу после `INSERT` у строки не прогружены `has_many`, поэтому
`to_entity` терял детей и мог упасть на доменной валидации уже **после** успешной записи. Обходом
служила пара публичных методов `write_insert/4` / `write_update/4` (`:ok | {:error, _}`) — ровно для
того call site, который результат отбрасывает.

Отдельно расходились пути по эталону: `Repo.Pg.Es` обновлял `Repo.Sc` после записи, generic-путь —
нет, из-за чего второй `save` на репозитории с `shadow_copy?: true` падал `:version_mismatch` по
устаревшему эталону.

## Рассмотренные варианты

- **`:ok | {:error, _}` + норма «агрегат после записи отработан».** Формально чище по CQS и
  единообразно с `delete`. Отвергнут: норма выводилась не из домена, а из сигнатуры — сначала
  убирали возврат, потом запрещали то, что без него невозможно. Elixir иммутабелен, флаш событий
  меняет агрегат, и других каналов сообщить об этом нет: `save` → mutate → `save` перестал бы
  работать вовсе, потому что повторный flush упирается в unique-индекс
  `(aggregate_id, aggregate_version)` event store.
- **`:ok | {:error, _}` + продолжение через повторный `get`.** Норму выдумывать не пришлось бы, но
  цена — `SELECT`, заведомо избыточный: нужное значение в этот момент уже лежит эталоном в
  `Repo.Sc`. Плюс ломающее изменение для всех приложений-потребителей.
- **Дуальный API (`save` → `:ok`, отдельный метод → `{:ok, entity}`).** Второе имя за
  гипотетического потребителя — тот же расчёт «под возможные кейсы», который уже один раз не
  окупился (задуманный инкремент версии на уровне репозитория так и не появился: версию поднимает
  домен, `Repo.Pg` её только фильтрует в `lock_version/3`).

## Последствия

- `write_insert/4` и `write_update/4` удалены: без decode они стали дубликатами `insert/4` и
  `update/4`.
- `Repo.Pg.Es` собирает `written` **до** записи строки и передаёт его в запись строки и детей, а
  исходный агрегат — только в flush. Иначе очистка событий разошлась бы с эталоном, который кладёт
  `Repo.Pg.insert/4` из того, что ему передали.
- Эталон `Repo.Sc` обновляет тот, кто пишет, а не call site; `save` → mutate → `save` работает
  одинаково на обоих путях.
- Угол поведения: мутация, породившая событие, но не изменившая ни одной колонки (включая
  `version`), теперь идёт по ветке `:unchanged` — строка не переписывается, событие пишется. Раньше
  непустые `events` делали агрегат неравным эталону и давали реальный `UPDATE`. Практически угол
  пуст: домен поднимает `version` и `updated_at` на мутации, и обе — колонки.
