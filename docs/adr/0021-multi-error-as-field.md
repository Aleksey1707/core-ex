# Множество ошибок — поле в `%Error{}`, а не отдельный тип

Несколько независимых отказов одной операции представлены полем `errors: [t()]` в существующем
`%Error{}`. Контейнер собирается `Error.many/1,2`, `kind` выводится из состава, а обход причин
(`has?/2`, `find/2`, `chain/1`, `root/1`, `Enumerable`) множества не касается.

## Контекст

Факты на 2026-09-21:

- `%Error{kind, ns, module, code, message, detail, parent}` описывает **одну** ошибку; `parent`
  даёт линейную цепочку причин (`wrap/2`, `root/1`, `chain/1`, `has?/2`, `format_chain/1`),
  и `Enumerable` итерирует именно её;
- представления «несколько независимых отказов» нет вовсе: `Result.traverse/2` обрывается на
  первом (`lib/core/result.ex:77`), список валидаторов одного Prim — тоже
  (`lib/core/prim.ex:375`), загрузка списка сущностей кодеком — тоже
  (`lib/core/codec/helper.ex:63`);
- границы разбирают reason паттерном по `%Error{}`: `Core.Web.ErrorMapper.map/2` (три clause),
  `Core.Exc.exception/1`, `Core.Result.unwrap!/1`, `String.Chars`, каталоги `<Aggregate>.Errors`;
  последняя clause маппера отдаёт 500 `:critical` на любой неопознанный reason;
- конверт ответа `%{code, messages}` уже несёт **список** строк, но `Response.__error__/3` всегда
  кладёт ровно один элемент, а `map/2` возвращает один `String.t()` третьим элементом 4-кортежа,
  который потребители матчат у себя;
- библиотека подключена git-зависимостью к нескольким приложениям: смена формы `{:error, _}`
  в существующих API переписывает у каждого из них все `with`-цепочки.

## Рассмотренные варианты

- **Отдельный struct `Core.Error.Multi`.** Отвергнут: множество промахивается мимо каждого
  паттерна `%Error{}` на границе и уходит в последнюю clause маппера — 500 `:critical` вместо
  доменного ответа. То есть тип, заведённый ради показа состава клиенту, ломает ровно тот путь,
  по которому состав должен ехать; чтобы его починить, пришлось бы править границу у всех
  потребителей одновременно.
- **Голый список `{:error, [%Error{}, ...]}` как reason.** Отвергнут по той же причине, плюс
  теряется текст «в целом»: клиенту нечего показать, если состав ему показывать нельзя
  (прикладная ошибка, 401).
- **Ветвление `parent`: причина становится списком.** Отвергнут: `root/1` на дереве неопределима,
  `chain/1` и `Enumerable` перестают быть линейными, `has?/2` меняет смысл с «в цепочке причин»
  на «где-то в дереве», и отрицательная проверка перестаёт что-либо гарантировать. Цена —
  переписанные обработчики у всех потребителей, при том что причина и соседний отказ остаются
  разными отношениями (`CONTEXT.md`, «Ошибки»).
- **Поле `errors` в `%Error{}` (принято).** Множество, попавшее туда, где его не ждут, ведёт себя
  как обычная ошибка с осмысленным `message`, и раскрывается там, где про поле знают.

## Решение

- поле `errors: [t()]` с дефолтом `[]`, вне `@enforce_keys`; `parent` и `errors` независимы;
- конструктор — макросы `Error.many/1,2`, симметрично `domain` / `app` (`/1` — `module` из
  `__CALLER__`, `/2` — явный) с compile-check ключей: обязательны `code:`, `ns:`, `message:`,
  `errors:`, опциональны `detail:`, `parent:`;
- `kind` конструктор не принимает, а выводит по слабейшему звену: хотя бы один элемент `:app` →
  контейнер `:app`. Иначе вызывающий мог бы назвать доменным множество с прикладным элементом,
  и граница показала бы клиенту то, что показывать нельзя;
- `ns` и `code` — из словаря потребителя; общего кода библиотека не вводит;
- пустой список — `ArgumentError`; одиночный элемент допустим и заворачивается наравне с прочими;
  порядок входа сохраняется, дубли `{ns, code}` не схлопываются;
- элемент с непустым `errors` — `ArgumentError`: множество плоское, адресация поля — в `detail`
  элемента;
- контейнер не бывает причиной: `wrap/2` вторым аргументом и `parent:` любого конструктора его не
  принимают — `ArgumentError` с текстом правила. Обратное направление разрешено;
- `has?/2`, `find/2`, `chain/1`, `root/1` и `Enumerable` читают **только** цепочку причин; состав
  читается из поля;
- `format_chain/1` печатает состав — `"outer (e1 | e2): root"`; у ошибки с пустым `errors` вывод
  прежний;
- `Error.messages/1` → `[String.t()]`: у контейнера — тексты элементов, у обычной ошибки —
  `[to_string(error)]`;
- `Exc.message/1` для контейнера — `format_chain/1`: читатель bang-границы — разработчик в логе;
- `Result.traverse_all/2` → `{:ok, [b]} | {:error, [Error.t()]}`; заворачивание в `Error.many`
  происходит в теле той же функции;
- `ErrorMapper.map/2` не меняется; `Response.error/2,3` получает clause на `[String.t()]`; состав
  уходит клиенту только там, где маппер вернул `:domain_error`.

## Цена

- **Два смысла в одной структуре:** `%Error{}` — и узел цепочки, и контейнер. `Enum.count(err)`
  считает цепочку, а не состав, и на месте вызова это неотличимо.
- **Множество молча схлопывается в одну ошибку** у потребителя, который про поле не знает: клиент
  получит outer `message` без состава. Дефолт безопасный, но потеря ничем не сигнализируется.
- **`kind` по слабейшему звену прячет доменную часть:** один прикладной отказ в пачке уводит весь
  ответ в 500, и клиент не узнает про свои невалидные поля — их придётся искать в логе.
- **Плоскость ограничивает вложенный ввод:** отказ по `items[3].price` адресуется строкой в
  `detail` элемента, а структурой контейнера — никак.
- **Голый список из `traverse_all/2` удерживается нормой, а не типом:** возвращённый наружу, он
  уйдёт в 500 через последнюю clause маппера, и компилятор этого не покажет.
- **Состав отдаётся клиенту вручную:** `map/2` его не несёт, и потребитель, забывший позвать
  `Error.messages/1`, получает прежний одиночный `messages`.
