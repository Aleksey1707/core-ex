# Ответ дополняется запросом `Query` другого контекста

Usecase чтения MAY дополнить свой ответ полем другого контекста его экспортированным `Query`: логин
автора действия в ссылке на учётную запись берёт запрос контекста учётных записей, а не копия
в каждом контексте-читателе. Снимает с ADR-0053 ограничение «чтение — шаг проверки или решения»;
join между контекстами по-прежнему запрещён (ADR-0038), а копия поля своей проекцией остаётся путём,
когда по полю нужны фильтр или сортировка. Норма — `docs/rules/app/10-architecture.md`, «Usecases»;
`docs/rules/app/13-repos.md`, «Read-модель».

## Контекст

Факты на 2026-10-11 (потребитель A):

- ответы двух контекстов-читателей отдают автора действия и ответственного ссылкой на учётную
  запись `{id, login}` с текущим логином; колонки ресурсов хранят только id;
- по своду показать поле другого контекста можно было только копией: join по таблице чужой
  read-модели — MUST NOT (ADR-0038), а `Query` — только шаг проверки или решения (ADR-0053);
- копия дала две одинаковые таблицы и две проекции в одной базе, повторявшие read-модель
  самого контекста учётных записей; события производителя стали контрактом каждого читателя,
  а промах копии из-за отставания её проекции usecase чтения всё равно добирал запросом `Query`;
- потребитель снял копии и читает логин пачкой через `Query` контекста учётных записей —
  отступлением в своём `DEBT.md`, пока норма яруса запрещает чтение для показа.

## Рассмотренные варианты

- **Свод как есть, копия в каждом контексте-читателе.** Отвергнут: ограничение `Query` не защищает
  ничего, что открыто копией. Копия показывает то же поле из экспортированных событий владельца
  и тоже без его проверки доступа, только ценой таблицы, проекции, пересборки и контракта событий
  на каждого читателя.
- **Join через read-only схему, которую владелец кладёт в `exports`.** Отвергнут: ссылку видит
  сборка, но остальные доводы ADR-0038 стоят — пересборка проекции владельца опустошает таблицу
  под чужим join, у двух проекций разное отставание, а схема таблицы становится контрактом.
- **Дополнение в точке входа вторым usecase владельца.** Отвергнут: своя декларация доступа на
  чтение поля и второй вызов в каждом контроллере, а `Query` точка входа звать не может
  (`entry-query`).
- **Поле для показа помечает владелец (`@doc` или маркер линтера).** Отвергнут: View `Query`,
  отданный для решения, уже лежит в коде чужого контекста без проверки, и тот может положить его
  в ответ. Граница доверия — `exports`, а не цель чтения; пометку владелец и так ставит составом
  View.
- **Поддержка ссылок в `Core.View` (поле `ref:`, обход по известным путям).** Отложен до второго
  потребителя с тем же шаблоном: пока обход View — код приложения.

## Решение

- usecase MAY дополнить ответ полем другого контекста его экспортированным `Query`;
- View экспортированного `Query` владелец публикует любому контексту из `deps`: поле, доступ к
  которому решает право пользователя, в нём MUST NOT, такие данные отдаёт usecase владельца с
  декларацией (ADR-0046);
- дополнение MUST читать `Query` одним вызовом на ответ — пачкой по всем id View или страницы;
- usecase MUST NOT отдавать View, поле которого ещё ждёт дополнения;
- свежесть ответа (отставание проекции, добор промаха из потока) — контракт `Query` в его `@doc`,
  свод её не задаёт;
- копия поля своей проекцией — когда по нему нужны фильтр или сортировка; join между контекстами —
  MUST NOT, как в ADR-0038.

## Цена

- **Лишний запрос на чтение:** один вызов `Query` на ответ, в котором есть поля для дополнения.
- **Пачку и полноту View держит ревью:** вызов на строку и недополненное поле линтер не видит.
- **Форма View шире ответа:** поле, которое ставит дополнение, в типе View — `optional`, хотя
  наружу оно уходит заполненным.
- **Фильтр и сортировка по полю другого контекста** без копии невозможны; понадобились — поле
  копирует проекция читателя.
