# Стартовая инициализация нескольких контекстов — сессионная блокировка, а не одна транзакция

Задача оператора, которая заводит данные нескольких контекстов, зовёт usecase каждого контекста его
транзакцией, а параллельный старт реплик исключает сессионная advisory-блокировка одного соединения
`Core.Helper.Lock.with_advisory!/4`. Прерванный запуск доводит повторный. Исключения из «одна
транзакция пишет один контекст» (ADR-0038) для задач корня нет. Норма —
`docs/rules/app/10-architecture.md`, «Usecases».

## Контекст

Факты на 2026-10-03 (адаптация потребителя A к rc после 0.10.0):

- стартовая инициализация потребителя A под одной `advisory_xact!` создаёт администратора в
  контексте учётных записей и выдаёт ему роли в контексте прав;
- ADR-0038 запрещает транзакции писать два контекста и исключений не знает; разделение на две
  транзакции снимало `advisory_xact!` на commit первой, и реплики, стартующие вместе, гонялись
  бы за вторым шагом;
- `Core.Helper.Lock` давал только блокировку транзакции;
- `repo.checkout/1` держит одно соединение на весь колбэк, и транзакции внутри берут его же.

## Рассмотренные варианты

- **Исключение для задач корня: одна транзакция на несколько контекстов.** Отвергнут: задача зовёт
  usecases контекстов, а usecase о внешней транзакции не знает и может делать то, что внутри неё
  запрещено (ADR-0038).
- **Склеить контексты учётных записей и прав.** Отвергнут: несоразмерно ради одной задачи старта.
- **Своя блокировка в каждом приложении.** Отвергнут: сессионная блокировка требует снятия при
  исключении и сброса `lock_timeout` сессии, иначе соединение возвращается в пул с чужой
  настройкой; это механизм, а не правило приложения.

## Решение

- `Core.Helper.Lock.with_advisory!/4`: `repo.checkout/1`, `pg_advisory_lock` с `lock_timeout` на
  время взятия, снятие в `after`; внутри транзакции — `ArgumentError`;
- задача корня зовёт usecases контекстов их транзакциями внутри блокировки;
- шаги задачи идемпотентны: прерванный запуск доводит повторный.

## Цена

- **Нет атомарности:** между транзакциями видно состояние первого контекста без второго, а сбой
  второй транзакции оставляет первую — до повторного запуска.
- **Соединение пула занято на всё время задачи**, а не на одну транзакцию.
