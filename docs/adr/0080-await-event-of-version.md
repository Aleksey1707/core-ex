# Ожидание проекции до события заданной версии

Модуль проекции получает `await(Agg, %Agg.ID{} = id, %Core.Version{} = version, timeout)`: цель —
позиция события потока с этой версией, а не последнего события на момент вызова. Нет события —
цель перечитывается на каждом сигнале чекпоинта и шаге страховки, а не `:ok` сразу. Исходы —
прежние `:ok`, `:projection_timeout`, `:projection_rebuilding`. Дополняет ADR-0039 (ждёт usecase
по `wait:`); `await/3` не меняется. Норма — `docs/rules/22-projections.md`, «Read-after-write»;
исходы — moduledoc `Core.Es.Projection`, «Ожидание».

## Контекст

Факты на 2026-10-19 (проектирование потребителя F):

- реакции между контекстами потребителя F идут брокером: событие → outbox → подписчик
  реагирующего контекста → команда агрегату. Команда-источник после commit отвечает клиенту
  итогом цепочки, если он успел за бюджет ожидания, иначе — `202`;
- следующее событие потока после записи источника известно по модели агрегата: его пишет реакция,
  и версия его — следующая за записанной;
- `await/3` берёт цель на момент вызова: событие реакции ещё не записано, и ожидание отдаёт `:ok`
  по уже обработанной записи источника — итог реакции чтение не видит;
- первичный ключ `es_events` — `(aggregate_type, aggregate_id, aggregate_version)`: позиция события
  версии находится по ключу.

## Рассмотренные варианты

- **Цикл опроса read-модели в приложении.** Отвергнут: повторяет сигнал чекпоинта и шаги
  страховки `await/3` своим кодом в каждом usecase, и сборка не сверяет агрегат и ID.
- **Сразу `202`, клиент перечитывает.** Отвергнут: при цепочке, которая укладывается в бюджет,
  клиент платит лишним запросом ради итога, который уже есть.
- **Синхронная реакция в транзакции источника.** Отвергнут потребителем: противоречит доставке
  фактов брокером между контекстами.
- **Опция `version:` у `await/3`.** Отвергнут: у `await` нет `opts`, а версия меняет цель, а не
  способ ожидания; отдельная clause держит `%Core.Version{}` закрытым паттерном в голове.
- **Цель — последнее событие потока, но не ниже версии.** Отвергнут: при обогнавшей записи
  ожидание шло бы до события, которого вызывающий не ждал.
- **Отдельный код «событие не записано».** Отвергнут: для вызывающего оба недобора — `202`, а
  множество `result` telemetry осталось бы прежним только ценой лишнего различения.
- **`RuntimeError` в `await: :inline` без события версии.** Отвергнут: в тесте реакцию через
  брокер никто не исполняет, и ветка `:accepted` usecase стала бы нетестируемой.

## Решение

- `use Core.Es.Projection` генерирует `await/4` рядом с `await/3` — clause на каждый агрегат из
  `events:`, голова — литерал агрегата, `%Agg.ID{}` и `%Core.Version{}`;
- цель — позиция события с `aggregate_version == version`; поток ушёл дальше — ждётся всё равно
  событие этой версии;
- события нет: при пересборке — сразу `:projection_rebuilding`, иначе цель перечитывается на
  сигнале и шаге; истёк `timeout` — `:projection_timeout`;
- `await: :inline`: после `:idle` без события версии — сразу `:projection_timeout`, без ожидания;
- span `Core.Otel.Es.await` несёт ожидаемую версию; telemetry `[:es, :projection, :await]` — без
  изменений: версия в метке метрики — кардинальность.

## Цена

- **Ожидание события, которое может не появиться:** реакция упала или ушла в DLQ — usecase ждёт
  весь `timeout` и отвечает `202`; отличить это от медленной проекции по исходу нельзя, только по
  трейсу.
- **Версия реакции — знание модели агрегата в usecase:** правка модели, при которой следующее
  событие перестаёт быть итогом реакции, сборкой не ловится.
- **Перечитывание цели — запрос на каждом сигнале и шаге,** пока события нет: по первичному ключу,
  но и на сигналах чужих пачек проекции.
