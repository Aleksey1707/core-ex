# Реализация репозитория резолвится по конвенции `<Behaviour>.Pg`

`Core.Config.repo!/1` выводит реализацию из имени behaviour: `User.Repo` → `User.Repo.Pg`.
Ключ в конфигурации нужен только тому, кто подменяет реализацию. То же правило —
у инфраструктурного `Core.Config.outbox_repo/0`.

## Контекст

DI репозиториев жил целиком в конфигурации потребителя, по строке на каждый behaviour:

```elixir
config :core, Core.Outbox.Repo, Core.Outbox.Repo.Pg
config :my_app, MyApp.Domain.Users.Common.User.Repo, MyApp.Domain.Users.Common.User.Repo.Pg
config :my_app, MyApp.Domain.Users.Admin.User.Repo, MyApp.Domain.Users.Admin.User.Repo.Pg
config :my_app, MyApp.Domain.Users.Common.User.ReadRepo, MyApp.Domain.Users.Common.User.ReadRepo.Pg
```

Примерно в 90% случаев значение выводится из ключа механически: `13-repos.md` уже требует
класть реализацию в `<Behaviour>.Pg`, и конфигурация повторяла эту раскладку вручную. Строка
`config :core, Core.Outbox.Repo` выделялась особо: у неё нет и не было альтернативной
реализации, но написать её был обязан каждый потребитель.

Цена дублирования — не только объём. Потребитель, забывший строку, получал
`Application.compile_env!` с ошибкой на компиляции; потребитель, ошибшийся в ней, —
рабочую сборку с чужой реализацией.

## Рассмотренные варианты

- **Генерировать `impl/0` на самом модуле-behaviour** (`use Core.Repo.Behaviour`). Отвергнут:
  `use Core.Repo.Pg` делает `Code.ensure_compiled!(behaviour)`, и обратная ссылка
  behaviour → реализация даёт цикл компиляции, который поймает `mix xref --format cycles`.

- **Сделать behaviour делегатором** (`User.Repo.get(...)` диспатчит в реализацию). Отвергнут:
  убирает `@repo`, но заводит рантайм-диспатч на каждый вызов и ломает подмену реализации
  через конфигурацию в тестах.

- **Опция `default:` на call site** (`Config.repo!(User.Repo, default: User.Repo.Memory)`).
  Отвергнут: это тот же DI, переехавший из конфигурации в код, где его нельзя переопределить
  в `config/test.exs`.

- **Оставить обе формы легальными** (новая рекомендуется, старая допустима). Отвергнут: смысл
  изменения — чтобы существовал ровно один ответ на вопрос «откуда берётся реализация»; две
  формы возвращают тот же разнобой, только на call site вместо конфигурации.

## Решение

`Core.Config.repo!/1` — макрос, разворачивающийся в `Application.compile_env(otp_app(),
behaviour, <Behaviour>.Pg)`. Резолв остаётся там же, где был (`@repo` в модуле-потребителе),
значение по-прежнему запекается на компиляции, а правка ключа по-прежнему заставляет call
site перекомпилировать.

Модуль-реализация проверяется на компиляции — и выведенный по конвенции, и заданный ключом.
Асимметрия («проверяем только то, что вывели сами») оставила бы без защиты как раз тот
случай, где имя писал человек.

`Core.Config.outbox_repo/0` резолвится в рантайме: ключ читают PromEx-плагин, mix-задача и
`Repo.Pg.Es`, и запекание развело бы их по разным моментам чтения. Имя `Core.Outbox.Repo.Pg`
при этом не упоминается статически — `Core.Outbox.Repo.Pg` ходит в `Core.Config` за `dao/0`,
и ссылка отсюда замкнула бы цикл компиляции.

Доступ к app-env потребителя целиком сжат в `Core.Config`: `Repo.Pg.Es` больше не читает его
сам. Это позволило заменить греп-инвариант из `10-architecture.md` на линтер
(`make boundary-check`), в котором отступление стало проверяемым правилом, а не абзацем.

## Цена

- **Граф компиляции у потребителя густеет.** Проверка реализации даёт ребро
  call site → `<Behaviour>.Pg`: правка реализации репозитория рекомпилирует usecases
  агрегата. Цикла это не создаёт по построению (реализация зависит от behaviour, call site —
  от реализации), и `mix xref --format cycles` остаётся зелёным.

- **`otp_app` становится обязательным для всех.** Раньше ключ читал только
  `use Core.Repo.Pg.Es`; теперь — любой call site `repo!/1`, поэтому он обязан лежать
  в `config.exs`, а не в `runtime.exs`.

- **Конвенция становится нормой.** `<Behaviour>.Pg` перестаёт быть соглашением об
  именовании и делается частью контракта: реализация в другом месте требует ключа.
