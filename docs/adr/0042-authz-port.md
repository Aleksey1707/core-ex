# Проверка доступа — порт, ключи пространств объявляет контекст

Проверка доступа — порт `MyApp.Authz`: behaviour проверки, макрос декларации и каталог ошибок
отказа, граница без `deps` на контексты. Реализует порт контекст, который владеет моделью прав, а
у приложения без неё — заглушка порта; реализацию и реестр называет ключ конфигурации, порт читает
его в рантайме. Ключи пространств разрешений и их описание объявляет контекст в оглавлении,
макрос декларации сверяет ключ при компиляции, корень склеивает реестр. Тест usecase идёт с моком
порта, авторизацию операции держит интеграционный тест с боевой реализацией. Заменяет пункты
ADR-0025 «механизм над моделью — подсистема» и «ключ механизма лежит у механизма». Норма —
`docs/rules/app/10-architecture.md`, «Проверка доступа»; `docs/rules/app/19-testing.md`,
«Проверка доступа»; `docs/rules/19-testing.md`, «Контрактные тесты behaviour».

## Контекст

Факты на 2026-10-02 (разбор потребителя A —
`.scratch/consumer-architecture/research/02-consumer-a-structure.md`, решения —
`.scratch/consumer-architecture/decisions.md`, Q32, Q33):

- по ADR-0025 механизм над моделью — макрос декларации, проверка, реестр — лежит в подсистеме, ключ
  пространства — в реестре механизма; путь «контекст → механизм → контекст модели» циклом моделей
  не считался;
- у потребителя A проверку зовут 30 модулей usecases через макрос декларации; механизм читает
  read-модель прав и тип пространства контекста прав, реестр деклараций собирается на старте
  обходом модулей по префиксу имени, каталог пространств — ручной список;
- usecases контекста прав у A сами проверяют доступ. С границей Boundary на контекст (ADR-0037)
  механизм-подсистема, которая читает контекст прав, и контекст прав, который зовёт механизм, —
  цикл границ, и сборка его ловит;
- тест любого usecase у A готовит роли, служебные учётные записи и прогон проекций трёх
  контекстов; 60 тестовых модулей домена — `async: false`;
- каждый новый агрегат у A правит реестр механизма: ключ пространства лежит у механизма;
- у потребителя F агрегатов прав нет: проверка — заглушка;
- проверено на копии `fixtures/consumer`: реализация, которую порт берёт `compile_env`, — литерал,
  и `boundary` репортит `forbidden reference` порта на модуль реализации; реализация из
  `Application.fetch_env!/2` предупреждений не даёт. Сверка ключа вызовом из тела макроса
  инкрементальная сборка не повторяет при правке оглавления (`require` даёт только зависимость по
  экспорту), вызов в теле модуля актора — повторяет, и удалённый ключ даёт `CompileError`.

## Рассмотренные варианты

- **Механизм — подсистема (ADR-0025).** Отвергнут: контекст прав зовёт механизм, а механизм
  читает контекст прав — цикл границ; `dirty_xrefs` на нём стал бы постоянным отступлением.
- **Проверка в контексте прав, контексты зовут его напрямую.** Отвергнут: каждый контекст зависит
  от модели прав, тест usecase готовит её данные, а приложению без модели заглушку положить
  некуда — контекст без агрегатов запрещён.
- **Ключ в реестре порта.** Отвергнут: реестр перечислял бы ключи всех контекстов, и порт знал бы
  контексты; каждый новый агрегат правил бы центральный список, как реестр кодека до объявлений
  контекста.
- **Ключ у агрегата (`<Aggregate>.ns/0`).** Отвергнут: агрегат ключ не читает, пространство может
  покрывать несколько агрегатов, а корень видит контекст только через `exports`, куда агрегат не
  входит.
- **Ключи в `<BC>.Supervision`.** Отвергнут: макрос декларации читает ключи на компиляции, а
  объявления ссылаются на проекции и корни компонентов — правка любого из них пересобирала бы
  модули деклараций. Оглавление уже читается на компиляции фасадом кодека.
- **Оглавление явной опцией декларации (`context:`).** Отвергнут: опция повторяет имя модуля
  актора, путь = имя модуля и оглавление `MyApp.Domain.<BC>` уже держит линтер, а опция могла бы
  назвать чужой контекст.
- **Реализация через `compile_env`.** Отвергнут: литерал реализации в порте — ссылка, которую
  `boundary` репортит, а `deps` порта на контекст прав замкнул бы цикл.
- **Реализация и реестр в `:persistent_term` со старта корня.** Отвергнут: интеграционному тесту
  нужна боевая реализация в процессе теста, а `:persistent_term` глобален; выбор расползается
  между конфигурацией и `start/2`.
- **Свой дублёр вместо Mox.** Отвергнут: интеграционный тест переключал бы реализацию через app env
  глобально, а это `async: false` на каждый тест доступа, даже когда модель прав читает
  write-репозитории без проекции; Mox держит реализацию на процесс теста. Тесту, который ждёт
  проекцию прав, `async: false` нужен в любом случае.
- **Общий контрактный набор на мок и боевую реализацию (`rules/19` в прежней редакции).**
  Отвергнут: мок отвечает тем, что задал тест, и набор проверял бы сам себя. Расхождение
  декларации актора и операции с выданными правами видит только тест с боевой реализацией.

## Решение

- проверка доступа — порт `MyApp.Authz`, граница с `deps: []`: behaviour `check/4`, макрос
  декларации, каталог ошибок отказа `MyApp.Authz.Errors`; у приложения без модели прав —
  заглушка `MyApp.Authz.Stub`;
- реализация — `MyApp.Domain.<BC>.Authz` в контексте, который владеет моделью прав, вне его
  `exports`; контексты держат в `deps` порт, а не контекст прав;
- декларация на модуле usecases актора — тип учётной записи и ключ пространства, на usecase —
  операция в `check_user/2` до транзакции;
- ключи пространств и их описание объявляет контекст в оглавлении (`authz_namespaces/0`); макрос
  выводит оглавление из имени модуля актора и сверяет ключ в теле его модуля — `CompileError` на
  необъявленный ключ;
- корень склеивает реестр `MyAppApp.authz_namespaces/0`, дубль ключа — `CompileError`; реализация
  получает реестр через `MyApp.Authz.namespaces/0` из MFA в конфигурации;
- реализацию и реестр называет `config :my_app, MyApp.Authz` (`impl:`, `namespaces:`), порт читает
  ключ в рантайме, `start/2` корня проверяет его до подъёма дерева;
- тест usecase — с моком Mox `MyAppTest.Authz`; при реализации в контексте прав каждая операция —
  интеграционный тест с боевой реализацией через `Mox.stub_with/2`; общий контрактный набор
  (`rules/19`) — MUST только на боевые реализации одного behaviour, тестовая реализация под него не
  попадает.

## Цена

- **Опечатку в `impl:` видит старт, а не сборка:** порт читает ключ в рантайме, и проверку держит
  `MyApp.Authz.validate!/0` в `start/2` корня.
- **Mox — тестовая зависимость приложения**, а мок — ещё один модуль `test/support`.
- **Интеграционный тест на каждую операцию:** тестов доступа столько же, сколько операций с
  `check_user/2`, и им нужны данные контекста прав.
- **Правка оглавления пересобирает модули деклараций контекста** и, как прежде, фасад кодека.
- **Третий ручной список контекстов в корне:** `MyAppApp.authz_namespaces/0` перечисляет
  оглавления литералами рядом с `MyAppApp.contexts/0` и `MyApp.Codec.plugins/0` — обход списка
  контекстов на компиляции зависимость от оглавления не регистрирует, и реестр устарел бы молча.
- **Оглавление выводится из имени модуля:** декларация вне `MyApp.Domain.<BC>.*` не собирается.
- **Переезд потребителей:** у A макрос декларации, проверка, реестр и каталог пространств уходят в
  порт и в реализацию контекста прав, ключи пространств — в оглавления контекстов, каталог ошибок
  отказа — в порт; у F заглушка становится реализацией порта.
