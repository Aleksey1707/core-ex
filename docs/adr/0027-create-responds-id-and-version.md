# Создание отвечает `{id, version}` / `{id}` общими схемами корня

Форма ожидания пересмотрена: ADR-0030 (`0030-prefer-controls-projection-await.md`) передал хелперу
колбэк ожидания, ADR-0039 (`0039-usecase-awaits-projection-by-wait.md`) перенёс ожидание в usecase —
он отдаёт `{:projected | :accepted, id, version}`, а ответ собирает `MyAppWeb.Accepted.written/2`.
Ответ создания `{id, version}` одной схемой `Written` на 200 и 202 и `{id}` схемой `Created` — в
силе. Ответ создания event-sourced агрегата на 200 пересмотрен ADR-0055
(`0055-create-and-upsert-respond-view.md`): представление, как у команды; `{id, version}` на 200
осталось у удаления. Ниже — решение в редакции 2026-09-29.

Создание event-sourced агрегата ждёт проекцию, как любая команда, и отвечает `{id, version}` записи
одной схемой `MyAppWeb.Schemas.Written` на 200 и на 202: статус несёт готовность представления,
тело — одно. Создание state-stored агрегата отвечает `{id}` схемой `MyAppWeb.Schemas.Created`.
Обе схемы лежат в корне web при любом числе поверхностей. Норма записана в
`docs/rules/app/15-web-api.md`, «Раскладка», «Controller», «Ожидание проекции».

## Контекст

Факты на 2026-09-29:

- ярус потребителя описывал ответ команды event-sourced агрегата представлением из read-модели
  после ожидания проекции, а на `:projection_timeout` / `:projection_rebuilding` — 202 с
  `{id, version}`; создание отдельно не описано, единственный пример создания — state-stored,
  `{id}` без ожидания;
- usecase создания event-sourced агрегата уже отдаёт `{:ok, {ID, Version}}`, state-stored — только
  `{:ok, ID}` (`docs/rules/app/10-architecture.md`, «Usecases»);
- создание пишет несколько событий, поэтому версию после него клиент
  не угадает, а без неё не пошлёт следующий `If-Match` (`explicit_version/2` на команде);
- потребитель A отвечал на создание `{id}` на 200 и `{id, version}` на 202: версия приходила только
  тогда, когда представление не готово, и узнать её оставалось `GET` с `If-Match: *`. Потребитель A
  перешёл на `{id, version}` на обоих статусах и держал отступление от яруса записью `DEBT.md`;
- «Раскладка» поднимает схему в корень `MyAppWeb.Schemas` только когда её делят поверхности; схема
  `{id}` у потребителя A используется одной поверхностью и лежит в корне второй записью `DEBT.md`.

## Рассмотренные варианты

- **Представление на 200, как у остальных команд.** Отвергнут: ответ создания распадается на две
  формы по статусу, а клиенту после создания нужны `id` и `version`. Представление он читает `GET`:
  после 200 проекция его уже видит, риска прочитать отставшую нет.
- **`{id, version}` без ожидания проекции.** Отвергнут: 200 перестаёт гарантировать, что `GET` сразу
  после него видит запись, — `:not_found` на свежем объекте.
- **Две схемы одной формы на 200 и 202.** Отвергнут: расходятся при первой правке; одна схема с
  разными описаниями ответов держит форму в одном месте.
- **`{id, version}` и у state-stored создания.** Отвергнут: usecase state-stored команды версию не
  отдаёт вовсе (команда — `:ok`), и ответ создания был бы единственным местом, где она появляется;
  проекции, готовность которой несёт статус, у state-stored агрегата нет.
- **Схемы ответа создания по лестнице «Раскладки».** Отвергнут: схема одной поверхности уехала бы
  в её namespace, и вторая поверхность завела бы копию той же формы. Форма ответа создания — одна на
  приложение, как конверт.
- **Форма ответа без имён хелпера и схем.** Отвергнут: ярус уже держит `MyAppWeb.Accepted` одним
  хелпером на приложение, и одну схему на 200 и 202 без имени ревью не сверяет.

## Решение

- создание event-sourced агрегата ждёт проекцию литеральным `Projection.await(Agg, id, timeout)`
  с суженным ID и отвечает `MyAppWeb.Accepted.written/4` (`conn`, результат ожидания, `id`,
  `version`): 200, если дождался, 202 — если нет; тело `{id, version}`;
- операция команды event-sourced агрегата объявляет `MyAppWeb.Schemas.Written` в `accepted:`,
  операция создания — ещё и в `ok:`; остальные команды на 200 отвечают представлением, как прежде;
- создание state-stored агрегата отвечает `{id}` схемой `MyAppWeb.Schemas.Created`;
- `Written` и `Created` MUST лежать в корне `MyAppWeb.Schemas` при любом числе поверхностей.

## Цена

- **Второй запрос за представлением:** клиент, которому после создания нужен собранный сервером
  состав, читает его `GET`, а не получает в ответе команды.
- **Исключение из лестницы схем:** две схемы корня живут там, где правило «общее для поверхностей»
  их бы не поставило; ревью различает их по имени, линтер число поверхностей не считает.
- **Две формы ответа создания:** `{id, version}` и `{id}` по виду агрегата; клиент API узнаёт форму
  из схемы операции.
