# Адаптер Kafka на `brod`

Kafka-клиент библиотеки — `:brod` вместо `:klife`, на запись и на чтение. Причина — чтение с
кластера без KIP-848: у `:klife` оно держится на внутреннем API клиента, у `:brod` — на
публичном потребителе партиции. Решение принято вместе с читателем Kafka (`.scratch/kafka-reader`,
ADR-0033).

## Контекст

Факты на 2026-09-30:

- consumer group `:klife` 1.2 реализует только протокол KIP-848; классического протокола в
  клиенте нет. Кластер потребителя, ради которого пишется читатель, KIP-848 не поддерживает;
- без группы у `:klife` публичен только `Client.fetch/4` (`Fetch` ≥ v13, Kafka ≥ 3.1). Число
  партиций (`Klife.MetadataCache`) и earliest / latest (`ListOffsets` через
  `Klife.Connection.Broker.send_message/4`) — во внутренних модулях; смену лидера и
  `OFFSET_OUT_OF_RANGE` `fetch` отдаёт вызывающему без повтора. Читатель поверх него — свой цикл
  fetch и пин `~> 1.2.0`;
- `:klife` 1.0 вышел 2026-05; `:brod` 4.7.0 — 2026-09-25, на нём построен `broadway_kafka`;
- `brod_consumer` читает партицию без consumer group: подписка `brod:subscribe/5` с
  `begin_offset`, `prefetch_count` и `offset_reset_policy`, подтверждение `brod:consume_ack/4`,
  переподключение при смене лидера внутри процесса, `high_wm_offset` в `#kafka_message_set{}`.
  Число партиций — `brod:get_partitions_count/2`. Всё это — публичный API;
- продюсер `:klife` по умолчанию идемпотентен и раскладывает ключ по партициям murmur2, как
  `DefaultPartitioner` Kafka (`Klife.Producer.DefaultPartitioner`);
- партиционер `hash` у `:brod` — `erlang:phash2(Key) rem PartitionCount`, не murmur2.
  Идемпотентного продюсера у `:brod` нет; `partition_onwire_limit` по умолчанию 1 — один запрос
  в полёте на партицию, порядок внутри партиции держится, повтор (`max_retries`) может задвоить
  запись;
- `kafka_protocol` 4.3 (транспорт `:brod`) не различает null и пустые байты ни у ключа, ни у
  значения: `<<>>` уходит на провод как null (`enc_byte_size(<<>>) -> enc(varint, -1)`), null
  читается как `<<>>` (`copy_bytes(Size, _) when Size =< 0`);
- обязательная нативная зависимость `kafka_protocol` — `crc32cer`; кодеки сжатия (`snappyer`,
  `lz4b`, `ezstd`) — по выбору потребителя. У `:klife` `snappyer` обязателен;
- заголовки записи требуют формата сообщений v2 — Kafka ≥ 0.11.

## Рассмотренные варианты

- **`:klife` на запись и чтение** (первая редакция ADR-0033). Отвергнут: читатель — свой цикл
  fetch поверх внутренних модулей клиента, обновление `:klife` — ручной шаг с прогоном тестов на
  живом брокере.
- **`:brod` на чтение, `:klife` на запись.** Отвергнут: два клиента к одному кластеру — две
  конфигурации подключения и SASL / TLS у потребителя, два набора нативных зависимостей, две
  нормализации ошибок.
- **`kafka_ex` 1.x.** Отвергнут: чтение без группы у него — тот же низкоуровневый fetch, выигрыша
  перед `:brod` нет.
- **`erlkaf` (NIF над librdkafka).** Отвергнут: сборка librdkafka у каждого потребителя — тяжело
  для optional-клиента.
- **Партиционер `hash` из `:brod`.** Отвергнут: ключ попадал бы не в ту партицию, что у `:klife`
  и Java-клиентов, — порядок по ключу рвётся на переходе и у топика с продюсерами на разных
  клиентах.

## Решение

- Kafka-клиент библиотеки — `{:brod, "~> 4.7", optional: true}`; `:klife` удаляется.
  `Core.Mq.Kafka.ensure_available!/0` проверяет `:brod`;
- handle адаптера — id клиента `:brod` (атом). Клиента стартует app-слой потребителя в своём
  дереве, как раньше модуль `use Klife.Client`;
- `Kafka.Writer` публикует `brod:produce_sync/5` с партиционером murmur2, совместимым с
  `DefaultPartitioner` Kafka; сообщение без ключа — в случайную партицию, как у `:klife`;
- `body: nil` публикуется как tombstone, `body: ""` — `{:error, _}` до отправки: на проводе он
  стал бы tombstone и молча удалил бы ключ компактного топика. Читатель отдаёт пустое значение как
  `nil` (ADR-0032);
- `Kafka.Reader` — подписка на `brod_consumer` партиций без consumer group (ADR-0033).

## Цена

- **Ломающее изменение для потребителей `Kafka.Writer`.** Зависимость `:klife` → `:brod`, handle
  — модуль `use Klife.Client` → id клиента `:brod`, конфигурация подключения переписывается.
- **Нет идемпотентного продюсера.** Повтор отправки может задвоить запись. Outbox и без того
  at-least-once, подписчик обязан быть идемпотентным.
- **Свой murmur2.** Совместимость с Kafka держит тест на эталонных значениях `DefaultPartitioner`
  Java-клиента.
- **Пустое тело неотличимо от удаления.** Сообщение с пустым телом через Kafka-адаптер не
  публикуется, а прочитанное приходит как tombstone.
