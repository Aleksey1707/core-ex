# Резерв изменяемого ключа: таблица библиотеки, объявление в репозитории event-sourced агрегата

Изменяемый уникальный ключ event-sourced агрегата держит резерв ключа — строка `es_key_reservations`
`(scope, key) → aggregate_id`, у агрегата в одной области не больше одного ключа. Резервы объявляются опцией
`key_reservations:` репозитория агрегата: `append` ставит, переносит и снимает их в транзакции записи событий по
сопоставлению событий, которое потребитель пишет в модуле `use Core.Es.KeyReservation`. Состояние агрегата для этого
не нужно, а путь записи событий мимо резерва через репозиторий не существует.

## Контекст

- `app/13-repos.md`, «Уникальность без индекса состояния»: уникального индекса по состоянию у event-sourced агрегата
  нет — строки пишет проекция, а `clear/0` очищает их при пересборке. Неизменяемый ключ задаёт идентификатор из ключа
  (ADR-0017). Изменяемый не покрыт: id потока постоянен, а ключ меняется событием.
- quality-control-back решил это у себя (ADR-0005 qc, ветка `core-rc`): таблица `unique_keys (scope, key) →
  aggregate_id`, behaviour `reserve` / `rename` / `release` / `find` с отказом `{:error, :taken}`, модули
  `*Key.sync(events, state, context)` у трёх агрегатов, вызов из usecase до `append`. Специфичного для приложения в
  механике нет.
- Изъяны переноса как есть:
  - таблица не знает текущего ключа агрегата: переименованию нужен старый ключ, снятию при `Deleted` без нагрузки —
    состояние после команды, а `release` удаляет по `(scope, key)` без проверки владельца;
  - колбэк `Agg.Process.execute` получает только события — агрегат с таким ключом через процесс агрегата не пишется;
  - вызов `sync` повторён в пяти usecase: забытый на новом пути записи — молчаливый дубль ключа;
  - порядок «резерв после чтения потока» держит дисциплина, а INSERT до чтения назначает xid и делает достижимым
    ложный `:version_mismatch` (ADR-0008, «Цена»).
- `Core.Es.Migration.up/0` с тремя таблицами вышел в v0.2.0: таблица, добавленная в него, у потребителя, который
  миграцию уже накатил, не появится.

## Рассмотренные варианты

### Объём

- **Только норма.** Отвергнут: колонки задаёт Pg-реализация, и каждый потребитель повторял бы таблицу, behaviour и
  тест гонки.
- **Норма, код и DDL в библиотеке (принято).**

### Модель владения

- **PK `(scope, key)`, у агрегата несколько ключей области — схема qc.** Отвергнут: снятию и переносу нужен старый
  ключ из события или состояния, запрет снять чужой ключ держится проверкой в каждой операции, колбэку процесса нужно
  состояние.
- **Один ключ области на агрегат, unique `(scope, aggregate_id)` (принято).** Новый ключ занимается одной операцией,
  она же снимает прежний ключ владельца; снятие — по владельцу; событиям состояние не нужно. Набор ключей одной области
  моделируется агрегатом на элемент с идентификатором из ключа.

### Точка встраивания

- **Явный вызов в usecase и в колбэке процесса.** Отвергнут: вызов повторяется на каждом пути записи, а порядок
  относительно чтения потока и `append` держит дисциплина.
- **Состояние после команды в колбэке `Process.execute`.** Отвергнут: при сопоставлении по событиям не нужно, а
  путь usecase → repo не покрывает.
- **Опция репозитория, как `outbox:` (принято).** `append` — единственная точка записи событий агрегата. Порядок
  «события → резервы → outbox» держит библиотека: конкурентная команда того же потока получает `:version_mismatch` до
  резервов. Полноту сопоставления и код отказа проверяет сборка — паритет с `constraint_errors:` state-stored.

### Каноническая форма и поиск

- **Нормализация в базе (`citext`, `lower()`).** Отвергнут: зависимость от расширения и локали, одно правило
  сравнения на все области.
- **Сопоставление отдаёт строку, `find` принимает строку, общая функция — нормой.** Отвергнут: вызов `find` мимо
  функции компилятор не видит.
- **Без `find`.** Отвергнут: «найти или создать» по ключу (`quick_start` qc) пошёл бы через read-модель, которую
  асинхронно пишет проекция.
- **Сопоставление отдаёт доменное значение, строку даёт `to_key/1`, её зовёт библиотека на записи и в `find`
  (принято).**

### Составной ключ

- **Склейка частей в строку приложением.** Отвергнут: `"x:y" + "z"` совпадает с `"x" + "y:z"` — по той же причине,
  что в ADR-0017.
- **Строка или список частей, колонка `text[]` (принято).**

### Отказ

- **`{:error, :taken}`, код подставляет вызывающий — схема qc.** Отвергнут вместе с явным вызовом.
- **Фиксированный код библиотеки.** Отвергнут: у агрегата с двумя ключами код один, потребитель переименовывает свой.
- **Значение ключа в `detail`.** Отвергнут: логин и email — ПДн, а ключ резерва — строка без `sensitive`-Prim.
- **Код задаёт модуль ключа, `detail` — `%{scope}` (принято).**

### DDL

- **Таблица в `Core.Es.Migration.up/0`.** Отвергнут: у потребителя, накатившего v0.2.x, не появится.
- **Версии DDL — `up(version: n)`, как в Oban.** Отвергнут: новая ось контракта ради одной таблицы.
- **Отдельный модуль `Core.Es.KeyReservation.Migration` (принято).**

### Существующие потоки

- **Функция библиотеки: прогон потоков через модуль ключа со списком дублей.** Отложен до второго потребителя с
  историей.
- **Норма: потребитель заполняет таблицу до первой записи нового кода (принято).**

## Решение

- Модуль ключа `<Aggregate>.<Name>Key` — `use Core.Es.KeyReservation, scope:, event:, id:, code:`. Потребитель пишет
  `reservation/1` → `{:reserve, value} | :release | :keep` на каждое событие агрегата и `to_key/1` →
  `String.t() | [String.t(), ...]`; строка равна списку из одной части. Генерируется
  `find(value, context) :: Agg.ID.t() | nil`.
- `use Core.Es.Aggregate.Repo.Pg, key_reservations: [...]`: `append` — `Es.Store.append` → резервы → outbox одной
  транзакцией. Отказ — `errors.domain(behaviour, code, %{scope: scope})`.
- Сборка репозитория проверяет: clause `code:` в `errors:`; clause `reservation/1` на каждое событие кодека
  (`Core.Es.Check`); `event:` — семейство кодека; `id:` — `id:` репозитория; области в `key_reservations:` не
  повторяются.
- `es_key_reservations`: `scope text`, `key text[]`, `aggregate_id uuid NOT NULL`; PK `(scope, key)`, unique
  `(scope, aggregate_id)`; DDL — `Core.Es.KeyReservation.Migration`. Повторный резерв тем же владельцем — успех;
  занятый ключ транзакцию в aborted не переводит.
- Нормы: событие, занимающее ключ, MUST нести ключ в нагрузке; catch-all в `reservation/1` MUST NOT; ключ
  сравнивается побайтно в форме `to_key/1`; резервы существующих потоков заполняются до первой записи нового кода.

## Цена

- **Событие несёт ключ.** Событие без нагрузки ключ не занимает: восстановление после удаления кладёт ключ в нагрузку.
- **Схема ключа неизменяема.** Правка `to_key/1` или области после первых данных — миграция строк таблицы, иначе
  прежние ключи перестают совпадать с новыми.
- **Набор ключей одной области у агрегата не выражается** — только агрегатом на элемент.
- **Заполнение держится нормой.** `key_reservations:`, добавленный к агрегату с историей без заполнения, молча
  пропускает дубли старых ключей.
- **Репозиторий с резервами зависит от таблицы**: без миграции `Core.Es.KeyReservation.Migration` запись падает.
