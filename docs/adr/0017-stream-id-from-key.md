# Идентификатор из ключа: вложенный UUIDv5 в области ключа, конструктор внутри Prim

Неизменяемый естественный ключ event-sourced агрегата становится идентификатором его потока через
`use Core.Prim.UUID, version: 5, namespace: …, scope: …`. Идентификатор считается вложенным UUIDv5: namespace
приложения → область ключа → части ключа по одной. Сгенерировать такой идентификатор нельзя (`new/0` нет), а
вычислить — только внутри Prim: библиотека даёт приватный `from_key/1`, который зовёт `from_<key>` потребителя.
Схема фиксирует id потоков навсегда, поэтому она совпадает со схемой первого потребителя и закреплена эталоном.

## Контекст

- `app/13-repos.md`, «Уникальность без индекса состояния»: id потока — UUIDv5 от ключа, namespace один на
  приложение, конструктор в Prim. Как считать составной ключ и как развести ключи разных агрегатов — не сказано.
- `Core.Prim.UUID` знал версии 1 / 4 / 7. quality-control-back считает id своим модулем через транзитивную `:uuid`
  и объявляет четыре Prim с `version: 7, check_version: false`: проверка версии на разборе снята, а `new/0`
  генерирует v7, которой у настоящих id этих агрегатов не бывает.
- Схема qc: `uuid5(namespace, scope)`, затем свёртка `uuid5(acc, part)` по частям ключа. Она на ветке, выпущенных
  данных на ней нет.
- Один Prim идентификатора бывает общим у нескольких типов агрегатов (`User.ID` у `User` и `UserRoles` в qc).
  Адрес потока — тип агрегата и id, PK `es_events` включает `aggregate_type`.

## Рассмотренные варианты

### Схема

- **Без области ключа, `uuid5(namespace, key)`.** Отвергнут: одинаковый ключ у двух видов даёт один id. Хранилище
  это переживёт, но id перестаёт быть уникальным в приложении — логи, права, ссылки.
- **Склейка области и частей через разделитель.** Отвергнут: `"x:y" + "z"` совпадает с `"x" + "y:z"`, а
  экранирование — ещё одна неизменяемая деталь схемы.
- **Область ключа — тип агрегата.** Отвергнут: Prim идентификатора агрегата не знает, и идентификатор бывает общим.
- **Части — Prim, строку берёт библиотека (`value/1` → `to_string`).** Отвергнут: схема привязалась бы к строковому
  представлению Integer / Decimal / DateTime, и его смена тихо переименовала бы потоки.
- **Вложенный UUIDv5 по строкам — схема qc (принято).**

### Где задаётся namespace

- **Аргумент конструктора.** Отвергнут: правило размазывается по вызовам.
- **`Core.Config` в рантайме.** Отвергнут: namespace зависел бы от окружения, а его смена переименовывает потоки.
- **Опция `use` со значением из одной функции приложения (принято).** Выражение вычисляется при сборке
  потребителя, компиляция библиотеки конфигурации потребителя не требует (`10-architecture.md`).

### `new/0`

- **Генерировать v7, как в qc.** Отвергнут: противоречит `version: 5` и требует снять проверку версии.
- **Случайный v5 в области ключа.** Отвергнут: пробы в тестах не меняются, но `Agg.ID.new()` в коде приложения
  обходит ключ — ровно «плохо» нормы, — и компилятор этого не видит.
- **Раздельные опции версии генерации и версий разбора.** Отвергнут: новая ось опций ради проб.
- **`new/0` нет (принято).**

### Конструктор

- **Публичный `from_key/1`.** Отвергнут: зовётся из usecase с произвольной строкой, и «конструктор в Prim» снова
  держится только дисциплиной.
- **Только функция библиотеки `v5(namespace, scope, parts)`.** Отвергнут: namespace и область потребитель хранит
  сам и повторяет обвязку.
- **Приватный `from_key/1`, публичный `from_<key>` пишет потребитель (принято).**

## Решение

- `use Core.Prim.UUID, version: 5, namespace: …, scope: "…"`. При сборке: namespace — валидная UUID-строка, scope —
  непустая строка; обе обязательны при `version: 5` и запрещены при других версиях. `check_version: false` при
  `version: 5` допустим: агрегат, переходящий на идентификатор из ключа, разбирает свои прежние случайные id.
- id — `Enum.reduce(parts, uuid5(namespace, scope), &uuid5(&2, &1))`; `from_key(part) == from_key([part])`.
- Генерируется `defp from_key(String.t() | [String.t(), ...]) :: t()`; `new/0` не генерируется.
- Нормы `app/13-repos.md`: `from_<key>` любой арности зовёт `from_key/1`; область ключа MUST у каждого
  идентификатора из ключа; namespace MUST браться из одной функции модуля приложения, литерал в Prim — MUST NOT.

## Цена

- **Пробы несуществующего агрегата** в тестах переписываются с `ID.new()` на `from_<key>` от уникального ключа.
- **Prim с `version: 5` без `from_<key>`** не собирается: `from_key/1` не используется, `--warnings-as-errors`.
- **Схема неизменяема**: её правка даёт другие id всем таким потокам. Эталонный тест ломается намеренно.
- **Единственность namespace держится нормой**: литерал с опечаткой в одном Prim компилятор не отличит.
- **Ключ с именем `key`**: `def from_key` потребителя сталкивается с `defp from_key/1` — `CompileError`, ключ
  переименовывается.
