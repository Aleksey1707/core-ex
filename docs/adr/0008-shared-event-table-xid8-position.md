# Общая таблица событий и глобальная позиция по `xid8`

События обоих видов агрегатов — event-sourced и state-stored — пишутся в одну таблицу `es_events`, DDL
которой поставляет библиотека. Глобальная позиция события — пара `(xid, номер)`: читатель забирает только
события транзакций старше самой старой активной, а append отвергает запись в поток, где уже лежит событие
более поздней транзакции, — иначе выдача переставляет версии потока.

## Контекст

До решения у каждого state-stored агрегата своя таблица событий (`Es.Event.Repo.Pg.Schema`, `table:`),
миграцию пишет потребитель, глобальной позиции нет. ADR-0007 требует глобального порядка, при котором
запись в разные потоки не ждёт commit чужой транзакции: остаются `xid8 < pg_snapshot_xmin` (Emmett) и
high-water mark (Marten).

Проверено на PostgreSQL 18.4 (2026-09-13):

- `pg_snapshot_xmin(pg_current_snapshot())` удерживают только транзакции с назначенным xid (запись,
  `FOR UPDATE` хотя бы по одной строке), в любой базе кластера; читающие, в том числе `REPEATABLE READ`, — нет;
- при `ORDER BY xid, position` версия 2 потока идёт раньше версии 1, если транзакция получила xid до commit
  писателя версии 1, а поток прочитала после; по одному `position` порядок версий верный;
- `INSERT … WHERE NOT EXISTS (… xid > pg_current_xact_id())` в этом сценарии вставляет 0 строк, в штатном — 1.

## Рассмотренные варианты

- **Таблица на агрегат.** Отвергнута: сквозной порядок по нескольким типам агрегатов требует общей sequence
  и `UNION` по таблицам, а подписка — реестра таблиц, которых библиотека не знает. Ни EventStore, ни Marten,
  ни Emmett, ни Message DB так не устроены.
- **Общая таблица только для event-sourced.** Отвергнута в пользу одного хранилища событий на приложение:
  state-stored оставался бы со своими таблицами и без глобальной позиции.
- **High-water mark по номеру.** Отвергнут: порядок потока сохраняется сам, но читателю нужен детектор дыр
  с проверкой живых транзакций (`pg_stat_activity`, `pg_snapshot_xip`) и закрытием окна между `nextval` и
  назначением xid; долгие транзакции останавливают его так же.
- **`xid8` без проверки порядка потока** (как в Emmett). Отвергнут: выдача переставляет версии потока.

## Решение

- Таблица `es_events`, DDL — `Core.Es.Migration`. Ключ потока — тип агрегата (`type:` у
  `use Core.Es.Event.Codec`) и `aggregate_id`; unique `(тип, aggregate_id, aggregate_version)` — проверка
  ожидаемой версии, таблицы потоков нет.
- `xid xid8 default pg_current_xact_id()` и номер из identity. Читатель берёт
  `xid < pg_snapshot_xmin(pg_current_snapshot())` в порядке `(xid, номер)`; сортировать выдачу по одному
  номеру нельзя — номер выдаётся до commit.
- Append в поток, где есть событие с `xid` больше текущего, возвращает `:version_mismatch`.

## Цена

- **Ломающее изменение для state-stored.** Таблицы событий на агрегат уходят вместе с `table:`, `by_schema:`
  и `payload_type:`; перенос истории пишет потребитель по `CHANGELOG.md` — по возрастанию версии внутри потока
  и до первой записи нового кода.
- **Ложный `:version_mismatch`**, в том числе у state-stored: usecase получил xid до чтения агрегата, а
  конкурентная команда по тому же агрегату успела закоммититься. Снимается повтором команды.
- **Чтение по позиции ждёт любую пишущую транзакцию кластера**, включая другие базы. На нагрузке не
  проверено.
- `by_id` без FK на таблицу пользователей потребителя, `payload` — jsonb библиотеки.
