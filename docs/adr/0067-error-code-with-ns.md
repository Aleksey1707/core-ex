# `code` доменной ошибки — `"<ns>/<code>"` без нового поля обёртки

`code` обёртки ответа у доменной ошибки — пара `ns` и `code` из `%Error{}` строкой
`"<ns>/<code>"` (`"account/not_found"`), у элементов `data.errors` — так же. Константы границы
(`"internal_error"`, `"not_authorized"`, имена статусов `by_status/2`) — без `ns`. Форма обёртки
ADR-0062 не меняется. Это уточняет ADR-0062, где `code` — голый `to_string(error.code)`.
Норма — `docs/rules/10-architecture.md`, «Граница HTTP»; `docs/rules/app/12-errors.md`,
«Словарь `ns`».

## Контекст

Факты на 2026-10-14:

- `code` уникален только внутри `ns`: каталог каждого агрегата обязан нести `:not_found`,
  `:version_mismatch` и коды `constraint_errors:` (это проверяет сборка репозитория), а
  различаются каталоги одним `ns/0`; `:invalid_value` ставят и `:enum`, и `:codec`;
- у фронта есть сценарий, где команда ссылается на сущности разных видов, и по `400 not_found`
  он не может подсветить, какой из них нет; `message` различает их для человека, но не для
  ветвления;
- `ns` у каталогов уникален: два каталога с одним `ns` — дефект, `ns` библиотеки приложению
  брать нельзя (`docs/rules/app/12-errors.md`); пара `ns/code` однозначна;
- форма обёртки `{status, data, code, message}` согласована с общим фронтом и не меняется — ни
  новым ключом верхнего уровня, ни ключом в `data`; зарезервированный `data.fields` (ADR-0062)
  остаётся единственным согласованным расширением;
- ADR-0062 ещё не выпущен: потребители переходят на строковый `code` один раз.

## Рассмотренные варианты

- **Не отдавать `ns`.** Отвергнут: сценарий фронта реальный, а `message` — текст для человека, и
  ветвиться по нему нельзя.
- **Отдельное поле `ns` в обёртке или `data.ns`.** Отвергнут: форма обёртки зафиксирована, ключ
  в открытом `data`, на который ветвится клиент, — то же новое поле.
- **Уникальные коды в каталогах (`:account_not_found`).** Отвергнут: обязательные коды каталога
  (`:not_found`, `:version_mismatch`) задаёт библиотека, по ним сопоставляют код и маппер (412),
  переименование ломает контракт каталога ради границы HTTP.
- **`ns` только у кодов каталогов агрегатов или только у общих кодов (`not_found`).** Отвергнут:
  фронту пришлось бы держать список «каких `ns` касается», синхронный с библиотекой.
- **Разделитель `.` или `:`.** Отвергнут: `/` — та же запись, что у `String.Chars` для
  `%Error{}` и у fallback `Error.format_chain/1`, и код из ответа находится grep-ом в логе.
- **Путь поля вместо `ns`.** Не заменяет: ссылки сценария ведут на сущности разных видов, и `ns`
  их разводит; ссылки на сущности одного вида — задача `data.fields`.

## Решение

- `code` доменной ошибки и элемента `data.errors` — `"<ns>/<code>"`; `ns` добавляется только при
  сборке обёртки, `%Error{}` и сопоставления по `code:` внутри приложения не меняются;
- константы границы — без `ns`: код без `/` — константа, с `/` — доменный; заодно разошлись
  `"not_found"` неизвестного маршрута и `"<ns>/not_found"` сущности;
- доменную обёртку собирает `Core.Web.Response.error/1` от `%Error{kind: :domain}`; атомная
  `error/2,3` — для констант; своя клоза маппера приложения — `Response.error(err)`;
- `ns` каталога после первого релиза приложения менять нельзя, как и его коды.

## Цена

- **`ns` стал публичным контрактом:** переименование `ns/0` каталога и `ns` библиотеки
  (`:prim`, `:enum`, `:codec`, `:web`, …) ломает клиента, который ветвится по коду.
- **Шум у библиотечных `ns`:** `"prim/max_len"` клиенту говорит не больше, чем `"max_len"`, —
  плата за одно правило без списков.
- **Ссылки на сущности одного вида не различаются:** `ns` называет вид, а не поле; это остаётся
  за `data.fields`.
