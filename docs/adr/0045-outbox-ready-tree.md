# Очередь outbox — готовое дерево `Core.Outbox.Supervisor`, wake — по его отметке

Очередь outbox поднимает только готовое дерево библиотеки `Core.Outbox.Supervisor`: соединение,
writer'ы, поллеры и cleaner под `rest_for_one`, проверки единственности и разбиения поллеров при
старте, тумблер `enabled:` и `watch_list/1`. Своего корня очереди у приложения нет: дерево стоит в
`Application` без корня, опции собирает одна функция `MyAppApp.Application.outbox_opts/0` из
`config :my_app, Core.Outbox.Supervisor`. Поллеры будит отметка, которую дерево пишет при
старте; ключ `config :core, Core.Outbox` библиотека больше не читает. Решает кандидата «корень
очереди — готовое дерево» из ADR-0043. Норма — `docs/rules/14-events-outbox.md`,
`docs/rules/app/14-events-outbox.md`, «Единственность поллера», «Конфигурация»;
`docs/rules/app/17-otp-concurrency.md`, «Готовое дерево без корня».

## Контекст

Факты на 2026-10-03 (обзор корней — `.scratch/consumer-architecture/research/03-component-roots.md`,
«Корень очереди у пяти потребителей»; сверка кода корней очереди —
`.scratch/consumer-architecture/issues/11-outbox-ready-tree.md`, «Comments»):

- корень очереди есть у всех пяти потребителей с компонентами (A, B, C, D, F): `rest_for_one`,
  порядок writer → поллер(ы) → cleaner, доставка `Core.Outbox.Delivery.Mq`, одни ключи
  `OUTBOX_*`, обёртки tunables в Prim через `new!`; файл корня — 138–191 строка. Функция поиска
  фильтра топиков поллера по имени у четырёх совпадает побайтно;
- порядок детей — `MUST` свода (`17-otp-concurrency.md`, «Дерево процессов»), проверка
  единственности — `MUST` корня очереди (`app/14`, «Единственность поллера»), её вызов держит
  ратчет (`app/19`, «Ратчеты»). Библиотечный `Core.Outbox.check_singleton!/1` зовёт только A; у
  B, C, D, F — свои копии с разными текстами, у D пустой `DNS_CLUSTER_QUERY` считается кластером,
  у библиотеки — нет. `Core.Outbox.validate_partition!/1` зовёт только B, и не из корня, а из
  `start/2` `Application`;
- поллер будит `Core.Outbox.Repo.Pg` после вставки: на каждый вызов он читает `poller_name` /
  `pollers` из `config :core, Core.Outbox`. Корень берёт имена поллеров из того же ключа, и
  расхождение не видно: `Poller.wake/1` на отсутствующий процесс отдаёт `:ok`, записи уходят по
  safety poll с задержкой до `poll_interval_ms`. У B при выключенном Kafka wake адресует
  неподнятый Kafka-поллер;
- у F очередь не стартует ни в одном окружении: корень читает ключ приложения, а
  `config/runtime.exs` пишет под `:core`; `enabled` всегда `false`, в лог уходит штатное
  «отключены». Включённый корень упал бы на незаданном ключе `repo:` и на отсутствии
  обязательной `delivery_module:` поллера;
- у B два поллера на разных транспортах: Stream через writer-процесс корня и Kafka через клиента,
  которого поднимает `Application` под тумблером брокера. У D соединение Stream — первый ребёнок
  корня: других пользователей у него нет (`app/17`, «Дерево процессов»: соединение с одним
  пользователем живёт в корне компонента);
- готовые деревья библиотеки config и env не читают: опции собирает одна функция приложения, её же
  принимает `watch_list/1` дерева (`Core.Es.Projection.Supervisor`, `projection_opts/0`);
- ADR-0043 забирает повтор корней в библиотеку функцией или готовым деревом, когда за ним стоят
  порядок или проверка, которые можно держать построением, и назвал корень очереди кандидатом.

## Рассмотренные варианты

- **Корень очереди остаётся у приложения.** Отвергнут: порядок детей и две проверки старта держат
  ревью и ратчет, и у четырёх из пяти потребителей проверка — своя копия, у F корень мёртв молча.
  Переезд B–F на вертикаль переписал бы корень ещё раз.
- **Отложить до второго потребителя с корнем очереди на вертикали.** Отвергнут: повтор измерен у
  пяти потребителей, а не у одного, и отсрочка оставила бы B–F переписывать корень дважды — тот же
  довод, по которому ADR-0043 не ждал.
- **Дерево `MAY` рядом со своим корнем.** Отвергнут: ради своих корней пришлось бы держать
  публичные проверки и ратчет, а wake без отметки дерева такой корень не будил бы.
- **Wake читает env, дерево — опции.** Отвергнут: два источника имён поллеров, расхождение которых
  видно только задержкой доставки. **Дерево читает `pollers` из env** — отвергнут: деревья
  библиотеки config не читают.
- **`delivery:` поллера как есть и writer'ы отдельной опцией.** Отвергнут: порядок «writer раньше
  своего поллера» снова держало бы приложение. **Writer-процесс или чужой процесс по форме второго
  элемента** (`keyword` / атом) — отвергнут: форма данных молча решала бы, поднимается ли процесс.
- **Тумблер на поллер.** Отвергнут: тумблер транспорта — функция владельца разделяемой
  инфраструктуры (`app/17`), список поллеров с его учётом собирает приложение, и один список —
  правда для старта, wake и `watch_list/1`.
- **Проверка полноты разбиения топиков.** Отвергнута: она запретила бы выключать транспорт — у B
  при выключенном Kafka записи его топиков ждут в `pending` до включения.
- **Дефолты tunables в библиотеке**, как у дерева проекций. Отвергнуты: все `OUTBOX_*` заданы в
  `config/runtime.exs` каждого потребителя, у D — со своими значениями; дефолт в библиотеке стал бы
  вторым источником.
- **Переходный период:** wake без отметки читает env с `warning`. Отвергнут: на текущей форме
  только A, остальные переписывают корни при переезде; громкий отказ старта дешевле.

## Решение

- **Дерево.** `Core.Outbox.Supervisor`, одно на ноду, `rest_for_one`: `connection:` → на каждый
  поллер его writer-процесс (если есть) и сам поллер в порядке `pollers:` → cleaner. Свой
  супервизор очереди — `MUST NOT`. `Poller.init/1`, не найдя своего имени в отметке дерева,
  отказывает `ArgumentError`: поллер стартует только из дерева.
- **Опции.** Обязательные: `enabled:`, `cluster_query:` (без дефолта; `nil`, `:ignore`, `""` —
  кластеризации нет), `repo:`, `pollers:`, `poll_interval_ms:`, `idle_min_ms:`, `batch_size:`,
  `lock_duration_seconds:`, `max_attempts:`, `published_ttl_seconds:`, `cleaner_interval_ms:` —
  tunables голыми целыми, в Prim их оборачивает дерево. Необязательные: `allow_cluster:`
  (`false`), `context_factory:` (`&Context.new/0`, одна на поллеры и cleaner), `connection:`
  (`{mod, opts}` — первый ребёнок под тумблером дерева).
- **Поллер.** Элемент `pollers:` — `name:`, `topics:` (по умолчанию `:all`), `label:` (строка,
  метка компонента в `watch_list/1`) и ровно один из `writer: {mod, opts}` — writer-процесс,
  который поднимает дерево, пишет через `opts[:name]` — или `via: {mod, name}` — процесс, которым
  владеет приложение. `delivery_module` / `delivery` собирает дерево. Тумблер транспорта
  учитывает приложение при сборке списка.
- **Старт.** `start_link/1` проверяет опции при любом `enabled:`, затем единственность на кластере
  и непересечение фильтров поллеров; обе проверки — приватные детали дерева. `enabled: true` при
  `pollers: []` — `ArgumentError`. Полнота разбиения не проверяется: топики вне фильтров ждут в
  `pending`. `enabled: false` — `:ignore` с `info`.
- **Wake.** До подъёма детей, и при `:ignore`, дерево пишет отметку в `:persistent_term`: имена и
  фильтры поднятых поллеров. Wake после вставки читает только её; нода без дерева или с выключенным
  деревом не будит никого. `config :core, Core.Outbox` библиотека не читает.
- **Приложение.** Дерево стоит в `Application` без корня (`app/17`, «Готовое дерево без корня»).
  Опции собирает `MyAppApp.Application.outbox_opts/0` из `config :my_app, Core.Outbox.Supervisor`;
  её же принимает `Core.Outbox.Supervisor.watch_list/1`. Модуля `MyAppApp.Outbox` нет.
- **Наблюдение.** `watch_list/1`: `outbox_connection`, `outbox_writer:<label>` (только
  writer-процесс дерева), `outbox_poller:<label>`, `outbox_cleaner`; при выключенном дереве —
  пусто. Процесс из `via:` наблюдает его владелец.

## Цена

- ломающее изменение для каждого потребителя: ключ конфигурации переезжает из `:core` в ключ
  приложения, рукописный корень очереди заменяется деревом, `check_singleton!/1` и
  `validate_partition!/1` уходят из публичного API, ратчет вызова проверки снимается;
- приложение со старым корнем после обновления библиотеки не стартует — отказ `Poller.init/1`, а не
  деградация доставки;
- при выключенном транспорте `pending` его топиков растёт без отказа: это видно только метриками
  `Core.Outbox.PromEx`;
- имена компонентов в `watch_list` меняются у всех потребителей (`outbox_poller` у A,
  `outbox:poller` у D) — дашборды и алерты на старые имена правятся при переезде;
- тесты библиотеки и фикстура-потребитель поднимают поллер только через дерево.
