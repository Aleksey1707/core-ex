# Метрики очереди outbox не считают `:published`

`Outbox.Repo.queue_counts/0` (бывший `counts_by_status/0`) считает только `:new`,
`:in_work` и `:failed` — по частичным индексам. `:published` не считается: это архив,
ждущий TTL, единственный неограниченно растущий статус.

## Контекст

`counts_by_status/0` был одним `GROUP BY status` по всей таблице — ни один частичный индекс
под него не подходит. При дефолтном `poll_rate: 5_000` это seq scan таблицы каждые пять
секунд ради четырёх gauge'ей: замер на 400k строк — 28–40 мс и ~12 200 буферов на опрос.

Отдельно у `:failed` не было **никакого** индекса, хотя на нём висит алерт
`OutboxQueueFailedGrowing`, а `Cleaner` эти строки не удаляет — они копятся до разбора
оператором. Счёт `:failed` и `requeue_failed/2` были seq scan'ом всей таблицы ради почти
всегда пустого ответа.

## Рассмотренные варианты

Три варианта, все измерены на одних данных (Postgres 18, 400k строк):

| Вариант | Здоровая очередь (`new=0`) | Забитая (`new=200k`) |
|---|---|---|
| `GROUP BY status` (как было) | 27,4 мс | 39,9 мс |
| четыре скалярных `count` по статусам | 57,1 мс | — |
| **три `count` без `:published`** | **0,14 мс** | **23,2 мс** |

- **Четыре скалярных `count`** — очевидный вариант, отвергнут измерением: медленнее исходного
  вдвое. Счёт `:published` идёт Index Only Scan'ом по всем 200k записям индекса, и это дороже
  одного seq scan'а, покрывающего сразу все статусы.
- **Индекс по `status` + `GROUP BY`.** Убрал бы обращение к куче, но остался бы O(N) по
  индексу: точный счёт большой таблицы дешевле не становится.
- **Приблизительный счёт (`reltuples`).** Неприемлемо для gauge глубины очереди: значение
  используется в алертах, а не в оценке.

Победивший вариант выигрывает в **обоих** режимах, потому что убирает единственную
неограниченную составляющую. Оставшиеся три статуса ограничены по природе: `:in_work` не
больше `batch_size` × число поллеров, `:new` дренится, `:failed` — инцидент.

## Последствия

- Callback переименован: `counts_by_status/0` → `queue_counts/0`. Имя, обещающее счёт по
  **каждому** статусу и не выполняющее обещания, было бы хуже переименования; новое совпадает
  с именем метрики `outbox_queue_count`.
- Gauge `outbox_queue_count{status="published"}` больше не выставляется — ломающее изменение
  для дашбордов. Про запас опубликованных говорят `outbox_cleaner_deleted_total` и размер
  таблицы; если `Cleaner` сломан, об этом прямо сообщает
  `outbox_cleaner_cycles_total{result="error"}`.
- Миграция получила `ix_outbox_failed (created_at, id) WHERE status = 'failed'`: счёт
  `:failed`, `oldest_age_seconds(:failed)` и `requeue_failed/2` — **12 351 → 1 буфер**.
  Индекс безопасно накатывается `CONCURRENTLY`; таблица `outbox` в `priv/repo/migrations` —
  исполняемая спецификация, состав индексов у потребителя обязан совпадать.
- В забитом состоянии счёт `:new` остаётся O(N) (Parallel Index Only Scan). Это осознанно:
  ровно тогда точная глубина очереди и нужна, а 23 мс на опрос в разгар инцидента не имеют
  значения.
