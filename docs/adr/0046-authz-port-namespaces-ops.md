# Порт доступа: несколько пространств, операции в реестре, общее чтение, 401

Частично заменён ADR-0053 (`0053-query-for-other-contexts-without-declaration.md`): чтение, которое
контекст отдаёт другим контекстам, лежит в `Query` без декларации, а точки входа на него не
ссылаются; пункт «общее чтение без проверки отвергнуто» остаётся только для чтения точками входа.
Частично заменён ADR-0054 (`0054-authz-ops-checked-at-compile.md`): операции `check_user` сверяет
сборка, `check_user` — макрос порта; пункт «сверка операций на сборке отвергнута» и сверка операций
только портом не действуют. Ниже — решение в редакции 2026-10-03.

Декларация `use MyApp.Authz` стоит на каждом модуле usecases, который проверяет доступ, включая
модуль общего чтения `<Aggregate>.Usecases`; `account:` принимает список типов учётной записи.
Дополнительные пространства своего контекста декларация перечисляет `namespaces:`, usecase зовёт
их `check_user/3`. Оглавление объявляет у пространства не только описание, но и операции, порт
сверяет операции с реестром до вызова реализации. Каталог ролей — модель контекста прав, а не
порта. Отказ порта — `:access_denied` (403) или `:unauthorized` (401). Дополняет ADR-0042: тот
дал порт с одним пространством на модуль актора, реестр «ключ → описание» и один код отказа.
Норма — `docs/rules/app/10-architecture.md`, «Проверка доступа», «Модуль-оглавление»;
`docs/rules/app/12-errors.md`, «Границы»; `docs/rules/app/19-testing.md`, «Проверка доступа».

## Контекст

Факты на 2026-10-03 (адаптация потребителя A к rc после 0.10.0):

- usecase потребителя A проверяет кроме пространства своего модуля второе пространство своего
  контекста — 12 вызовов в 6 модулях; декларация ADR-0042 давала
  только `check_user/2` над одним пространством;
- реестр потребителя A собирает операции каждого пространства из деклараций; на нём стоят
  стартовая выдача прав и endpoint фактических прав, а рядом лежит каталог ролей (роль — набор
  пространств); реестр ADR-0042 — `[{key, описание}]`, операций в нём нет;
- `app/10` выносит чтение нескольких акторов в `<Aggregate>.Usecases`, а декларацию требовал
  только на модуле актора: у модуля общего чтения не было ни `account:`, ни `check_user/2`;
- плаг существование пользователя не проверяет (`app/15`), а отказ порта был только
  `:access_denied`: «учётной записи нет или она заблокирована» уходило 403 вместо 401;
- `Core.Web.ErrorMapper` отвечает 401 на `:unauthorized` любого `kind` без своей клозы;
- проверено на Elixir 1.20: вызов `defp` с литералом атома, которого нет ни в одной clause, —
  предупреждение типов при сборке.

## Рассмотренные варианты

- **Второе пространство — второй модуль актора.** Отвергнут: usecase один, и его проверка
  разъехалась бы по двум модулям, а модуль без usecases существовал бы ради декларации.
- **Ключ пространства параметром каждого `check_user`.** Отвергнут: основное пространство модуля
  повторялось бы в каждом usecase, а сверку ключа с оглавлением делал бы рантайм.
- **Ключ пространства другого контекста в декларации.** Отвергнут: сверка идёт по оглавлению
  своего контекста, а доступ к данным другого контекста проверяет его экспортированный usecase.
- **Сверка операций на сборке.** Отвергнут: `check_user` — `defp`, а операции — список, который
  guard не сверит; макрос вместо функции не вызвать из модуля, который его определил. Сверка в
  порте ловится тестом usecase с моком: мок подменяет реализацию, а не порт.
- **Каталог ролей в порте.** Отвергнут: роль — модель прав (её выдают и отзывают usecases
  контекста прав), и порт стал бы знать модель.
- **Общее чтение без проверки, проверка у вызывающего.** Отвергнут: web зовёт usecase напрямую,
  и чтение без проверки было бы открыто.
- **`account:` модуля общего чтения не задаётся, тип берёт реализация из контекста.** Отвергнут:
  какие акторы читают модуль, перестало бы быть видно в его исходнике.
- **401 своей клозой `map/1`.** Отвергнут: `ErrorMapper` уже понимает `:unauthorized`, а своя
  клоза в каждом приложении повторяла бы одно и то же.

## Решение

- декларация — на каждом модуле usecases с проверкой доступа, включая `<Aggregate>.Usecases`;
  `account:` — атом или список, порт передаёт реализации список;
- `namespaces:` — дополнительные ключи своего контекста; макрос генерирует `check_user/3` с
  clause на каждый объявленный ключ и сверяет все ключи с оглавлением в теле модуля;
- `authz_namespaces/0` — `[{key, {описание, операции}}]`; порт сверяет операции с реестром до
  реализации, необъявленная — `ArgumentError`;
- каталог ролей лежит в контексте прав и берёт пространства и операции из
  `MyApp.Authz.namespaces/0`;
- отказ порта — `:access_denied` (403) или `:unauthorized` (401) каталога `MyApp.Authz.Errors`.

## Цена

- **Behaviour `check/4` меняет тип первого аргумента** на список: реализация и мок правятся.
- **Операции пространства — третий список рядом с описанием и `check_user`:** новая операция
  правит оглавление, иначе тест usecase падает `ArgumentError`.
- **Интеграционных тестов доступа больше:** по одному на каждую проверку пространства, а не на
  usecase.
- **Чужое пространство в одном usecase не выразить:** проверка уходит в экспортированный usecase
  другого контекста.
