# Читатель Kafka без consumer group: смещения и аренда в Postgres

`Core.Mq.Kafka.Reader` читает топик прямым `fetch` клиента `:klife`, а не через consumer group.
Смещения хранятся в таблице БД потребителя, одну активную ноду на топик выбирает аренда строкой с
fencing-токеном. Решение рассчитано на кластеры Kafka без поддержки KIP-848 и работает на любой
Kafka ≥ 3.1.

## Контекст

Факты на 2026-09-30:

- consumer group `:klife` 1.2 реализует только протокол KIP-848: ей нужны
  `ConsumerGroupHeartbeat` v1 и `OffsetCommit` / `OffsetFetch` v9. Классического протокола
  (`JoinGroup` / `SyncGroup` / `Heartbeat`) в клиенте нет. На брокере без KIP-848 фича
  `:consumer_group` отключается при согласовании версий, и `start_link` группы падает;
- кластер потребителя, ради которого пишется читатель, KIP-848 не поддерживает (проверено
  `ApiVersions` каждого брокера); сроков обновления нет;
- топики принадлежат внешней системе; ACL на ресурс `Group` для коммита смещений в Kafka
  выдают их владельцы, и выдадут ли — неизвестно;
- прямой `Client.fetch/4` `:klife` публичен и от фичи `:consumer_group` не зависит; ему нужен
  `Fetch` ≥ v13 (Kafka ≥ 3.1);
- число партиций (`Klife.MetadataCache`) и earliest / latest смещения (`ListOffsets` через
  `Klife.Connection.Broker.send_message/4`) у `:klife` есть только во внутренних модулях
  (`@moduledoc false`); `log_start_offset` и high watermark из ответа `Fetch` наружу не отдаются;
- при смещении ниже начала лога `fetch` отдаёт `{:error, 1}` (`OFFSET_OUT_OF_RANGE`), при смене
  лидера — `{:error, code}` без повтора: повторяет вызывающий;
- у библиотеки уже есть аренда строкой с fencing-токеном — у поллера outbox (`lease_id`,
  `locked_until`).

## Рассмотренные варианты

- **Consumer group `:klife`.** Отвергнут: не работает на кластере без KIP-848 и требует ACL на
  группу.
- **`brod` на чтение (classic group, `resolve_offset` и high watermark в публичном API).**
  Отвергнут: второй Kafka-клиент рядом с `:klife`, вторая конфигурация подключения к тому же
  кластеру у потребителя, и классической группе всё равно нужен ACL на `Group`.
- **Ждать обновления кластера.** Отвергнут: срока нет, загрузка стоит без даты.
- **Advisory lock Postgres вместо аренды строкой.** Отвергнут: сессионный замок не работает за
  pgbouncer в режиме транзакций, а обрыв соединения отдаёт его молча — устаревшая нода не узнает,
  что потеряла топик.
- **Остановка чтения при `OFFSET_OUT_OF_RANGE` до вмешательства оператора.** Отвергнут: для
  загрузки справочников простой хуже громкого пропуска.

## Решение

- `Kafka.Reader` читает все партиции топика, обходя их по кругу; одно сообщение в работе на
  читатель (контракт `Mq.ReaderReliable`);
- следующее смещение — строка таблицы БД потребителя с ключом `(subscriber_name, topic,
  partition)`; `commit` — синхронный upsert, `:ok` значит «записано». Миграция — хелпером
  библиотеки, repo — опция читателя. Гарантия — at-least-once, commit отдельно от обработчика;
- топик читает одна нода — владелец аренды строкой с fencing-токеном; `commit` проверяет токен, у
  устаревшей ноды он возвращает `{:error, _}`, и сообщение повторит новый владелец. Нода без
  аренды отдаёт `:empty`;
- без сохранённого смещения — earliest по `ListOffsets`; смещение вне лога (съела retention или
  топик пересоздан) — переход на earliest с `error` в лог и счётчиком сброса;
- смена лидера, `:timeout`, `:unexpected_resp` — повтор с backoff внутри читателя, `get` отдаёт
  `:empty`;
- вызовы внутреннего API `:klife` — в одном модуле адаптера; требование сужено до
  `{:klife, "~> 1.2.0"}`; `Core.Mq.Kafka.ensure_available!/0` проверяет, что внутренние функции
  на месте; изменение ловит тест `:kafka` на живом брокере.

## Цена

- **Одна нода на топик.** Потребитель, которому нужно делить партиции между нодами, этого не
  получит. На кластере с KIP-848 это закрывается отдельным режимом на consumer group `:klife`
  рядом с этим, без смены контракта `Mq.ReaderReliable`.
- **Смещения не видны владельцам топика.** `kafka-consumer-groups.sh` и мониторинг групп
  брокера читателя не показывают; отставание видно только по метрикам `Core.Mq.PromEx`.
- **Внутренний API клиента.** Обновление `:klife` за пределы `1.2.x` — осознанный шаг с прогоном
  тестов `:kafka`, а не `mix deps.update`.
- **Своя аренда и своя таблица.** У потребителя появляется ещё одна миграция и ещё одна таблица,
  которую нельзя чистить вручную: потеря строки — перечитывание топика с начала.
