# Читатель Kafka без consumer group: смещения и аренда в Postgres

`Core.Mq.Kafka.Reader` подписывается на `brod_consumer` каждой партиции топика, а не на consumer
group. Смещения хранятся в таблице БД потребителя, одну активную ноду на топик выбирает аренда
строкой с fencing-токеном. Решение рассчитано на кластеры Kafka без поддержки KIP-848 и работает
на любой Kafka ≥ 0.11. Клиент — `:brod` (ADR-0034).

## Контекст

Факты на 2026-09-30:

- кластер потребителя, ради которого пишется читатель, KIP-848 не поддерживает (проверено
  `ApiVersions` каждого брокера); сроков обновления нет;
- топики принадлежат внешней системе; ACL на ресурс `Group` для коммита смещений в Kafka
  выдают их владельцы, и выдадут ли — неизвестно;
- `brod_consumer` читает одну партицию без группы: подписчик — любой процесс
  (`brod:subscribe/5`), сообщения приходят ему в почтовый ящик пачками `#kafka_message_set{}` с
  `high_wm_offset`; неподтверждённых (`brod:consume_ack/4`) не больше `prefetch_count` /
  `prefetch_bytes`; стартовая позиция — `begin_offset` (смещение или `earliest`);
- смену лидера `brod_consumer` обрабатывает сам — переподключением; ошибки, после которых
  процесс перезапускается, приходят подписчику сообщением;
- при `OFFSET_OUT_OF_RANGE` и `offset_reset_policy: reset_by_subscriber` `brod_consumer`
  сообщает подписчику и ждёт переподписки с новым `begin_offset`;
- `brod_topic_subscriber` читает все партиции без группы, но зовёт колбэк-модуль в своём
  процессе и ждёт от него ack — push, а контракт `Mq.ReaderReliable` — pull (`get` / `commit`);
- у библиотеки уже есть аренда строкой с fencing-токеном — у поллера outbox (`lease_id`,
  `locked_until`).

## Рассмотренные варианты

- **Consumer group `:klife`.** Отвергнут: только KIP-848, на кластере не работает (ADR-0034).
- **Классическая группа `:brod` (`brod_group_subscriber_v2`).** Отвергнут: требует ACL на
  `Group`, а выдадут ли его — неизвестно.
- **`brod_topic_subscriber`.** Отвергнут: колбэк в чужом процессе пришлось бы блокировать до
  `commit` читателя; подписка самого читателя на `brod_consumer` даёт то же без моста.
- **Прямой `fetch` `:klife`.** Отвергнут: свой цикл fetch поверх внутреннего API клиента
  (ADR-0034).
- **Ждать обновления кластера.** Отвергнут: срока нет, загрузка стоит без даты.
- **Advisory lock Postgres вместо аренды строкой.** Отвергнут: сессионный замок не работает за
  pgbouncer в режиме транзакций, а обрыв соединения отдаёт его молча — устаревшая нода не узнает,
  что потеряла топик.
- **Остановка чтения при `OFFSET_OUT_OF_RANGE` до вмешательства оператора.** Отвергнут: для
  загрузки справочников простой хуже громкого пропуска.

## Решение

- `Kafka.Reader` — GenServer, подписчик `brod_consumer` каждой партиции топика. Пачки из
  почтового ящика — в буфер по партициям, `get` обходит партиции по кругу; одно сообщение в
  работе на читатель (контракт `Mq.ReaderReliable`), буфер ограничен `prefetch_count`;
- следующее смещение — строка таблицы БД потребителя с ключом `(subscriber_name, topic,
  partition)`; `commit` — синхронный upsert, `:ok` значит «записано», затем `consume_ack`.
  Миграция — хелпером библиотеки, repo — опция читателя. Гарантия — at-least-once, commit
  отдельно от обработчика;
- топик читает одна нода — владелец аренды строкой с fencing-токеном; `commit` проверяет токен, у
  устаревшей ноды он возвращает `{:error, _}`, и сообщение повторит новый владелец. Нода без
  аренды не подписана и отдаёт `:empty`;
- без сохранённого смещения — `begin_offset: earliest`. `offset_reset_policy:
  reset_by_subscriber`: смещение вне лога (съела retention или топик пересоздан) — `error` в лог,
  счётчик сброса и переподписка с earliest;
- смена лидера — внутри `brod_consumer`, `get` отдаёт `:empty`, пока буфер пуст; перезапуск
  `brod_consumer` читатель видит по monitor и переподписывается с зафиксированного смещения;
- число партиций — `brod:get_partitions_count/2` раз в интервал, новые партиции получают
  подписку; отставание в сообщениях — `high_wm_offset` минус зафиксированное смещение;
- только публичный API `:brod`.

## Цена

- **Одна нода на топик.** Потребитель, которому нужно делить партиции между нодами, этого не
  получит. На кластере с выданным ACL на `Group` это закрывается отдельным режимом на
  классической группе `:brod` рядом с этим, без смены контракта `Mq.ReaderReliable`.
- **Смещения не видны владельцам топика.** `kafka-consumer-groups.sh` и мониторинг групп
  брокера читателя не показывают; отставание видно только по метрикам `Core.Mq.PromEx`.
- **Своя аренда и своя таблица.** У потребителя появляется ещё одна миграция и ещё одна таблица,
  которую нельзя чистить вручную: потеря строки — перечитывание топика с начала.
