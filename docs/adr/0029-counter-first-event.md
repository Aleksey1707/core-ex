# Первое событие серии счётчика

Рекомендованный алерт на единичное событие поднимается на первое событие новой серии счётчика.
Условие таблицы «Рекомендованные алерты» получает правую ветку — серию, которая есть сейчас и
у которой не было точек окно назад:
`increase(x[w]) > 0 or (x unless last_over_time(x[w] offset w)) > 0`. Новый счётчик под
такой алерт с закрытым множеством меток объявляется `sum` по `count` и засевается нулём
процессом-владельцем — тогда его условию правая ветка не нужна. Норма записана в
`docs/rules/21-observability.md`, «Первое событие серии счётчика».

## Контекст

Факты на 2026-09-29:

- серия `counter` у `telemetry_metrics_prometheus_core` появляется после первого события сразу со
  значением 1 (`:ets.update_counter(…, 1, {key, 0})`); `increase` по серии, у которой в окне нет
  точки до первого события, прироста не видит, и внешняя `sum(...)` это не лечит;
- алерты таблицы `OutboxFailedDelivery`, `MqPublishErrors` (с вариантом Kafka), `MqDecodeDrops`,
  `MqSubscriberDlq`, `CacheUnavailable`, `CacheStoreErrors` стояли на `increase(x[5m]) > 0` и не
  поднимались на первое событие по каждой паре меток после старта ноды: единичное сообщение в DLQ
  или единичный отказ публикации проходили молча;
- у всех шести счётчиков есть открытая метка (`topic`, `dlq_topic`, `cache`): множество её
  значений при старте ноды неизвестно;
- `EsKeyReservationUnresolved` уже стоит на форме с правой веткой: у резервов нет
  процесса-владельца, который засеял бы серию; метрики сигнала чекпоинта
  (`es_projection_signal_{sent,received}_total`) уже объявлены `sum` и засеваются нулём
  слушателем (ADR-0028);
- `EsProjectionRetrying` и `PromExCollectFailing` несут `for:`, а их событие повторяется каждый
  цикл, пока длится отказ: второй инкремент рост видит;
- неудачный скрейп Prometheus отмечает серии цели staleness marker'ом: мгновенный селектор на
  метке и после неё до следующей точки серии не находит, а диапазонный маркеры пропускает;
- потребитель A закрывает каждую строку матрицы отказов алертом с тестом `promtool test rules`.

## Рассмотренные варианты

- **Засев нулями существующих счётчиков при старте.** Отвергнут: засеять можно только известную
  серию, а открытые метки (`topic`, `dlq_topic`, `cache`) при старте неизвестны — первое событие по
  новому топику всё равно появилось бы сразу с 1.
- **`created-timestamp-zero-ingestion` Prometheus** — сервер сам вставляет 0 в момент создания
  серии. Отвергнут: флаг опирается на created timestamp серии, а экспортёр библиотеки серий
  `_created` не отдаёт; правка экспортёра — вне библиотеки.
- **Проверка `up` в условии** — правая ветка только при цели, которая скрейпилась окно назад.
  Отвергнута: после простоя ноды дольше окна серии снова «новые», и проверка прятала бы первое
  событие после такого простоя — ровно тот случай, ради которого ветка заведена.

- **Правая ветка `x unless x offset w`.** Отвергнута: мгновенный `offset` попадает на staleness
  marker единичного пропуска скрейпа, и через окно алерт поднимается по каждой ненулевой серии цели
  на интервал скрейпа (проверено `promtool test rules`). Диапазон `last_over_time(x[w] offset w)`
  маркер пропускает и терпит разрывы короче окна.

## Решение

- шесть алертов таблицы получают форму
  `sum by (<метки>) (increase(x{<фильтр>}[w])) > 0 or sum by (<метки>) (x{<фильтр>} unless
  last_over_time(x{<фильтр>}[w] offset w)) > 0` с метками и фильтром каждого алерта как прежде;
  `EsKeyReservationUnresolved` переходит с `x offset w` на ту же форму;
- `offset` и диапазон `last_over_time` равны окну `increase`, фильтр по меткам повторяется в
  каждом `x`; значение правой ветки — полный счёт серии, а не прирост;
- `EsProjectionRetrying` и `PromExCollectFailing` не меняются: отказ повторяется каждый цикл;
- новый счётчик под алерт на единичное событие с закрытым множеством меток объявляется `sum` по
  measurement `count` и засевается `count: 0` при старте процесса-владельца; засевает
  владелец, а не плагин PromEx: метрики плагина подключаются к telemetry после его сборки;
- объявления метрик `Core.*.PromEx` не меняются.

## Цена

- **Ложное срабатывание после разрыва скрейпа дольше окна**: у серии нет точек окно назад, и
  вернувшуюся со старым значением правая ветка видит новой — алерт без нового события. Разрыв
  короче окна алерта не даёт.
- **Условие вдвое длиннее**: фильтр по меткам повторяется трижды, и расхождение фильтров между
  ветками ревью ловит глазами — линтера правил Prometheus у библиотеки нет.
- **Две формы в одной таблице**: засеянный счётчик идёт с обычным `increase > 0`, и по условию
  видно, засеян ли счётчик.
