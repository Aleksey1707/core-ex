# Соглашения приложения

- **Область.** Весь код приложения: пайплайн проверок, граф зависимостей, решения о
  производительности, настройки Credo, глоссарий, логи подсистем, прикладные соглашения по
  алиасам, инструменты агента.
- **Читать перед.** Любой правкой кода — за нормами оформления модуля, CQS, спек, логирования
  и safe / bang идти в свод библиотеки, за составом проверок — сюда.
- **Словарь.** Плейсхолдеры и модальность — `deps/core/docs/rules/00-index.md`.

Соглашения по коду общие для библиотеки и приложения, поэтому их дом —
`deps/core/docs/rules/20-agreements.md`: шапка модуля, CQS, load/save в одной функции,
`find` / `get` / `get!`, `@spec` и `@doc`, домен функции, алиасы, правило понижения,
разделители, `if`, safe
против bang, атомы из внешних данных, уровни и формат логирования. Здесь — то, что
специфично для приложения-потребителя.

Пересказывать нормы библиотеки таблицей «что нормируют там» MUST NOT: такая таблица — копия,
которая расходится с источником, а её роль исполняет ссылка выше.

## Пайплайн проверок

Запускай `make` сразу после внесения изменений; найденные ошибки MUST быть исправлены до
следующего шага работы.

Состав и порядок MUST быть одинаковы в `Makefile` и в `.pre-commit-config.yaml`:

```text
boundary-check → rules-check → layout-check → spec-check → format-check → compile → deps-clean →
dialyzer → test → credo → security → audit
```

| Шаг | Что проверяет |
|---|---|
| `boundary-check` | `deps/core/scripts/boundary_lint.exs --consumer lib test` — DI через `Core.Config.repo!/1` (`13-repos.md`); в `lib/` правила раскладки из таблицы маркеров `10-architecture.md`, «Отступление»: путь файла, оглавление и корень контекста, проекции, корень web; направления держит `boundary` на шаге `compile` |
| `rules-check` | `deps/core/scripts/rules_lint.exs --consumer` — форма локального свода, его карты и ссылки на оба яруса (`00-index.md`) |
| `layout-check` | `deps/core/scripts/layout_lint.exs` — разделители внутри модуля (`deps/core/docs/rules/20-agreements.md`) |
| `spec-check` | `deps/core/scripts/spec_lint.exs` — форма результата в типах через `Core.Result` (`deps/core/docs/rules/20-agreements.md`, «Форма результата») |
| `format-check` | `mix format --check-formatted` — падает, а не правит |
| `compile` | `--warnings-as-errors`: предупреждение `boundary` — отказ сборки (`10-architecture.md`, «Boundary») |
| `deps-clean` | `mix deps.clean --unused` |
| `dialyzer` | типы, `dialyzer.ignore.exs` |
| `test` | инфраструктура + `mix test` |
| `credo` | `mix credo --strict` |
| `security` | статический security-скан; проверенные ложные срабатывания помечаются с причиной |
| `audit` | известные CVE в зависимостях и отозванные пакеты |

- Порядок не произвольный: дешёвые проверки идут раньше дорогих, а линтеры — раньше
  компиляции, чтобы не ждать сборку ради замечания о форме.
- Шаги, чей скрипт приезжает из библиотеки (`boundary-check`, `rules-check`, `layout-check`,
  `spec-check`), MUST звать его из `deps/core/scripts/`, а не копировать к себе: правило и его
  проверка обновляются вместе.
- Пропустить шаг MUST NOT: пайплайн, разный в двух приложениях, перестаёт быть нормой и
  становится привычкой конкретного репозитория.
- `xref` в пайплайн не входит — это диагностика, а не гейт.
- Компилятор `boundary` MUST стоять в `compilers:` проекта (`[:boundary] ++ Mix.compilers()`) во
  всех окружениях: без него границы не проверяются вовсе, а `--warnings-as-errors` шага `compile`
  превращает их предупреждения в отказ сборки.

## Граф зависимостей

Циклы компиляции не гейтятся. Направление зависимостей между слоями держит `boundary` на
компиляции (`10-architecture.md`), а внутри одного boundary цикл
`<Aggregate> ↔ Event ↔ Event.Codec` структурен: агрегат объявляет Prim, события ссылаются на
них, кодек знает модули событий.

Ни одна из двух возможных метрик не отражает цену. Ратчет по числу циклов не различает
подмены: убрали один, завели другой — счётчик тот же. Ратчет по `--label compile-connected`
пришлось бы ставить на весь граф, и он падает с `--fail-above 0` уже сейчас.

Гейт заводится обратно, когда инкрементальная пересборка начнёт мешать работе, и мерить он
тогда MUST каскад, а не циклы. Перечень нынешних циклов в `DEBT.md` MUST NOT: их показывает
`make xref` (`00-index.md`, «`DEBT.md` приложения»).

| Команда | Что показывает |
|---|---|
| `make xref` | рёбра, циклы, топы входящих и исходящих |
| `mix xref graph --format cycles` | сами циклы и файлы в них |
| `mix xref graph --label compile-connected --sink <file>` | кто пересоберётся от правки файла |
| `mix compile --profile time` | где уходит время сборки |

## Решения о производительности

Механизм, единственная цель которого — скорость, вводится по замеру, а не по предположению:
снапшот, `<ReadRepo>.Cached`, мемоизация в ETS, денормализация read-модели, подбор `batch_size`
и `max_concurrency`. Каждый из них — вторая копия данных или второй путь кода, и без замера
неизвестно, окупает ли выигрыш эту цену.

- Включение снапшота и смена `every:` (`13-repos.md`, «Снапшоты»), включение `.Cached`
  (`16-caching.md`, «Чек-лист перед включением») MUST опираться на замер; прочие механизмы
  ради скорости — SHOULD.
- Норма действует на новое решение: уже включённый механизм переобосновывать не нужно, пока не
  меняется его параметр.

Замер — три шага:

| Шаг | Источник | Что даёт |
|---|---|---|
| повод | метрика prod (`21-observability.md`); у приложения без prod — нагрузочный сценарий | проблема есть, и на каких размерах |
| решение и параметр | сценарий benchee на размерах из повода | выигрыш механизма и значение параметра |
| проверка | та же метрика после выкладки | сбылось ли ожидание, записанное в коммит |

Сценарий без повода отвечает «быстрее ли», но не «нужно ли»: размеры, на которых он гоняется,
без метрики выбраны наугад.

- Зависимость — `{:benchee, "~> 1.5", only: :dev, runtime: false}`; сценарий —
  `bench/<тема>_bench.exs`, запуск — `mix run bench/<тема>_bench.exs` против dev-БД.
- Сценарий в пайплайн проверок и CI MUST NOT: время зависит от машины, и гейт по нему флакает.
- Сценарий остаётся в `bench/`: при смене нагрузки замер повторяется им же.
- Цифры замера (машина, размеры, итог) и ожидание для шага «проверка» MUST идти в описание
  коммита, который вводит механизм или меняет его параметр. Комментарий с цифрами у параметра —
  MUST NOT: цифры привязаны к машине и дате и в комментарии устаревают молча, а коммит
  находится `git blame` по строке параметра.

```text
# плохо — механизм без замера: проверить после выкладки нечего
account: enable snapshots

Streams are long, snapshots should help.

# хорошо — повод, замер, параметр и ожидание
account: enable snapshots every 100 events

Load p99 grew to 40 ms, fold events p99 is 600.
bench/snapshot_bench.exs, 8 cores, dev DB, load plain -> snapshot:
  N=10: 0.50 -> 0.81 ms; N=100: 1.99 -> 1.19 ms; N=1000: 16.65 -> 1.08 ms.
Load budget is 5 ms: plain load fits it up to N=100, hence every 100.
Expected after deploy: fold events p99 <= 100.
```

## Настройки Credo

Длина строки (`Readability.MaxLineLength`, ≤ 120) и разбиение литерала `Logger.*` —
`deps/core/docs/rules/20-agreements.md`, «Linters & Formatters» и «Логирование (`Logger`)».

Проверки сводов `CredoChecks.*` лежат в `deps/core/scripts/credo_checks.exs`: `.credo.exs`
подключает их строкой `requires: ["deps/core/scripts/credo_checks.exs"]`, без неё модулей
`CredoChecks.*` в `enabled:` нет.

Включены осознанно, потому что проверяют письменные правила:

| Чек | Правило |
|---|---|
| `Readability.Specs` | `@spec` у публичных функций; исключены `test/` и контроллеры (`**/controller.ex`) |
| `CredoChecks.UseOptsPerLine` | два и более параметра `use` — каждый на своей строке (`deps/core/docs/rules/20-agreements.md`, «Стиль кодирования») |
| `CredoChecks.EnumValuesTable` | строка таблицы значений в `@moduledoc` у каждого значения `Core.Enum` (`deps/core/docs/rules/11-domain.md`, «Описание значений в `@moduledoc`»); область — `lib/` и `test/support/`: `{CredoChecks.EnumValuesTable, [files: %{included: ["lib/", "test/support/"]}]}` |
| `Warning.UnsafeToAtom` | атомы из внешних данных; исключён `test/` |
| `Warning.LeakyEnvironment` | утечка окружения в подпроцессы |
| `Warning.MixEnv` | runtime-конфиг вместо `Mix.env/0` |
| `Refactor.PassAsyncInTestCases` | явный `async:` в тестах (`deps/core/docs/rules/19-testing.md`) |
| `Refactor.IoPuts` | `Logger` вместо `IO.puts` (`deps/core/docs/rules/20-agreements.md`, «Логирование (`Logger`)»); исключены `test/` и пути задач релиза в корне — `lib/my_app_app/release.ex` и `lib/my_app_app/release/` (строки без `*` Credo сравнивает префиксом, фигурные скобки не раскрывает) — в релизе нет `Mix.shell()`, и ответ оператору задачи `MyAppApp.Release.*` печатает `IO.puts` |

Отключены осознанно:

| Чек | Почему |
|---|---|
| `Readability.AliasAs` | конфликтует с профилями Codec: они алиасятся через `as:` |
| `Readability.Specs` в контроллерах | контракт экшена описывает `operation/2` (`15-web-api.md`); `Params`, `Presenters`, `Plugs` и прочий web — со `@spec`, как везде |
| `Readability.StrictModuleLayout` для `use`, атрибутов, вложенных модулей | их место диктует компилятор (`deps/core/docs/rules/20-agreements.md`, «Шапка модуля») |
| `Design.AliasUsage` | противоречит адресации через родителя: чек требует алиасить лист |
| `Consistency.UnusedVariableNames` | `_` и `_name` несут разный смысл: «значение не важно вообще» (`{:ok, _}`) против «не важно, но читателю стоит знать, что это» (`_reason`); чек требует единообразия при любой настройке и ловит только идиоматичные места |
| `Refactor.AppendSingleItem` | синтаксический: ловит `x ++ [:a]`, но пропускает соседнее `x ++ [:a, :b]` и не отличает горячий цикл от разовой сборки; там, где `++` нужен по порядку элементов, делает только хуже |

Правка `.credo.exs` MUST сопровождаться строкой в этой таблице у себя: включённый или
выключенный чек без записанной причины через полгода читается как случайность.

## Алиасы приложения

Общее правило — лист, родитель, `as:` последним средством при конфликте имён —
`deps/core/docs/rules/20-agreements.md`, «Алиасы модулей». Здесь — конвенции приложения.

- Профили Codec MUST алиаситься через `as:` всегда, а не только при конфликте: `InCodec` /
  `OutCodec` — имена фасадов, общие для всего кода, а листы `Internal` / `External` у фасада и
  у Prim-профиля совпадают. Прочие конфликты имён разводятся алиасом **родителя**, а не
  переименованием.

  ```elixir
  alias MyApp.Codec.Internal, as: InCodec
  alias MyApp.Codec.External, as: OutCodec
  alias MyApp.Codec.Prim.Internal, as: PrimInCodec
  ```

  `InCodec` / `OutCodec` — entity-фасады (Prim + плагины); `PrimInCodec` — явный Prim-only.
- Репозиторий агрегата (`<Aggregate>.Repo`) MUST адресоваться через алиас **агрегата**:
  `alias MyApp.Domain.<BC>.<Aggregate>` → `<Aggregate>.Repo.Pg.Schema`. Отдельный
  `alias …<Aggregate>.Repo` — MUST NOT: короткое имя `Repo` в том же файле почти всегда
  занято `Core.Repo` (`use Repo.Pg`), и такой алиас молча его перебивает (`13-repos.md`).
- `MyApp.Infra.DAO` — единственный `Ecto.Repo`; обращаться к нему из web-слоя MUST NOT — ссылку
  ловит сборка (`10-architecture.md`, «Boundary»).
- `Core.Config` требует `require Config` рядом с алиасом: `repo!/1` — макрос.
- Типовые конфликты приложения и их разрешение MUST быть выписаны таблицей в локальном своде:
  одноимённые агрегаты двух контекстов, общие схемы против ресурсных,
  `Errors` агрегата, одноимённые модули библиотеки и домена.

## Термины

Язык предметной области задаёт `CONTEXT.md` в корне репозитория: канонический термин на каждое
понятие и синонимы, которых текст избегает.

- Термин глоссария MUST употребляться как есть — в `@moduledoc`, сводах, сообщениях об ошибках,
  выводе команд и логах; синоним вместо него — дефект текста наравне с опечаткой.
- Понятие, которого в глоссарии нет, MUST попадать туда вместе с кодом, который его вводит:
  иначе имя расходится по файлам раньше, чем его кто-либо согласует.

Разделение глоссария и свода — `deps/core/docs/rules/00-index.md`, «Как пользоваться».

## Логи подсистем

Формат сообщения нормирует свод библиотеки (`"<контекст>: key=#{value} …"`). Приложение
уточняет две вещи: контекст — **подсистема**, ключи — латиницей в snake_case, теми же именами,
что у полей в коде.

```elixir
# плохо — контекст не назван подсистемой, ключи на русском
Logger.info("Выгрузка применена: версия=#{version} пропущено=#{skipped}")

# хорошо
Logger.info("Импорт: выгрузка применена: version_id=#{version} skipped=#{skipped}")
```

Вывод команд оператора под это правило не подпадает: он читается человеком целиком, а не
грепается по ключам.

## Ссылки на другие проекты

Код, комментарии, `@moduledoc` / `@doc`, документация, своды, сообщения коммитов и логов
MUST NOT ссылаться на **чужие** проекты и репозитории — ни именем, ни namespace, ни намёком
(«зеркало X», «портировать в Y», «сделано как в Z»).

Чужой — тот, что не входит в этот же продукт. Компоненты одного продукта, разнесённые по
репозиториям (`my_app_back`, `my_app_front`, `my_app_proxy`, `my_app_docs`), друг другу не
чужие: ссылка на компонент-сосед MAY — его именем, его namespace и путём внутри него.

Перечень компонентов MUST лежать в `CONTEXT.md` в корне репозитория, рядом с глоссарием: имя
компонента, зона ответственности, репозиторий. Компонент, которого в перечне нет, для этого
репозитория чужой; попадает он туда по тому же правилу, что и термин, — вместе с кодом или
документом, который на него ссылается.

```markdown
<!-- плохо — чужой проект: ни проверить, ни поддержать изнутри репозитория -->
Схема тега повторяет `acme/billing`.

<!-- хорошо — компонент из перечня `CONTEXT.md` -->
Схема тега — контракт с `my_app_front`: новый тег выкладывается вместе с ним.
```

Разрешены ссылки на **библиотеки** и внешние спецификации: hex-зависимости, их документация,
протоколы и стандарты; сюда же относится свод библиотеки `:core`, которая подключена
зависимостью и лежит в `deps/`.

Почему: репозиторий обязан читаться самодостаточно. Ссылку на чужой проект нельзя ни
проверить, ни поддерживать изнутри этого репозитория — она молча устаревает и утекает во
внешние артефакты (спецификация API, логи, релиз). Компонент-сосед этим не страдает: перечень
в `CONTEXT.md` называет его и его зону, а контракт между компонентами продукта — предмет
самого продукта, а не внешнее знание.

Обоснование решения формулируется по существу, без указания источника: «compile-time
валидация в макросах ловит опечатки в опциях» вместо «так сделано в X»; источник не называется
и тогда, когда это компонент-сосед.

## Инструменты агента

Tidewave — MCP-сервер внутри dev-узла: агент выполняет в нём код (`project_eval`) и SQL
(`execute_sql_query`) и читает логи (`get_logs`). Подключать его MAY; подключённый — только так:

- Зависимость MUST объявляться `only: :dev`: в test и в релиз пакет не попадает, а документация
  пакета запрещает включать его в prod. `only:` шире `:dev` — MUST NOT.
- Плаг MUST стоять в `MyAppWeb.Endpoint` под `if Code.ensure_loaded?(Tidewave)`, прямо над блоком
  `if code_reloading?`. README пакета ставит условие `Mix.env() == :dev`; условие по наличию
  зависимости оставляет список окружений одному `only:` в `mix.exs`, без второго в эндпоинте.
  Безусловный `plug Tidewave` — MUST NOT. После `Plug.Parsers` или `Phoenix.LiveReloader` плаг
  падает на первом запросе.
- Только localhost: `allow_remote_access: true` MUST NOT. Tidewave выполняет код с правами
  разработчика и на запрос не с loopback отвечает 403: dev-узел в контейнере агенту недоступен.

`.mcp.json`, хуки агента и порядок, в котором dev-узел поднимается до сессии агента, ярус не
нормирует: это решение приложения, его дом — `AGENTS.md` и локальный свод.

```elixir
# плохо — безусловный плаг с удалённым доступом: без зависимости сборка падает, с ней код
# выполняет любой, кто дошёл до порта
plug Tidewave, allow_remote_access: true

# хорошо — mix.exs
{:tidewave, "~> 0.9", only: :dev}

# хорошо — lib/my_app_web/endpoint.ex
if Code.ensure_loaded?(Tidewave) do
  plug Tidewave
end

if code_reloading? do
  plug Phoenix.CodeReloader
end
```
