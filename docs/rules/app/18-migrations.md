# Миграции

- **Область.** `priv/dao/migrations/**`, схема БД, массовое обновление данных.
- **Читать перед.** Любой миграцией: новой таблицей, колонкой, индексом, переименованием,
  удалением, backfill.
- **Словарь.** Плейсхолдеры и модальность — `deps/core/docs/rules/00-index.md`.

Миграции выполняются на работающей БД с трафиком. Цена ошибки — не упавший тест, а залипшая на
минуты блокировка в проде.

## История миграций

До первого релиза история MAY переписываться на месте. После первого релиза применённую
миграцию MUST NOT править и удалять — изменение схемы идёт новой миграцией.

- Миграция на замену удалённой MUST получать **новый** timestamp: номер, уже числящийся
  накатанным, Ecto пропустит, и на существующей базе DDL не выполнится.
- Переписанная история поверх накатанной базы не применяется: после обновления кода базы
  пересоздаются вручную.

```text
# плохо — после релиза: из применённой миграции вырезана таблица
priv/dao/migrations/20260902110000_create_claims.exs

# хорошо — удаление отдельной миграцией
priv/dao/migrations/20260915120000_drop_claim_counterparties.exs
```

## Блокировки

`CREATE INDEX` берёт `SHARE` и блокирует запись в таблицу на всё время построения. На непустой
таблице индекс MUST создаваться `concurrently`:

```elixir
defmodule MyApp.DAO.Migrations.AddOutboxTopicIndexes do
  use Ecto.Migration

  # concurrently нельзя выполнять внутри транзакции
  @disable_ddl_transaction true
  @disable_migration_lock true

  def change do
    create index(:outbox, [:topic, :created_at],
             name: :ix_outbox_new_topic,
             where: "status = 'new'",
             concurrently: true
           )
  end
end
```

- Исключение — индекс на таблице, которую **эта же** миграция и создаёт: блокировать нечего, а
  внутри транзакции миграции `concurrently` невозможен.
- `concurrently: true` не откатывается автоматически при сбое: индекс остаётся `INVALID`, его
  нужно удалить вручную (`DROP INDEX CONCURRENTLY`) и повторить.
- Правило MUST быть закрыто ратчетом, различающим обе легальные формы (`19-testing.md`).
  Миграции, применённые до введения правила, перечисляются в замороженном списке: лок был взят
  при первом применении, пересоздание индексов ничего не улучшит.

Миграция, берущая тяжёлые блокировки, MUST начинаться с ограничения ожидания:

```elixir
execute "SET lock_timeout TO '5s'", "SET lock_timeout TO DEFAULT"
```

Лучше упасть по `lock_timeout` и повторить, чем встать в очередь за долгой транзакцией и
заблокировать за собой все последующие запросы к таблице.

## Expand / contract

Переименование и удаление колонки в одном релизе с кодом ломает работающие инстансы: во время
выката одновременно живут старая и новая версия приложения.

| Шаг | Релиз |
|---|---|
| expand: добавить новую колонку, писать в обе | N |
| backfill старых строк | N (фоном) |
| переключить чтение на новую колонку | N+1 |
| contract: удалить старую колонку | N+2 |

MUST NOT в одной миграции: `rename` колонки, `remove` колонки, сужение типа, добавление
`NOT NULL` без значения по умолчанию.

## `NOT NULL` на большой таблице

`ALTER TABLE ... SET NOT NULL` сканирует таблицу под `ACCESS EXCLUSIVE`. Вместо этого:

1. `CHECK (col IS NOT NULL) NOT VALID` — мгновенно, без сканирования;
2. backfill;
3. `VALIDATE CONSTRAINT` — под `SHARE UPDATE EXCLUSIVE`, чтение и запись не блокируются.

## Данные

- Backfill в миграции MUST NOT: миграция обязана быть быстрой и предсказуемой. Массовое
  обновление — отдельной mix-таской или фоновой задачей, батчами с паузой.
- Миграция MUST NOT вызывать код приложения (схемы, кодеки, агрегаты): код меняется, миграция
  остаётся. Только SQL и `Ecto.Migration`.
- Наполнение таблиц данными из внешнего источника — задача импорта, а не миграции.

## Обратимость

- `change/0` — когда Ecto умеет вывести откат сам.
- Иначе — явные `up/0` и `down/0`.
- Необратимая миграция помечается в `@moduledoc` («данные удаляются, откат невозможен»), а
  `down/0` содержит `raise Ecto.MigrationError`: откат, который выглядит рабочим, не будучи
  прежним, хуже явного отказа.

## Таблицы библиотеки

DDL очереди (`outbox`) и event sourcing (`es_events`, `es_snapshots`, `es_checkpoints`) живёт в
библиотеке — `Core.Outbox.Migration` и `Core.Es.Migration`; миграция приложения только
делегирует:

```elixir
defmodule MyApp.DAO.Migrations.CreateOutbox do
  use Ecto.Migration

  defdelegate up, to: Core.Outbox.Migration
  defdelegate down, to: Core.Outbox.Migration
end
```

- Своей копии колонок и индексов у приложения нет: изменение схемы приезжает с обновлением
  зависимости, править её у себя MUST NOT.
- Установка, где таблица заведена собственной цепочкой миграций, переезжает так: делегирующая
  миграция берёт **timestamp первой** из них (версия уже числится накатанной, повторно DDL не
  выполнится), а расхождение состава индексов снимает отдельная миграция с `concurrently` и
  `IF EXISTS` / `if_not_exists` — на чистой установке она отрабатывает вхолостую.

## Append-only таблицы

Хранилище событий и очередь — append-only с исторической нагрузкой:

- изменения только аддитивные: новая nullable-колонка, новый индекс `concurrently`;
- MUST NOT: переименование и удаление колонок, изменение семантики нагрузки, «чистящие»
  UPDATE по историческим строкам;
- совместимость самих событий — `14-events-outbox.md`.

## Таблицы read-модели проекций

Таблицы проекции пересобираются её `clear/0`, а миграция идёт **до** смены кода на всех нодах —
отсюда три правила (`deps/core/docs/rules/22-projections.md`):

- миграция под подъём `version:` проекции SHOULD быть расширяющей: новая таблица,
  nullable-колонка, колонка с default. Старые ноды ещё пишут и читают эти таблицы, и сужение
  схемы идёт отдельной выкладкой после пересборки;
- таблицы проекции MUST NOT удаляться в той же выкладке, что убирает её модуль или читающий их
  ReadRepo: до смены кода на всех нодах она ещё проецирует;
- миграция, удаляющая таблицы проекции, MUST удалять и её строку чекпоинта —
  `Core.Es.Migration.delete_checkpoint/1`. Имя удалённой проекции MUST NOT переиспользоваться:
  забытая строка вернула бы новую проекцию на чужой чекпоинт — без `clear/0` и с середины
  истории.

```elixir
# хорошо — миграция последней выкладки: таблицы и строка чекпоинта
def up do
  drop table(:account_list)
  Core.Es.Migration.delete_checkpoint("account_list")
end

def down, do: raise(Ecto.MigrationError, "удаление проекции account_list необратимо")
```

## Таблицы, которые пересобирает код

Таблица, которую приложение пересоздаёт целиком (проекция, поисковый индекс), объявляет свои
индексы **дважды**: в миграции и в коде, который её пересобирает. Индекс, добавленный только
миграцией, исчезнет после первой же пересборки.

Внешние ключи на такую таблицу и между такими таблицами MUST NOT: их ломает очистка при
пересборке. Существование цели проверяет вызывающий (`13-repos.md`).
