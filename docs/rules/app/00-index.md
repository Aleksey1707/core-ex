# Свод правил приложения-потребителя

- **Область.** `docs/rules/app/**` — нормы, общие для любого приложения на `Core.*`: их форма,
  доставка потребителю и порядок ведения.
- **Читать перед.** Правкой любого файла `app/**`; решением, где живёт правило — в своде
  библиотеки, здесь или в локальном своде приложения.
- **Словарь.** Плейсхолдеры и модальность — `deps/core/docs/rules/00-index.md`.

## Три яруса свода

Правило живёт ровно на одном ярусе. Ярус выбирается по тому, **насколько широко** правило
верно, а не по тому, где его вспомнили.

| Ярус | Где лежит у потребителя | Что нормирует | Кому верно |
|---|---|---|---|
| библиотека | `deps/core/docs/rules/NN-*.md` | контракты `Core.*`: опции макросов, семантика функций | всем, кто зовёт `Core.*` |
| потребитель | `deps/core/docs/rules/app/NN-*.md` | как устроено приложение на `Core.*`: слои, раскладка, пайплайн, эксплуатация | любому приложению-потребителю |
| приложение | `docs/rules/NN-*.md` | инвентарь и решения одного приложения | одному приложению |

Первые два яруса приезжают вместе с зависимостью: после `mix deps.get` они лежат
в `deps/core/docs/rules/` и `deps/core/docs/rules/app/`. Копировать их текст к себе
MUST NOT — копия расходится с оригиналом на первом же обновлении зависимости.

В самой библиотеке те же файлы лежат в `docs/rules/` и `docs/rules/app/`: путь у потребителя
получается приписыванием `deps/core/`, а путь в библиотеке — его отбрасыванием. Пути записываются
в форме потребителя (см. «Адресация ссылок»): читает их прежде всего агент приложения, и у него
`docs/rules/` — это уже третий ярус, локальный свод.

При расхождении ярусов приоритет обратный ширине: контракт `Core.*` сильнее нормы потребителя,
норма потребителя сильнее локального решения. Локальный свод приложения не вправе
переопределить ни то, ни другое: несогласие с нормой — это либо правка файла `app/**` здесь,
либо строка в `DEBT.md` приложения с причиной, а не тихое расхождение.

## Что попадает сюда, а что — в локальный свод

Критерий один: норма верна для **любого** приложения на `Core.*`.

| Сюда | В локальный свод приложения |
|---|---|
| конвенция тела usecase, состав boundary, направление слоёв | список BC, акторов и агрегатов |
| раскладка файлов репозитория, read vs write | инвентарь репозиториев и их таблиц |
| правило «`ns` заводится вместе с каталогом» | словарь `ns` приложения |
| правило «тег квалифицирован именем агрегата» | таблица топиков и их потребителей |
| чек-лист включения кеша | какой именно ReadRepo закеширован |
| состав пайплайна `make`, решения Credo | ключи env, дашборды, пороги алертов |
| требование golden-фикстур и ратчетов | список ратчетов приложения |

Формулировка нормы здесь MUST быть записана плейсхолдерами (`MyApp`, `:my_app`, `<BC>`,
`<Actor>`, `<Aggregate>`), а не именем конкретного потребителя: имя приложения в общем своде
превращает норму в пересказ чужого кода.

Проверяется: `make rules-check` (`deps/core/scripts/rules_lint.exs`; у потребителя — с
флагом `--consumer`, см. «Проверка яруса»).

## Версия библиотеки

Ярус нормирует **текущий** контракт `Core.*`. Приложение, собранное на прежней версии, отличается
от него не стилем, а устройством: узнать устаревшую форму по коду сложнее, чем по этой таблице.
Как правится код — в `CHANGELOG.md` библиотеки, пунктом на каждое изменение.

| Устаревшая форма | Текущая |
|---|---|
| `use Core.Repo.Pg.Es`, опция `event_repo:` | `use Core.Repo.Pg.StateStored`, обязательная `event_codec:` |
| `<Aggregate>.Event.Repo` и таблица `<aggregate>_events` на агрегат | одно хранилище `es_events`, DDL — `Core.Es.Migration` (`13-repos.md`) |
| `Event.Repo.page_by_aggregate/4` | `@repo.page_stream/4` репозитория агрегата (`13-repos.md`, «Страница потока») |
| агрегат с событиями только state-stored | `use Core.Es.Aggregate` с `decide/2` и `evolve/2` и команды `use Core.Es.Cmd` (`11-domain.md`) |
| `{Event.X, payload}` / `Event.X` в результате `decide` | `Event.Codec.draft(Event.X, payload)` / `Event.Codec.draft(Event.X)` (`deps/core/docs/rules/11-domain.md`) |
| read-модель пишет usecase или репозиторий | её пишет проекция `use Core.Es.Projection` (`13-repos.md`, «Проекции read-модели») |
| чтение read-модели сразу после команды | ожидание проекции и 202 на таймаут (`15-web-api.md`) |
| `Core.Es.Projection.await(Projection, Agg, id, timeout)` | `Projection.await(Agg, id, timeout)` у модуля проекции (`deps/core/docs/rules/22-projections.md`) |
| `Core.Es.Store.page_stream(Agg.Event.Codec, id, limit, offset, context)` | `@repo.page_stream(id, limit, offset, context)` у репозитория агрегата (`13-repos.md`, «Страница потока») |
| «тег события неизменяем навсегда» | версия схемы — тег: новый тег плюс апкаст со старого (`14-events-outbox.md`) |
| свой `EventCompatCase` в `test/support` | `use Core.Es.EventCompatCase` (`19-testing.md`) |
| ключ конфигурации на каждый репозиторий | конвенция `<Behaviour>.Pg`, ключ — только на подмену (`13-repos.md`, «DI») |
| `tagged:` / `tags:` у плагина кодека, `dump_tagged` / `load_tagged` у фасада | `types:` и `union:`, у фасада только `dump/1`, `load/2`, `load!/2` (`11-domain.md`) |

Встреченная в приложении устаревшая форма — не повод для точечной правки посреди чужой задачи:
это либо отдельная задача, либо строка в `DEBT.md` с условием выхода.

## Форма файла

Форма та же, что у свода библиотеки (`deps/core/docs/rules/00-index.md`, «Шаблон файла правил»):
шапка из трёх пунктов, один H1, блоки H2, подтемы H3, язык у каждого fenced-блока, проза
до 100 символов в строке, последний H2 — `## Связанные правила`. Отличается только адресация
ссылок — раздел ниже.

Пункт **Область** описывает код **потребителя** (`lib/my_app/**`), а не библиотеки: файл
нормирует приложение, а лежит в библиотеке только потому, что оттуда доставляется.

## Адресация ссылок

Имена файлов на всех трёх ярусах совпадают, поэтому ярус задаёт **путь**, и записывается он
в форме потребителя: ссылка на другой ярус MUST начинаться с `deps/core/`, ссылка на свой
ярус MUST быть коротким именем файла.

| Откуда | Куда | Как записывается |
|---|---|---|
| `docs/rules/app/**` (этот ярус) | сосед по ярусу | `` `13-repos.md` `` |
| `docs/rules/app/**` (этот ярус) | свод библиотеки | `` `deps/core/docs/rules/13-repos.md` `` |
| `docs/rules/**` (свод библиотеки) | сосед по своду | `` `13-repos.md` `` |
| `docs/rules/**` (свод библиотеки) | этот ярус | `` `deps/core/docs/rules/app/16-caching.md` `` |
| локальный свод приложения | любой из двух ярусов | `` `deps/core/docs/rules/…` `` |

Путь без префикса MUST NOT: у потребителя он резолвится в его локальный свод — то есть в файл
противоположного яруса с тем же именем, и ни читатель, ни проверка отличить это от опечатки не
могут. В самой библиотеке префикс `deps/core/` отбрасывается — разрешить путь можно с обеих
сторон. Словесная пометка вместо пути MUST NOT: она говорит человеку, где искать, но не даёт
файла ни `grep`, ни линтеру.

```markdown
<!-- плохо — у потребителя оба пути ведут в его локальный свод -->
Схема таблиц — `docs/rules/13-repos.md`, кеш — `16-caching.md` свода приложения.

<!-- хорошо -->
Схема таблиц — `deps/core/docs/rules/13-repos.md`, кеш — `16-caching.md`.
```

Проверяется: `make rules-check` — короткая ссылка резолвится в своём ярусе, префиксная —
в соседнем; путь `docs/rules/NN-*.md` внутри обоих ярусов запрещён.

## Нумерация

Сквозная с остальными ярусами: номер задаёт тему, а не ярус. Номера `15`, `16` и `18`
своих файлов в своде библиотеки не имеют — они целиком принадлежат приложению, и здесь
занимают общую часть.

| Номер | Тема | Свод библиотеки |
|---|---|---|
| `10-architecture.md` | namespaces, boundary, срезы, usecases, DI, `Transact.run` | есть |
| `11-domain.md` | профили Codec, реестр плагинов, Prim и Enum, `ContextFactory` | есть |
| `12-errors.md` | словарь `ns`, каталоги ошибок, границы | есть |
| `13-repos.md` | раскладка репозиториев, read vs write, View, Specs | есть |
| `14-events-outbox.md` | теги событий, топики, поллер, подписчики, идемпотентность | есть |
| `15-web-api.md` | Controller / Schemas / Presenter, конверт, аутентификация | нет |
| `16-caching.md` | `<ReadRepo>.Cached`, ACL в ключе, инвалидация | нет |
| `17-otp-concurrency.md` | дерево процессов, тумблеры, наблюдение, циклы | есть |
| `18-migrations.md` | блокировки, expand/contract, backfill, append-only | нет |
| `19-testing.md` | case-модули, фикстуры, ратчеты, внешние зависимости | есть |
| `20-agreements.md` | пайплайн `make`, граф зависимостей, решения Credo, алиасы | есть |
| `21-observability.md` | PromEx, сервер метрик, дашборды, алерты | есть |

Обратное тоже бывает: номер `22` (проекции) занят только сводом библиотеки
(`deps/core/docs/rules/22-projections.md`), своего файла здесь нет. Раскладка проекций у
потребителя нормируется по месту — таблицы read-модели и её репозиторий в `13-repos.md`,
ожидание проекции в ответе API в `15-web-api.md`, дерево и его тумблеры в
`17-otp-concurrency.md`, DDL и пересборка в `18-migrations.md`, тесты в `19-testing.md`,
алерты в `21-observability.md`. Отдельный файл MAY заводиться, когда норм станет больше, чем
ссылок на них из этих файлов; до тех пор номер `22` в ярусе свободен, и занимать его другой
темой MUST NOT.

## Доставка потребителю

Приложение подключает ярус тремя вещами:

- в карте свода `AGENTS.md` — строка с путём `deps/core/docs/rules/app/NN-*.md` рядом со
  своим файлом той же темы;
- в своём `SKILL.md` — ссылка на **три** файла: локальный, свод библиотеки и этот ярус;
  тело скилла остаётся указателем, пересказ правил в нём MUST NOT;
- в своём файле свода — вводный абзац «что нормирует библиотека, что — этот ярус, что
  остаётся здесь», а не пересказ их норм.

Локальный файл, из которого убраны перенесённые сюда нормы, MUST остаться дельтой: инвентарь,
решения и отступления. Файл, в котором после переноса не осталось ничего своего, удаляется
вместе со своим скиллом, а карта `AGENTS.md` ссылается прямо сюда.

### Файл без скилла

`20-agreements.md` — единственная тема, у которой скилла нет ни на одном ярусе: нормы
оформления кода нужны при любой правке, и грузить их по триггеру поздно. Доставка у неё
поэтому другая — импортом в `AGENTS.md` потребителя, **тремя** строками подряд:

```markdown
@deps/core/docs/rules/20-agreements.md
@deps/core/docs/rules/app/20-agreements.md
@docs/rules/20-agreements.md
```

Порядок — от широкого к узкому, как приоритет ярусов. Библиотечный файл в импорте MUST быть
наравне с прочими: его область — код библиотеки **и** потребителя, а скилла, который подтянул
бы его по задаче, не существует. Локальная строка ставится, если свой файл этой темы у
приложения есть.

Проверяется: `make rules-check` — обе строки `deps/core/…` в `AGENTS.md` обязательны.

### Проверка яруса

Стандарт ввела библиотека, поэтому и проверка живёт в ней: `deps/core/scripts/rules_lint.exs`
— один скрипт с двумя режимами. Без аргументов он проверяет оба яруса в самой библиотеке,
с `--consumer` — локальный свод приложения: форму файлов, карты `00-index.md` и `AGENTS.md`,
разрешимость ссылок `deps/core/…`, скиллы с тремя файлами темы и импорты `20-agreements.md`.

Приложение MUST звать его из `deps/core/scripts/`, как `boundary_lint.exs` и `layout_lint.exs`
(`20-agreements.md`, «Пайплайн проверок»). Копия скрипта у потребителя — MUST NOT: разойдясь
с оригиналом, она начинает проверять прошлую редакцию стандарта, и расхождение видно только
тому, кто откроет оба файла.

## Как добавлять правило

- Правило живёт в **одном** файле одного яруса; в остальных — строка-ссылка.
- Норма, верная только при определённой библиотеке поверх `Core.*` (Phoenix, Oban, Cachex,
  PromEx), здесь MAY: потребители собраны на одном наборе, и норма без него бессмысленна.
  Норма, верная только для одного приложения, — MUST NOT.
- Новое правило MUST приносить с собой либо пример «плохо / хорошо», либо строку
  `Проверяется: …` — иначе оно нечитаемо в разборе конкретной правки.
- Правка этого яруса — изменение контракта для всех потребителей: она MUST попадать в
  `CHANGELOG.md` библиотеки тем же коммитом, разделом «Изменения контракта макросов» либо
  «Ломающие изменения контракта», если приложение придётся править.
- Новый файл: имя `NN-<тема>.md`, шапка и хвост по шаблону, строка в таблице нумерации выше.

## Связанные правила

- Стандарт свода библиотеки — `deps/core/docs/rules/00-index.md`
- Главный инвариант библиотеки — `deps/core/docs/rules/10-architecture.md`
- Архитектура приложения — `10-architecture.md`
- Соглашения по коду — `20-agreements.md`
