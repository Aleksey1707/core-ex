# 05: Общие тексты `CompileError` опций

Type: grilling
Status: resolved

Blocked by: 01

## Question

Нужны ли общие `where` / `reject!` для сообщений `CompileError` в `Core.Helper.Opts`, и в какой форме?

Сейчас свои копии: `where/1` — в пяти модулях `Labels.*` и `Core.View.Opts`, `reject!` / `fail!` — в трёх
`Labels.*`; префикс текста у них разный (`label`, модуль, поле). Решить:

- выносить ли в `Core.Helper.Opts` и с какой сигнатурой (метка builder'а, модуль вызывающего, путь до поля);
- единый формат префикса для всех builder'ов или только для тех, кто проверяет вложенные декларации;
- `CompileError` против `raise` с `file:` / `line:` вызывающего `use`.

## Comments

- Из «Канонический режим разбора и критерий исключения»: появились новые тексты — «ожидается литерал» (`literal!/3`)
  и «ожидается литеральный keyword» для каждого builder'а — и value-варианты примитивных проверок в
  `Core.Helper.Opts`. Префикс у них должен совпадать с префиксом валидаторов `<key>!` в теле.
- Из «Прототип канонического режима на двух builder'ах»: у `Codec.Plugin` тексты `loadable:` / `union:` / `types:`
  (`Codec.Plugin.Opts`) идут без метки builder'а, а «ожидается литерал» и неизвестные ключи — с ней. Ошибка при
  раскрытии и ошибка в теле указывают на строку `use` по-разному (стек «expanding macro» против «(module)»).
- Из «Ключи опций при композиции builder'ов»: ошибка по ключу, отданному внутреннему builder'у как есть, приходит с
  меткой внутреннего (`Repo.Pg:` у `use Core.Repo.Pg.StateStored`, `Prim:` у `name:` / `sensitive:` / `personal:`
  обёрток) — входное условие для формата префикса, метка внешнего не пробрасывается.

## Answer

Тексты ошибок опций — одна норма для всех builder'ов, `raise` — через общий `Core.Helper.Opts.reject!/2`.

- **Охват — проверки опций**: при раскрытии (`expand!` / `validate!` / `literal!` / `module!`) и в теле (валидаторы
  `<key>!`). Проверки хуков `@before_compile` / `@after_compile` (полнота клауз, struct, `@enforce_keys`) — о модуле, а
  не об опции; остаются как есть, с `file: env.file, line: env.line`.
- **Префикс** — `<метка builder'а>: <ключ>[: <элемент>…]: <текст>`, путь через `: `. Модуля вызывающего в префиксе нет:
  стек и при раскрытии («expanding macro»), и в теле («(module)») указывает на строку `use`. Уходят `"<label>
  <Модуль>:"` у `Labels.*`, `", поле <name>"` у `View.Opts`; тексты `types:` / `union:` / `loadable:` `Codec.Plugin`
  получают метку `Codec.Plugin:`. При композиции — метка внутреннего builder'а («Ключи опций при композиции
  builder'ов»).
- **`Core.Helper.Opts.reject!(where, message) :: no_return()`** — `raise CompileError, description: "#{where}:
  #{message}"`. Префикс собирает вызывающий конкатенацией `"#{label}: #{key}"`, как уже делает `module!`; построителя
  пути нет. Через неё идут и все `raise` самого `Helper.Opts`. Локальные `where/1`, `reject!`, `fail!` (`Labels.*`,
  `View.Opts`) удаляются в срезах своих builder'ов; `fail!` хуков не трогается.
- **`CompileError` без `file:` / `line:`**: позицию даёт стек, `ParallelCompiler` берёт строку `use` из него.
  Протаскивать `__CALLER__` в `Helper.Opts` и валидаторы тела не нужно. Другие классы исключений — MUST NOT.
- **Хвост**: несовпадение формы или типа — `ожидается <что>, получено <значение>`; значение — `inspect/1`, AST
  (нелитерал у `literal!`, список выражением у `expand!`) — `Macro.to_string/1`. Нарушение смыслового правила —
  свободный текст без «получено». «задано» заменяется на «получено».

Отвергнуто:

- модуль вызывающего в префиксе у builder'ов, проверяющих вложенные декларации, — два формата и правило выбора;
- `reject!(label, path :: [segment], message)` — строже, но список на каждом call site и переделка `module!` /
  `fetch!`;
- явные `file:` / `line:` при раскрытии и в теле — `__CALLER__` во всех функциях `Helper.Opts` ради одинакового
  заголовка.

Где записано: `20-agreements.md` («Стиль кодирования», рядом с проверкой опций `__using__`) — формат, `reject!/2`,
без `file:` / `line:`, хвост; `@moduledoc` `Core.Helper.Opts`. В ADR — не больше строки «тексты ошибок — норма
`20-agreements.md`»: решение легко откатить. Тексты сообщений в CHANGELOG не идут.

Для нарезки: `reject!/2` входит в `Helper.Opts` первым срезом перевода, вместе с `expand!` / `literal!`.
