# 04: Ключи опций при композиции builder'ов

Type: grilling
Status: resolved

Blocked by: 02

## Question

Что становится с `required_keys/0` / `optional_keys/0` и кто владеет ключами, когда один builder собран из другого?

- При проверке ключей во время раскрытия тело в списках ключей не нуждается: уходят ли проходные `@doc false`
  `required_keys/0` / `optional_keys/0` вместе с переводом?
- Композиции, где списки нужны снаружи: `Repo.Pg.StateStored` → `Repo.Pg` (ключи `Repo.Pg` плюс свои), `Prim.Opts`
  → протокол wrapper'а (`wrapper.required_keys()`). Остаются функции, заменяются общим механизмом
  `Core.Helper.Opts` или чем-то третьим?
- Двойная проверка `StateStored` → `Repo.Pg`: какой из двух `validate!` владеет ключами, а какой их не проверяет.

## Comments

- Из «Канонический режим разбора и критерий исключения»: к спискам ключей добавился `@expression_keys`. При
  композиции он тоже нужен снаружи: у `StateStored` опции-выражения `Repo.Pg` (`query:`, `to_entity:` …) проходят
  насквозь, и `literal!/3` должен знать их на внешнем уровне.
- Из «Прототип канонического режима на двух builder'ах»: `name:` у `Prim.String` проверяется дважды — обёрткой
  (`binary_value!` с меткой `Prim.String`) и `Core.Prim`. `Core.Prim`, `Prim.Wrapper` и семь обёрток переводятся
  одним срезом; `kind` / `sensitive` / `personal` у `Core.Prim` после него — литералы.

## Answer

Композиция — вложенным `use`, у каждого ключа один владелец: **кто отбрасывает ключи, тот их и проверяет**. Ключ,
отданный внутреннему builder'у как есть, — владение внутреннего; поглощённый или пересобранный — внешнего.

- **Проходные функции ключей уходят.** `required_keys/0` / `optional_keys/0`, которые читает только собственное тело
  из `bind_quoted` (`Enum`, `Labels.*`, `Web.Event`, `Es.ValueChanged`, `Context.Accessor`, `Repo.Pg`), удаляются в
  срезе своего builder'а; мёртвые (`Es.Outbox`, `Core.Repo`, `Es.Event.Codec` — не читаются с первого коммита) — тоже.
  Функции `@doc false`, в CHANGELOG не идут. Норма: builder функций ключей не экспортирует, кроме протокола
  `Prim.Wrapper`.
- **`Repo.Pg.StateStored` → `Repo.Pg`.** `StateStored` проверяет при раскрытии свои ключи (`event_codec`, `outbox`,
  `children`) и обязательность усиленных (`to_entity`, `to_model`, `entity`, `id`); остаток отдаёт `use Core.Repo.Pg`
  как есть. Неизвестные ключи и опции-выражения остатка проверяет `Repo.Pg` при своём раскрытии, ошибка — с меткой
  `Repo.Pg:`; это принятая цена, `@moduledoc` `StateStored` говорит «`Repo.Pg` плюс свои ключи». Двойной проверки
  нет, `@expression_keys` `Repo.Pg` снаружи не нужен.
- **Читатель чужого ключа** проверяет форму, без которой ключ не прочесть (`module!` без опций), и свои усиления, а
  не контракт владельца. У `StateStored`: `exports: [domain: 3]` у `errors:` уходит (это `validate_errors_module!`
  `Repo.Pg`), `ensure_version_mismatch!` и `ensure_aggregate_id!` остаются.
- **Протокол `Prim.Wrapper` остаётся**: обёртка пересобирает базовые опции и сама проверяет неизвестные ключи по
  полному набору (общие + свои). `required_keys/0` / `optional_keys/0` сохраняются, добавляется `expression_keys/0`
  (общие `name` / `mutate` / `validate` + свои: `re`, `max_len`, `namespace` …). `Prim.Opts.prepare!` — единый пролог
  семи обёрток при раскрытии: `expand!` → `validate!` → `literal!` → `kind!` → `validate_opts!` обёртки (без шага
  флагов); инлайн-пролог прототипа в `Prim.String` не берётся.
- **Владение общими ключами Prim:**
  - `name`, `sensitive`, `personal` — `Core.Prim` (обёртка отдаёт как есть, ошибка с меткой `Prim:`);
    `binary_value!(name)` в обёртке уходит;
  - `kind` — обёртка (`validate_kind!` против `native_kind` — её усиление);
  - `mutate` / `validate` — обёртка, под своими именами (переименовывает в `custom_*`, то есть поглощает);
    проверка `custom_*` у `Core.Prim` остаётся контрактом базы для прямых вызовов;
  - `sensitive` / `personal` у `Prim.Compose` — сама `Prim.Compose` (наследование от базы, запрет понижения),
    `Core.Prim` получает готовое значение.

Отвергнуто:

- композиция функцией сборки AST (`@doc false` `(opts, caller, label)` у внутреннего, метка внешнего) — внутренний
  API сборки у каждого составного builder'а ради метки в тексте;
- функции ключей + `expression_keys/0` и проверка полного набора снаружи (как сейчас) — двойная проверка и
  проходные функции.

Где записано: `20-agreements.md` — нормы (функций ключей нет, кроме протокола обёртки; композиция вложенным `use`;
«кто отбрасывает, тот проверяет»; читатель чужого ключа — форма чтения и усиления); ADR — почему A, а не функция
сборки и не двойная проверка, метка внутреннего как цена. Перечня владения по builder'ам нет — виден по коду.

Для нарезки: `StateStored` читает функции ключей `Repo.Pg`, поэтому `Repo.Pg` и `StateStored` — один срез.
