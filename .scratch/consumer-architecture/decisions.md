# Решения опроса по целевой архитектуре потребителя A

Источник элементов — `proposal.md` (A1–A14). Нумерация вопросов — сквозная по раундам опроса.

## Раунд 1

| Q | Элемент | Решение |
|---|---|---|
| Q1 | A1 | Одно OTP-приложение; каждый контекст — граница Boundary с явными `deps` / `exports` (верхнего уровня — уточнено Q17); композиционный корень (`Application`, PromEx, release, mix-таски) — отдельная граница; предупреждения Boundary в CI — ошибки |
| Q2 | A3 | Вертикаль по агрегату: всё об агрегате — в его каталоге; срезов-каталогов `common` / `actor_x` / `actor_y` / `system` / `admin` на уровне контекста нет. Usecases внутри каталога агрегата — по модулю на актора. Пересмотрено с (a) на (b) при разборе Q7: актор остаётся видимым в структуре кода |
| Q3 | A4 | Отклонён: гранулярность файлов остаётся — событие, команда, outbox, пара `behaviour` + `Pg`, схема и specs — по файлу |
| Q4 | A5 | Контекст объявляет свои проекции, плагины кодека, пространства разрешений, детей супервизора и наблюдаемые процессы; корень держит список контекстов и собирает из него `Application`, кодек, дерево проекций, PromEx. A12 этим решением покрыт |
| Q5 | A6 | Справочники С1..С4 остаются в К1 своей единицей с одним механизмом; вид справочника объявляет реквизиты, разбор записи внешней системы (`Record`) — в `AppAIngest` (уточнено после Q11). Отдельный контекст — когда их начнёт читать второй контекст |
| Q6 | A10 | Операция записи принимает `wait:`, ждёт проекцию после commit и возвращает представление; web проекций не знает |

## Раунд 2

| Q | Элемент | Решение |
|---|---|---|
| Q7 | A2 | Граница контекста экспортирует модули usecases акторов (`<Aggregate>.<Actor>.Usecases` — имя уточнено Q22) и один общий модуль чтения агрегата (`<Aggregate>.Usecases`) с декларацией допущенных акторов; в модуле актора — только его usecases. Плюс View, типы ID, события-контракты |
| Q8 | A7 | Внутри контекста join своих таблиц проекций допустим; между контекстами — нет: К3.А3 строит копию нужных полей К5 своей проекцией из событий К5 |
| Q9 | A8 | Модуль события и топик экспортирует производитель, у потребителя литерала топика нет. Данные другого контекста — через его модули usecases; К2 читает К1 читающим usecase с `wait:`: ожидание последнего события потока на момент вызова покрывает событие, на которое реагирует К2, — ожидание конкретной версии не нужно |
| Q10 | A9 | Порт `AppA.Authz`. Декларация доступа: на модуле актора — тип учётной записи и пространство разрешений, на usecase — операция. Боевая реализация — К3 с кешем, выбор — в корне; тесты предметной логики — тестовая реализация; авторизация каждой операции — отдельный интеграционный тест |
| Q11 | A11 | Входящие адаптеры — по виду входа: сообщения внешнего источника (Kafka, разбор Avro, DLQ) — граница `AppAIngest` рядом с `AppAWeb`, `deps` только на модули usecases; реакция на доменное событие — в реагирующем контексте; Oban-воркер — в контексте, чей usecase он выполняет; этот контекст экспортирует функцию постановки задачи, а контекст, которому задача нужна, зовёт её в своей транзакции (уточнено при разборе Q16); mix- и release-задачи — в корне `AppAApp`. Дерево подписчика с DLQ — один параметризуемый модуль вместо копий |
| Q12 | A14 | Общий презентер по умолчанию, свой — только при отличии; шаг конструктора объявляет форму нагрузки, web строит из неё OpenAPI-схему |
| Q13 | — | Заменено Q17. Было: фасады кодека — модули самой родительской границы `AppA` (не подграницы); контексты экспортируют плагины и `codec_plugins/0`, объявляют `deps: [AppA]`; `AppA` экспортирует только фасады кодека. Связь «родитель → подграница» Boundary разрешает неявно и в поиск циклов не включает |

## Раунд 3

| Q | Элемент | Решение |
|---|---|---|
| Q14 | A13 | Тесты по уровням: агрегат — given/when/then без БД, `async: true`, включая С1..С4 и А6; usecase — с тестовой реализацией `AppA.Authz` и данными только своего контекста; авторизация — интеграционный тест на операцию с боевой реализацией; web — по ресурсу; сквозные пути — немногочисленные flow-тесты |
| Q15 | A3 | Подграницы внутри К1 — только «справочники» (С1..С4 и механизм) и «конструктор»; агрегаты А1–А7 — в одной границе К1 |
| Q16 | A11 | Реакция и воркер — в каталоге агрегата, чей usecase они вызывают; вызывают usecases нескольких агрегатов — `reactions/` на уровне контекста |
| Q17 | A1, A15 | `AppA` границей не является; контексты, `AppAWeb`, `AppAIngest`, корень `AppAApp` — границы верхнего уровня, `deps` web и ingest — прямо на контексты. Кодек — граница верхнего уровня `AppA.Codec` с `check: [out: false]`, контексты объявляют `deps: [AppA.Codec]`. Причина: зависимость от подграницы чужой границы Boundary запрещает, ре-экспорт требует двойного списка экспортов, `top_level?` документация не рекомендует |

## Раунд 4

| Q | Элемент | Решение |
|---|---|---|
| Q18 | A16 | `AppA.Infra` — граница-сток без зависимостей на домен: `DAO`, `Storage`, `StreamID`, `Otel`, телеметрия подписчиков; от неё зависят контексты, web и ingest — нет. `AppA.Authz` — порт и макрос декларации доступа; реализация и проверка типа учётной записи — в К3 через К5. `ContextFactory` — экспорт К5 (пересмотрено тикетом 09: своя граница над границей аксессора — ADR-0044). `Command.execute_all/3` — внутренний модуль К3. Корень `AppAApp` — `Application`, сборка контекстов, дерево outbox, PromEx, `MetricsServer`, `Release`, mix-таски. `AppATest` — test support с `check: [in: false, out: false]` |
| Q19 | A17 | Префикс `AppA.Domain.<BC>` остаётся; модуля `AppA.Domain` нет. Корневой модуль контекста — корень его границы: `use Boundary`, объявления Q4, `@moduledoc` с картой контекста |
| Q20 | A8 | Контракт между контекстами — доменные события производителя: он экспортирует модули событий, семейство и топик; совместимость — апкаст и golden-фикстуры. Отдельные интеграционные события — когда события начнёт читать система вне приложения |

## Раунд 5

| Q | Элемент | Решение |
|---|---|---|
| Q21 | A3 | То, что не принадлежит одному агрегату, — каталоги уровня контекста по виду содержимого: значения без владельца — `values/`, общие ошибки — `errors.ex`, read-модель не по агрегату — каталог по назначению рядом с агрегатами (проекция или свёртка, ReadRepo, View, usecases; у К3 — R1), реакции на несколько агрегатов — `reactions/` (Q16) |
| Q22 | A2, A3 | У актора — подкаталог внутри каталога агрегата: `<aggregate>/<actor>/usecases.ex` и, при своём ACL-фильтре или своей форме данных, `read_repo*` (свои specs с `default_filters`; таблица, проекция и схема — общие) и `view.ex`. Модули — `<Aggregate>.<Actor>.Usecases`, `.ReadRepo`, `.View`. Общее чтение нескольких акторов — `<aggregate>/usecases.ex` |

## Раунд 6 — контракт для всех потребителей

Вопросы мейнтейнеру из `reconciliation.md`, раздел «Вопросы мейнтейнеру»; номер вопроса — во втором столбце.

| Q | Вопрос | Решение |
|---|---|---|
| Q23 | 1 | Каждый контекст любого потребителя — граница Boundary верхнего уровня (MUST). Цикл, который пока не развязать, — `dirty_xrefs` на одной стороне и строка `DEBT.md`; неиспользуемый `dirty_xrefs` Boundary репортит сам. ADR-0025 в части циклов заменяется: цикл ловит сборка, а не ревью |
| Q24 | 2, 3, 4 | Вертикаль по агрегату — единственная раскладка, новый ADR вместо ADR-0023. Нормой яруса становятся Q21 и Q22: каталог агрегата с подкаталогом актора, `values/`, `errors.ex`, read-модель по назначению, `reactions/`. Тип модели контекста (ADR-0025) — в каталоге агрегата-владельца, общий нескольким агрегатам — в `values/`. Линтер и фикстура переписываются; изменение ломающее для всех потребителей |
| Q25 | 5 | Запись в главный и подчинённый агрегаты — в каталоге главного, критерий подчинённости `app/10:357-368` прежний. Операция над равноправными агрегатами — каталог уровня контекста по имени операции: `<bc>/<operation>/<actor>/usecases.ex` → `<BC>.<Operation>.<Actor>.Usecases` |
| Q26 | 5 | Одна транзакция пишет один контекст: запись двух — MUST NOT. Вторая запись — задача второго контекста, поставленная в той же транзакции его экспортированной функцией (Q11), или реакция на событие. Нужна атомарная запись двух контекстов — контексты склеиваются |
| Q27 | 6 | Изменяющий usecase event-sourced агрегата принимает `wait: :none \| timeout()`, после commit ждёт проекцию литеральным `Projection.await(Agg, %Agg.ID{} = id, timeout)` и возвращает `{:ok, {:projected, View.t()}}` или `{:ok, {:accepted, id, version}}`; `:projection_timeout` и `:projection_rebuilding` — `:accepted`. Создание в обоих случаях отдаёт `{id, version}`: ADR-0027 и wire не меняются. Разбор `Prefer` — в web (ADR-0030), `MyAppWeb.Accepted` переводит результат в 200 / 202. Исключение из CQS — нормой в `rules/20`. MUST NOT `rules/22:149`, `app/10:377-379` снимается; ADR-0030 в части «usecase не ждёт» заменяется |

## Раунд 7 — контракт для всех потребителей

| Q | Вопрос | Решение |
|---|---|---|
| Q28 | 8 | Компонент лежит у исполнителя. Реакция на доменное событие — в реагирующем контексте, в каталоге агрегата, чей usecase зовёт, при нескольких агрегатах — `reactions/`; Oban-воркер — в каталоге агрегата-исполнителя, контекст-исполнитель экспортирует функцию постановки задачи; кеш read-модели — в её каталоге; компонент без вызовов usecases — подсистема, своя граница верхнего уровня. Вход внешней системы (её брокер, разбор формата, DLQ) — граница `MyAppIngest` рядом с `MyAppWeb`: MAY, при таком входе; `deps` — только на контексты |
| Q29 | 9 | Корень — одна граница `MyAppApp`: `Application`, список контекстов, `Outbox`, `PromEx`, `MetricsServer`, `Release`, mix-таски через `classify_to`. `MyApp.Projections` и `MyApp.Processes` исчезают — корень собирает их из контекстов (Q4). Сток — граница `MyApp.Infra`: `DAO`, `StreamID` и прочее без зависимостей на домен. Плейсхолдеры переименовываются по своду; у потребителей меняются `mod:` в `mix.exs` и команды `bin/my_app eval` |
| Q30 | 10 | Join таблиц проекций внутри контекста — MAY, как сейчас; между контекстами — MUST NOT: нужные поля проекция копирует себе из экспортированных событий производителя |
| Q31 | 11 | Отсрочка `use Core.Component` снимается отдельным тикетом, который не блокирует раскладку: обзор корней компонентов у потребителей, затем ADR и макрос (уточнено обзором: макроса нет — ADR-0043; корень очереди — тикет 11) |
| Q32 | 12 | MUST общего набора тестов (`rules/19`) относится к боевым реализациям одного контракта (`.Pg`, `.Cached`); тестовая реализация порта — тестовый двойник вне этого MUST. Авторизацию держит интеграционный тест на операцию с боевой реализацией (Q14) |
| Q33 | 13 | Проверка доступа — порт `MyApp.Authz` (behaviour и макрос декларации), граница без зависимостей на контексты; реализация — контекст прав или заглушка, выбор — в корне. Контекст объявляет ключи своих пространств и их описание в корневом модуле; проверка ключа при компиляции сохраняется; корень собирает реестр для реализации. В ADR-0025 заменяются пункты «механизм — подсистема» и «ключ у механизма» |
