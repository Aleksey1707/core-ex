# Корни компонентов у потребителей: обзор для решения о `use Core.Component`

- Дата: 2026-10-03
- Вход: тикет `issues/08-core-component-survey.md`, ADR-0024, ADR-0040, `docs/rules/app/17-otp-concurrency.md`
- Метки потребителей — сквозные; метки контекстов потребителя A — из `02-consumer-a-structure.md` (К1–К5)

## Вопрос

Есть ли у корней компонентов `<Component>.Supervisor` общая форма — тумблер, сборка опций, проверки старта,
`watch_list/0`, — которую стоит закрепить макросом `use Core.Component`, и какие у неё отклонения. ADR-0024
отложил макрос до переезда компонентов: «он закрепил бы API у всех потребителей раньше, чем переезд компонентов
покажет общую форму корня».

## Методика

- Только чтение: `find`, `grep`, `wc`, `git log`. Компилятор и тесты потребителей не запускались.
- Корень компонента — модуль с `use Supervisor` в `lib/` потребителя, кроме `MetricsServer` и `Telemetry` web
  (инфраструктура, а не компонент). Процессы компонента, стоящие детьми `Application` без корня, учтены отдельно.
- Строки кода — без пустых строк, комментариев, `@moduledoc`, `@doc`, `@spec`. Роли строк — по функции, в которой
  они стоят:
  - **шапка** — `defmodule`, `use`, `alias`, `require`, атрибуты модуля;
  - **скелет** — `start_link`, `watch_list`, `readers`, `kafka_readers`, фильтр списков тумблером, `enabled?`,
    `config`;
  - **дети** — `init/1`;
  - **опции** — сборка опций процессов из конфигурации (`tree_opts`, `topic_opts`, `poller_opts`, имена процессов);
  - **проверки** — свои проверки старта (единственность на кластере, наличие соединения).

  Вызов библиотечной проверки внутри `start_link` (`Core.Outbox.check_singleton!/1`) считается скелетом.
- 92 % совпадения корней A1 и A2 — из `02-consumer-a-structure.md`: там строки считались по всему корню, с `@spec`.

## Совпадающие части

- **Тумблер.** 13 из 14 корней читают `enabled` из конфигурации и при `false` отдают `:ignore` с `info`; у A3
  тумблера корня нет. Форма чтения одна у всех 14 — `Keyword.get(config, :enabled, false)`: у A3 так читается
  подчинённый тумблер инвалидатора, у B3 — функцией модуля компонента. Дефолт `false` стоит в модуле, хотя
  значение задаёт `config/runtime.exs`, — против `app/17`, «Опции процессов» (опция без дефолта, отсутствие ловит
  `Keyword.fetch!`); так у всех пяти корней A тоже.
- **Имя и регистрация.** Все корни стартуют `Supervisor.start_link(__MODULE__, _, name: __MODULE__)`, `init/1`
  возвращает `Supervisor.init(children, strategy: _)`.
- **`watch_list/0` тем же тумблером.** У A (5 из 5) и D (1 из 1) список строит корень и фильтрует тумблером старта;
  у A это функция `observe/1`: в A1 и A2 одинаковая до символа, в A4 — со своим условием старта.
- **Корни подписчиков A.** A1 и A2 совпадают почти целиком — 92 % строк (`02-consumer-a-structure.md`, раздел 7):
  различаются только константы (метка компонента, имя подписчика, префикс DLQ, два текста лога, модуль
  обработчика). Из 88 строк кода каждого 50 — сборка опций дерева подписчика, 21 — скелет. Те же 50 строк
  повторяет A3 при другом скелете: DLQ-writer Stream с префиксом по умолчанию, на топик читатель с общим
  соединением, именем подписчика и `credit`, подписчик с обработчиком, фабрикой контекста и `max_attempts` /
  `retry_max_ms`, имена процессов из топика через `Module.concat` с отключённой проверкой Credo. Общая трём
  корням часть — сборка опций; скелет общий только A1 и A2.
- **Корень очереди у пяти потребителей.** A5, B4, C2, D1, F2 — один состав детей в одном порядке (writer Stream →
  поллер → cleaner, `rest_for_one`), опции поллера и cleaner собираются из одних ключей `Core.Outbox`
  (`reference_prefix`, `poll_interval_ms`, `idle_min_ms`, `batch_size`, `lock_duration_seconds`, `max_attempts`,
  `poller_name` / `pollers`, `published_ttl_seconds`, `cleaner_interval_ms`) — 31–63 строки опций на корень.
  Отличия: у D1 соединение Stream внутри корня, у B4 второй поллер Kafka под тумблером подсистемы брокера, у F2
  ключ конфигурации — приложения, а не `:core`; `repo:` поллера — `Core.Config.outbox_repo/0` или ключ
  приложения. Это единственный вид компонента, который повторяется у нескольких потребителей.

## Отклонения

Пять корней A — четыре разных скелета:

| Скелет | Корни | Чем отличается |
|---|---|---|
| тумблер корня → `:ignore`, дереву Core — `enabled: true`, списки фильтрует корень | A1, A2 | — |
| тумблера у корня нет, кеш стоит всегда; дереву — подчинённый тумблер, списки фильтрует само дерево, кеш — всегда в `watch_list` | A3 | нет ветки `:ignore`; `init/1` засевает метрику только при включённом инвалидаторе |
| тумблер корня и третий случай «пропущено: нет топиков»; `watch_list/0` добавляет клиента Kafka к двум деревьям | A4 | два дерева, клиент с одним пользователем, `rest_for_one`, `kafka_readers/0` вместо `readers/0` |
| проверка единственности до ветки тумблера, тумблер под `:core`, `watch_list/0` перечисляет процессы руками | A5 | проверка получает тумблер аргументом и выключенную очередь пропускает сама |

Прочие отклонения:

- **Своя работа корня в `init/1`.** A1–A3 засевают нулём серию метрики потерянных событий подписчика — метрика
  приложения, библиотеке не известная.
- **Опции корня — разные ключи конфигурации:** модуль обработчика (A1–A3), сам корень (A4), `Core.Outbox` под
  `:core` (A5, B4, C2, D1) или под ключом приложения (F2), функция модуля компонента (B3).
- **Список для `Core.Mq.PromEx`:** `readers/0` у A1–A3, `kafka_readers/0` у A4, ни того ни другого у A5 и
  у корней без подписчиков.
- **Условие старта по наличию процесса соединения** (B1, B2: `Process.whereis/1` → `:ignore`) — против
  `app/17`, «Тумблер компонента»: недоступная внешняя система — не причина `:ignore`.
- **Реестр `watch_list` повторяет тумблеры** компонентов у B, C, F — против `app/17`, «Наблюдение за процессами»
  (MUST NOT); у A и D реестр только склеивает списки корней.

Повторы в корнях, которые были до ADR-0024, ушли в библиотеку функцией или готовым деревом, а не скелетом корня:

| Повтор | Где | Чем закрыт |
|---|---|---|
| своё дерево подписчика: читатель, подписчик, процесс-bootstrap с `subscribe/3` (27–35 строк детей и опций, bootstrap 44–50 строк отдельным модулем) | B1, B2, F1 | `Core.PubSub.MqSubscriberReliable.Supervisor` (2026-09-27): у A1–A4 детей 5–12 строк, bootstrap нет |
| проверка единственности очереди на кластере (15–27 строк) | B4, C2, D1, F2 | `Core.Outbox.check_singleton!/1` (2026-09-18): у A5 — один вызов |

Не закрыта: проверка единственности для компонента, который не очередь (C1, своя копия той же логики):
`check_singleton!/1` называет опции и ошибку по outbox.

## Сверка с ADR-0024 и местом компонента (Q28)

- **Корень владеет тумблером, сборкой опций, проверками старта и `watch_list/0`.** У A — все пять корней;
  кеш A3 — по «Подчинённому тумблеру». Проверка клиента брокера у A — в `Application`, как у разделяемой
  инфраструктуры (`app/17`, «Компонент»). У B, C, F — нет: реестр повторяет тумблеры, процессы компонентов
  стоят детьми `Application`; это код до ADR-0024 на версиях библиотеки до него.
- **Место по Q28 (ADR-0040)** у корней A после переезда на вертикаль:

  | Корень | Место |
  |---|---|
  | A1 | реакция К1 — каталог агрегата, чей usecase зовёт |
  | A2 | реакция К2 — каталог агрегата, чей usecase зовёт, или `reactions/` |
  | A3 | кеш read-модели — `<read_model>/read_repo/supervisor.ex`, уходит только `common/` |
  | A4 | вход внешней системы — `MyAppIngest.<Source>` |
  | A5 | корень приложения — `MyAppApp.Outbox` |

  Переезд меняет имя модуля и путь корня, а не его тело: форма корня следует виду компонента, а не месту.
  Общей формы переезд не добавляет — A4 уходит из контекста в границу входа с тем же скелетом.

## Выводы

1. Общая форма корня за пределами сборки опций — скелет: чтение тумблера, `:ignore` с `info`,
   `Supervisor.start_link` с именем модуля, `watch_list/0` и списки читателей для `Core.Mq.PromEx` с фильтром по
   тому же тумблеру. У A это 11–32 строки кода на корень, всего 117 из 495 (24 %, с шапкой в знаменателе), в
   четырёх разных скелетах на пять корней.
2. Повтор, общий трём корням подписчиков A, — сборка опций дерева подписчика (50 строк на корень A1–A3); скелет
   совпадает только у A1 и A2. Параметры сборки — ключи конфигурации, соединение, фабрика контекста, модуль
   обработчика, имена процессов — данные потребителя; макрос над скелетом её не убирает.
3. Повторы, которые уже ушли из корней, ушли в библиотечную функцию (`check_singleton!/1`) и в готовое дерево
   (дерево подписчика), каждый — с порядком или проверкой, которые держатся построением. Скелета корня ни один не
   затронул.
4. Один тумблер для старта и `watch_list` у A держат рукописные корни; реестр, который повторяет тумблеры, есть
   только у B, C, F — в коде до ADR-0024, переписываемом при переезде. Норму, которую макрос держал бы построением
   и которую сейчас не держит никто, обзор нашёл одну: тумблер без дефолта в модуле — дефолт `false` у всех 14
   корней, включая A.
5. Доказательная база для API — один потребитель на текущей форме; его корни подписчиков и входа написаны за
   2–4 дня до обзора. У B, C, D, F корни будут написаны заново при переезде после выпуска core-ex.
6. Корень очереди повторяется у всех пяти потребителей с компонентами: состав и порядок детей — `MUST` свода,
   проверка единственности — его же проверка старта, опции — из ключей `Core.Outbox`. Это кандидат на готовое
   дерево библиотеки, как дерево подписчика, а не на макрос.
7. Кандидаты на функцию библиотеки, которым нужен второй потребитель на текущей форме: проверка единственности
   для компонента, который не очередь (C1), и сборка опций дерева подписчика из общих опций топика (A1–A3).
