# 09: `ContextFactory` — место в границах

**What to build:** решение, в какой границе живёт `MyApp.ContextFactory`. После тикетов 01 и 03 `MyApp` границей не
является, а строка таблицы namespaces (`app/10`, «Top-level namespaces») оставляет модуль верхнего уровня
`lib/my_app/context_factory.ex` — вне границ, хотя «каждый модуль `lib/` MUST принадлежать границе». Своя
граница-подсистема даёт цикл с контекстом учётной записи: его воркеры берут актора у фабрики, а фабрика зовёт
аксессор `CurrentUser` этого контекста. У потребителя A решение Q18 — экспорт контекста учётной записи рядом с
аксессором; для потребителя без агрегата учётной записи аксессор живёт в подсистеме `MyApp.Auth` (`app/11`,
«Context»).

**Проверка (03.10.2026).**

- Утверждение тикета подтверждено по своду: строка namespaces кладёт фабрику модулем верхнего уровня, `MyApp`
  границей не является (ADR-0037), а «Boundary» требует границу для каждого модуля `lib/`.
- `boundary` ищет циклы по объявленным `deps` (`Boundary.Checker`, `cycles/1` → `dependency cycle found`);
  ссылка на границу без неё в `deps` — запрещённая ссылка. Нарушение исключения ниже сборка ловит в обоих случаях.
- Фабрики потребителей A, B, C, D, F (у E фабрики нет): ключей контекста два — `Sc` и текущий пользователь.
  Знание приложения у фабрики — только учётная запись (аксессор, ID пользователя, ID системной и анонимной
  учётных записей); `empty/0` и `sc/0` — обёртки над `Core`; у D — только `as_user/1` без `Sc`. У B, C, F аксессор
  и ID учётных записей лежат в разных местах — фабрика сшивает два.
- Фабрику зовут воркеры, подписчики и обработчики контекстов, outbox, mix-таски и задачи релиза, репозитории и
  кеш read-модели (A, C, F) и плаг контекста web — у всех пяти, вопреки «вне web» в таблице namespaces.
- Изнутри границы аксессора фабрику не зовёт ни один потребитель: цикл из тикета 03 сейчас гипотетический.

**Решения триажа (03.10.2026, с мейнтейнером).**

1. Фабрика — не «про пользователя»: она собирает контекст единицы работы. Место ей задаёт направление
   зависимостей: её зовут изнутри контекстов, значит её граница ниже всех вызывающих — `Core`, сток или граница
   аксессора. Сток отпадает: ему не виден тип ID учётной записи.
2. Своя граница-подсистема `MyApp.ContextFactory` с `deps` на границу аксессора; модуль и путь прежние.
   Отвергнуто: фабрика внутри границы аксессора (Q18 — экспорт контекста учётной записи) — граница учётной
   записи держала бы обвязку всего приложения, а новый ключ контекста привязал бы её к владельцу ключа;
   `MyApp.Infra` — см. п. 1; макрос в `Core` — состав фабрики прикладной.
3. Цикл закрывается исключением: граница аксессора фабрику не зовёт и собирает контекст своей единицы работы
   сама.
4. Попутно: «вне web» снимается — плаг контекста web собирает контекст фабрикой, фабрика входит в `deps`
   `MyAppWeb`.
5. ADR заводится: решение пересматривает Q18 и вводит исключение из «контекст — только через фабрику».

- Ревью реализации (Standards / Spec): из свода убраны разбор отвергнутого варианта и «ровно» —
  `deps` фабрики названы владельцами ключей контекста, сейчас только граница аксессора; запрет
  границе аксессора — и на зависимость через её `deps`; ссылка на исключение — в `app/17`,
  «Фоновые задания»; «Граница аксессора» — термин `CONTEXT.md`; фабрика названа в скобке `deps`
  границы входа.

## Agent Brief

**Category:** enhancement
**Summary:** `MyApp.ContextFactory` — своя граница-подсистема над границей аксессора текущего пользователя;
граница аксессора фабрику не зовёт и собирает контекст своей единицы работы сама

**Current behavior:**
Свод потребителя кладёт `MyApp.ContextFactory` модулем верхнего уровня `lib/my_app/context_factory.ex` с
назначением «сборка `%Context{}` вне web» (`app/10`, «Top-level namespaces»). `MyApp` границей не является, а
`app/10`, «Boundary», требует, чтобы каждый модуль `lib/` принадлежал границе: по своду фабрика — модуль вне
границ, у потребителя это ошибка сборки. Строки фабрики в таблице «Boundary» нет, в `deps` `MyAppWeb` её нет,
хотя `app/11`, «Context», велит собирать контекст только фабрикой — и плаг контекста web тоже. Usecases, которые
зовут не из web, MUST получать актора от фабрики (`app/10`, «Состав контекста»), и исключения для границы, от
которой зависит сама фабрика, норма не знает.

**Desired behavior:**

- `MyApp.ContextFactory` — подсистема приложения, своя граница верхнего уровня (`use Boundary` в модуле); имя
  модуля и путь прежние.
- `deps` фабрики — граница аксессора текущего пользователя: контекст агрегата учётной записи или подсистема
  `MyApp.Auth` (`app/11`, «Context», место аксессора). Из неё фабрика берёт аксессор, тип ID учётной записи, ID
  системной и анонимной учётных записей. Других `deps` нет; новый ключ контекста обязан принадлежать границе
  ниже всех вызывающих и добавляется строкой `deps` фабрики.
- Фабрику держат в `deps` контексты, `MyAppWeb`, `MyAppIngest` (его норма «контексты и подсистемы» её уже
  покрывает) и корень.
- Граница аксессора MUST NOT звать фабрику: фабрика зависит от неё, и ссылка замкнула бы цикл границ. Контекст
  своей единицы работы (воркер контекста учётной записи) она собирает сама — `Core.Context.new/0`,
  `Core.Repo.Sc.init/1` и свой аксессор. Нарушение ловит сборка: с фабрикой в `deps` — цикл, без неё —
  запрещённая ссылка `boundary`.
- Назначение фабрики в таблице namespaces — сборка `%Context{}` единицы работы, включая плаг контекста web;
  «вне web» снимается.
- ADR фиксирует решение: контекст (Q18 — экспорт контекста учётной записи; тикет 03 — модуль вне границ),
  довод «место задаёт направление зависимостей, а не смысл», рассмотренные варианты (внутри границы
  аксессора, сток `MyApp.Infra`, макрос в `Core`) и цену (граница аксессора собирает контекст сама).
