## Agent Brief

**Category:** enhancement
**Summary:** отказ быстрого пути `await` виден сравнением «сигнал чекпоинта отправлен кластером / получен нодой»

**Current behavior:**
Пачка проекции шлёт `NOTIFY` в канал `core_es_checkpoint` в своей транзакции; слушатель
`Core.Es.Projection.Listener` (по одному на `repo:` проекций, `auto_reconnect: true`) переводит
уведомление в сигнал через `Core.Es.Projection.Registry`. Потеря соединения слушателя или
`LISTEN` за pgbouncer в transaction mode не видны ничем: telemetry у слушателя нет, `await` молча
доходит шагами страховки, в «Цене» ADR-0013 — «отдельной метрики быстрого пути нет».

**Desired behavior:**
Каждая слушающая нода получает все уведомления канала, включая свои, поэтому на здоровой ноде
«получено» ≈ «отправлено кластером». Нода, которая за окно не получила ничего, пока кластер
отправлял, — отказ быстрого пути.

- **Отправлено.** После commit пачки с исходом `:processed` — там, где читатель уже рассылает
  локальный сигнал через Registry, — telemetry `[:es, :projection, :signal, :sent]`,
  measurement `%{count: 1}`, metadata `%{repo: <dao декларации>}`. Не эмитится, если в отметке
  дерева `notifications: false` (тогда `NOTIFY` не шлётся). Откатившаяся пачка не засчитывается.
  Ручной `run_once/2` без дерева не засчитывается — недосчёт в безопасную сторону.
- **Получено.** Слушатель на каждое уведомление канала — telemetry
  `[:es, :projection, :signal, :received]`, `%{count: 1}`, `%{repo: repo}`.
- **Засев нулём.** Слушатель после подписки (`handle_continue`) эмитит оба события с
  `%{count: 0}` для своего `repo`: серия ноды существует и равна 0 до первого уведомления.
  Повторный засев после рестарта слушателя безвреден.
- **Метрики** в event-группе `Core.Es.PromEx` (строится всегда): `es_projection_signal_sent_total`
  и `es_projection_signal_received_total`, тег `repo`. Тип — `sum` по `count`, а не `counter`:
  `counter` у `telemetry_metrics_prometheus_core` прибавляет 1 на событие и нулём серию не
  засеет; `sum` экспортируется в Prometheus с типом `counter`.
- **Выключенный путь.** При `notifications: false` слушателя нет и пачка не шлёт — серий нет, алерт
  на ноде не горит.
- Процессная модель ADR-0013 не меняется: `sync_connect: false`, `auto_reconnect: true`, своих
  логов у слушателя нет.

**Key interfaces:**
- Имена событий — через `Core.Telemetry.event/1`, как у остальных событий `[:es, …]`.
- `Core.Es.PromEx` moduledoc — перечень event-метрик дополнен двумя новыми.
- `Core.Es.Projection.Listener` moduledoc — «своих логов и telemetry у слушателя нет» заменяется
  ссылкой на метрики сигнала и алерт.
- Алерт `EsProjectionSignalLost` в таблице «Эксплуатация» `22-projections.md`:

  ```
  increase(my_app_prom_ex_es_projection_signal_received_total[10m]) == 0
    and on (repo) sum by (repo) (increase(my_app_prom_ex_es_projection_signal_sent_total[10m])) > 0
  ```

  `for: <порог>`; смысл — кластер шлёт сигнал чекпоинта, а нода его не получает: соединение
  слушателя потеряно или стоит за pgbouncer в transaction mode, `await` на ноде идёт шагами.
  Серия ноды — слева: так сохраняется `instance`. Условие `== 0`, а не доля потерь: короткий разрыв,
  который Postgrex восстановил сам, штатен. К строке — пример теста `promtool test rules`
  (нода с нулём при отправке кластера → алерт; нода с получением → тишина).
- ADR-0028 «Наблюдаемость сигнала чекпоинта»: решение — сравнение «отправлено / получено»;
  отвергнуты (A) своё переподключение без `auto_reconnect` с gauge подписки — меняет процессную
  модель ADR-0013 и не ловит pgbouncer, где `LISTEN` проходит, а уведомления теряются;
  (B) проба `NOTIFY` слушателем — каждая берёт общую на кластер блокировку коммита, от которой
  ADR-0013 уводит всё, кроме пачек. В «Цене» ADR-0013 строка «отдельной метрики быстрого пути
  нет» заменяется ссылкой на ADR-0028.
