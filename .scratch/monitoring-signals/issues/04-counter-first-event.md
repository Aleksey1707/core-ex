## Agent Brief

**Category:** enhancement
**Summary:** рекомендованные алерты на единичное событие поднимаются на первое событие новой серии счётчика

**Current behavior:**
Серия `counter` у `telemetry_metrics_prometheus_core` появляется после первого события сразу со
значением 1 (`:ets.update_counter(…, 1, {key, 0})`). `increase(x[5m])` по одной точке — 0, и
внешняя `sum(...)` это не лечит. Алерты таблицы «Рекомендованные алерты» `21-observability.md`
на единичное событие не поднимаются на первое событие по каждой паре меток после старта ноды:
единичное сообщение в DLQ или единичный отказ публикации проходят молча. У всех этих счётчиков есть
открытая метка (`topic`, `dlq_topic`, `cache`) — нулями при старте их серии не засеять.

**Desired behavior:**
- **Таблица.** Шесть алертов — `OutboxFailedDelivery`, `MqPublishErrors` (с вариантом Kafka
  `mq_kafka_publish_total`), `MqDecodeDrops`, `MqSubscriberDlq`, `CacheUnavailable`,
  `CacheStoreErrors` — получают форму

  ```
  sum by (<метки>) (increase(x{<фильтр>}[w])) > 0
    or sum by (<метки>) (x{<фильтр>} unless x{<фильтр>} offset w) > 0
  ```

  с метками и фильтрами каждого алерта как сейчас (у `OutboxFailedDelivery` — `sum` без `by`).
  Правая ветка — серия, которая есть сейчас и которой не было окно назад.
- **Правила формы** в тексте нормы: `offset` MUST равняться окну `increase`; фильтр по меткам
  повторяется в каждом `x`; значение правой ветки — полный счёт, а не прирост.
- **Цена** в тексте нормы: ложное срабатывание, когда скрейп цели не проходил дольше окна (серия
  стала stale и вернулась со старым значением). Проверка `up` в условии не ставится: она снова
  прячет первое событие после простоя ноды дольше окна.
- **`EsProjectionRetrying` не меняется** — оговорить в норме: у него `for:`, повтор идёт каждый
  цикл, пока пачка отказывает, второй инкремент виден.
- **Норма для новых счётчиков** в `21-observability.md`: счётчик под алерт на единичное событие
  с закрытым множеством меток SHOULD объявляться `sum` по measurement `count` и засеваться
  `count: 0` при старте процесса-владельца — тогда условие в таблице обычное `increase > 0`.
  Засевает владелец, а не плагин PromEx: метрики плагина подключаются к telemetry после его сборки.
  `sum` экспортируется в Prometheus с типом `counter`, имя серии не меняется. В норме — пример
  объявления и засева; ссылка на метрики сигнала чекпоинта
  (`es_projection_signal_{sent,received}_total`) — только если заявка 01 уже выполнена.
- **ADR** «Первое событие серии счётчика», следующий свободный номер: решение — форма условия для
  таблицы, засев нулём для новых счётчиков с закрытыми метками. Отвергнуты: засев нулями для
  существующих счётчиков (открытые метки при старте неизвестны); `created-timestamp-zero-ingestion`
  Prometheus (экспортёр не отдаёт серий `_created`); проверка `up` в условии (см. «Цена»). Норма
  ссылается на ADR.

**Key interfaces:**
- Раздел «Рекомендованные алерты» `21-observability.md` — таблица, правила под ней, пример
  `promtool test rules`.
- Пример `promtool test rules` на `MqSubscriberDlq` (вход — серии `input_series`, проверка —
  `alert_rule_test`): серия появляется сразу с 1 → алерт горит; серия с 1 и без роста → тишина;
  счётчик растёт → алерт горит.
- Объявления метрик в `Core.*.PromEx` не меняются.
