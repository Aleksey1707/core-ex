# 11: Форма ADR и спека

Type: grilling
Status: resolved

Blocked by: 10, 12

## Question

Решения тикетов 02–10 собраны. Как они ложатся в документы назначения карты?

- Новый ADR «Связи event-sourced агрегата»: что он фиксирует сам, а что — ссылкой на тикеты-прототипы. Как уточняется
  ADR-0014 («Полнота», источник литерала агрегата в `await`) — правкой с пометкой или ссылкой из нового. ADR об
  `await` (0027, 0030, 0039, 0080) не уточняются: формы прежние (пересмотр тикета 07).
- `spec.md`: порядок работ под `/to-tickets` (семейство → кодек и события → репозиторий → ключ → проекция → `Opts`),
  что переносится из веток `prototype/*`, какие тесты библиотеки и сценарии фикстуры уходят или переписываются.
- Пункты CHANGELOG «было → стало» по разделам «Ломающие изменения контракта» и «Изменения контракта макросов»:
  один пункт на выпуск или по билдеру.
- Сверки владельца потока (тикет 12): `@after_verify` семейства с `IO.warn` — новый для библиотеки приём; фиксирует
  ли его ADR как общий способ сверять атомарные ссылки без ожидания.
- Строки таблицы «Версия библиотеки» (`docs/rules/app/00-index.md`) и правка сводов `13-repos.md`,
  `14-events-outbox.md`, `22-projections.md`, `11-domain.md`, яруса `app/`.

## Answer

Решено в обсуждении 2026-10-24.

**ADR-0084 «Связи event-sourced агрегата» — самодостаточный.** Решение излагает сам:
- цепочка владельцев «агрегат → кодек → семейство», таблица опций «было → стало» по билдерам;
- `codec:` / `aggregate:` у семейства — runtime-ссылки (вариант Б тикетов 09 и 12);
- сверки владельца потока — в билдерах записи (`Repo.Pg`, `StateStored`), полнота `reservation/1` — в ключе;
- `@after_verify` + `IO.warn` — только для двух ссылок семейства, с объяснением, почему не `raise` (падает процесс
  проверки, кириллица под `mix run`). Нормой сводов не становится до второго случая. Противоречия с тикетом 10 нет:
  там `IO.warn` был периодом перехода с двумя формами, здесь — сверка без срока жизни.

«Рассмотренные варианты» пересказывают отвергнутое (хаб в behaviour репозитория, манифест `<Aggregate>.Wiring`, кодек
как хаб, вариант А ссылок, формы `await` без агрегата) с итогами замеров xref и перекомпиляции в одну-две фразы.
Тикеты карты — строкой «Источник»; на ветки `prototype/*` ADR не ссылается.

**ADR-0014** — строка в шапке, как у ADR-0062 / ADR-0023: «Уточнён ADR-0084: полнота `reservation/1` проверяется в
модуле ключа; литерал агрегата в голове `await` — из `aggregate:` семейства, а не из имени кодека». Тело не правится.
ADR об `await` (0027, 0030, 0039, 0080) не уточняются.

**CHANGELOG** — один пункт в «Изменения контракта макросов» с таблицей «было → стало» по билдерам (семейство — новый
`Core.Es.Event.Family`, событие, кодек, `Outbox`, `Repo`, `Repo.Pg`, ключ) и новыми сверками под ней. В «Ломающие
изменения контракта» ничего: `await` и публичные функции не меняются. Каждый срез реализации дополняет этот пункт.

**«Версия библиотеки»** (`docs/rules/app/00-index.md`) — четыре строки:
1. `use Core.Es.Event, aggregate_id:, by:`, семейство — простой модуль с `@type t` → `use Core.Es.Event, family:` и
   `use Core.Es.Event.Family, aggregate:, aggregate_id:, by:, codec:`;
2. `event:` у `use Core.Es.Event.Codec` и `use Core.Es.Outbox` → `family:`;
3. `id:` у `use Core.Es.Aggregate.Repo`, `aggregate:` / `id:` у `use Core.Es.Aggregate.Repo.Pg` → `aggregate:` у
   `Repo`, у `Repo.Pg` — `behaviour:`;
4. `event:` / `id:` у `use Core.Es.KeyReservation` → `aggregate:`.

**Своды.** Имя `<Aggregate>.Event.Codec` остаётся нормой раскладки яруса `app/`; из `22-projections.md` и описания
skill `projections` уходит «кодек находится по имени семейства». Своды (`11-domain.md`, `13-repos.md`,
`14-events-outbox.md`, `19-testing.md`, `22-projections.md`, `23-personal-data.md`, `app/11-domain.md`,
`app/13-repos.md`) и moduledoc правит каждый срез в своей части — отдельного среза документации нет.

**`spec.md`** — прежний шаблон (`es-type-safety`, `codec-plugin-by-fields`): Problem Statement / Solution / User Stories
(перевод потребителя, ошибки сборки) / Implementation Decisions (раздел на билдер, «Порядок работ», «Документация,
свод, CHANGELOG» с текстом пункта и строками таблицы) / Testing Decisions / Out of Scope / Further Notes.

Порядок работ; `make` зелёный после каждого среза, срез сам переводит `test/support`, `fixtures/consumer` и
`Core.Es.Personal.Event`:
1. `Opts.validate!` — одна ошибка с обоими списками;
2. семейство целиком: `Core.Es.Event.Family` с `@after_verify`, `family:` у событий, кодека и `Outbox`, сверки кодека,
   `ensure_family_aggregate!` в `Repo.Pg` / `StateStored`, удаление `derive!`;
3. репозиторий, 4. ключ, 5. проекция — параллельно после 2.

`test/support`: у кодека `Core.EventFixture.Event.Codec` три владельца потока. `Core.EsFixture.Catalog` получает своё
семейство, кодек и события; `MacroConfigTest` (тест «без dao») переходит на `StateStoredFixture.Entity`.

**Тесты.** `CompileError` (ключ чужого агрегата, чужой владелец у семейства, `codec:` на чужой кодек) — тестами
библиотеки. Предупреждение `@after_verify` — тестом, если `Code.compile_string` его вызывает (проверяет срез 2), иначе
сценарием `fixtures/consumer` с маркером `# expect:`. Сценарии `BadKey.Repo.Pg` / `BadKeyPayload.Repo.Pg` удаляются,
маркеры неполного `reservation/1` — на `use` ключа.

**Ветки `prototype/*`** — в Further Notes как образец, не источник истины; удаляются после реализации.

**Глоссарий.** В `CONTEXT.md` — термин «Владелец потока»; «Семейство событий агрегата» определено через него.
