# Сигнал чекпоинта: ожидание проекции без задержки опроса

Type: spec
Status: ready-for-agent

## Problem Statement

Автор usecase после записи ждёт проекцию через `Core.Es.Projection.await/4` и отдаёт клиенту read-модель уже с
новыми событиями (read-after-write). Ожидание сейчас — опрос строки чекпоинта с удвоением шага 10 → 100 мс, а
читатель проекции узнаёт о записи только через `wake` в пределах своей VM. Ответ задерживает не пачка, а три
источника, и два из них больше самой пачки:

- **Шаг опроса.** Пачка закоммитила чекпоинт, а ожидающий спит до следующего шага: пачка 35 мс даёт ответ на 70-й мс,
  пачка 80 мс — на 150-й. Сверх пачки — до 100 мс.
- **Событие ещё не видно пачке.** Пачка читает события транзакций старше самой старой активной пишущей транзакции
  кластера (ADR-0008). Если при `wake` такая транзакция открыта — другой usecase, пачка соседней проекции, запись в
  другую базу кластера, — пачка отдаёт `:idle`, `wake` израсходован, и следующий тик читателя приходит через
  `idle_ms`, который `wake` не сбрасывает и который в тихой системе дорос до `poll_interval_ms` (1 с). Старая
  транзакция закоммитилась через 30 мс, а ожидание длится около секунды.
- **Пачку гонит другая нода.** Дерево проекций стоит на всех нодах, пачки одной проекции разводит advisory lock, и под
  нагрузкой они остаются за нодой, которая их гонит. На N нодах ожидающий оказывается на этой ноде примерно в 1/N
  случаев; в остальных сигнала нет, только опрос.

Опрос задумывался страховкой, а работает основным механизмом. Шаг опроса потребитель не настроит: он зашит
константами модуля.

## Solution

Ожидание опирается на сигнал чекпоинта, опрос остаётся страховкой (ADR-0013):

- пачка проекции сообщает о сдвиге чекпоинта в своей транзакции через `NOTIFY` — его получают ожидающие на всех нодах,
  кластер Erlang не нужен; читатель после commit пачки дублирует сигнал внутри ноды;
- пока ожидающий ждёт, каждый его шаг будит локального читателя проекции — событие, которого пачка не видела,
  подхватывается за шаг после commit старой транзакции, а не за `poll_interval_ms`;
- шаг ожидания задаётся опциями дерева; `notifications: false` снимает `NOTIFY` целиком — для одной ноды, где хватает
  сигнала внутри VM, и для окружений, где `LISTEN` недоступен.

Контракт `Core.Es.Projection.await/4` — исходы, ошибки программиста, span, telemetry, режим `:inline` — не меняется:
меняется только то, как скоро приходит `:ok`.

## User Stories

1. As an автор usecase, I want `Core.Es.Projection.await/4` возвращать `:ok` вскоре после commit пачки, обработавшей
   последнее событие потока, so that read-after-write отвечал за время пачки, а не за шаг опроса.
2. As an автор usecase на нескольких нодах, I want получать сигнал о пачке, которую прогнала другая нода, so that
   ожидание было одинаково быстрым на любой ноде.
3. As an автор usecase, I want ожидание без кластера Erlang, so that оно работало в приложениях с outbox, которым
   кластеризация запрещена.
4. As an автор usecase, I want, пока жду, будить локального читателя проекции на каждом шаге, so that событие, которое
   пачка не видела из-за старой пишущей транзакции, подхватывалось за шаг после её commit.
5. As an автор usecase, I want прежние исходы `await/4` — `:ok`, `:projection_timeout`, `:projection_rebuilding` — и
   прежние `raise`, so that правка не трогала код вызова.
6. As an автор usecase, I want сразу получать `:projection_rebuilding`, когда сигнал пришёл от пачки, начавшей
   пересборку, so that ожидание не висело до таймаута на неполной read-модели.
7. As an автор usecase, I want чтобы после возврата `await/4` в mailbox моего процесса не оставалось сигналов, so that
   GenServer или LiveView, вызвавший ожидание, не получал неожиданных сообщений в `handle_info/2`.
8. As an автор usecase, I want чтобы потерянный сигнал — разрыв соединения слушателя, `LISTEN` через пулер —
   замедлял ожидание до шага страховки, а не давал таймаут, so that быстрый путь был оптимизацией, а не условием
   корректности.
9. As an автор usecase, I want чтобы сигнал чужой проекции не будил моё ожидание, so that каждая пачка каждой проекции
   не порождала перечитывание чекпоинта у всех ожидающих.
10. As an автор usecase, I want шаги страховки по своему расписанию независимо от сигналов, so that поток сигналов
    занятой проекции не отменял пробуждение читателя и перечитывание чекпоинта.
11. As an автор usecase, I want чтобы `timeout` по-прежнему ограничивал всё ожидание, so that сигналы и шаги не
    растягивали его сверх заданного.
12. As a разработчик приложения, I want задавать первый шаг и предел удвоения шага ожидания опциями дерева
    `await_min_ms:` и `await_max_ms:`, so that подобрать баланс задержки и нагрузки на базу под своё приложение.
13. As a разработчик приложения, I want по умолчанию прежний шаг — удвоение 10 → 100 мс, so that без настройки
    страховка вела себя как раньше.
14. As a разработчик приложения, I want `ArgumentError` на старте дерева при недопустимых `await_min_ms:`,
    `await_max_ms:` или `notifications:` при любом `enabled:`, so that ошибка конфигурации не всплывала в рантайме.
15. As a разработчик приложения, I want чтобы опции шага ожидания не смешивались с интервалами читателя, so that дерево
    с интервалами читателя 60 000 мс не превращало ожидание в таймаут.
16. As a разработчик приложения на одной ноде, I want отключить `NOTIFY` опцией `notifications: false`, so that не
    держать лишнее соединение и не ставить коммиты пачек в очередь кластерной блокировки.
17. As a разработчик приложения на одной ноде, I want при `notifications: false` сохранять быстрый путь, so that сигнал
    внутри VM и пробуждение читателя закрывали read-after-write без `LISTEN`.
18. As a разработчик приложения, I want чтобы при `notifications: false` пачки ноды не слали `NOTIFY` вовсе, so that не
    платить блокировкой коммита, которую PostgreSQL берёт и без слушателей.
19. As a разработчик приложения за pgbouncer в transaction mode, I want задать соединение слушателя keyword-опциями
    поверх конфигурации repo — например прямой хост, so that `LISTEN` шёл в обход пулера.
20. As a разработчик приложения, I want чтобы по умолчанию слушатель брал соединение из конфигурации `repo:` проекций,
    so that быстрый путь работал без настройки.
21. As a разработчик приложения с проекциями на разных `repo:`, I want по слушателю на каждый различный repo, so that
    сигнал приходил из той базы, где идёт пачка.
22. As a разработчик приложения, I want чтобы слушатель соединялся после старта дерева, а не в `init/1`, so that
    недоступная база не роняла старт приложения.
23. As a разработчик приложения, I want чтобы слушатель сам переподключался и восстанавливал подписку, so that разрыв
    соединения с базой не требовал рестарта дерева.
24. As a разработчик приложения, I want чтобы падение слушателя не перезапускало читателей проекций, so that пачки не
    прерывались из-за сигнального соединения.
25. As a разработчик приложения, I want рекомендуемые env `ES_PROJECTIONS_NOTIFICATIONS`, `ES_PROJECTIONS_AWAIT_MIN` и
    `ES_PROJECTIONS_AWAIT_MAX` в `config/runtime.exs`, so that настраивать ожидание так же, как остальные опции дерева.
26. As a разработчик приложения, вызывающий `run_once/2` вне дерева, I want чтобы пачка сигналила, если нода не
    отказалась от `NOTIFY`, so that ожидающие других нод видели ручной прогон.
27. As a эксплуатация, I want знать из документации, что нода открывает по соединению на каждый `repo:` проекций, so

28. As a эксплуатация, I want узнавать сломанный быстрый путь по `duration` `[:es, :projection, :await]`, который

29. As a эксплуатация, I want чтобы при поэтапной выкладке ноды старого кода (опрос) и нового (сигнал) работали вместе,

## Implementation Decisions

### Сигналы внутри ноды — `Core.Es.Projection.Registry`

- Registry (`keys: :duplicate`) несёт три сигнала, ключ — кортеж с видом сигнала, чтобы строка типа агрегата не
  совпала с именем проекции:
  - **сигнал записи** (`wake`) — по типу агрегата; получатель — читатель, отправитель — `append` после commit, как
    сейчас;
  - **пробуждение читателя** — по имени проекции; получатель — читатель, отправитель — ожидающий;
  - **сигнал чекпоинта** — по имени проекции; получатель — ожидающий на время ожидания, отправители — читатель после
    commit пачки и слушатель канала.
- Registry не запущен (дерево `:ignore`): отправка — `:ok`, регистрация ожидающего пропускается, ожидание идёт одними
  шагами.
- Новые функции Registry — `@doc false`, как `register/1` и `wake/1`.

### Ожидание — `Core.Es.Projection.Await`, режим `:poll`

- Порядок: подписка на сигнал чекпоинта своей проекции → цель (позиция последнего события потока) → разбор чекпоинта.
  Подписка идёт до чтения: сигнал между чтением и ожиданием иначе теряется.
- Подписка — alias процесса (`Process.alias/1`) значением записи Registry; рассылка шлёт на alias. После ожидания при
  любом исходе — снятие регистрации, `Process.unalias/1` и вычерпывание доставленных сигналов: поздний сигнал runtime
  отбрасывает, mailbox вызывающего остаётся чистым.
- Разбор исходов — прежний: чекпоинт не ниже цели — `:ok`; пересборка — сразу `:projection_rebuilding`; иначе ждать.
- Ожидание: сигнал своей проекции — перечитать чекпоинт; наступил шаг — перечитать чекпоинт и разбудить локального
  читателя своей проекции. Шаги идут по расписанию от начала ожидания — удвоение от `await_min_ms` до `await_max_ms` —
  и сигналами не сдвигаются. Истёк `timeout` — `:projection_timeout`.
- Первое пробуждение читателя — на первом шаге: при записи его уже разбудил сигнал `append`.
- Интервалы шага берутся из отметки дерева; константы модуля уходят. `:inline` не меняется и шагов не использует.
- Span `await <имя>` и telemetry `[:es, :projection, :await]` не меняются; перечитывания и пробуждения идут внутри
  span'а.

### Читатель — `Core.Es.Projection.Reader`

- В `init/1` читатель регистрируется ещё и под ключом пробуждения по имени своей проекции.
- Пробуждение от ожидающего — то же сообщение `wake` с той же обработкой: цикл сразу при `:idle` / `:locked` / до
  первого цикла, пропуск при `:retry` / `:outdated`; счётчик простоя не сбрасывается; частые пробуждения склеивает
  вычерпывание в начале и конце цикла.
- После пачки с исходом `:processed`, включая старт пересборки, — сигнал чекпоинта своей проекции через Registry. К
  этому моменту транзакция пачки закоммичена.

### Пачка — `Core.Es.Projection.Batch`

- В транзакции пачки после сдвига чекпоинта или старта с начала — `pg_notify` в канал сигнала чекпоинта с именем
  проекции. Отказ пачки откатывает транзакцию, и сигнал не доставляется.
- `NOTIFY` не шлётся, только если отметка дерева на ноде есть и в ней `notifications: false`. Отметки нет — дерево на
  ноде не стартовало, `run_once/2` вручную — шлётся, как при умолчании.
- `Core.Es.Store.append/5` `NOTIFY` не получает: сигнал записи остаётся в пределах VM.

### Протокол канала

- Один канал на все проекции — `core_es_checkpoint`; payload — `name:` проекции как есть, больше ничего: ожидающий
  перечитывает строку чекпоинта.
- Имя канала и формат payload — протокол между нодами разных версий: смена — ломающее изменение с записью в CHANGELOG
  и ADR.
- Сигнал с именем проекции, которой на ноде нет, никого не будит.

### Слушатель — новый `Core.Es.Projection.Listener`

- Процесс дерева на каждый различный `repo:` проекций. Держит `Postgrex.Notifications` с `sync_connect: false` и
  `auto_reconnect: true`; опции соединения — `repo.config()`, поверх — keyword из `notifications:`.
- Подписка на канал — после `init/1` (`handle_continue`, `17-otp-concurrency.md`); после переподключения
  `Postgrex.Notifications` сам повторяет `LISTEN` на все каналы.
- Уведомление канала → сигнал чекпоинта через Registry по имени проекции из payload.
- Разрывы соединения логирует Postgrex; своих логов и telemetry у слушателя нет.
- При `notifications: false` слушатели не стартуют.

### Дерево — `Core.Es.Projection.Supervisor`

- Новые опции:
  - `notifications:` — `true` (по умолчанию), `false` или keyword опций соединения Postgrex поверх `repo.config()`;
    иное — `ArgumentError`;
  - `await_min_ms:` — первый шаг ожидания, по умолчанию 10;
  - `await_max_ms:` — предел его удвоения, по умолчанию 100.
  Числа — положительные целые, пара не сверяется, как у `idle_min_ms` / `poll_interval_ms`.
- Опции проверяются при любом `enabled:`, попадают в отметку и в опции читателей не передаются.
- Порядок потомков при `rest_for_one`: Registry → читатели → слушатели. Падение слушателя читателей не трогает,
  падение Registry перезапускает всех, как сейчас.
- `enabled: false` и `projections: []` — `:ignore`, как сейчас: ни Registry, ни слушателей.
- `watch_list/1` не меняется.

- ADR-0013 уже записан; ADR-0009, grilling проекций и спека event sourcing не правятся.

## Testing Decisions

- Хороший тест наблюдает поведение через публичный API: исход `await/4`, отметку и `ArgumentError` дерева, уведомления
  канала. Ключи Registry, цикл читателя и процесс слушателя напрямую не проверяются.
- Быстрый путь доказывается не временем, а невозможностью другого исхода: шаги ожидания 60 000 мс при таймауте в
  секунды — `:ok` приходит только сигналом; интервалы читателя 60 000 мс — пачка идёт только по пробуждению.
- **Шов 1 — `Core.Es.Projection.await/4`:**
  - sandbox, живое дерево: запись через репозиторий → `:ok` сигналом внутри VM при шагах 60 000;
  - sandbox: событие вставлено мимо `append`, `wake` нет, интервалы читателя 60 000, шаг короткий → `:ok` через
    пробуждение читателя;
  - после `await/4` — `:ok`, таймаут, пересборка — в mailbox теста нет сигналов;
  - настоящие коммиты: пачку прогоняет `run_once/2` в другом соединении, шаги 60 000 → `:ok` через `NOTIFY` и
    слушателя;
  - настоящие коммиты: старая пишущая транзакция другого соединения держит видимость, событие закоммичено, пачка
    отдала `:idle`; после commit старой транзакции ожидание с коротким шагом при интервалах читателя 60 000 → `:ok`;
  - настоящие коммиты, `notifications: false`: `:ok` сигналом внутри VM, слушателя нет;
  - существующие тесты `await: :poll`, `:inline`, пересборки, ошибок программиста, span и telemetry остаются; меняются
    только те, что опирались на константы шага.
- **Шов 2 — `Core.Es.Projection.Supervisor.start_link/1`:** недопустимые `notifications:`, `await_min_ms:`,
  `await_max_ms:` — `ArgumentError` при любом `enabled:`; умолчания и заданные значения — в отметке; при `false`
  слушателей нет, при `true` — по одному на repo.
- **Шов 3 — канал `core_es_checkpoint`:** тест сам подписывается `Postgrex.Notifications.listen`; после `run_once/2`
  с настоящим коммитом при `notifications: false` уведомления нет, при `true` — уведомление с именем проекции.
- Тесты с настоящими коммитами — отдельный модуль, `async: false`, очистка `es_events` и `es_checkpoints` в `on_exit`.
  Глобальный режим sandbox — `:manual`, а процессам дерева нужны соединения вне sandbox: режим на время модуля
  выбирает тикет.
- Prior art: `Core.Es.Projection.AwaitTest` — `start_tree!`, `mark!`, `commit_event!`, `in_other_connection`,
  интервалы `@quiet`; `Core.Es.StoreRaceTest` — участники с настоящими коммитами через `Sandbox.unboxed_run`, очистка
  в `on_exit`; `Core.Es.Projection.SupervisorTest` — «опции — ArgumentError при любом enabled:», «Registry не запущен —
  wake отдаёт :ok».
- `make` зелёный.

## Out of Scope

- `NOTIFY` в `append` и сигнал записи между нодами; быстрый путь на ноде с `enabled: false` (ADR-0013).
- `:pg` и кластер Erlang.
- Метрика доли быстрого пути (`via: :signal | :poll`), новые telemetry-события и PromEx-метрики.
- Опции шага на вызов — `await/5`.
- Сброс счётчика простоя читателя по `wake` и другие изменения цикла читателя, кроме регистрации и сигнала.
- Позиция чекпоинта в payload.
- Сверка `await_min_ms` ≤ `await_max_ms`.
- Замеры на нагрузке.

## Further Notes

- **Не проверено на нагрузке:** очередь коммитов пачек под блокировкой `NOTIFY` при многих проекциях и нодах;
  нагрузка от пробуждений читателя и перечитываний чекпоинта при многих одновременных ожиданиях.
- Цена, отвергнутые варианты и проверенное поведение PostgreSQL — ADR-0013.
- **Предлагаемый порядок срезов** (зависимости, не решение тикетов):
  1. Registry: ключи по виду сигнала, пробуждение читателя и сигнал чекпоинта внутри VM; ожидание с подпиской и шагами
     из опций дерева; sandbox-тесты. Самостоятельный выигрыш на одной ноде.
  2. `NOTIFY` в пачке, слушатель, опция `notifications:`, протокол канала; тесты с настоящими коммитами.
  Документация свода, README и CHANGELOG идут в том же срезе, который меняет поведение.
