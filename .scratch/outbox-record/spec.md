# Один владелец переходов записи outbox

Внутренний рефакторинг `Core.Outbox.Record` / `Core.Outbox.Repo.Pg`. Термины — `CONTEXT.md`,
«Запись outbox», «Заявка на готовность»; нормы — `docs/rules/14-events-outbox.md`,
`docs/adr/0082-outbox-delivery-test-double.md`.

## Problem Statement

Жизненный цикл записи outbox описан в двух слоях одновременно. `Core.Outbox.Record` считает переходы
структуры (`reserve/4` инкрементит `attempts`, `release/2` возвращает в `:new`, `record_failure/4`
выбирает `:failed` или `:new`), а `Core.Outbox.Repo.Pg` повторяет часть той же арифметики в SQL:
`mark_reserved!/2` делает `inc: [attempts: 1]`, `release/2` обнуляет `lease_id`, `requeue_failed/2`
сбрасывает счётчики мимо переходов. Синхронность держится комментарием «инкремент в строке совпадает с
инкрементом в структуре». Любая правка перехода требует помнить о двух местах, а расхождение видно
только в проде: например, структура после `release/2` оставляет `lease_id`, а SQL его обнуляет.

## Solution

`Core.Outbox.Record` становится единственным владельцем таблицы переходов: он вычисляет целевые
`status`, `attempts`, `errors`, `locked_until`, `lease_id`, `published_at`, `updated_at`.
`Core.Outbox.Repo.Pg` только сохраняет то, что посчитала структура, сохраняя батчевую запись по группам
одинаковых наборов полей. Два действия получают разные имена и разные инварианты: снятие резервации с
фехтованием по токену (`Repo.release/2`) и возврат записи в очередь после обработки (`Record.requeue/2`).
Публичное поведение, схема таблицы, число запросов и тест-дублёр доставки не меняются.

## User Stories

1. As мейнтейнер библиотеки, I want таблицу переходов в одном модуле, so that правка статуса или счётчика делалась один раз.
2. As мейнтейнер библиотеки, I want `attempts` инкрементировался одной записью значения, so that не держать в голове два синхронных инкремента.
3. As мейнтейнер библиотеки, I want падение процесса между резервацией и результатом по-прежнему считало попытку, so that недоступный брокер не крутил запись бесконечно.
4. As мейнтейнер библиотеки, I want `Repo.Pg` не обнулял и не сбрасывал lifecycle-поля мимо структуры, so that SQL не был вторым источником истины.
5. As мейнтейнер библиотеки, I want `requeue/2` называл возврат в очередь, so that не путать его со снятием резервации.
6. As мейнтейнер библиотеки, I want `Repo.release/2` сохранил фехтование по токену, so that просроченная аренда не снималась чужим поллером.
7. As мейнтейнер библиотеки, I want разницу двух действий зафиксировать в `@doc` и тесте, so that следующий рефакторинг не «унифицировал» их обратно.
8. As мейнтейнер библиотеки, I want неразобранную строку по-прежнему помечать `:failed` через SQL, so that запись, которую нельзя декодировать, не блокировала очередь.
9. As мейнтейнер библиотеки, I want батчевую запись по группам сохранить, so that fail-stop по-прежнему давал три `UPDATE`, а не по одному на запись.
10. As мейнтейнер библиотеки, I want машину переходов проверять без базы, so that ошибка в статусе ловилась unit-тестом, а не приёмкой.
11. As мейнтейнер библиотеки, I want `Record.release/2` оставить помеченным `@deprecated`, so that чужой `Delivery` не сломался молча.
12. As разработчик приложения, I want поведение очереди не изменилось, so that обновление библиотеки не потребовало правок.
13. As разработчик приложения, I want схему `outbox` не менять, so that миграции не понадобились.
14. As разработчик приложения, I want свой `Outbox.Repo` продолжал работать, so that кастомный репозиторий не переписывался.
15. As разработчик приложения, I want метрики и логи повтора не изменились, so that алерты остались прежними.
16. As оператор приложения, I want запись после сбоя процесса по-прежнему считала попытку, so that `max_attempts` оставался реальным предохранителем.
17. As оператор приложения, I want `requeue_failed` по-прежнему сбрасывал счётчики, so that ручной перезапуск работал как документировано.

## Implementation Decisions

- **`Record` — владелец переходов.** Публичные функции: `reserve/4`, `mark_published/3`,
  `record_failure/4`, `requeue/2`. `requeue/2` — бывший `release/2`: `status: :new`,
  `locked_until: nil`, `lease_id` не трогает (токен нужен для фехтования последующих записей).
- **`Record.release/2` остаётся `@deprecated`-делегатом** на `requeue/2`. Причина: `Core.Outbox.Record`
  публичный, и чужой `Delivery`/`Poller` мог его звать; ломать без нужды не нужно. Внутренние вызовы
  переводятся на `requeue/2`.
- **Два действия не унифицируются.** `Repo.release/2` — снятие резервации: группирует по `lease_id` и
  фехтует `fence(lease)`, обнуляет `lease_id` и `locked_until`. `Record.requeue/2` — возврат записи в
  очередь после обработки: токен сохраняется, потому что строка ещё не записана и её результат будет
  принят только под прежней арендой. Инвариант — в `@doc` обеих функций и в тесте.
- **Публичный behaviour `Core.Outbox.Repo` не меняется.** Колбэки, их аргументы и исходы прежние;
  кастомный репозиторий потребителя продолжает работать.
- **`Repo.Pg` пишет значения структуры.** `mark_reserved!/2` вместо `inc: [attempts: 1]` пишет
  `attempts` из записи (запись уже посчитала его в `Record.reserve/4`); `result_group/1` продолжает
  писать поля из `Schema.to_model!/1`, без жёсткого `lease_id: nil` и без пересчёта `attempts`.
  `attempts` в строке растёт в момент резервации, поэтому падение до сохранения результата попытку
  учитывает.
- **Батчевая запись сохраняется.** `Repo.Pg` группирует записи по одинаковому набору значений
  (`status`, `attempts`, `errors`, `locked_until`, `lease_id`, `published_at`, `updated_at`) и пишет
  группу одним `UPDATE`. При fail-stop это по-прежнему три запроса: опубликованный префикс,
  проваленная запись, возвращённый хвост.
- **Неразобранная строка.** `mark_row_failed/3` остаётся SQL-инкрементом: структуры для записи нет
  (кодек не разобрал строку), поэтому передать вычисленное значение некому. Эта ветка — исключение из
  правила «пишем из структуры» и помечается комментарием.
- **`requeue_failed/2`** продолжает сбрасывать `attempts`/`errors`/`lease_id` одним запросом; это
  административная операция над записями в `:failed`, а не переход жизненного цикла.
- **Схема не меняется.** Миграция не нужна.
- **Тест-дублёр доставки** (`Core.Outbox.Test`, ADR-0082) не трогается: его политика повтора остаётся
  своей, спек не пытается свести её с `Record`.
- **CHANGELOG.** «Новое»: `Record.requeue/2`; `Record.release/2` — `@deprecated`. Ломающих изменений нет.
- **Порядок работ (тикеты).** 01 — `requeue/2`, `@deprecated`-делегат, документация двух действий и
  тест инварианта; 02 — `Repo.Pg` пишет `attempts` из записи, снятие второго инкремента, тест
  батчевой группировки.

## Testing Decisions

- Хороший тест проверяет наблюдаемое поведение: переходы структуры как чистые функции и эффект записи
  через репозиторий. Приватные имена, форма SQL и число `UPDATE` (кроме зафиксированного «три на
  fail-stop») не проверяются.
- **Шов машины переходов — `Core.Outbox.Record` без базы.** `record_test.exs` расширяется табличным
  тестом: `reserve` инкрементит `attempts` ровно один раз, `requeue` возвращает в `:new` и сохраняет
  токен, `record_failure` на границе `max_attempts` даёт `:failed`, ниже — `:new`, `mark_published`
  чистит аренду. Образец — существующие тесты `Record`.
- **Шов репозитория — `Core.Outbox.Repo` через `Repo.Pg` на `Core.DataCase`:** резервация пишет
  `attempts` в строку, `save_results` возвращает те же значения, `release` фехтует по токену и обнуляет
  `lease_id`, `requeue_failed` сбрасывает счётчики. Образец — `repo/pg_test.exs`.
- **Регрессия fail-stop** проверяется на существующей цепочке доставки через `Core.Outbox.Test`
  (`drain`, реактор): исходы `published`/`retry`/`failed` и число записей не меняются.
- **Отсутствие второго инкремента** проверяется не чтением SQL, а значением `attempts` в строке после
  резервации и после сохранения результата: одна попытка — один прирост.

## Out of Scope

- Порядок доставки, DLQ и lifecycle записей `Mq.Dlq` — отдельная спека (`mq-lease-reader`).
- Аренда outbox как общий порт `Core.Mq.Lease`: outbox остаётся на своих часах и `LeaseID`.
- Политика повтора и мёртвых писем в `Core.Outbox.Test` (ADR-0082).
- Схема `outbox`, миграции, очистка `published`, метрики `Outbox.PromEx`.
- `Core.Es.Outbox` (запись события в outbox в транзакции команды) — не трогается.

## Further Notes

- Мотивация: правило свода «запись outbox — одна строка с lifecycle» соблюдается, но владелец переходов
  размыт между структурой и репозиторием; волна делает владельца явным.
- Осторожно: `attempts` в строке обязан расти в момент резервации, иначе падение процесса до
  `save_results` не учтёт попытку и `max_attempts` перестанет ограничивать недоступный брокер.
  Это главный риск рефакторинга и главный тест.
