# Общий конструктор полей и рекурсивные ПДн-места

Пересмотр языка спеки полей и механизма персональных данных: единый конструктор модулей по
декларации полей, реестр метаданных, типы чтения/записи, `Core.Union` и рекурсивное шифрование
ПДн на любой глубине. Термины — `CONTEXT.md` («Спека полей», «Структура по полям»,
«Codec-плагин по полям», «Семейство (union)», «ПДн-значение», «Субъект данных», «Уничтоженное
ПДн-значение»); новые термины «ПДн-место», «тип чтения», «тип записи» вводятся этой спекой.
Нормы и решения, которые пересматриваются: `docs/rules/11-domain.md`, `docs/rules/23-personal-data.md`,
ADR-0056, ADR-0073, ADR-0078, ADR-0090, ADR-0092.

## Problem Statement

Разработчик приложения не может объявить ПДн у поля вложенной структуры. Единица шифротекста
сейчас — значение поля нагрузки верхнего уровня целиком, поэтому ПДн внутри вложенной сущности
приходится выносить в отдельное параллельное поле и шифровать его целиком. Это ломает доменную
модель: открытая часть и ПДн-часть одного объекта живут в двух списках, склеиваемых по индексу,
а после уничтожения ключа теряется вся открытая структура, а не только ПДн.

Одновременно язык спеки полей разбирается и порождается в нескольких builder’ах независимо:
структура, Codec-плагин, нагрузка события, View и подписи каждый заново обходят декларацию.
`personal: true` у Prim внутри вложенной сущности сборкой не проверяется и молча уходит в
историю открытым. Отдельный флаг `destroyable:` дублирует то, что уже следует из ПДн, и позволяет
рассогласовать «значение шифруется» и «его тип допускает уничтоженное значение». Декларация
структуры и её Codec-плагина объявляются дважды, а семейство вариантов (`union:`) живёт в
Codec-плагине, а не в модуле семейства, и не поддерживает Prim-варианты.

## Solution

Один общий конструктор разбирает декларацию полей в единый IR и порождает struct, типы и
Codec через роли-потребители. Метаданные поля (`optional`, `wire`, `default`, `personal`,
`subject`) обрабатываются централизованным реестром. ПДн объявляется у Prim или у поля и
рекурсивно находится обходчиком декларации; шифрование и уничтожение работают на каждом
найденном ПДн-месте, а не только на поле верхнего уровня. Тип чтения включает уничтоженное
значение на ПДн-местах, тип записи — нет; отдельный флаг `destroyable:` удаляется. Семейство
вариантов объявляется в модуле семейства (`Core.Union`) и поддерживает варианты любого вида.
Одна декларация типа служит источником и структуры, и Codec, и ПДн-метаданных.

## User Stories

1. As разработчик приложения, I want объявить `personal: true` у поля вложенной структуры, so that ПДн шифровалось на месте, без выноса в параллельное поле.
2. As разработчик приложения, I want `personal: true` у Prim автоматически делал каждое место с этим Prim ПДн-местом, so that не размечать каждое поле вручную.
3. As разработчик приложения, I want `personal: true` у составного поля шифровал всё его значение, so that opaque-сущность с ПДн защищалась целиком.
4. As разработчик приложения, I want открытая часть вложенного объекта оставалась читаемой после уничтожения ключа, so that маршрут, статусы и попытки переживали уничтожение ПДн.
5. As разработчик приложения, I want `subject:` только выбирал субъекта, а не переключал единицу шифрования, so that семантика была однозначной.
6. As разработчик приложения, I want субъект по умолчанию `:aggregate_id`, so that типичный случай не требовал разметки субъекта.
7. As разработчик приложения, I want `subject: {:payload, field}` ссылался на поле нагрузки верхнего уровня, so that ПДн другого лица шифровалось под его ключом.
8. As разработчик приложения, I want локальный `subject: :field` ссылался на соседнее поле той же структуры, so that элементы одного списка могли иметь разных субъектов.
9. As разработчик приложения, I want `destroyable:` исчез, so that не было второго флага, рассогласованного с ПДн.
10. As разработчик приложения, I want тип чтения автоматически включал `%Destroyed{}` на ПДн-местах, so that свёртка после уничтожения ключа была типизирована.
11. As разработчик приложения, I want тип записи не допускал `%Destroyed{}`, so that команда и конструктор не принимали уничтоженное значение.
12. As разработчик приложения, I want одна декларация типа порождала и struct, и Codec, so that не объявлять поля дважды.
13. As разработчик приложения, I want `Core.Union` объявлял варианты в модуле семейства, so that реестр вариантов жил рядом с семейством.
14. As разработчик приложения, I want `union:` поддерживал Prim-варианты, so that полиморфный получатель (телефон/email) выражался одним полем.
15. As разработчик приложения, I want `union:` поддерживал варианты с ручным Codec, so that нестандартная wire-форма варианта не мешала шифрованию поля целиком.
16. As разработчик приложения, I want `Core.Codec.Plugin` регистрировал типы, а не дублировал поля, so that плагин читал общую декларацию.
17. As разработчик приложения, I want `default:` был одним типизированным значением, so that смысл не зависел от того, кто его читает.
18. As разработчик приложения, I want Codec подставлял `default:` при отсутствующем ключе, so that старые строки читались с новым полем.
19. As разработчик приложения, I want явный `null` не заменялся `default:`, so that отсутствие и нулевое значение различались.
20. As разработчик приложения, I want непрозрачный тип в нагрузке требовал `personal: true/false`, so that ПДн не уходило открытым молча.
21. As разработчик приложения, I want `set:` с ПДн-элементами автоматически шифровался целиком, so that уничтоженные элементы не схлопывались в `MapSet`.
22. As разработчик приложения, I want `map:` с ПДн-ключом автоматически шифровался целиком, so that ключ не оставался открытым.
23. As разработчик приложения, I want `list:` и значения `map:` шифровались поэлементно, so that открытая структура коллекции сохранялась.
24. As разработчик приложения, I want `Payload.new/N` и guard `dump` отвергали `%Destroyed{}` на любой глубине, so that уничтоженное значение не записывалось в новое событие.
25. As разработчик приложения, I want непустое ПДн при `nil` субъекта отвергалось на записи, so that значение не оставалось без ключа.
26. As разработчик приложения, I want `Inspect` скрывал ПДн-место, а не весь содержащий его список, so that открытая часть была видна в диффе и логах.
27. As разработчик приложения, I want ошибка загрузки под ПДн-местом редактировала `detail` и cause-цепочку, so that сырое ПДн не попадало в текст ошибки.
28. As разработчик приложения, I want `Core.View` не получал `%Destroyed{}` автоматически, so that read-модель сама выбирала представление уничтоженного значения.
29. As автор проекции, I want проекция получала `%Destroyed{}` на вложенных ПДн-местах, so that явно очищать или маскировать ПДн в read-модели.
30. As автор проекции, I want `ProjectionCase` прогонял уничтоженный вариант по всем ПДн-местам, so that забытая обработка уничтоженного значения ловилась тестом.
31. As разработчик приложения, I want страница событий отдавала `{"$destroyed": true}` на вложенном месте, so that клиент видел признак уничтожения по пути.
32. As разработчик приложения, I want подписи и OpenAPI-схема понимали вложенные уничтоженные места, so that сведения события были полными.
33. As разработчик приложения, I want golden-фикстура уничтоженного варианта ставила `{"$pd": null}` на каждом ПДн-месте, so that формат был зафиксирован рекурсивно.
34. As разработчик приложения, I want `EventCompatCase` проверял отсутствие personal-значений вне ПДн-мест, so that открытая утечка ловилась фикстурой.
35. As разработчик приложения, I want `Core.Es.ValueChanged` применял ПДн-план к `old_value` и `new_value`, so that смена значения с ПДн шифровалась в обеих позициях.
36. As разработчик приложения, I want state-stored строка могла хранить `%Destroyed{}` как `{"$pd": null}`, so that перезапуск не превращал уничтоженное значение в `nil`.
37. As разработчик приложения, I want живое ПДн в state-stored строке оставалось открытым, so that mutable-строка стиралась `update`/`delete`, а не шифровалась.
38. As оператор приложения, I want снапшот оставался одним шифротекстом под `:aggregate_id`, so that после уничтожения ключа он просто не использовался.
39. As оператор приложения, I want открытые строки до разметки продолжали читаться, so that история не становилась нечитаемой.
40. As оператор приложения, I want смена формы поля шла через новый тег и апкаст, so that записанная история оставалась читаемой.
41. As подписчик того же приложения, I want тело сообщения разбиралось тем же рекурсивным шагом расшифровки, so that вложенные `$pd` открывались до `load`.
42. As мейнтейнер библиотеки, I want один IR и реестр метаданных, so that новый ключ поля добавлялся одним обработчиком.
43. As мейнтейнер библиотеки, I want единая интроспекция декларации, so that Codec, Payload, Labels и обходчик ПДн не знали, каким `use` собран модуль.
44. As мейнтейнер библиотеки, I want ПДн-план события как интроспекцию, so that dump/load, Wire, case-модули и снапшоты читали один источник.
45. As мейнтейнер библиотеки, I want тип записи рекурсивно ссылался на `write_t()` вложенных типов, so that узость команды сохранялась на любой глубине.
46. As мейнтейнер библиотеки, I want AAD включал путь от корня нагрузки, so that шифротекст был привязан к вложенному месту.
47. As мейнтейнер библиотеки, I want batch-шифрование и batch-расшифровку на всех уровнях, so that число вызовов порта не росло с глубиной.
48. As мейнтейнер библиотеки, I want `consumer-check` ловил сужение типов, so that опечатка в поле давала предупреждение, а не неверное значение.
49. As мейнтейнер библиотеки, I want `CompileError`-тексты оставались частью контракта, so that диагностика сборки не ухудшалась.
50. As мейнтейнер библиотеки, I want внутренний IR не попадал в публичную документацию, so that потребитель не опирался на него.

## Implementation Decisions

- **Общий конструктор и IR.** Декларация полей нормализуется один раз в единый IR. Роли
  (`Core.Struct`, `Core.Es.Event.Payload`, `Core.Codec.Plugin`, `Core.Union`, `Core.View`,
  `Core.Labels`) — потребители IR, а не независимые парсеры. Семантика по ролям остаётся разной
  (View — голые значения и другой конструктор), общей является механика разбора, обхода и
  проекций, а не универсальная семантика всех хостов.
- **Реестр метаданных.** Каждый ключ поля обрабатывается своим модулем-обработчиком в Core.
  Обработчик объявляет ключ, допустимые роли, нормализацию значения и вклад в тип чтения/записи,
  guard, `Inspect` и ПДн-план. Неизвестный ключ — `CompileError`. Публичная регистрация
  обработчиков потребителя не вводится.
- **Матрица метаданных по ролям.** `optional` — `| nil` и guard; `wire` — wire-ключ (допустим в
  структуре, используется Codec); `default` — типизированное значение поля, Codec подставляет при
  отсутствующем ключе, в нагрузке события запрещён; `personal` — ПДн-место и тип чтения;
  `subject` — метаданные субъекта для событий, Codec игнорирует, в нагрузке резолвится;
  `loadable: false` — dump-only. `Core.View` не принимает `personal:`/`subject:`.
- **`default:` — одно типизированное значение.** Struct использует его как значение поля; Codec
  при отсутствующем wire-ключе подставляет уже типизированное значение без промежуточного
  dump/load. Явный `null` `default:` не заменяет: у `optional: true` это `nil`, у обязательного
  поля — ошибка загрузки. `optional: true, default: nil` допустимо. Иной fallback для старого
  wire — апкаст или ручной Codec.
- **Типы чтения и записи.** Каждая общая структура порождает `t()` (чтение, включает
  `%Destroyed{}` на ПДн-местах) и `write_t()` (запись, без `%Destroyed{}`). Если ПДн-мест нет,
  типы совпадают. Команда использует узкий тип записи; `Payload.new/N` и `draft/1` принимают
  проекцию записи рекурсивно. Форма типа (из прототипа решения):

  ```elixir
  @type t :: %Step{
          recipient: Recipient.t() | Core.Es.Personal.Destroyed.t(),
          content: Content.t() | Core.Es.Personal.Destroyed.t()
          # открытые поля
        }
  @type write_t :: %Step{recipient: Recipient.t(), content: Content.t()}
  ```

- **Рекурсивная проекция записи.** Поле `entity:` в типе записи ссылается на `Mod.write_t()`,
  `union:` — на объединение `Variant.write_t()`, `list:`/`map:` проецируются поэлементно/по
  значению. Тип чтения ссылается на `Mod.t()`.
- **`Core.Union`.** Семейство объявляет состав и адрес вариантов в модуле семейства, порождает
  `__core_variants__/0`, `types/0`, `variant/1` и проверку уникальности адресов. Адрес — прежние
  три формы (тег; тег + дискриминатор; адрес среди полей). Вариант может быть Prim,
  декларативной структурой или типом с ручным Codec; полей от варианта не требуется.
- **`Core.Codec.Plugin` после редизайна.** Регистрирует типы (`types:`), читает `__core_fields__`
  для декларативных типов, требует ручные `dump/2`/`load/3` для типов без декларации.
  `fields:`/`variants:` как способ объявить поля/адреса удаляются. Смешанный плагин допустим.
  `loadable: false` и запрет ручной клаузы на декларативный тип сохраняются. Redump-спека
  выводится из общей декларации.
- **Единая интроспекция.** `__core_fields__/0` (поля и метаданные) и `__core_variants__/0`
  (только `Core.Union`) заменяют ролевые атрибуты и ручную диспетчеризацию. Codec, Payload,
  Labels, проекции и ПДн-обходчик читают только их.
- **ПДн-место и обход.** `personal: true` у Prim делает ПДн каждое место с этим Prim; у поля —
  всё значение места и останавливает спуск. `subject:` задаёт субъект поддереву, но сам ПДн не
  создаёт; ближайший перекрывает внешний; корневой default — `:aggregate_id`. `subject:` в
  поддереве без ПДн и переопределение `subject:` под `personal: true` — `CompileError`.
- **Адреса субъекта.** `:aggregate_id`, `{:payload, field}` (поле нагрузки верхнего уровня),
  локальное имя поля той же структуры. Субъект — UUID-Prim или `Prim.Compose` над ним, открытый
  в wire; поле субъекта само не ПДн. Непустое ПДн при `nil` субъекта — отказ записи; обязательное
  ПДн при необязательном субъекте — `CompileError`.
- **Непрозрачные типы.** Тип с общей декларацией обходится рекурсивно; поле с `personal: true`
  не обходится; непрозрачный тип без `personal: true` требует явного `personal: false`.
  `personal: false` не понижает `personal: true` у известных Prim/полей. `type: :map` в нагрузке
  требует `personal: true/false`.
- **Эскалация границы шифрования.** ПДн-лист в `set:` или в ключе `map:` поднимает границу до
  контейнера: шифруется весь `set:`/`map:`, `%Destroyed{}` в типе чтения — на месте контейнера.
  `list:` и значения `map:` шифруются поэлементно.
- **ПДн-план события.** `Core.Es.Event.Codec` порождает `__es_personal__/0` вместо
  `__es_subjects__/0`: план по модулям событий с путями и субъектами. План используют dump/load,
  `Personal.Wire`, `EventCompatCase`, `ProjectionCase`, проверка снапшотов и генерация
  уничтоженных фикстур. Форма (из прототипа решения):

  ```elixir
  %{Event.Created => [
      %{path: [:metadata], subject: :aggregate_id},
      %{path: [:steps, :each, :recipient], subject: :aggregate_id},
      %{path: [:steps, :each, :content], subject: :aggregate_id}
    ]}
  ```

- **Маркеры и AAD на любой глубине.** `dump` общего Codec оставляет значения открытыми; обходчик
  заменяет каждое ПДн-место маркером с субъектом и wire-значением. Писатели `es_events`/outbox
  рекурсивно собирают маркеры и шифруют одним batch-вызовом. AAD — `event_id` плюс путь от корня
  `payload` (wire-ключи, индексы `list:`, ключи `map:`). Чтение рекурсивно открывает все `$pd`
  одним batch-вызовом до апкаста.
- **Загрузка уничтоженного значения.** `{"$pd": nil}` на ПДн-месте → `%Destroyed{}` до разбора
  вида/варианта; вне ПДн-места — `:invalid_value`; `{"$pd": "<строка>"}` в любом месте —
  `:sealed_personal_value`; `null` необязательного ПДн-поля — `nil`. Для `union:`-поля с
  `personal: true` уничтоженное значение возвращается до выбора варианта, ручной Codec не
  вызывается.
- **Runtime-защита записи.** `Payload.new/N`, `draft/1` и guard `dump` отвергают `%Destroyed{}`
  на любом месте записи и непустое ПДн при `nil` субъекта, по ПДн-плану. `Core.Struct` остаётся
  без runtime-конструктора; защиту дают тип записи и роли-потребители.
- **`Inspect` и редакция ошибок.** `Core.Struct` и `Payload` генерируют `Inspect`, скрывающий
  каждое ПДн-место, а не весь содержащий его список; составное поле с `personal: true`
  скрывается целиком. Ошибка загрузки под ПДн-местом редактирует `detail` и cause-цепочку,
  сохраняя путь ошибки (`field`, `index`, wire-ключ).
- **Read-путь.** `Core.View` не расширяет типы `%Destroyed{}`; проекция преобразует его явно.
  `Core.Web.Event` и `Labels.Details` понимают вложенные уничтоженные места: `{"$destroyed": true}`
  по пути, деталь `kind: :destroyed`, OpenAPI-схема ПДн-места допускает обычное значение или
  признак уничтожения.
- **`Core.Es.ValueChanged`.** `old_value`/`new_value` строятся из одной декларации типа; ПДн-план
  применяется к обеим позициям независимо, субъект по умолчанию `:aggregate_id`.
- **State-stored и снапшоты.** Живое ПДн в mutable state-stored строке остаётся открытым (стирается
  `update`/`delete`); `%Destroyed{}` в строке допустим как `{"$pd": null}` и загружается без
  обращения к хранилищу ключей. Новый event с уже уничтоженным ПДн запрещён. Снапшот остаётся
  одним шифротекстом под `:aggregate_id`; после уничтожения ключа не используется, состояние
  восстанавливается полной свёрткой. Рекурсивное шифрование Erlang-term снапшота не делается.
- **Совместимость истории.** Открытые строки до разметки читаются (загрузчик принимает открытое
  значение на ПДн-месте). Смена формы поля (верхнеуровневый `subject:` → рекурсивные места) идёт
  через новый тег и апкаст; апкастер получает расшифрованный wire и переносит уничтоженное целое
  как `{"$pd": null}` на новые места без строковых операций. Инструмента переписывания истории нет.
- **Порядок работ.** (1) общий конструктор, IR, реестр, `t`/`write_t`, `Core.Union`, новый
  `Core.Codec.Plugin`, интроспекция; (2) ПДн-план, маркеры, `Personal.Wire`, загрузка
  `%Destroyed{}`, `Payload`/`ValueChanged`/`Event.Codec`; (3) `Core.Web.Event`, `Labels.Details`,
  case-модули, уничтоженные фикстуры; (4) синтетические фикстуры/тесты в Core; (5) ADR, своды,
  `CONTEXT.md`, CHANGELOG.

## Testing Decisions

- Хороший тест проверяет объявление и наблюдаемое поведение: `new/N` возвращает ожидаемое
  значение, `dump`/`load` через фасад дают ожидаемую wire-форму, неверная спека даёт
  `CompileError` с ожидаемым текстом, уничтожение ключа даёт `%Destroyed{}` на ПДн-местах.
  Внутренние имена IR и форма ПДн-плана как публичный контракт не проверяются.
- **Основной (высший) шов — запись/чтение события через репозиторий и фасад кодека.**
  Существующий набор личных тестов событий (`$pd` в `es_events`/outbox, открытое и уничтоженное
  значение на путях чтения) расширяется на вложенные ПДн-места: декларация → `dump` → маркеры на
  глубине → `seal` → строка → `open` → `load` → `%Destroyed{}` только на ПДн-полях, открытая
  часть читается. Покрывает `Personal.Wire` с путями AAD и загрузку уничтоженного значения до
  разбора варианта. Prior art — существующие personal-тесты событий и проекций.
- **Швы объявлений builder’ов.** `use Core.Struct` / `Core.Union` / `Core.Codec.Plugin` /
  `Core.Es.Event.Payload`: объявления, `CompileError`, `t`/`write_t`, `new/N`, `Inspect`.
  Prior art — тесты структуры по полям и нагрузки события.
- **Round-trip через фасад** по всем видам, включая `union:` с Prim-вариантами и вариантами с
  ручным Codec. Prior art — codec round-trip тесты.
- **`Core.Es.EventCompatCase` и `Core.Es.ProjectionCase`** — golden-фикстуры и уничтоженный
  вариант по рекурсивному ПДн-плану; проверка отсутствия personal-значений вне ПДн-мест.
- **`make consumer-check`** (`fixtures/consumer`) — храповик вывода типов, маркеры `# expect:`;
  синтетический сценарий «шаги маршрута с получателем и контентом» как фикстура Core, без
  адаптации конкретного потребителя.
- Новых публичных швов не вводится: ПДн-план и интроспекция проверяются через поведение.

## Out of Scope

- Адаптация конкретных приложений-потребителей (отдельная задача; пример используется только как
  синтетический сценарий фикстур Core).
- Шифрование живого ПДн в mutable state-stored строках.
- Публичные пользовательские обработчики метаданных поля.
- Рекурсивное шифрование Erlang-term снапшотов и раздельные снапшоты по субъектам.
- Переписывание уже записанной истории.
- Унификация runtime-конструкторов значений (`new`) между ролями; роли сохраняют свои контракты
  (`%Struct{}`, позиционный `Payload.new/N`, keyword `View.new/1`).
- Объединение обходов подписей в один walker сверх того, что нужно для рекурсивных ПДн-мест.

## Further Notes

- Спека явно пересматривает ADR-0056 (разделение struct/Codec и load литералом сохраняется, но
  декларация становится общей), ADR-0073/ADR-0078 (единица шифротекста, адрес AAD, проверки
  фикстур), ADR-0090 (запрет `wire:`/`subject:` в структуре, два смысла `default:`), ADR-0092
  (`destroyable:` как отдельная разметка). Требуется новый ADR и обновление `CONTEXT.md`
  («ПДн-место», «тип чтения», «тип записи», `Core.Union`; переопределение `destroyable:`).
- Риск высокий: redesign затрагивает сборку всех структур/Codec/нагрузок у потребителей, поэтому
  `make consumer-check`, `make compile-no-optional` и boundary-check обязательны;
  `CompileError`-тексты считаются частью контракта.
- При конфликте «общий механизм» и «семантика роли» побеждает семантика роли: общий конструктор
  даёт разбор/обход/проекции, но не универсальное значение `default:`/`optional:` для всех хостов.
- CHANGELOG: ломающие изменения DSL/API и новая семантика ПДн; миграция потребителей через новые
  теги/апкасты описывается обезличенно.
