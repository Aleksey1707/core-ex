# Заметки по тикету 02 (реестр семейства)

## Что осталось общего у сведений и словаря (для тикета 04)

Обход узлов уже общий: и `Core.Labels.Details`, и `Core.Labels.Refs` начинают с
`Core.Labels.Walk.values/2` (поля по объявлению, стороны изменения) и ходят по `entry`-узлам
(`data: :leaf | {:group, _} | {:list, _} | {:set, _} | {:map, _} | {:change, _, _}`). Различается
**интерпретация узла**:

- `Details` держит две таблицы: `shape/1` (вид спеки → `%{kind: …}`) и `leaf_value/2` (значение
  листа: `:enum` → подпись, `:text` → текст функции, `:prim` → правило Prim). Плюс
  `prim_shape/1` (через `Core.Labels.Kind`) — вот здесь и вызывается правило вида Prim.
- `Refs` держит своё правило `prim/3` (`Core.Labels.Kind.of/1`, `Core.Labels.Text.find/1`,
  `Core.Labels.ID` с резолвером, `Core.Labels.Kind.scalars/0`) и спуск по значению (`visit/2`,
  `raw/2`), не по `kind` сведения.

То есть новый вид значения сейчас оплачивается правками в `Walk.data/3` (общий обход) и в двух
таблицах `Details` (`shape/1` + `leaf_value/2`), а в `Refs` — только если вид несёт id. Это и есть
цель тикета 04: один узел описания (подпись + вид + значение + ссылки), `Details` — его проекция,
`Refs` — сбор ссылок с описанных узлов.

## Асимметрия, которую нельзя потерять в 04

- `Refs.visit/2` обходит **struct без объявления полей** целиком (`raw/2` по `Map.values`), а
  `Details.struct_details/1` на нём падает: сведения необъявленного struct'а — ошибка программиста.
  Словарь шире сведений ровно на этот защитный путь плюс автор события (`by`), который в сведения
  не входит.
- Подмена спеки варианта семейства (`Walk.variant_spec/2`, ADR-0098) остаётся в обходе значений, а
  не в описании: спека листа варианта — модуль варианта, не семейство.
- Канонический порядок `set:` (по `Core.Prim.unwrap/1` / `compare/2`) и пар словаря — в
  `Details.sorted/1` / `sorted_pairs/1`; в `Refs` порядка нет (там `MapSet`). В 04 порядок должен
  жить в описании, иначе словарь начнёт зависеть от проекции.

## Швы

- Публичный шов остаётся прежним: `Core.Labels.Details.build/1` и `Core.Labels.Refs.get/2`; тесты
  сведений и словаря (`test/core/labels/details_test.exs`, `refs_test.exs`) — контракт сохранности
  поведения, ожидания в них не правятся.
- Ратчет полноты стоит в `Details` (храповик `shape/1`) и в `Walk` (`data/3`); при появлении модуля
  описания храповик «вид спеки → вид значения» переезжает туда, в `Walk` остаётся храповик обхода.

## Что сделано в 02

- `Walk.visit/5` для `{:union, family}`: место `{:family, owner, field, family}` — на каждое видимое
  поле; состав — сначала `Core.Field.union_variants/1` (реестр `__core_variants__/0`), при пустом
  реестре — `__codec_types__/0` плагина семейства из модулей приложения, иначе только место.
- `CompletenessCase.check_variants/1`: `unknown_family` ⟺ нет реестра И нет плагина среди модулей;
  `diverged` — по реестру каждого достигнутого места. Проба «плагин → семейство → реестр»
  удалена.
- `Core.Field.union_write_type/1`: мёртвая ветка `types/0` удалена; семейство без реестра —
  `struct()`. `Union.variant/1` и `types/0` не трогались.
- Фикстуры: `test/support/labels_family_fixture.ex` (смешанный плагин `Mark.Codec`, вариант
  `Foreign` другого семейства, семейство без реестра `Legacy` с плагином, неизвестное `Loose`);
  шов — `test/core/labels/completeness_case_family_test.exs`.

## Замечания на будущее

- `diverged` (сверка `Fields.specs/1` с `__core_fields__/0`) у `:domain`-варианта сейчас недостижим:
  у декларативного хоста `__label_specs__` выводится из той же декларации (`pairs/1` + `grammar_spec/1`),
  а `fields:` рядом с декларацией — `CompileError`. Расхождение может появиться только у варианта с
  ручной спекой; если тикет 04 тронет `Fields.specs/1`, эту сверку стоит либо оживить тестом, либо
  снять осознанно (отдельным решением, не в 02).
- `Core.Labels.Fields.paths/1` (`union:` даёт только подпись поля) остался прежним: реестр в обходе
  подписей по путям не читается — это отдельный вопрос, если понадобятся подписи вариантов в
  путях.
