# Заметки по тикету 01 (виды подписей и тип записи View)

## Что выяснилось про обход и швы

- Обход значений (`Core.Labels.Walk`): `values/2` → `fields/2` (или `change/3`) → `node/3`.
  `node/3` подменяет спеку варианта семейства (`variant_spec/2`) и раскрывает значение через
  `data/3` — по клаузе на вид `{:text, _}`, `{:prim, _}`, `{:enum, _}`, `{:type, :map}`,
  `{:type, _}`, `{kind, _}` из `Field.group_kinds()` (`entity` / `union`), `{:list, _}`,
  `{:set, _}`, `{:map, _, _}`. Спека подписей шире плагина только на `text:`, поэтому полный
  набор видов — `Field.Spec.kinds(:labels) ++ [:text]`.
- Храповик ставится одной строкой в конце модуля (образец — `Core.Field: spec_type`,
  `Core.Codec.Plugin.Redump`, `Core.View.Field`):
  `Core.Field.Spec.check_kinds!(:labels, <список литералом>, [:text], "<Модуль>")`. Список видов
  обязан быть литералом, а не `Field.kinds(:labels)`: иначе новый вид в грамматике молча
  расширит ожидание и ратчет не сработает. Проверено вручную: удалённый из списка `:map` валит
  сборку `Core.Labels.Walk` / `Core.Labels.Details`, добавленный в `@base_kinds` вид — сборку
  `Core.Field`.
- Сведения (`Core.Labels.Details`): вид значения даёт `shape/1` (плюс `shape_of/2` для `nil` и
  свободной map'ы) — тот же набор видов, что у обхода значений. Ратчет там же.

## Ключевой факт про View (важно для 02/04)

- `Core.View` до тикета 01 **не** ставил атрибут `@core_fields`, только функцию
  `__core_fields__/0`. Поэтому `Core.Field.introspect/1` во время тела модуля View возвращал
  `nil`, и `Core.Labels.Fields.host/1` считал View ручным struct'ом: `labels:` без `fields:`
  падал «не нагрузка», а единственным способом подписать View был `fields:` (ручной путь).
  Путь интроспекции для View не существовал, поэтому и валидации видов там было нечего делать.
- Тикет добавил `@core_fields` в `Core.View` — после вложенного `Codec`. Порядок существен:
  плагин кодека представления (`types: [View]`) при компиляции читает
  `Core.Field.introspect/1`; если атрибут уже стоит, тип считается декларативным, плагин
  порождает свои `dump/2`, а дампер View (`Core.View.Dumper`) даёт ручную клаузу — сборка
  падает `ручные клаузы never match`. Ставить атрибут выше `Codec` нельзя.
- Шов проверки видов — `__after_compile__` (`ensure_kinds!/1`), рядом с полнотой: там `host/1`
  уже отдаёт `{:declared, fields}`, а `specs/1` уже выкидывает `:hidden`. Отказ поднимается
  через `Core.Field.kind_key!/3` с `:labels`, поэтому текст совпадает с грамматикой ручного
  пути: «вид view: недопустим в хосте «подписи»», с префиксом
  `Labels.Fields <Хост>: поле <поле>:`.
- Виды вне allowlist рекурсивно ищутся по `list:` / `set:` / `map:` (значение и ключ):
  сведения падают и на вложенном `list: [view: …]`.

## Для тикета 02 (реестр семейства)

- Обход объявлений: `Walk.declarations/1` → `families/1` (по `__codec_union__/0` плагинов) →
  `visit/5`, место семейства — `{:family, owner, field, family}`; `completeness` читает места.
  Реестр уже читается протоколом `Core.Field.union_variants/1` (`__core_variants__/0`) — ребро
  `Core.Field → Core.Union` не нужно и запрещено.
- Ратчет `check_kinds!` в `Walk`/`Details` на виды значения не мешает: состав семейства — не
  вид.
- Смешанный плагин: `families/1` сегодня группирует плагины по `__codec_union__/0`, а
  `visit(owner, field, {:union, family})` берёт всех провайдеров; атрибуция пробела (чужие
  декларативные типы как варианты) — ровно это место.
- Ручной путь подписей (`fields:`) по-прежнему валидируется грамматикой `:labels`; если 02
  меняет состав мест, вид спеки не трогается.

## Для тикета 04 (одно описание значения)

- Ратчет, поставленный в `Details` (`@shape_kinds` + `check_kinds!`), — временный хозяин
  полноты «вид → вид значения». Когда появится модуль описания, `check_kinds!` переезжает туда
  (и в `Walk` остаётся ратчет обхода значений: `variant_spec/2` и канонический порядок
  `set:` / `map:` — по спеке остаются в обходе).
- `Details.shape/1` — таблица «вид спеки → `%{kind: …}`», `Details.leaf_value/2` — правило
  значения (Prim-вид вызывается ровно здесь); словарь ссылок идёт по `Refs`, а не по `shape`.
- `Core.View` ставит `@core_fields` после `Codec`: любой общий «протокол установки
  декларации» (кандидат №3) обязан сохранить этот порядок, иначе сборка View сломается
  `never match`.
