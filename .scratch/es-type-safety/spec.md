# Типобезопасность потребителя `Core.Es`: ошибки ловит компилятор

Type: spec
Status: ready-for-agent

## Problem Statement

Автор приложения на `Core.Es` пишет агрегат, команды, события, кодек, репозиторий, процесс, проекцию и usecase'ы, а
сборка идёт с `mix compile --warnings-as-errors`. Он рассчитывает, что Elixir 1.20 с выводом типов поймает ошибку при
сборке. Большую часть ошибок в вызовах `Core.Es` компилятор при этом молча пропускает, и они падают только в runtime
(коды сценариев — `.scratch/es-type-safety/research/02-core-es-blind-spots.md`):

- **Команда не того агрегата.** `Account.execute(state, %Order.Cmd.Place{})` и команда без clause в `decide`
  собираются без предупреждений, падает `FunctionClauseError` внутри транзакции (A1, A2).
- **Неверный результат `decide`.** Событие не из кодека агрегата, нагрузка чужого события, голый модуль события,
  которому нужна нагрузка, — компилятор молчит, хотя выведенная сигнатура `decide` знает результат точно (B1–B3).
- **Неполнота.** Нет clause `evolve/2` или `project/1` для объявленного события, нет `dump_payload` / `load_payload`
  для события с нагрузкой, `load_payload` вернул нагрузку чужого события (C1, G1, H1, H2). `evolve` и `project/1`
  проверяют только `EventCompatCase` и `ProjectionCase` при прогоне — и только если потребитель их подключил.
- **Опечатка в поле.** Поле состояния из `execute` и `get`, события из `InCodec.load`, нагрузки при
  `%Event{payload: p}`, команды при `%mod{} = cmd when mod in @mutations` — `KeyError` в runtime (A5a, E5, H3, C2a,
  G3a, J1).
- **Чужой ID и чужой агрегат.** ID из `Order.ID.new()` проходит в `Account.Repo.get` и `Event.new`: `new/0`,
  `new!/1`, `now!/0` возвращают `dynamic()` (D2b, E1b, F1b). `Core.Es.Projection.await/4` и
  `Core.Es.Store.page_stream/5` с чужим агрегатом молчат, а `page_stream` отдаёт пустую страницу (G4, X3).
- **Результаты без формы.** Невозможная clause по результату `Process.execute`, `append`, `InCodec.load` не
  сообщается (F5, E8, H3c).

Причина одна: библиотека зовёт код потребителя через модуль-переменную, головы генерируемых функций построены на
`is_struct/2`, а результат из библиотеки — `dynamic()`. `@spec` и `@callback` компилятор не читает
(`.scratch/es-type-safety/research/01-elixir-1-20-type-system.md`). Кроме того, `is/2` и `is_opt/2` из `Core.Guard`
дают открытую map, и опечатка в поле значения, суженного ими, тоже молчит.

Мейнтейнер библиотеки при этом не видит регресса: новая catch-all clause или обёртка внутри `Core` молча возвращает
`dynamic()`, и все тесты остаются зелёными.

## Solution

Ошибки потребителя ловит вывод типов Elixir при сборке (ADR-0014), норма о чтении полей держится линтером (ADR-0015):

- функции, которые `Core` генерирует у потребителя, становятся границей типов: голова принимает только свой struct,
  результат библиотеки сужается паттерном — у вызывающего известны состояние агрегата, форма результата и ошибки;
- `Agg.execute/2` зовёт `decide/2` в модуле агрегата, поэтому домен команды выводится из clauses `decide`;
- элемент результата `decide` — черновик события — строится генерируемым конструктором кодека
  `Event.Codec.draft(Event.X, payload)` / `draft(Event.X)`, и неверная пара событие–нагрузка ловится при сборке;
- полноту `evolve/2`, `project/1`, `dump_payload/2` / `load_payload/3` проверяют генерируемые функции-проверки:
  предупреждение указывает на строку `use` и в имени говорит, что нарушено;
- `await` и `page_stream` генерируются у модуля потребителя с ID его агрегата; фасад Codec сужает `load/2`;
- поле читается только у значения, суженного паттерном, — это проверяет новый линтер, который потребитель зовёт из
  `deps/core/scripts/`;
- фикстура-потребитель в core-ex собирается в `make` и сверяет предупреждения с маркерами: регресс вывода виден сразу.

Поведение при исполнении не меняется: тот же `execute`, те же исходы репозитория, процесса, проекции и кодека.
Меняются формы вызовов `decide`, `await`, `page_stream` и то, что сообщает компилятор.

## Implementation Decisions

### Граница типов генерируемых функций

- Функция, которую `Core` генерирует у потребителя, закрывает struct в голове: `%__MODULE__{}`, `%unquote(id){}`,
  `%unquote(aggregate){}` вместо `is_struct/2`.
- Результат, пришедший из библиотеки, сужается паттерном в той же функции. Код сужения — в `quote generated: true`:
  у агрегата, чей `decide` никогда не ошибается, clause ошибки недостижима, и без разметки компилятор предупреждает.
- В clause, которая у части потребителей недостижима, не возвращать голую переменную (`{:error, _} = error -> error`):
  тело недостижимой clause типизируется `dynamic()`, и объединение схлопывается. Пишется
  `{:error, reason} -> {:error, reason}`.
- Bang-конструкторы (`new!/1`, `now!/0`) вызывают `raise Core.Exc` сами: `Core.Result.unwrap!/1` при сборке core —
  модуль того же проекта, и результат остаётся `dynamic()`.
- Функции-проверки и места, где предупреждение должно быть, `generated: true` не размечаются целиком; подавление —
  точечно, в meta конкретной clause.

Форма из прототипа (`.scratch/es-type-safety/prototype/`), суть — не код:

```elixir
quote generated: true do
  def execute(%__MODULE__{} = state, command) when is_struct(command) do
    case Core.Es.Aggregate.apply_decision(__MODULE__, state, command, decide(command, state)) do
      {:ok, {events, %__MODULE__{} = executed}} when is_list(events) -> {:ok, {events, executed}}
      {:error, reason} -> {:error, reason}
    end
  end
end
```

### Агрегат — `Core.Es.Aggregate`

- `execute/2` зовёт `decide(command, state)` локально и передаёт решение в библиотечную функцию, которая собирает
  события и сворачивает состояние. Библиотека сама `aggregate.decide` больше не зовёт. Прежняя `@doc false`
  `execute/3` уходит, если после правки не используется.
- `fold/2` и `fold/3` закрывают голову `%__MODULE__{}` и сужают результат до `%__MODULE__{}`.
- Результат `execute/2` у потребителя: `{:ok, {list, %Agg{}}} | {:error, _}`.
- Колбэки `decide/2` и `evolve/2`, `@after_compile`-проверка `id` / `version`, `Aggregate.Test.given/3` не меняются.

### Черновик события — `draft` в `Core.Es.Event.Codec`

- Кодек генерирует по `tags:` (без источников `upcasts:`):
  - `draft/2` — clause на каждое событие с нагрузкой: `draft(Event.X, %Event.X.Payload{} = payload)` →
    `{Event.X, payload}`;
  - `draft/1` — clause на каждое событие без нагрузки: `draft(Event.Y)` → `Event.Y`.
- Форма единая для всех событий. Модуль нагрузки, общий у нескольких событий кодека, ошибкой не является.
- Возврат — прежний элемент результата `decide`, тип `Es.Aggregate.result()`, поэтому `events/5`, `given/3` и тесты с
  кортежами не меняются. Кортеж, собранный вручную, библиотека по-прежнему принимает; норма свода требует `draft`.
- Место — кодек, не семейство `<Aggregate>.Event`: семейство и кодек ждут компиляции друг друга (прототип, P1).
  Вызовы `draft` из `decide` — рёбра runtime, циклов компиляции не добавляют.
- Макрос занимает в модуле кодека имена `draft/1` и `draft/2` — в moduledoc перечня занятых имён.
- Термин — «Черновик события» (`CONTEXT.md`).

### Функции-проверки полноты

- Генерируются с литеральным вызовом на каждое событие; предупреждение даёт сам вывод типов:
  - полнота `evolve/2` — в `use Core.Es.Aggregate.Repo` (знает агрегат и уже грузит кодек при сборке): функция на
    каждое событие кодека вызывает `Agg.evolve(%Agg{} = state, %Event.X{payload: …} = event)`. Ловит и опечатку в
    ключе `%{state | …}`, и опечатку в поле нагрузки без паттерна `%Payload{}`;
  - полнота `project/1` — в `__before_compile__` `use Core.Es.Projection` по `events:`: функция на каждый модуль;
  - `dump_payload/2`, `load_payload/3` и модуль возвращённой нагрузки — в `__before_compile__` `use Core.Es.Event.Codec`
    по `tags:`, только для событий с нагрузкой. Проверка `load_payload` сопоставляет результат с
    `{:ok, %Event.X.Payload{}}`; clause `{:error, _}` помечена `generated: true` в meta.
- Паттерн события в проверке задаёт только `payload:` (`%Payload{}` или `nil`): полный заголовок события забивает
  сообщение шумом.
- Имя функции — нарушенное утверждение (`"evolve/2 принимает <Event>"`, `"load_payload/3 отдаёт нагрузку <Payload>"`):
  компилятор печатает его в месте предупреждения. Функции `@doc false`. Атом ограничен 255 символами: при длинном
  пути модуль в имени укорачивается до последних сегментов. Сборка атома при компиляции — с комментарием для
  `Credo.Check.Warning.UnsafeToAtom`.
- Место предупреждения — строка `use`: `__before_compile__` получает её через атрибут, записанный в `__using__`, и
  `quote line:`.
- Агрегат без `<Aggregate>.Repo` полноту `evolve` не проверяет — это цена места проверки (ADR-0014).

### Репозиторий event-sourced агрегата — `Core.Es.Aggregate.Repo.Pg`

- `get` / `refresh` сужают результат до `{:ok, %Agg{}}`, `get_many` — до `{:ok, list}`, `append` — до
  `:ok | {:error, _}`. Головы — закрытые struct ID и агрегата.
- Новый колбэк `page_stream(id, limit, offset, context)` в `use Core.Es.Aggregate.Repo` и его генерация в
  `Core.Es.Aggregate.Repo.Pg`: голова `%Agg.ID{}`, кодек — свой. Исходы — как у нынешнего
  `Core.Es.Store.page_stream/5` («Страница потока», `13-repos.md`).
- `Core.Repo.Pg.StateStored` с `event_codec:` генерирует ту же `page_stream/4`: страница потока доступна агрегату
  любого вида.
- `Core.Es.Store.page_stream/5` уходит из публичного API (`@doc false`, зовут генерируемые функции).

### Процесс агрегата — `Core.Es.Aggregate.Process`

- Результат `execute/4..6` сужается до `:ok | {:error, _}` паттерном в самой `execute` (`quote generated: true`).
- Домен команды остаётся «любой struct»: процесс не видит `decide` агрегата. Чужая команда в `Process.execute` —
  отложена (`DEBT.md`, условие возврата — вызовы `Process.execute` у потребителей).

### Ожидание проекции — `Core.Es.Projection`

- `use Core.Es.Projection` генерирует `await(Agg, %Agg.ID{} = id, timeout)` — clause на каждый агрегат, чьи события
  есть в `events:`. Агрегат — модуль, в котором лежит кодек событий, как сейчас.
- `Core.Es.Projection.await/4` уходит из публичного API и остаётся реализацией. Исходы (`:ok`,
  `:projection_timeout`, `:projection_rebuilding`), `ArgumentError` внутри транзакции, `RuntimeError` без дерева,
  режим `:inline`, span `Core.Otel.Es.await/4` и telemetry `[:es, :projection, :await]` не меняются.
- Результат генерируемой `await/3` сужен до `:ok | {:error, %Core.Error{}}`.

### Prim и `Version`

- `new/0`, `new!/1` у `Core.Prim.*` (в том числе UUID), `now!/0` у `Core.Prim.DateTime`, `Core.Version.new/0` сужают
  результат до своего struct; bang — `raise Core.Exc` напрямую.
- Safe-конструкторы (`new/1`, `now/0`) уже выводятся точно, их не трогаем.

### Фасад Codec — `Core.Codec.Facade`

- `load/2` на модуль типа или семейства сужает результат по типам плагина: `{:ok, %A{}} | {:ok, %B{}} | {:error, _}`
  (для семейства событий — объединение событий кодека). Сужение — в `generated: true`.
- `load!/2` получает те же clauses по плагинам и падает `raise` сам; Prim-фолбэк остаётся.
- Фолбэк `dump/1` сужен guard'ом `is_prim/1`: struct, который не Prim и не тип плагина, ловится при сборке. Фолбэк
  `load/2` по атому не сужается — Prim по атому в guard не распознать.

### Остальные генерируемые функции `Core`

- Тот же разбор проходят `use`-модули вне `Core.Es`: `Core.Repo.Pg` (головы `(@id_type == nil or is_struct(id,
  @id_type))` — вариант головы выбирается при раскрытии макроса), `Core.Repo.Pg.StateStored`, `Core.Repo.Pg.Schema`,
  `Core.View`, `Core.Enum`, `Core.Context.Accessor`, `Core.Prim.*`, `Core.Codec`, `Core.Codec.Plugin`,
  `Core.Es.Outbox`, `Core.Es.ValueChanged`.
- Порядок: сценарии типовых ошибок вызова в фикстуре → граница там, где вызов молчит → маркеры. Правка без сценария,
  который она делает видимым, не вносится.

### Норма о полях и линтер — ADR-0015

- Поле (`var.field`, `%{var | field: …}`, `Map.get` / `Map.fetch!` / `Map.update!(var, :field, …)`) читается только
  у значения, суженного паттерном `%Mod{}` (в голове или в теле) или map-паттерном с этим ключом.
- Новый скрипт `scripts/field_lint.exs` и цель `make field-check`, после `layout-check`, в `make` по умолчанию и в
  `.pre-commit-config.yaml`. Ловит три формы связывания переменной при чтении её поля в той же clause:
  - из `is/2` / `is_opt/2` в guard;
  - из `%mod{}` с модулем-переменной;
  - из значения поля struct-паттерна (`%Mod{field: var}`).
- Проверяет `lib/**` и `test/**`; каталоги — аргументами, как у `boundary_lint.exs`. Формат вывода и код выхода — как
  у `layout_lint.exs`.
- Потребитель зовёт `elixir deps/core/scripts/field_lint.exs`; копии у него нет.
- Нарушители в `lib/` исправляются в том же срезе, что вводит линтер; списка исключений нет. `is/2` и `is_opt/2`
  остаются в `Core.Guard`.

### Храповик — фикстура-потребитель

- Mix-проект в core-ex вне `config|lib|test` (иначе в проверки попадут его `deps`: formatter, `layout_lint`, Credo) —
  `fixtures/consumer/`. Зависимость `{:core, path: …}` на корень репозитория, `lockfile:` — `mix.lock` библиотеки
  (lock не меняется), свой `_build`.
- Состав:
  - корректный потребитель — два агрегата, команды, события с нагрузкой и без, кодеки (с `upcasts:` и без
    нагрузок), общий модуль нагрузки, репозитории, процесс, проекция на события двух агрегатов, фасад, usecase'ы в
    типовых вызовах — 0 предупреждений;
  - сценарии — функция или модуль на ошибку, маркер строкой над ошибочной строкой: `# expect: <начало заголовка
    предупреждения>` для компилятора, `# expect-lint: <правило>` для `field_lint`.
- Скрипт-сверка живёт при фикстуре: предупреждения — из диагностик Mix API (`compile --force --return-errors`), а не
  разбором текста; перед сборкой — `deps.loadpaths`, иначе изменённая path-зависимость не пересобирается. Падает на
  пропавшем ожидании и на лишнем предупреждении; сдвиг строк переживает.
- Цель `make consumer-check` после `compile-no-optional`, в `make` по умолчанию и в `.pre-commit-config.yaml`.
  Dialyzer на фикстуре не запускается (dialyxir с чужим `lockfile:` пропускает PLT).

## Testing Decisions

- Хороший тест наблюдает то, что видит потребитель: предупреждение компилятора или сообщение линтера на его коде, исход
  публичной функции при исполнении. Как генерируются функции-проверки, clauses `draft`, AST-обход линтера — напрямую не
  проверяется.
- **Шов 1 — фикстура-потребитель (`make consumer-check`).** Всё, что проверяется при сборке и линтером:
  - корректный потребитель — ноль предупреждений компилятора и линтера; это страховка от ложных срабатываний
    `generated: true`, функций-проверок и `draft`, в том числе у агрегатов, чей `decide` никогда не ошибается и всегда
    ошибается;
  - сценарии со слепыми сейчас ошибками, которые спека делает видимыми: A1, A2, A5a, E5, E8, D2b, E1b, F1b, F5, B1–B3
    через `draft`, «не та нагрузка у своего события», C1, C2a, C4, G1, G3a, H1, H2, H3a, H3c, H6, G4, G4b, X3,
    опечатка в поле `now!()` / `Version.new()`;
  - сценарии, которые ловятся уже сейчас (A3, A4, E1, E2, F3, F4, D1–D4 и прочие из карты 02), — тоже с маркерами:
    храповик держит и их;
  - сценарии линтера: чтение поля у `is` / `is_opt`, у `%mod{}` с модулем-переменной, у значения поля
    struct-паттерна — сообщение; `is` / `is_opt` без чтения поля — молчание;
  - остаток (F2, I1–I3 и пределы компилятора из таблицы свода) маркера не получает: сценарий без предупреждения
    храповик не держит, и в фикстуре его нет.
- **Шов 2 — существующие ExUnit-тесты публичного API.** Поведение при исполнении не меняется, меняются формы вызова:
  - `test/core/es/aggregate_test.exs`: `decide` фикстуры на `draft`; `execute`, `fold`, `given/3` — прежние исходы;
  - тесты кодека событий: `draft/1,2` возвращают элемент результата `decide`;
  - `test/core/es/aggregate/repo/pg_test.exs` и тесты `StateStored`: `page_stream/4` — исходы нынешней
    `Store.page_stream/5`; `get` / `refresh` / `append` — прежние;
  - `test/core/es/aggregate/process_test.exs` — прежние исходы;
  - тесты ожидания проекции — на `Projection.await/3`, исходы, span, telemetry, `:inline` прежние;
  - тесты Prim и `Version`: `new!/1`, `now!/0` падают `Core.Exc`, как сейчас;
  - тесты фасада Codec: `load/2`, `load!/2`, `dump/1` — прежние исходы;
  - `test/core/es/event_compat_case_test.exs`, `projection_case_test.exs`: тесты удалённых проверок уходят,
    остальные остаются.
  Новых ExUnit-модулей нет. Линтеры в репозитории тестов не имеют и проверяются прогоном по коду; `field_lint`
  дополнительно держит шов 1.
- Prior art:
  - прототип `.scratch/es-type-safety/prototype/`: `consumer/` (корректный потребитель и сценарии), `ratchet/`
    (скрипт-сверка, `selftest.sh` — пропавшее / лишнее / сдвиг строк), `lib.diff` (правки макросов), `RESULTS.md`
    (сообщения компилятора, сигнатуры, находки);
  - карта сценариев и их коды — `.scratch/es-type-safety/research/02-core-es-blind-spots.md` и `02-experiments/`;
  - `scripts/layout_lint.exs` — форма скрипта-линтера, вывод и код выхода;
  - `test/support/es_fixture/**` — образец агрегата с событиями, кодеком, репозиторием, процессом и проекцией.
- `make` зелёный, включая `consumer-check` и `field-check`.

## Further Notes

- **Источники решений:** ADR-0014 (граница типов, функции-проверки, `draft`, храповик), ADR-0015 (норма о полях),
  исследования `research/01` и `02`, мини-проверки `research/03-grilling-checks/`, прототип `prototype/` с `lib.diff`
  (снят с `47f692f`; как запустить — `prototype/README.md`).
- **Выведено из решений, а не решено отдельно:**
  - `page_stream/4` генерируется и у `Core.Repo.Pg.StateStored`: `13-repos.md` определяет страницу потока для
    агрегата любого вида, а обобщённая функция уходит из API;
  - опция `aggregate:` у `EventCompatCase` остаётся источником кодека — удаляется только проверка `evolve`;
  - `load!/2` фасада сужается вместе с `load/2` — иначе сужение на границе `%Mod{} = InCodec.load!(…)` осталось бы
    единственным способом.
- **Риски:**
  - вывод типов хрупок: catch-all clause или обёртка внутри `Core` молча вернёт `dynamic()` — держит только
    `consumer-check`, и его маркеры нужно сопровождать при каждой правке генерируемого кода;
  - поведение вывода меняется между версиями Elixir: при подъёме Elixir `consumer-check` — первый шаг, который надо
    прогнать;
  - сообщения компилятора — не контракт: маркер сверяет начало заголовка, а не текст целиком.
- **Предлагаемый порядок срезов** (зависимости, не решение тикетов):
  1. Храповик: фикстура с корректным потребителем и сценариями, которые ловятся уже сейчас; скрипт-сверка; цель
     `consumer-check`. Каждый следующий срез добавляет маркеры сценариев, которые делает видимыми.
  2. Граница `Core.Es.Aggregate` (локальный `decide`, `execute`, `fold`) и bang-конструкторы Prim / `Version`.
  3. Репозиторий event-sourced агрегата и процесс: сужение результатов.
  4. `draft/1,2` в кодеке событий; `es_fixture` на `draft`.
  5. Функции-проверки: `evolve` (репозиторий), `project/1` (проекция), `dump_payload` / `load_payload` (кодек);
     урезание `EventCompatCase` / `ProjectionCase` и перестройка сломанных фикстур.
  6. `Projection.await/3`.
  7. `page_stream/4` у обоих репозиториев.
  8. Фасад Codec: `load/2`, `load!/2`, `dump/1`.
  9. Остальные генерируемые функции `Core`.
  10. Норма о полях: `field_lint`, исправление нарушителей в `lib/`, сценарии линтера в фикстуре.
  11. Свод потребителя: таблица пределов компилятора, `DEBT.md`.
  Документация свода, moduledoc и CHANGELOG идут в том же срезе, который меняет поведение.
