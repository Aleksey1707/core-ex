# Проекции: источник событий, чекпоинт, порядок

Type: grilling
Status: resolved
Blocked by: 02, 06, 12
Map: [Event-sourced агрегат в :core](../map.md)

## Question

Как устроены асинхронные проекции (синхронных нет — Out of scope):

- источник: хранилище событий по глобальной позиции (своя подписка), outbox → брокер →
  подписчик (`PubSub.MqSubscriberReliable`), оба;
- где хранится чекпоинт и как он фиксируется атомарно с изменением read-модели; идемпотентность;
- порядок обработки и конкурентность обработчиков; поведение при ошибке на событии;
- что видит usecase сразу после записи (read-after-write без синхронной проекции).

## Answer

- **Проекция** строит только read-модель в той же базе через `DAO`; реакции с внешним эффектом — outbox → брокер →
  подписчик: пересборка повторила бы их.
- **Источник** — `Core.Es.Store` по глобальной позиции, свой читатель в `:core`; outbox → брокер и оба источника
  сразу отвергнуты.
- **Объявление.** `use Core.Es.Projection, name:, events: [модули событий]` (+ `repo:`, `codec:` из `Core.Config`);
  тип агрегата — из кодека события, без `type:` — `CompileError`; семейство `Agg.Event` в `events:` нельзя. В SQL —
  фильтр по типу агрегата (индекс `(тип, xid, номер)`), тег — в коде, после цепочки `upcasts:`: тег, известный кодеку,
  но не объявленный, пропускается без `load`, чекпоинт продвигается; неизвестный кодеку — retry без пропуска
  (пересмотрено в [«Эволюция событий: где апкастится история»](09-grilling-event-evolution.md)). События state-stored
  агрегатов объявляются наравне с event-sourced.
- **Колбэк** — `project(event) :: :ok | {:error, Error.t()}` на `%Es.Event{}` в транзакции пачки, без `Context`;
  read-модель — Ecto через `DAO`, хелпера записи нет, DDL — миграции потребителя; полнота клауз по `events:` — тестом.
- **Чекпоинт** — `es_checkpoints` (DDL в `Core.Es.Migration`): строка на проекцию, позиция `(xid, номер)`. Имя
  проекции неизменяемо, переименование — новая проекция; новая проекция стартует с начала истории.
- **Пачка** — транзакция `DAO` до `batch_size`: `pg_try_advisory_xact_lock(имя)` → чекпоинт → `project/1` на каждое
  событие → CAS `WHERE position = прочитанная`; lock не получен — пропуск тика, 0 строк CAS — откат. Singleton-конфиг
  не нужен.
- **Ошибка** на событии `i`, в том числе исключение, — откат, `0..i-1` коммитятся повторным прогоном, на `i` — retry с
  backoff `retry_min_ms` → `retry_max_ms` без предела и без пропуска.
- **Конкурентность** — у каждой проекции свой последовательный читатель и чекпоинт; партиционирования нет.
- **Сигнал** — опрос с adaptive backoff + `wake` после commit `append` через `AfterCommit` (одна VM).
- **Read-after-write** — `Core.Es.Projection.await(projection, aggregate, aggregate_id, timeout)` → `:ok | {:error, _}`:
  опрос чекпоинта до позиции последнего события потока на момент вызова; пустой поток — `:ok`; истечение таймаута —
  прикладная `:projection_timeout`; неподписанный тип агрегата — `FunctionClauseError`; внутри `Transact.run` —
  `raise`. `append` остаётся `:ok`.
- Не проверено на нагрузке: задержка чтения на пишущих транзакциях кластера, в том числе на транзакциях пачек.
- Термины «Проекция», «Чекпоинт» — в `CONTEXT.md`, раздел «Хранение».
