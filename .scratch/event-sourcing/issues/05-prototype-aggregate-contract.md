# Контракт event-sourced агрегата

Type: prototype
Status: resolved
Blocked by: 04, 12
Map: [Event-sourced агрегат в :core](../map.md)

## Question

Как для автора домена выглядит event-sourced агрегат в `:core`:

- как агрегат получает состояние из событий: применение события к состоянию, начальное состояние
  пустого потока;
- как мутация порождает события: копит и сразу применяет событие (как state-stored сейчас) или
  раздельные decide (команда → события) и evolve (состояние + событие → состояние);
- кто и как поднимает `Version` события (сейчас — домен, ADR-0001);
- что даёт макрос библиотеки, что пишет потребитель, что проверяется на компиляции.

Сравнить синтетический агрегат в обоих стилях. Прототип —
[prototype/es-aggregate-contract](../prototype/es-aggregate-contract/README.md).

## Answer

- **Стиль — decider.** Автор пишет `decide(команда, состояние) → {:ok, [результат]} | {:error, Error.t()}` и
  `evolve(состояние, событие) → состояние`. `initial_state/0` нет: начальное состояние — `%__MODULE__{}` с `id` из
  адреса вызова (`get(id, …)`, процесс на id), «не создан» — `version: nil`. Стиль A (мутация записывает событие)
  отвергнут: процессу агрегата нужна команда-данные в очереди, а состояние event-sourced агрегата — свёртка.
- **Команда** — `<Aggregate>.Cmd.<Name>` с `use Core.Es.Cmd`: struct из Prim, собирает usecase; `by` (Prim автора
  событий агрегата) и `at` (`%Es.Event.At{}`) обязательны в `@enforce_keys` — проверка на компиляции. Термин
  «Команда» — в `CONTEXT.md`, CQS-смысл в определении Usecase переименован в «изменяющий / читающий».
- **Результат `decide`** — `{Event.Mod, payload}` или `Event.Mod` у события без нагрузки. `id`, `aggregate_id` (из
  состояния), `aggregate_version` (по порядку от `state.version`), `by` и `at` (из команды) ставит библиотека;
  отдельного термина нет, конвертом эти поля не называются. Команда без изменений — `{:ok, []}`: запись не идёт,
  версия не растёт. `not_found` / `already_exists` — доменные ошибки `decide`.
- **`evolve`** возвращает голое состояние, чистый, без проверки инвариантов и без catch-all; `id` и `version` не
  трогает — их ведёт библиотека.
- **Версия.** `aggregate_version` назначает библиотека, домен `Version` не трогает; у state-stored — как есть
  (ADR-0001).
- **`use Core.Es.Aggregate, event_codec: Agg.Event.Codec`** генерирует:
  - `fold/2` — свёртка истории от любого состояния; разрыв версий или чужой `aggregate_id` — `raise`;
  - `fold/3` — состояние + команда + результат `decide` → состояние: несколько событий из одной команды автор
    сворачивает через `with`;
  - `execute/2` — чистый шаг «состояние + команда → `{:ok, {[Es.Event], состояние}} | {:error, _}`» для пути
    usecase → repo и для процесса агрегата.

  Кодек событий получает интроспекцию списка модулей событий; модуль из результата `decide` сверяется guard'ом.
- **На компиляции** — `id` и `version` в `defstruct`, `decide/2` / `evolve/2` через `@behaviour`. Полнота `evolve` —
  тестом: [«Тестовая поддержка event-sourced агрегата: given / when / then и полнота `evolve`»](15-grilling-aggregate-test-support.md).
- ADR не заводится: decider — известный образец, расхождение с state-stored объясняет свод.

## Comments

- 2026-09-13 — прототип показан. Пользователь склоняется к стилю B (decider) и предлагает не писать event
  sourcing с нуля, а взять готовую библиотеку и написать к ней адаптеры под принципы `:core`. Решение по
  тикету ждёт выбора «своя реализация или библиотека».
- 2026-09-13 — раунд 3 (после research «Готовые ES-библиотеки на Elixir и их совместимость с принципами core»):
  - готовая библиотека, если берётся, — только хранилище, подписки, снапшоты; decide / evolve и репозиторий —
    в `:core`; путь usecase → repo без router остаётся; дополнительно `:core` даёт режим агрегата-процесса
    (GenServer);
  - синхронных проекций нет — все read-модели асинхронные;
  - библиотека — optional-зависимость, модуль хранилища объявляет потребитель и передаёт адаптеру;
  - формат хранения задаёт кодек `:core`;
  - тикет возвращён в open и ждёт «Своя реализация или готовая библиотека»: форму контракта отчасти
    продиктует выбор.
- 2026-09-13 — раунд 4:
  - процесс агрегата — процесс на id: кэш состояния и очередь команд, прямой вызов, те же decide / evolve и
    репозиторий, idle timeout; таймеры, дедлайны и реакция на чужие события — Out of scope; вынесен в тикет
    «Процесс агрегата»; термин — в `CONTEXT.md`;
  - события пишутся в транзакции `DAO` вместе с outbox и Oban-джобами usecase — хранилище обязано это уметь.
- 2026-09-13 — раунд 5 (после «Своя реализация или готовая библиотека»):
  - стиль B — decider: `initial_state/0`, `decide(команда, состояние)`, `evolve(состояние, событие)`;
  - `aggregate_version` события назначает библиотека, домен `Version` не трогает; у state-stored — как есть (ADR-0001);
  - `evolve` возвращает голое состояние, чистый, без проверки инвариантов, без catch-all;
  - `by` и `at` — данные команды, не `Context` и не часы библиотеки.
  - команда — struct на команду в `<Aggregate>.Cmd.<Name>`, поля — Prim, собирает usecase; один `decide/2`;
  - термин «Команда» в `CONTEXT.md`; CQS-смысл в определении Usecase переименован (изменяющий / читающий);
  - `decide` возвращает `{:ok, [{Event.Mod, payload} | Event.Mod]} | {:error, _}` — без id, версии, `by`, `at`;
    их ставит библиотека: версии по порядку от `state.version`, `by` и `at` — из полей команды;
  - `id` и `version` — обязательные поля `defstruct` агрегата, ведёт их только библиотека;
  - пустой поток: `decide` видит `initial_state()`, `not_found` / `already_exists` — доменные ошибки `decide`;
  - разрыв версий или чужой `aggregate_id` при свёртке — `raise`;
  - команда без изменений — `{:ok, []}`, запись не идёт, версия не растёт.
  - начальное состояние получает `id` из адреса вызова (`get(id, …)`, процесс на id); «не создан» — `version: nil`;
  - несколько событий из одной команды — автор сворачивает сам через `with`, библиотека даёт функцию
    «состояние + команда + результат `decide` → состояние»;
  - `use` генерирует чистый шаг «состояние + команда → `{:ok, {[Es.Event], состояние}} | {:error, _}`» — его зовут
    и путь usecase → repo, и процесс агрегата;
  - `use Core.Es.Cmd` — проверка `by` / `at` в `@enforce_keys` на компиляции и интроспекция; `at` — `%Es.Event.At{}`,
    `by` — Prim автора событий агрегата;
  - термин для результата `decide` не заводится; `id` / версию / `by` / `at` конвертом не называть;
  - CQS-словарь `20-agreements.md` («команда / запрос») переименовать вместе с правкой сводов.
  - builder — `use Core.Es.Aggregate, event_codec: Agg.Event.Codec`; кодек получает интроспекцию списка модулей
    событий, модуль из результата `decide` сверяется guard'ом при проставлении;
  - `initial_state/0` нет: начальное состояние — `%__MODULE__{}` с `id` из адреса; у автора — `decide/2` и `evolve/2`;
  - на компиляции: `id` и `version` в `defstruct`, `decide/2` / `evolve/2` через `@behaviour`; полнота `evolve` — тестом;
  - генерируется `fold/2` (история), `fold/3` (результат `decide` с командой), `execute/2` (чистый шаг).
