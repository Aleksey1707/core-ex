# Процесс агрегата

Type: grilling
Status: resolved
Blocked by: 05, 07
Map: [Event-sourced агрегат в :core](../map.md)

## Question

Как устроен процесс агрегата. Рамка — Notes карты: процесс на id, состояние в памяти, команды по одной,
прямой вызов, те же decide / evolve и репозиторий, idle timeout; без router, таймеров и реакции на чужие
события.

- как процесс узнаёт о записи того же агрегата в обход него (usecase, другая нода): подписка на поток,
  дочитывание хвоста перед командой, только конфликт версии и перечитывание;
- единственность процесса: на ноду (`Registry`) или на кластер (`:global`, `:pg`, другое) — и что держит
  корректность, если процессов оказалось два;
- конфликт версии: перечитать и повторить decide самому или вернуть `:version_mismatch` вызывающему;
- транзакция и `Context`: запись идёт в процессе агрегата, а не у вызывающего — как usecase ставит
  Oban-джобы атомарно с append; `Repo.Sc` живёт в приватной ETS контекста вызывающего процесса;
- API и CQS: `execute(id, cmd, context)` → `:ok | {:error, _}`, таймаут вызова, падение процесса посреди
  команды;
- дерево процессов: супервизор у потребителя, отключаемость, старт из снапшота, idle timeout.

## Answer

- **Роль.** Процесс агрегата — кэш состояния и очередь команд на ноде; корректность держат проверки `append` (unique,
  `xid`, непрерывность потока). Два процесса одного id (гонка старта, другая нода) и запись через usecase → repo штатны:
  проигравший получает `:version_mismatch`. Единственность — `Registry` на ноду; единственный писатель на кластер
  (`:global`, `:pg`, Horde) и маршрутизация на ноду-владельца отвергнуты.
- **Модуль и дерево.** `use Core.Es.Aggregate.Process, repo: Agg.Repo` в `common/<aggregate>/process.ex` генерирует
  `execute` и `child_spec/1` — `Supervisor` из `Registry` и `DynamicSupervisor`; потребитель ставит `{Agg.Process, opts}`
  в своё дерево; реализация `repo:` — по ADR-0006; процессы `restart: :temporary`. Опции старта (`Core.Helper.StartOpts`):
  `idle_timeout:` (дефолт 60 000 мс), `retries:` (дефолт 3), `enabled:` — обязательна, без дефолта (выровнено в
  [«OTP-дерево асинхронных проекций»](18-grilling-projection-process-tree.md)). Общий модуль библиотеки отвергнут.
- **API.** `Agg.Process.execute(id, version, cmd, context, fun \\ nil, opts \\ [])` → `:ok | {:error, Error.t()}`,
  `version :: %Version{} | :current`, `timeout:` в opts — дефолт 5000 мс явно.
- **Команда — одна транзакция `Transact.run`:** в первой команде `Agg.Repo.get(id, version, context)`, дальше
  `Agg.Repo.refresh(state, version, context)` (хвост после `state.version`, `fold/2`, проверка `%Version{}`) →
  `Agg.execute/2` → `append` → `fun.(events)`; состояние процесса меняется только после commit. Оптимистичный путь и
  подписка на поток отвергнуты: отказ `decide` на устаревшем состоянии проверкой версии не ловится.
- **Конфликт.** `:version_mismatch` из `append` при `:current` — повтор новой транзакцией до `retries:`, затем ошибка
  вызывающему; `%Version{}` мимо версии после хвоста, в том числе пустого потока, — `:version_mismatch` без повтора.
- **Колбэк** `fun.(events) :: :ok | {:error, _}` — сопутствующие записи (Oban, `DAO`) в транзакции процесса после
  `append`; при повторе зовётся заново, ограничения `Transact.run` действуют. Двухфазная запись у вызывающего и путь без
  колбэка отвергнуты.
- **Окружение вызывающего** на время команды: `:shadow_copy` в `context` заменяется собственной таблицей `Repo.Sc`
  (`init` → команда → `delete`), OTel-контекст — `Otel.with_ctx/2`, `Logger.metadata()` ставится и снимается; `context`
  между командами не хранится.
- **Сбои.** Дедлайн в сообщении — просроченная команда отбрасывается до транзакции; истечение `timeout:` и падение
  процесса — exit вызывающему, до commit транзакция откатывается; `raise` в `decide` / `evolve` роняет процесс; `execute`
  внутри `Transact.run` — `raise`; `:noproc` — один повтор со стартом.
- **Жизненный цикл.** Холодный старт — лениво в первой команде, без запросов в `init/1` и `handle_continue/2`; уход по
  idle — `{:stop, :normal}` без записи снапшота; mailbox ограничен числом вызывающих, отдельного лимита нет.
- **Снапшот** пишет `refresh` по правилу `get`: запрос хвоста берёт версию снапшота с совпавшим маркером,
  `state.version − версия снапшота ≥ N` → upsert в `AfterCommit`; процесс о снапшотах не знает.
- **Отключение.** `enabled: false` → `:ignore`, `info` и отметка в `:persistent_term`: `execute` исполняет те же шаги в
  вызывающем процессе в одном `Transact.run`; дерево не запущено и отметки нет — `raise`. Тесты потребителя —
  `enabled: false`; тест процесса — `start_supervised`, `async: false`.
- Команда на несколько агрегатов — только путь usecase → repo.
- Не проверено на нагрузке: +1 запрос хвоста на команду, число процессов без `hibernate` и `max_children`.
- ADR не заводится: единственность и роль кэша меняются без правки API потребителя. `CONTEXT.md` — «Процесс агрегата»:
  состояние — кеш, процессов одного агрегата может быть несколько.
