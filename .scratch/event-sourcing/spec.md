# Event-sourced агрегат в :core

Type: spec
Status: ready-for-agent
Map: [Event-sourced агрегат в :core](map.md)

## Problem Statement

Разработчик приложения-потребителя умеет строить в `:core` только state-stored агрегат: источник истины — строка
таблицы, а события пишутся рядом, в отдельную таблицу на каждый агрегат, миграцию которой пишет сам потребитель.
Агрегат, у которого источник истины — события, построить нельзя:

- нет свёртки событий в состояние и проверки ожидаемой версии без строки состояния;
- у событий нет глобальной позиции, поэтому read-модель по событиям нескольких агрегатов в порядке записи не
  построить, а подписок с чекпоинтом, асинхронных проекций и их пересборки нет вовсе;
- схему события нельзя развивать: тег и `load_payload` живут вечно, а правило свода «upcast по `aggregate_version`»
  не реализовано и неверно — версия агрегата не разделяет потоки, начатые до и после выкладки;
- снапшотов нет — длинный поток пришлось бы сворачивать с начала на каждом чтении;
- конкурентные команды к одному агрегату дают только `:version_mismatch`, очереди команд нет;
- у потребителя нет тестовой поддержки: инварианты golden-фикстур и полнота обработчиков событий пишутся в каждом
  приложении заново и молча расходятся.

Готовые ES-библиотеки на Elixir не подходят: ни одна не пишет события в транзакции `DAO` вместе с outbox и
Oban-джобами usecase без глобальной сериализации записи, приватного API ecto_sql или собственного процесса агрегата
(ADR-0007).

## Solution

`:core` даёт event-sourced агрегат рядом со state-stored. Оба вида остаются навсегда, выбор делается на уровне
агрегата.

- **Одно хранилище событий на приложение** — таблица `es_events`, DDL которой поставляет библиотека, общая для обоих
  видов агрегатов. Глобальная позиция — `(xid, номер)`; запись не ждёт commit чужих транзакций, конфликт версии —
  доменная `:version_mismatch` без aborted-транзакции.
- **Агрегат-decider**: автор пишет команды, `decide/2` и `evolve/2`; `id`, версии, автора и время событий ставит
  библиотека.
- **Путь команды** — usecase → repo в одном `Transact.run`: `get` → `Agg.execute/2` → `append`. Второй путь —
  процесс агрегата: кэш состояния и очередь команд на ноде с теми же шагами.
- **Снапшоты** — одноразовый кэш свёртки, включаемый опцией репозитория.
- **Асинхронные проекции** читают хранилище по глобальной позиции собственным читателем, чекпоинт пишется в одной
  транзакции с read-моделью, `await` даёт read-after-write, пересборка — подъёмом `version:` в коде.
- **Эволюция событий** — новый тег и апкаст в кодеке агрегата при чтении; история не переписывается.
- **Страница потока** для экрана истории у обоих видов агрегатов.
- **Тестовая поддержка** в `lib/`: given / then агрегата, case-модули совместимости событий и проекций, синхронный
  прогон проекций.
- **Наблюдаемость**: span'ы `Core.Otel.Es`, telemetry, один PromEx-плагин и рекомендованные алерты.
- **Нормы** в сводах по слоям и новый свод проекций.

State-stored агрегат переезжает на общую таблицу событий — это ломающее изменение контракта с инструкцией переноса
истории в `CHANGELOG.md`.

## User Stories

### Агрегат и команда

1. As an автор домена, I want объявить агрегат через `use Core.Es.Aggregate, event_codec:` с `decide/2` и `evolve/2`,
   so that состояние восстанавливалось из событий, а решение по команде было отделено от применения события.
2. As an автор домена, I want, чтобы `id` и `version` состояния вела только библиотека, so that домен не нумеровал
   версии и не мог в них ошибиться.
3. As an автор домена, I want, чтобы отсутствие `id` / `version` в `defstruct` и `decide/2` / `evolve/2` ловила
   компиляция, so that недоделанный агрегат не собирался.
4. As an автор домена, I want описывать команду структурой `<Aggregate>.Cmd.<Name>` с `use Core.Es.Cmd` и
   обязательными `by` / `at`, so that автор и момент события приходили из данных команды, а не из `Context` или часов
   библиотеки.
5. As an автор домена, I want возвращать из `decide` только `{Event.Mod, payload}` или `Event.Mod`, so that не
   заполнять вручную `id` события, `aggregate_id`, версию, `by` и `at`.
6. As an автор домена, I want отвечать `{:ok, []}` на команду без изменений, so that запись не шла и версия не росла.
7. As an автор домена, I want отказывать доменной ошибкой из `decide`, в том числе `not_found` / `already_exists` по
   `version: nil`, so that существование агрегата решал домен, а не репозиторий.
8. As an автор домена, I want получать начальное состояние `%Agg{id: id}` из адреса вызова без `initial_state/0`,
   so that у агрегата не было лишнего колбэка.
9. As an автор домена, I want сворачивать промежуточные события одной команды через `fold/3`, so that следующее
   решение в той же команде видело состояние после предыдущего.
10. As an автор домена, I want чистый `execute/2` «состояние + команда → события и новое состояние», so that один и
    тот же шаг исполнялся и в usecase, и в процессе агрегата.
11. As an автор домена, I want, чтобы модуль события не из кодека агрегата в результате `decide` отвергался, so that
    чужое событие не попало в поток.
12. As an автор домена, I want `raise` на разрыв версий, чужой `aggregate_id` или неизвестный тег при свёртке, so that
    нечитаемый поток не превращался в тихо неверное состояние.
13. As an автор домена, I want удалять агрегат доменным событием, so that удаление было фактом истории, а не потерей
    потока.

### Write-репозиторий event-sourced агрегата

14. As an автор usecase, I want `get` → `Agg.execute/2` → `append` в одном `Transact.run`, so that чтение, решение и
    запись были видны в одном теле функции.
15. As an автор usecase, I want, чтобы `get(id, :current)` на пустом потоке отдавал `%Agg{id: id, version: nil}`, so
    that команда создания шла тем же путём, что и остальные.
16. As an автор usecase, I want передать ожидаемую `%Version{}` и получить `:version_mismatch` (на пустом потоке —
    `actual: nil`), so that клиент со старой версией не перезаписал чужое изменение.
17. As an автор usecase, I want `get_many` одним запросом с состояниями в порядке пар и одной `:version_mismatch` на все
    расхождения, so that пакетная команда не делала N запросов.
18. As an автор usecase, I want, чтобы `append([])` возвращал `:ok` без запросов, so that команда без изменений ничего
    не стоила.
19. As an автор usecase, I want писать `append` события нескольких потоков одного типа агрегата и откатывать пачку при
    конфликте в любом из них, so that пакетная команда была атомарной.
20. As an автор usecase, I want, чтобы события писались в транзакции `DAO` вместе с outbox и Oban-джобами, so that
    доставка в брокер и сопутствующие задачи были атомарны с событиями.
21. As an автор usecase, I want получать конфликт конкурентной записи как `:version_mismatch` без aborted-транзакции,
    so that usecase мог обработать ошибку внутри транзакции.
22. As an автор usecase, I want мутировать дальше состояние из `execute/2` без повторного `get`, so that цепочка команд
    не перечитывала поток.
23. As an автор домена, I want один репозиторий на агрегат в common-слое без `default_filters`, `Repo.Sc` и `delete`, so
    that доступ решали usecase (роли из `Context`) и `decide` (владение по состоянию и `by` команды).
24. As an автор домена, I want `CompileError` на `errors:` без `:version_mismatch` и на отсутствующий `outbox:`, so that
    ошибка конфигурации не доживала до рантайма.
25. As an автор тестов, I want подменять реализацию репозитория по конвенции `<Behaviour>.Pg`, so that DI был таким же,
    как у state-stored (ADR-0006).

### Хранилище событий и state-stored агрегат

26. As a разработчик state-stored агрегата, I want события всех агрегатов приложения в одной таблице `es_events` с DDL
    библиотеки, so that не писать миграцию таблицы событий на каждый агрегат.
27. As a разработчик state-stored агрегата, I want пошаговую инструкцию переноса истории в `CHANGELOG.md` (остановка
    записи, три миграции, SQL-шаблон), so that выпуск прошёл без потери событий и перестановки версий.
28. As a разработчик state-stored агрегата, I want заменить `use Core.Repo.Pg.Es, event_repo:` на
    `use Core.Repo.Pg.StateStored, event_codec:` без смены порядка записи, `Repo.Sc` и `check_events_for_change!`, so
    that перенос свёлся к механической правке.
29. As a разработчик state-stored агрегата, I want `CompileError` при кодеке без `type:`, расхождении Prim id кодека с
    `id:`, `event:` у outbox с семейством кодека и `errors:` без `:version_mismatch`, so that рассинхрон модулей ловила
    компиляция.
30. As a разработчик state-stored агрегата, I want, чтобы поток законно начинался не с 1 и имел разрывы, so that
    агрегаты, созданные без события и мутирующие без событий, писались как раньше.
31. As a разработчик state-stored агрегата, I want одну форму detail `%{aggregate_id, expected, actual}` и понятный
    новый источник `:version_mismatch` (страж `xid`), so that реакция на конфликт была одна — повтор usecase.
32. As an автор домена, I want обязательный `type:` у кодека событий и `CompileError` фасада на дубль `type:`, so that
    адрес потока был однозначен.
33. As a сопровождающий библиотеки, I want запрет `Core.Es.Store.append` вне двух write-builder'ов, so that событие не
    прошло мимо outbox.

### Снапшоты

34. As an автор домена, I want включать снапшоты опцией `snapshot: [every: N, version: V]` у репозитория, so that
    длинный поток не сворачивался с начала на каждом `get`.
35. As an автор домена, I want, чтобы снапшот был кэшем, удаление которого не меняет корректность, so that его можно
    стереть в любой момент.
36. As an автор домена, I want автоматическую инвалидацию снапшота при правке модуля агрегата, кодека или модулей
    событий и ручную — подъёмом `version:`, so that устаревшая форма состояния не попала в свёртку.
37. As an автор домена, I want, чтобы любой отказ снапшота давал полную свёртку, а не ошибку, so that битый снапшот не
    ронял команду.
38. As an автор usecase, I want, чтобы запись снапшота не шла в транзакции usecase и не зависела от её исхода, so that
    снапшот не удлинял и не ломал транзакцию.
39. As a дежурный инженер, I want `warning` на отвергнутый снапшот и `debug` на успешную запись, so that битые снапшоты
    были видны, а штатный поток не шумел.

### Эволюция событий

40. As an автор домена, I want при несовместимом изменении нагрузки заводить новый тег и объявлять `upcasts:` с
    `upcast/2`, so that старые события читались текущим кодом без переписывания истории.
41. As an автор домена, I want, чтобы апкаст действовал везде, где грузит фасад — `get`, проекция, подписчик брокера,
    страница потока, golden-фикстуры — у обоих видов агрегатов, so that у события было одно представление.
42. As an автор домена, I want цепочку апкастов v1 → v2 → v3 по шагам и проверку карты на компиляции, so that ошибка
    цепочки не доживала до чтения истории.
43. As an автор домена, I want удалять тип события без замены, оставляя тег в `tags:` и клаузу `evolve`, не меняющую
    состояние, so that историю с этим типом можно было прочитать.
44. As an автор домена, I want таблицу «Совместимость событий» в своде, so that знать, какое изменение разрешено, какое
    требует нового тега, а какое запрещено.
45. As a дежурный инженер, I want, чтобы проекция на теге, неизвестном кодеку ноды, стояла в retry, а не пропускала
    событие, so that read-модель не потеряла событие при поэтапной выкладке.

72. As an автор usecase, I want автоматический повтор при конфликте на `:current` до `retries:` и немедленную

73. As a разработчик приложения, I want, чтобы корректность не зависела от единственности процесса в кластере, so that

## Implementation Decisions

### Общие ограничения

- Своя реализация на `Repo.Pg` / `DAO`, без новых зависимостей (ADR-0007). Запись не опирается на приватные API
  Ecto / ecto_sql; конфликт версии не переводит транзакцию usecase в aborted.
- Главный инвариант библиотеки сохраняется: деревья процессов event sourcing получают настройки опциями старта
  (`Core.Helper.StartOpts`), repo и фасад кодека — из `Core.Config`; config и env потребителя библиотека не читает.
- Оба вида агрегатов остаются; контракт state-stored меняется только с записью в `CHANGELOG.md`. Внутри «Не выпущено»
  уже есть пункты про `Core.Es.Event.Codec` и `Es.Event.Repo.Pg.Schema` — их дополнять, а не заводить параллельные.
- Термины уже зафиксированы в `CONTEXT.md` («Event-sourced агрегат», «Процесс агрегата», «Команда», «Хранилище
  событий», «Поток событий», «Тип агрегата», «Глобальная позиция», «Проекция», «Чекпоинт», «Отставание проекции»,
  «Пересборка проекции», «Снапшот», «Апкаст»). В библиотеке говорится «страница потока» / «чтение потока»;
  «история» — имя экрана у потребителя.

### Схема хранилища (`Core.Es.Migration`)

- `up/0` / `down/0`, у потребителя — делегирующая миграция, как у `Core.Outbox.Migration`. Создаёт три таблицы всегда,
  независимо от того, включены снапшоты и проекции или нет.
- **`es_events`** — события обоих видов агрегатов:
  - тип агрегата, `aggregate_id`, `aggregate_version`, id события, тег события, `payload` jsonb, `by_id` без FK,
    `at` с точностью до секунды;
  - `xid xid8 default pg_current_xact_id()` и номер из identity;
  - unique `(тип, aggregate_id, aggregate_version)` — единственная проверка ожидаемой версии, таблицы потоков нет;
  - индексы `(xid, номер)` и `(тип, xid, номер)`.
- **`es_checkpoints`** — строка на имя проекции: позиция `(xid, номер)`, версия проекции, цель пересборки.
- **`es_snapshots`** — строка на поток: PK `(тип, aggregate_id)`, `aggregate_version`, `marker`, `state bytea`,
  `updated_at`.
- `Core.Es.Migration.delete_checkpoint/1` — для миграции потребителя, удаляющей проекцию; `down` у такой миграции
  необратим.
- Глобальная позиция — только пара `(xid, номер)`: сортировать выдачу по одному номеру нельзя, номер выдаётся до
  commit (ADR-0008).

### Хранилище событий (`Core.Es.Store`)

- **`append`** — пачка событий нескольких потоков одного типа агрегата:
  - `insert_all` с `on_conflict: :nothing` и сверкой числа строк (unique);
  - страж: запись отвергается, если в потоке есть событие с `xid` больше `pg_current_xact_id()`, — иначе выдача по
    позиции переставляет версии потока;
  - непрерывность потока — опция, её включает только builder event-sourced репозитория: первая версия потока в пачке
    равна `max + 1` (у пустого — 1); версии не подряд внутри пачки — `raise`;
  - любой отказ — `:version_mismatch` с detail `%{aggregate_id, expected, actual}`: `expected` — первая версия потока в
    пачке, `actual` — `max` версии потока отдельным `SELECT` только на пути ошибки; ns — `behaviour:` write-репозитория,
    код — из его `errors:`; отказ стража `xid` своего кода не получает;
  - после commit через `AfterCommit` — `Registry.dispatch` по типам агрегатов пачки в `Core.Es.Projection.Registry`;
    Registry не запущен — `:ok`.
- **Чтение потока** — целиком и после версии, в том числе одним запросом со снапшотом; используется билдерами
  репозиториев, публичного API «после версии» у потребителя нет.
- **Чтение по глобальной позиции** — для читателя проекций: события объявленных типов агрегатов с
  `xid < pg_snapshot_xmin(pg_current_snapshot()) OR xid = pg_current_xact_id_if_assigned()` в порядке `(xid, номер)`.
  Второе условие открывает события своей транзакции: в sandbox теста она одна на весь тест, а у транзакции пачки на
  проде своих событий нет.
- **`page_stream(event_codec, %Agg.ID{}, %Pagination.Limit{}, %Pagination.Offset{}, context)`** →
  `{:ok, Pagination.Result.t(Es.Event)}`:
  - тип агрегата — `type:` кодека, семейство событий — из кодека; у обоих видов агрегатов;
  - по возрастанию `aggregate_version`, `count` всего потока, без условия `pg_snapshot_xmin`;
  - строки грузятся фасадом `InCodec.load(Agg.Event, wire)` с апкастом; первая ошибка `load` (`:unknown_event_type`,
    `:invalid_envelope`) — на всю страницу через `Result.traverse`, без `raise`;
  - доступ не проверяет и `:not_found` не отдаёт: пустой поток — пустая страница с `count: 0`;
  - `context` — последний из данных и не используется; `opts`, span и telemetry нет.
  - Отдаёт `Es.Event`, а не View — отступление от «read-путь → View» обосновано ADR-0010: Prim события не
    ужесточается, проверенное на записи событие грузится.
- **Норма:** `Core.Es.Store.append` MUST NOT вызываться вне `use Core.Es.Aggregate.Repo.Pg` /
  `use Core.Repo.Pg.StateStored`; MAY — тестовые дублёры в `test/support`. Usecase зовёт только `page_stream`.

### Кодек событий (`Core.Es.Event.Codec`)

- `type:` — обязательная опция любого `use Core.Es.Event.Codec`, формат как у wire-тега; только колонка хранилища,
  конверт не меняется. Дубль `type:` среди плагинов фасада — `CompileError` в `use Core.Codec.Facade`. Связь `type:` с
  префиксом тега не проверяется: записанные теги неизменяемы.
- `upcasts: %{"старый тег" => "новый тег"}` и колбэк `upcast(old_tag, envelope)` → нагрузка:
  - срабатывает в `load_by_tag` до выбора модуля; цепочка по шагам;
  - меняются только тег и нагрузка; заголовок (`event_id`, `aggregate_id`, `aggregate_version`, `at`, `by`) колбэк
    только читает; одно записанное событие — ровно одно прочитанное; возврат — голая нагрузка, ошибку формы ловит
    `load_payload`;
  - на компиляции (`CompileError`): источник не в `tags:`, цель — в `tags:` или сама источник, циклов нет, колбэк
    обязателен при непустой карте; переименование тега — клауза с нагрузкой как есть.
- Интроспекция механизмов библиотеки — `__es_mods__/0` (модули из `tags:`) и `__es_upcasts__/0` (карта как объявлена)
  рядом с `__es_aggregate_id__/0`; конец цепочки наружу не выносится. `types/0`, `mod_by_tag/1` и публичная
  `to_fields/1` остаются.
- `Es.Outbox` получает интроспекцию `__es_event__/0` для сверки в `use Core.Repo.Pg.StateStored`.
- Нормы свода: версия схемы — тег; новое опциональное поле нагрузки тег не меняет, любое другое изменение — новый тег
  и апкаст; ужесточать Prim в нагрузке и заголовке MUST NOT; тег остаётся в кодеке навсегда — в `tags:` или в
  `upcasts:`; изменять строки `es_events` MUST NOT, инструмента переписывания нет. Правило «upcast по
  `aggregate_version`» из свода уходит.

### Контракт event-sourced агрегата (`Core.Es.Cmd`, `Core.Es.Aggregate`)

- **Команда** — `<Aggregate>.Cmd.<Name>` с `use Core.Es.Cmd`: struct из Prim, собирает usecase; `by` (Prim автора
  событий агрегата) и `at` (`%Es.Event.At{}`) обязательны в `@enforce_keys` — проверка на компиляции; интроспекция
  для процесса агрегата.
- **Колбэки автора** (`@behaviour`):
  - `decide(команда, состояние)` → `{:ok, [{Event.Mod, payload} | Event.Mod]} | {:error, Error.t()}`;
  - `evolve(состояние, событие)` → голое состояние; чистый, без проверки инвариантов и без catch-all; `id` и `version`
    не трогает; голова MUST матчить только событие, не значения состояния.
- **`use Core.Es.Aggregate, event_codec: Agg.Event.Codec`** генерирует:
  - `fold/2` — свёртка истории от любого состояния с проверкой непрерывности от его `version`; разрыв версий или чужой
    `aggregate_id` — `raise`;
  - `fold/3` — состояние + команда + результат `decide` → состояние (несколько событий одной команды автор сворачивает
    через `with`);
  - `execute/2` — чистый шаг «состояние + команда → `{:ok, {[Es.Event], состояние}} | {:error, _}`»;
  - `__es_event_codec__/0`.
- Проверки на компиляции: `id` и `version` в `defstruct`, `decide/2` / `evolve/2` через `@behaviour`. Полнота `evolve`
  — тестом (`Core.Es.EventCompatCase`), не компиляцией: иначе цикл агрегат → кодек → события → `Agg.ID`.
- Библиотека проставляет событию `id`, `aggregate_id` из состояния, `aggregate_version` по порядку от `state.version`,
  `by` и `at` из команды; модуль из результата `decide` сверяется guard'ом по интроспекции кодека.
- Начальное состояние — `%__MODULE__{}` с `id` из адреса вызова, «не создан» — `version: nil`; `initial_state/0` нет.
- У state-stored агрегата версию по-прежнему поднимает домен (ADR-0001); к event-sourced ADR-0001 не применим.

### Write-репозиторий event-sourced агрегата

- `use Core.Es.Aggregate.Repo, aggregate:, id:` — behaviour:
  - `get(id, version, context, opts \\ [])` → `{:ok, state} | {:error, Error.t()}`;
  - `get_many(pairs, context, opts \\ [])` → состояния в порядке пар;
  - `append(events, context, opts \\ [])` → `:ok | {:error, Error.t()}`;
  - `refresh(state, version, context, opts \\ [])` → `{:ok, state} | {:error, :version_mismatch}`.
- `use Core.Es.Aggregate.Repo.Pg, behaviour:, aggregate:, id:, errors:, outbox:` (+ `repo:`, `codec:`, `snapshot:`);
  кодек событий берётся из `use Core.Es.Aggregate`. `errors:` без `:version_mismatch` — `CompileError`; `outbox:`
  обязателен. Реализация резолвится по `<Behaviour>.Pg` (ADR-0006). Генерируемые функции освобождены от `@spec`, как у
  `Core.Repo.Pg`.
- **`get`**: `:not_found` не отдаёт — пустой поток при `:current` даёт `%Agg{id: id, version: nil}`; `%Version{}` мимо
  головы потока (в том числе пустого) — `:version_mismatch` с `actual: nil` на пустом; голова сверяется после свёртки.
- **`get_many`**: один запрос (со снапшотами — тоже), все расхождения — одна `:version_mismatch`, повтор id — `raise`.
- **`append`**: на `[]` — `:ok` без запросов; иначе сам в `Transact.run(dao)`: `outbox.from_events` →
  `Core.Es.Store.append` с непрерывностью потока → `outbox_repo().append`. Событие чужого типа —
  `FunctionClauseError`.
- **`refresh`**: хвост после `state.version` → `fold/2` → сверка `%Version{}`; снапшот пишет по правилу `get`.
- Нечитаемый поток (неизвестный тег, разрыв версий, чужой `aggregate_id`) — `raise`.
- Нет: `get!`, `list`, `page`, `count`, `exists?`, `exists_all?`, `find_many`, `delete`, `Repo.Sc` (`shadow_copy?` и
  аналога `check_events_for_change!`). Удаление — доменное событие.
- Один репозиторий на агрегат в common-слое, без `default_filters` и role-обёрток.
- Load/save: `get` / `get_many`, `Agg.execute/2` и `append` — в теле одной функции под одним `Transact.run`; `get` —
  читающая, `append` — изменяющая.

### State-stored агрегат поверх общей таблицы (`Core.Repo.Pg.StateStored`)

- `Core.Repo.Pg.Es` переименовывается в `Core.Repo.Pg.StateStored`.
- Модули `Core.Es.Event.Repo`, `Core.Es.Event.Repo.Pg`, `Core.Es.Event.Repo.Pg.Schema` и у потребителя
  `<Agg>.Event.Repo{,.Pg,.Pg.Schema}` удаляются вместе с `list_by_aggregate` (и `:from_version` / `:to_version`),
  `count_by_aggregate`, `page_by_aggregate`; у схемы уходят `table:`, `by_schema:`, `payload_type:`.
- `event_repo:` и её DI через `Config.repo!` → обязательная `event_codec:` — источник типа агрегата. Подменять можно
  только `<Agg>.Repo`.
- На компиляции `CompileError`, если кодек без `type:`, Prim `__es_aggregate_id__/0` кодека не равен `id:`, `event:` у
  `outbox:` (`__es_event__/0`) не равен семейству кодека, в `errors:` нет `:version_mismatch`. Событие не из `tags:`
  кодека — `FunctionClauseError`.
- Порядок записи прежний, в одном `Transact.run`: строка → дочерние строки → `outbox.from_events` →
  `Core.Es.Store.append` → `outbox_repo().append`. `Repo.Sc`, `shadow_copy?` и `check_events_for_change!` не меняются.
- Проверки `append` у state-stored — unique и страж `xid`, без непрерывности потока.
- `:version_mismatch` — тот же код из `errors:`, detail меняется с `%{aggregate_id, versions}` на
  `%{aggregate_id, expected, actual}`. Хелпера повтора usecase нет.
- **Перенос истории** — выпуск с остановкой записи state-stored агрегатов; миграции потребителя по порядку, первые
  две — одним `mix ecto.migrate` до старта нового кода:
  1. делегирующая `Core.Es.Migration`;
  2. копия `INSERT INTO es_events … SELECT … ORDER BY aggregate_id, aggregate_version` по каждой старой таблице без
     преобразования тегов и нагрузки, `down` — `DELETE FROM es_events WHERE <тип агрегата> IN (…)`;
  3. удаление старых таблиц — после проверки.

  Триггер на старых таблицах без простоя отвергнут: транзакция старой ноды получает `xid` меньше копии.
- **`CHANGELOG.md`**:
  - «Ломающие изменения контракта» — общая таблица и три миграции с SQL-шаблоном; удалённый триплет и его чтения,
    подмена `<Agg>.Event.Repo` в app-env; `page_by_aggregate(id, limit, offset, context)` →
    `Core.Es.Store.page_stream(Agg.Event.Codec, id, limit, offset, context)` и норма проверки доступа до чтения;
    `list_by_aggregate` в тестах → `Core.Es.Store.Test.events!/2`; ns, detail и новый источник `:version_mismatch`;
    Ecto-тип для `payload_type:` и схема для `by_schema:` больше не нужны, FK `by_id` нет;
  - «Изменения контракта макросов» — `Core.Repo.Pg.StateStored` с `event_codec:` и сверками; обязательный `type:` и
    его дубль в фасаде;
  - «Новое» — event-sourced агрегат, процесс агрегата, снапшоты, проекции, апкаст, тестовая поддержка, `Core.Es.PromEx`;
  - строка `22-projections.md` в таблицы «Файл библиотеки» сводов потребителей.

### Снапшоты

- Одноразовый кэш свёртки: по умолчанию выключен; удаление в любой момент корректность не меняет — версию проверяют
  события на `append`.
- Включение — `snapshot: [every: N, version: V]` у `use Core.Es.Aggregate.Repo.Pg`: `every:` обязателен без значения по
  умолчанию, `version:` — целое, по умолчанию 1; проверка на компиляции. Тестовая реализация behaviour о снапшотах не
  знает.
- Формат — `:erlang.term_to_binary` в `bytea`; чтение `binary_to_term(bin, [:safe])` и сверка ключей struct с текущим
  `defstruct`; Prim при чтении `new/1` не проходит. Снапшот — не wire, Codec-плагина состояния нет.
- Маркер — md5 модуля агрегата, кодека событий и модулей событий (через интроспекцию `event_codec:`) плюс `version:`.
  Правка `decide`, смена Elixir / OTP сбрасывают снапшоты; ноды разного кода при поэтапной выкладке перетирают снапшоты
  друг друга. Апкаст снапшот не покрывает — правка кодека меняет маркер.
- **Чтение** — один запрос: `LEFT JOIN LATERAL` снапшота с маркером в условии + события после его версии; `get_many` —
  все пары одним запросом.
- **Запись — при чтении**: `get` / `get_many` / `refresh` свернули ≥ N событий после снапшота (или с начала потока) →
  upsert свёрнутого состояния синхронно в хуке `AfterCommit` (вне транзакции — сразу); `get_many` — один upsert на
  несколько строк; upsert `WHERE marker <> new OR aggregate_version < new`. Свой `rescue` → `Logger.warning`, успех —
  `Logger.debug`. `append` не меняется.
- **Отказ** — полная свёртка: несовпавший маркер отсекает SQL (штатный промах без `warning`); ошибка `binary_to_term`,
  расхождение ключей struct или исключение `fold/2` от снапшота — `Logger.warning` и второй запрос всего потока.
  `raise` — только если не читается сам поток.
- Инструмента очистки нет — подъём `version:` или `DELETE`.
- Норма свода: MUST поднять `version:` в `snapshot:`, если `evolve` зависит от кода вне модуля агрегата, кодека и
  модулей событий.

### Проекции: объявление, пачка, ожидание, пересборка

- **`use Core.Es.Projection, name:, events: [модули событий], version:`** (+ `repo:`, `codec:` из `Core.Config`):
  - тип агрегата — из кодека события; модуль без `type:` — `CompileError`; семейство `Agg.Event` в `events:` нельзя;
  - кодек модуля события `<Aggregate>.Event.<Name>` — `<Aggregate>.Event.Codec` рядом с ним (раскладка `11-domain.md`,
    конвенция по имени, как `<Behaviour>.Pg` у ADR-0006): ссылки события на кодек нет, а `Core.Config` на компиляции не
    читается;
  - `name:` — неизменяемая строка, переименование — новая проекция; новая проекция стартует с начала истории,
    `start_from` нет;
  - `version:` — целое ≥ 1, по умолчанию 1, проверка на компиляции, только растёт.
- **Колбэки**: `project(event) :: :ok | {:error, Error.t()}` на событии внутри транзакции пачки, без `Context`;
  `clear() :: :ok | {:error, Error.t()}` — обязателен у каждой проекции. Read-модель — Ecto через `DAO` в модуле
  проекции, DDL — миграции потребителя, хелпера записи нет.
- **Фильтр событий**: тип агрегата — в SQL; тег — в коде после цепочки `upcasts:`. Объявленный тег — апкаст нагрузки,
  `load`, `project/1`; известный кодеку (`tags:` или источник `upcasts:`), но не объявленный — пропуск без `load`,
  чекпоинт продвигается; неизвестный кодеку — ошибка `load`, retry без пропуска.
- **Пачка** — одна транзакция `DAO` до `batch_size` событий:
  1. `pg_try_advisory_xact_lock(имя)` — не получен → `:locked`;
  2. строка `es_checkpoints` — нет или её версия меньше `version:` → старт с начала: `clear/0` → чекпоинт в начало со
     своей версией и целью (максимальная позиция событий типов агрегатов проекции с видимостью чтения пачки —
     `xid < pg_snapshot_xmin` или своя транзакция; таких событий нет — `nil`) → CAS по
     прочитанной строке → `info` с `projection=`, `from_version=`, `to_version=` → `:processed`;
  3. версия строки больше `version:` → `:outdated` (старая нода при поэтапной выкладке), `warning` один раз при переходе
     в пропуск;
  4. равна → события после чекпоинта → `project/1` на каждое → CAS `UPDATE … WHERE position = прочитанная` →
     `:processed`; событий нет → `:idle`. 0 строк CAS — откат.
- **Ошибка** на событии или в `clear/0`, в том числе исключение, exit, throw, недоступная БД, — откат; повтор с backoff
  без предела и без пропуска.
- Достижение цели пересборки — `info`; у новой проекции это признак «догнала».
- **`Core.Es.Projection.run_once(projection, opts \\ [])`** →
  `:processed | :idle | :locked | :outdated | {:error, Error.t()}` — одна пачка в вызывающем процессе, `batch_size:`
  по умолчанию 100; цикл читателя зовёт её же; внутри `Transact.run` — `raise`.
- **`Core.Es.Projection.await(projection, aggregate, aggregate_id, timeout)`** → `:ok | {:error, Error.t()}`:
  - `aggregate` — модуль, в котором лежит кодек событий `<Aggregate>.Event.Codec` (сам агрегат любого вида);
  - цель — позиция последнего события потока на момент вызова; пустой поток — `:ok`;
  - чекпоинт ≥ цели → `:ok`; идёт пересборка (строки нет, её версия ниже `version:` или чекпоинт < цели пересборки) →
    сразу прикладная `:projection_rebuilding`; иначе опрос `es_checkpoints` до таймаута → прикладная
    `:projection_timeout`; во время retry — ожидание до таймаута;
  - таймаут обязателен; тип агрегата, на который проекция не подписана, — `FunctionClauseError`; внутри
    `Transact.run` — `raise`;
  - отметки дерева проекций в `:persistent_term` нет — `raise` «дерево проекций не запущено»; проекция не из
    `projections:` — `raise`;
  - при `await: :inline` у дерева — прогон проекции до `:idle` в вызывающем процессе с `batch_size` из отметки и сверка
    чекпоинта; любой другой исход — `raise` с исходом и именем проекции.
  - `append` репозитория остаётся `:ok` — глобальную позицию он не возвращает.
- **Нормы свода проекций**:
  - у проекции нет внешних эффектов (Oban, HTTP, кеш) — это дело подписчика брокера: пересборка повторила бы их;
  - таблицу read-модели MUST писать ровно одна проекция — в `project/1` и `clear/0`; ReadRepo MAY читать таблицы
    нескольких проекций;
  - `version:` MUST подниматься, если правка `project/1` меняет результат для обработанных событий, в `events:` добавлен
    тип, события которого уже есть в истории, или удалён тип, чьи строки остались в read-модели; новый, ещё не
    записанный тип и рефакторинг без смены результата версию не меняют;
  - миграция таблиц при пересборке на месте SHOULD быть расширяющей; несовместимая — новая проекция;
  - новая проекция без неполного окна — три выкладки: (1) новый модуль под новым `name:` и миграция новых таблиц, ждать
    `info` о достижении цели; (2) ReadRepo на новые таблицы, старый модуль удалён; (3) миграция удаляет старые таблицы и
    зовёт `delete_checkpoint/1`. MUST NOT удалять таблицы проекции в выкладке, которая убирает её модуль или читающий
    их ReadRepo; выкладки 2 и 3 совмещает потребитель, у которого миграции идут после смены кода на всех нодах;
  - строку удалённой проекции удаляет миграция потребителя; имя удалённой проекции MUST NOT переиспользоваться.

### Дерево проекций (`Core.Es.Projection.Supervisor`)

- Потребитель ставит `{Core.Es.Projection.Supervisor, projections: [A, B], enabled: …}` в своё дерево. Внутри —
  `rest_for_one`: `Core.Es.Projection.Registry` (`keys: :duplicate`) → `one_for_one` читателей
  `Core.Es.Projection.Reader`, по одному на проекцию, имя процесса — модуль проекции.
- На старте через `StartOpts`: каждый модуль — `use Core.Es.Projection`, `name:` без дублей, иначе `ArgumentError`;
  второй супервизор на ноде — отказ старта по имени Registry.
- Опции — общие на супервизоре: обязательны `projections:` и `enabled:`; `batch_size` 100, `idle_min_ms` 50,
  `poll_interval_ms` 1 000, `retry_min_ms` 1 000, `retry_max_ms` 30 000, `shutdown` 30 000, `await: :poll | :inline`
  (по умолчанию `:poll`). Полный перечень и дефолты — в moduledoc; свод рекомендует env `ES_PROJECTIONS_*` в
  `runtime.exs` потребителя, длительности — `Core.DurationParser`.
- `enabled: false` → `:ignore` + `info`; `projections: []` → `:ignore` + `info` «пропущен: нет проекций»;
  `await: :inline` при `enabled: true` — `ArgumentError`. Любой старт супервизора ставит отметку в `:persistent_term`
  (список проекций и опции).
- Читатель в `init/1` регистрируется в Registry под типами агрегатов из `events:`; запросов в `init/1` нет, первый тик —
  таймер `idle_min_ms`.
- **Цикл** — исход → следующий тик:
  - `:processed` → `schedule(0)`, сброс backoff'ов;
  - `:idle` / `:locked` → от `idle_min_ms` с удвоением до `poll_interval_ms`; `wake` в ожидании — цикл сразу без сброса
    счётчика, `wake` во время цикла — `schedule(0)`;
  - `:retry` → от `retry_min_ms` с удвоением до `retry_max_ms`, `wake` не ускоряет; `warning` на каждую попытку с
    `projection=`, `position=` (чекпоинт до пачки), `event_id=` (событие отказа), `attempt=` и причиной; попытка,
    начало и код ошибки — в state и telemetry; серию заканчивает любой исход, кроме `:locked`; процесс жив, рестарта
    нет;
  - `:outdated` → `poll_interval_ms`, `wake` не ускоряет;
  - `flush_wakes` в начале и в конце цикла; пересборка идёт тем же `batch_size` без паузы между пачками.
- Решение о следующем тике — чистая функция `@doc false`.
- Остановка — `trap_exit`, `terminate/2` только логирует; отдельного таймаута транзакции пачки нет.
- `Core.Es.Projection.Supervisor.watch_list(opts)` — по опциям дерева элемент на каждого читателя под именем модуля
  проекции, `component: "es_projection:<name>"`; при `enabled: false` элементы не включаются.

### Процесс агрегата (`Core.Es.Aggregate.Process`)

- `use Core.Es.Aggregate.Process, repo: Agg.Repo` — модуль на агрегат в common-слое рядом с репозиторием; реализация
  `repo:` — по ADR-0006. Генерирует `execute`, `child_spec/1` (`Supervisor` из `Registry` и `DynamicSupervisor`) и
  хелпер `watch_list`. Потребитель ставит `{Agg.Process, opts}` в своё дерево; процессы на id — `restart: :temporary`.
- Опции старта (`StartOpts`): `enabled:` — обязательна; `idle_timeout:` 60 000 мс; `retries:` 3.
- **`Agg.Process.execute(id, version, cmd, context, fun \\ nil, opts \\ [])`** → `:ok | {:error, Error.t()}`,
  `version :: %Version{} | :current`, `timeout:` в `opts` (5 000 мс).
- **Роль**: кэш состояния и очередь команд на ноде. Единственность — `Registry` на ноду; корректность держат проверки
  `append`, поэтому два процесса одного id и запись в обход через usecase → repo штатны.
- **Команда — одна транзакция `Transact.run`**: в первой команде `Agg.Repo.get(id, version, context)`, дальше
  `Agg.Repo.refresh(state, version, context)` → `Agg.execute/2` → `append` → `fun.(events)`; состояние процесса меняется
  только после commit. Колбэк `fun.(events) :: :ok | {:error, _}` — сопутствующие записи (Oban, `DAO`) под ограничениями
  `Transact.run`, при повторе зовётся заново.
- **Конфликт**: `:version_mismatch` из `append` при `:current` — повтор новой транзакцией до `retries:` (`debug` на
  повтор), затем ошибка вызывающему (`warning` `type= aggregate_id= retries=`); `%Version{}` мимо версии после хвоста,
  в том числе пустого потока, — `:version_mismatch` без повтора.
- **Окружение вызывающего** на время команды: `:shadow_copy` в `context` заменяется собственной таблицей `Repo.Sc`
  (`init` → команда → `delete`), OTel-контекст — `Otel.with_ctx/2`, `Logger.metadata()` ставится и снимается; `context`
  между командами не хранится.
- **Сбои**: дедлайн в сообщении — просроченная команда отбрасывается до транзакции; истечение `timeout:` и падение
  процесса — exit вызывающему, до commit транзакция откатывается; `raise` в `decide` / `evolve` роняет процесс;
  `execute` внутри `Transact.run` — `raise`; `:noproc` — один повтор со стартом.
- **Жизненный цикл**: старт лениво в первой команде, без запросов в `init/1` и `handle_continue/2`; уход по idle —
  `{:stop, :normal}` без записи снапшота; `debug` на старт и уход; mailbox ограничен числом вызывающих.
- **Снапшоты** процесс не знает — их пишет `refresh` по правилу `get`: `state.version − версия снапшота ≥ N` → upsert в
  `AfterCommit`.
- **Отключение**: `enabled: false` → `:ignore`, `info` и отметка в `:persistent_term`; `execute` исполняет те же шаги
  в вызывающем процессе в одном `Transact.run`. Дерево не запущено и отметки нет — `raise`.
- Команда на несколько агрегатов — только путь usecase → repo.
- `watch_list` — только верхний супервизор под атомом `Agg.Process`, `component: "es_aggregate_process:<тип>"`; при
  `enabled: false` элемент не включается.

### Наблюдаемость

- **Трейсы** — словарь `Core.Otel.Es`, все span'ы `kind: :internal`:
  - `execute(type, aggregate_id, command, fun)` — `"execute <тип>"` на call site `Agg.Process.execute` у вызывающего
    (при `enabled: false` — тот же): ожидание в очереди и исполнение; атрибуты `core.es.aggregate.type` / `.id`,
    `core.es.command`, `core.es.execute.mode`, `core.es.retries`, span event `dequeued`; прикладная ошибка —
    `record_error/1`, доменный отказ статус span'а не меняет;
  - `project(projection_name, version, fun)` — корневой `"project <имя>"` только на пачку с работой (события или старт с
    начала): `project/1` / `clear/0` и CAS; `core.es.projection.name` / `.version` / `.reset`,
    `core.es.batch.event_count`, `core.es.checkpoint.from` / `.to` в виде `"<xid>/<номер>"`; при ошибке —
    `core.es.event.id` и `record_error/1`; исключение пачки — прикладная `%Error{}` с именем модуля исключения в
    `detail`, без текста;
  - `await(projection_name, type, aggregate_id, fun)` — `"await <имя>"`; `:projection_timeout` /
    `:projection_rebuilding` — `record_error/1`;
  - у восстановления агрегата (`get` / `get_many` / `refresh`) и у `page_stream` span'а нет.
  - Контекст трейса в `es_events` MUST NOT храниться; связь проекции с командой — `event_id`.
- **Telemetry** (`Core.Telemetry.event/1`):
  - `[:es, :aggregate, :load]` на вызов — `duration`, `streams`, `events`, `snapshot_hit` / `snapshot_miss` /
    `snapshot_rejected`; теги `type`, `op: :get | :get_many | :refresh`, `result: :ok | :version_mismatch`;
  - `[:es, :aggregate, :fold]` на поток — `events`; `type`, `snapshot: :hit | :miss | :rejected | :off`;
  - `[:es, :snapshot, :write]` — `duration`, `rows`; `type`, `result: :ok | :error`;
  - `[:es, :projection, :cycle]` на каждый цикл, включая `:idle` / `:locked`, — `duration`, `events`, `attempt`;
    `projection`, `result`, при `:retry` — `error` (`ns/code` или модуль исключения); старт с начала — `:processed` с
    `events: 0`;
  - `[:es, :projection, :await]` — `duration`; `projection`, `result: :ok | :timeout | :rebuilding`;
  - `[:es, :aggregate, :process, :execute]` у вызывающего — `duration`, `queue` (0 при `enabled: false`), `retries`;
    `type`, `mode: :process | :inline`, `result: :ok | :version_mismatch | :error | :exit`;
    `[:es, :aggregate, :process, :start]` и `:stop` с `reason: :idle | :error`; код доменной ошибки в теги не идёт;
  - `raise` на нечитаемом потоке событий telemetry не шлёт.
- **`Core.Es.PromEx`** — один плагин; repo из `Core.Config`, сбор под `Core.PromEx.Safe`:
  - event-метрики — всегда: `cycles.total{projection,result}`, `duration{projection,result}`,
    `events.total{projection}`, `retry.total{projection,error}` и метрики восстановления, снапшота, `await` и процесса;
  - polling проекций — при MFA `projections:` (тот же провайдер отдаёт список `Core.Es.Projection.Supervisor`):
    отставание — `now − at` первого события типов проекции после чекпоинта (`LIMIT 1` на тип по индексу
    `(тип, xid, номер)`, без условия `pg_snapshot_xmin`; нет событий — 0; нет строки — возраст первого события истории);
    gauge `rebuilding{projection}`, `outdated{projection}` (на этой ноде), `checkpoint.orphan{name}`;
  - polling процессов — при MFA `processes:`: `processes{type}` через `DynamicSupervisor.count_children/1`.
- **Алерты** (рекомендованные, пороги у потребителя): `EsProjectionRetrying`, `EsProjectionLagging` (при
  `rebuilding == 0`), `EsProjectionRebuildLong`, `EsProjectionOutdated`. Без алертов: падение читателей и процессов
  (`WorkerDown`), сироты чекпоинтов, запись снапшота, `version_mismatch` процесса, `await` `:timeout`.

### Тестовая поддержка в `lib/`

- ExUnit в `lib/` — только внутри `quote` case-модулей; проверки case-модулей — функции `@doc false` →
  `:ok | {:error, detail}`, сгенерированный `test` делает `assert :ok = …`.
- **`Core.Es.Aggregate.Test.given(state, results, by:, at:)`** → состояние: `results` — результаты `decide`, `id` — из
  состояния, версии — от `state.version`, `by` / `at` обязательны без значений по умолчанию; разные авторы — цепочкой.
  When — `Agg.decide(cmd, state)`; then SHOULD — короткая форма: `{:ok, [{Mod, payload}]}`, `{:ok, []}`,
  `{:error, %Error{kind: :domain, code: …}}` без `message` / `detail`. Состояние — тестами `evolve` через `fold`.
- **`use Core.Es.EventCompatCase`** — ровно одна из опций `aggregate:` (event-sourced, кодек — `__es_event_codec__/0`)
  или `event_codec:` (state-stored), иначе `CompileError`; `fixtures:` — по умолчанию каталог golden-фикстур событий
  по типу агрегата; фасад — `Core.Config.codec/0`. Генерирует:
  1. у каждого тега `types/0` есть фикстура;
  2. каждая грузится через `InCodec.load(Agg.Event, _)`;
  3. у каждого источника `upcasts:` есть фикстура;
  4. фикстура источника грузится в модуль конца цепочки;
  5. при `aggregate:` — полнота `evolve`: `evolve(%Agg{id: aggregate_id}, событие)` на фикстуре каждого тега; провал —
     только `FunctionClauseError` самой `Agg.evolve/2`.
- **`use Core.Es.ProjectionCase, projection:, fixtures:`** — свой sandbox checkout на `repo:` проекции (по умолчанию
  `Core.Config.dao()`), `async: false` — явной опцией ради Credo, `true` — `CompileError`; проверки — в транзакции с
  откатом; фикстура модуля — `<тип из кодека события>/<текущий тег>.json` от корня `fixtures:`, нет фикстуры —
  провал с модулем и путём; источники `upcasts:` не прогоняются. Генерирует:
  - полноту `project/1` — фикстура каждого модуля `events:` в savepoint с откатом; пропуск клаузы — только
    `FunctionClauseError` самой `P.project/1`;
  - `clear/0` — разница `n_tup_ins + n_tup_upd + n_tup_del` в `pg_stat_xact_user_tables` вокруг `project/1` на всех
    фикстурах → `clear/0` → у каждой найденной таблицы `count(*) = 0`; пустой набор таблиц — провал.
- **`Core.Es.Projection.Test.run_until_idle(projection | [projection], opts \\ [])`** →
  `:ok | {:error, :locked | :outdated | Error.t()}` — `run_once` до `:idle` без предела итераций.
- **`Core.Es.Store.Test.events!(event_codec, %Agg.ID{})`** — `[Es.Event]` всего потока через фасад по возрастанию
  версии, ошибка `load` — `raise`.

## Testing Decisions

- **Хороший тест** проверяет внешнее поведение через публичный контракт: результат `decide` / `execute`, результат
  функций репозитория и записанное через `Core.Es.Store.Test.events!/2` / `page_stream`, read-модель через ReadRepo,
  исход `run_once`, событие telemetry как факт цикла, span через `Core.OtelFixture`. Не проверяются SQL, состояние
  GenServer и приватные функции. Без `sleep` и без реального времени: шаги процессов — сообщениями, тики —
  `send(pid, :tick)`.
- **Точки стыка** — самые высокие из доступных:
  1. **Чистый контракт агрегата** — `decide/2`, `execute/2`, `fold/2,3` и `Core.Es.Aggregate.Test.given/3`, без БД,
     `async: true`.
  2. **Behaviour write-репозитория** — один контрактный набор в `test/support` на обе реализации: `Account.Repo.Pg` и
     `Account.Repo.Pg.Snapshotted` (`snapshot: [every: 2]`), `Core.DataCase`. Тесты снапшота — только на второй:
     upsert после ≥ N, один upsert у `get_many`, промах маркера прямым `UPDATE`, битый `bytea` или лишний ключ struct →
     `warning` и полная свёртка.
  3. **`Core.Es.Store`** — `append` / `page_stream` на `Core.DataCase`; гонки (страж `xid`, unique при конкурентной
     записи, событие более поздней транзакции при открытой более старой) — `ExUnit.Case, async: false`, участники в
     `Sandbox.unboxed_run` с настоящими commit, `TRUNCATE` в `on_exit`, без тега, входят в `make`.
  4. **Проекция** — `run_once` / `run_until_idle` / `await` на `Core.DataCase`, `async: false` (advisory lock и строка
     чекпоинта держатся до конца sandbox-транзакции). На пустом sandbox первый `run_once` — старт с начала без
     событий. `:outdated` — вставленная строка чекпоинта с версией выше.
  5. **Цикл читателя** — чистая функция следующего тика, тест таблицей исходов без процесса; процесс —
     `start_supervised` с интервалами 60 000 мс, тики `send(pid, :tick)`, `wake` через `Registry.dispatch`, факт цикла —
     `[:es, :projection, :cycle]` в pid теста, `refute_receive` — только «`wake` цикл не запустил»; `trap_exit` —
     блокирующий `project/1` и остановка посреди пачки.
  6. **Процесс агрегата** — `Agg.Process.execute` в режимах `enabled: true` (`start_supervised`, `async: false`,
     shared mode `Core.DataCase`, без `allow` и `$callers`) и `enabled: false`; повтор после конфликта —
     `Account.RacyRepo{,.Pg}`, который перед первыми K `append` дописывает конкурирующее событие через
     `Core.Es.Store.append`, и `Account.RacyProcess` с `repo: Account.RacyRepo`.
  7. **Case-модули** — функции проверок `@doc false` на сломанных модулях `test/support`: проекция без клаузы,
     `clear/0` с забытой таблицей, `evolve` без клаузы, тег без фикстуры.
  8. **Наблюдаемость** — span'ы `Core.Otel.Es` через `Core.OtelFixture.attach/0` с `async: false`; telemetry —
     хендлер в pid теста; polling-метрики — как тест PromEx-плагина outbox.
  9. **Компиляция** — `CompileError` опций `use` (`Core.Es.Aggregate`, `Core.Es.Cmd`, `Core.Es.Aggregate.Repo.Pg`,
     `Core.Repo.Pg.StateStored`, `Core.Es.Event.Codec` с `type:` / `upcasts:`, `Core.Es.Projection`, дубль `type:` в
     фасаде) — как нынешние тесты конфигурации макросов.
- **Синтетические фикстуры** (пилотного агрегата нет — требования задают они):
  - event-sourced `Core.EsFixture.Account`: ошибки `decide`, `{:ok, []}`, два события на команду, событие без
    нагрузки, апкаст v1 → v2 → v3, удалённый тип; с `Repo.Pg`, `Repo.Pg.Snapshotted` и `Process`;
  - state-stored `Entity` / `Child` из нынешнего теста `Repo.Pg.Es`, переехавшие в `test/support`, с кодеком
    `Core.EventFixture`, получившим `type:`; поток не с 1 и с разрывами;
  - `Core.EsFixture.Projection` по обоим типам агрегатов, объявляет не все теги;
  - golden-фикстуры обоих агрегатов, `use Core.Es.EventCompatCase` и `use Core.Es.ProjectionCase` на них;
  - таблицы фикстур и `Core.Es.Migration` — в тестовых миграциях библиотеки рядом с миграцией outbox.
- **Модули под тестами**: `Core.Es.Migration`, `Core.Es.Store` (+ `.Test`), `Core.Es.Event.Codec` (`type:`, `upcasts:`,
  интроспекция), `Core.Codec.Facade` (дубль `type:`), `Core.Es.Cmd`, `Core.Es.Aggregate` (+ `.Test`),
  `Core.Es.Aggregate.Repo{,.Pg}` со снапшотами, `Core.Repo.Pg.StateStored`, `Core.Es.Aggregate.Process`,
  `Core.Es.Projection` (+ `.Test`), `Core.Es.Projection.Supervisor` / `.Reader`, `Core.Es.EventCompatCase`,
  `Core.Es.ProjectionCase`, `Core.Otel.Es`, `Core.Es.PromEx`.
- **Образцы в кодовой базе**: `Core.DataCase` (`start_owner!(shared: not async)`); тесты `Outbox.Poller` / `Cleaner`
  (`start_supervised`, telemetry цикла → pid теста, `send(pid, :tick)`); контрактный набор писателя брокера в
  `test/support` и его прогон на фейке; `Core.OtelFixture`; тест PromEx-плагина outbox (polling под
  `Core.PromEx.Safe`); тесты `Repo.Pg` и `Repo.Pg.Es`; round-trip тесты кодеков; тесты конфигурации макросов.
- **Прогон** — `make` целиком: тесты гонок хранилища тегом не исключаются; адаптеры брокеров срезы не затрагивают.

## Out of Scope

- **Синхронные (inline) проекции** — все read-модели асинхронные.
- **Таймеры, дедлайны и реакция процесса агрегата на чужие события** — это поведение process manager.
- **Process manager / саги.**
- **Перевод state-stored агрегата в event-sourced** — оба вида сосуществуют, миграции данных между ними нет.
- **Хранилища, кроме PostgreSQL.** Read-модель проекции — только в той же базе, что `es_events`; read-модель в другом
  сервисе — интеграция через брокер.
- **Router и middleware команд.**
- **Физическое удаление и архивация потоков**, retention и персональные данные в событиях.
- **Отложено, добавляется без поломки**: переопределение опций читателя на проекцию, `disabled: [имена]`,
  отдельный `batch_size` и пауза на время пересборки, span `"load <тип>"`, nullable-колонка `headers` в `es_events`.
- **Отвергнуто в тикетах**: ручной `Core.Es.Projection.reset/1` и mix-задача пересборки,
  `Core.Es.Projection.status/1`, партиционирование читателя, единственный писатель агрегата на кластер (`:global`,
  `:pg`, Horde), `hibernate` / `max_children` процессов, инструмент очистки снапшотов, переписывание истории,
  курсорная пагинация и несколько потоков в `page_stream`, хелпер повтора usecase на `:version_mismatch`, файлы правил
  алертов в `priv/`, возврат глобальной позиции из `append`, `LISTEN` / `NOTIFY`.
- **Перевод Poller / Cleaner / подписчика брокера** на чистую функцию следующего тика.

## Further Notes

- **Не проверено на нагрузке** (пилотного агрегата нет): задержка чтения по позиции на пишущих транзакциях кластера,
  в том числе на транзакциях пачек проекций; частота ложного `:version_mismatch` от стража `xid`; свёртка без снапшота
  и выбор `every:`; задержка upsert снапшота у запроса, перешагнувшего порог; перетирание снапшотов в окно выкладки;
  +1 запрос хвоста на команду процесса и число процессов без `hibernate` / `max_children`; холостые запросы читателей
  (проекции × ноды до раза в `poll_interval_ms`); длительность пересборки и `TRUNCATE` в `clear/0` против чтений
  ReadRepo; polling отставания (проекции × типы × ноды); объём `[:es, :aggregate, :fold]` на `get_many` и
  `[:es, :projection, :cycle]` на холостых циклах; `offset` и `count` страницы потока на длинном потоке.
