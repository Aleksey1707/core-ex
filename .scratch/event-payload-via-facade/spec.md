# Нагрузку события кодирует плагин её типа

Type: spec
Status: ready-for-agent

Решение и отвергнутые варианты — ADR-0060 (`docs/adr/0060-event-payload-via-codec-plugin.md`, заводится первым
тикетом). Продолжает `.scratch/codec-plugin-by-fields/` (ADR-0056): там кодек событий научился выводить клаузы
нагрузки по полям, нагрузки-Prim и `Es.ValueChanged`.

## Problem Statement

Автор агрегата, у которого нагрузка события — сущность со своим Codec-плагином, пишет в `<Aggregate>.Event.Codec`
пару ручных клауз на каждое такое событие: `dump_payload/2` с телом `codec.dump(payload)` и `load_payload/3` с телом
`codec.load(Payload, wire)`. Сами по себе они ничего не кодируют — только передают нагрузку фасаду. Тот же код для
нагрузки-Prim кодек уже выводит сам; для struct — нет, потому что `derivation/1` знает только поля,
`Es.ValueChanged` и Prim.

Замер на 2026-10-11 у потребителя A (ветка на неопубликованном core-ex, все прочие нагрузки уже по полям):

- 7 кодеков событий из 15 держат ручные клаузы чистой передачи фасаду: 12 событий, 24 клаузы;
- ещё 7 событий в 4 кодеках закодированы руками по-настоящему: 3 из них выводятся уже сейчас (нагрузка-обёртка
  над одной сущностью, struct из двух Prim-полей, изменение value object со строковой wire-формой), 4 — нет
  (загрузка поля зависит от соседнего поля; открытое множество атомов с терпимой загрузкой; map, записанный
  отсортированным списком записей).

Пока кодек событий умеет кодировать нагрузку сам, у формы нагрузки два возможных места — плагин её типа и клаузы
кодека событий, и автор выбирает между ними каждый раз заново. Норма потребителя (`docs/rules/app/11-domain.md`)
до сих пор показывает ручную передачу фасаду как образец.

## Solution

Кодек событий перестаёт кодировать нагрузку руками:

- нагрузку-struct, которая не объявлена по полям, не `Es.ValueChanged` и не Prim, кодек выводит сам — передачей
  фасаду целиком, как нагрузку-Prim;
- колбэки `dump_payload/2` и `load_payload/3` уходят из контракта `Core.Es.Event.Codec`; ручная клауза —
  `CompileError` с указанием перенести форму в плагин типа нагрузки;
- что тип нагрузки обслуживает какой-то плагин, проверяет сборка фасада: тип без плагина — `CompileError` фасада;
- нестандартная wire-форма нагрузки живёт в ручном плагине её типа; wire при переносе не меняется.

Перевод кода потребителей — их собственная работа по CHANGELOG: ручные клаузы передачи фасаду удаляются, выводимые
нагрузки переходят на `use Core.Es.Event.Payload` / `use Core.Es.ValueChanged`, остальные переезжают в плагины
агрегатов.

## User Stories

1. As an автор агрегата, I want не писать `dump_payload/2` / `load_payload/3` для нагрузки-сущности со своим
   плагином, so that кодек событий состоял только из тегов и апкастов.
2. As an автор агрегата, I want, чтобы нагрузка-сущность в конверте была ровно `codec.dump(сущность)`, so that
   удаление ручных клауз не меняло wire уже записанных событий.
3. As an автор агрегата, I want, чтобы событие с нагрузкой-сущностью загружалось через фасад и по своему модулю, и
   по семейству, so that выведенная загрузка вела себя как ручная.
4. As an автор агрегата, I want получать ошибку `load` от плагина сущности как ошибку загрузки события, so that
   невалидная нагрузка не превращалась в исключение.
5. As an автор агрегата, I want получать `CompileError` при определении `dump_payload/2` или `load_payload/3` в
   модуле `use Core.Es.Event.Codec`, so that у формы нагрузки было одно место — плагин её типа.
6. As an автор агрегата, I want, чтобы текст этой ошибки называл событие и говорил, куда перенести код, so that
   перевод не требовал чтения ADR.
7. As an автор агрегата, I want получать `CompileError` при сборке фасада, если тип нагрузки события не обслуживает
   ни один плагин, so that забытый плагин ловился до исполнения, а не на первом `dump`.
8. As an автор агрегата, I want, чтобы ошибка фасада называла тип нагрузки и кодек событий, где она объявлена, so
   that было понятно, какой плагин дописать.
9. As an автор агрегата, I want, чтобы нагрузка по полям и `Es.ValueChanged` выводились, как сейчас, so that
   перевод не затрагивал уже выведенные нагрузки.
10. As an автор агрегата, I want, чтобы нагрузка-Prim выводилась, как сейчас, без плагина, so that Prim по-прежнему
    кодировал фасад встроенно.
11. As an автор агрегата, I want, чтобы событие без нагрузки не требовало ничего, so that поведение `payload: nil`
    не менялось.
12. As an автор агрегата, I want, чтобы `upcast/2` остался колбэком кодека событий, so that апкаст тега и формы
    нагрузки жил там же, где теги.
13. As an автор агрегата, I want описать нестандартную wire-форму нагрузки ручным плагином её типа, so that форма,
    которую не вывести из полей, имела законное место.
14. As an автор агрегата, I want держать ручную нагрузку в плагине агрегата рядом с его значимыми объектами, so
    that не заводить файл на каждую нагрузку.
15. As an автор агрегата, I want, чтобы нагрузка из ручного плагина проходила те же проверки сужения типа события,
    что выведенная, so that опечатка в поле нагрузки после `load` не молчала.
16. As an автор агрегата, I want, чтобы у результата `InCodec.load` события компилятор знал struct нагрузки, so that
    храповик вывода типов (ADR-0014) не просел.
17. As an автор потребителя на старом контракте, I want получить `CompileError` с подсказкой на каждую ручную
    клаузу, so that обновление библиотеки не превращало их в молча мёртвые функции.
18. As an автор потребителя, I want в CHANGELOG пункт «было → стало» для передачи фасаду и для нестандартной
    формы, so that перевод был механическим.
19. As an автор потребителя, I want, чтобы норма `docs/rules/app/11-domain.md` показывала нагрузку-сущность без
    клауз, so that образец не учил старому контракту.
20. As an мейнтейнер библиотеки, I want, чтобы фикстура-потребитель, `test/support` и тесты кодека событий шли на
    новом контракте, so that библиотека сама не держала удалённые колбэки.
21. As an мейнтейнер библиотеки, I want ADR-0060 с замером и отвергнутыми вариантами, so that следующий читатель не
    вернул колбэки «для гибкости».

## Implementation Decisions

### Вывод нагрузки через фасад (библиотека)

- `derivation/1` кодека событий получает четвёртый случай: нагрузка — struct, не по полям, не `Es.ValueChanged`,
  не Prim. Вывод тот же, что у Prim: дамп — `codec.dump(payload)`, загрузка — `codec.load(Payload, wire)`. Prim и
  struct отличаются только тем, кто их обслуживает (фасад встроенно или плагин), кодеку событий это безразлично.
- После этого каждое событие с нагрузкой имеет выведенные клаузы; ручных путей нет. Колбэки `dump_payload/2` и
  `load_payload/3` удаляются из behaviour и из `@optional_callbacks`; выведенные клаузы — внутренние функции кодека.
- Определение `dump_payload/2` или `load_payload/3` в модуле `use Core.Es.Event.Codec` — `CompileError` при его
  сборке. Текст называет функцию и указывает перенести форму нагрузки в плагин её типа (или объявить нагрузку по
  полям). Прежняя ошибка «never match» для ручной клаузы выводимой нагрузки и запрет `@spec` у этих функций
  поглощаются новой.
- Проверки, которые ловили ошибки ручных клауз (событие с нагрузкой без клаузы, клауза, отдающая нагрузку другого
  события), теряют предмет и удаляются. Сужение результата загрузки события по struct нагрузки (то, что держит
  храповик ADR-0014) остаётся.
- `upcast/2` — без изменений.

### Проверка в фасаде (библиотека)

- Сборка фасада для каждого кодека событий среди плагинов перебирает нагрузки его событий из `tags:`: нагрузка-struct
  (не Prim, не по полям, не `Es.ValueChanged`) MUST входить в `__codec_types__` какого-либо плагина того же фасада.
  Иначе — `CompileError` с типом нагрузки и кодеком событий.
- Нагрузка по полям и `Es.ValueChanged` в фасаде по-прежнему не регистрируются: их форму выводит кодек событий по
  спеке самой нагрузки.
- Проверка живёт рядом с `validate_es_types!` — тот же проход по кодекам событий фасада; прецедент переноса ошибки в
  фасад — ADR-0059.

### Документы (библиотека, одним коммитом с кодом)

- ADR-0060: контекст — замер выше; варианты — явный список событий в `use` (отвергнут: строка объявления на событие
  и два способа одного), объявление в `use Es.Event` (`payload: {:codec, M}`, отвергнут: меняет DSL события ради
  выводимого сведения), переходный период с предупреждением (отвергнут: ломающие изменения идут в каждом выпуске,
  перевод механический); решение; цена — перенос ручных нагрузок в плагины.
- `docs/rules/14-events-outbox.md`: состав `use Core.Es.Event.Codec` (колбэк — только `upcast/2`), перечень ошибок
  сборки, «формат payload задаёт плагин её типа».
- `docs/rules/11-domain.md`: раздел о выводимых клаузах нагрузки — четвёртый случай.
- `docs/rules/app/11-domain.md`: образец нагрузки-сущности — без клауз; нестандартная форма — ручной плагин в
  `<Aggregate>.Codec`. Правка `app/**` — тем же коммитом в CHANGELOG.
- CHANGELOG: дополняется существующий пункт «Не выпущено» о выводе клауз нагрузки (Prim и `ValueChanged`) — он сам
  ещё не выпущен; в «Ломающие изменения контракта» — удаление колбэков (было → стало: клаузы передачи фасаду →
  ничего; ручная форма → ручной плагин типа нагрузки) и `CompileError` фасада.
- `CONTEXT.md` не меняется: «Codec-плагин» и «Codec-фасад» покрывают решение.

## Testing Decisions

Хороший тест проверяет внешнее поведение через фасад и сообщения сборки: какой конверт дал `dump`, что вернул
`load`, какой `CompileError` получил автор. Устройство сгенерированных клауз не проверяется.

- **Фасад и сборка (основной шов, библиотека).** Событие фикстуры с нагрузкой-сущностью: нагрузка в конверте равна
  `codec.dump(сущность)`; round-trip через JSON по модулю события и по семейству; ошибка плагина сущности на загрузке
  — `{:error, %Error{}}`. `CompileError`: `dump_payload/2` / `load_payload/3` в кодеке событий (текст с подсказкой);
  фасад, где тип нагрузки не обслуживает ни один плагин. Нагрузка по полям, Prim, `ValueChanged` и событие без
  нагрузки — существующие тесты проходят без правки. Образец — `test/core/es/event/derived_payload_test.exs`
  (тот же фасад, `CompileError` через сборку строки) и тесты сборки фасада в `Core.Codec.FacadeTest`.
- **Вывод типов (библиотека).** `make consumer-check`: фикстура-потребитель на новом контракте без предупреждений;
  маркеры `# expect:` о ручной клаузе выводимой нагрузки заменяются ожиданием нового `CompileError` или снимаются,
  если сценарий теряет предмет; сужение результата `InCodec.load` события по struct нагрузки сохраняется.
- **Пайплайн.** `make` в библиотеке.

## Out of Scope

Каждый пункт — отдельный тикет с замером по потребителям A, B, E, F (прецедент — ADR-0059):

- хук конструктора или нормализации после загрузки у плагина по полям (сборка через `new`, сортировка вложенных
  списков);
- вид поля «открытое множество атомов» с терпимой загрузкой;
- вид поля «map как отсортированный список записей»;
- подмножество значений у `enum:`;
- проверка направления dump в `Core.Es.EventCompatCase` (нужно отличать golden-фикстуру текущей формы от старой,
  идущей через апкаст).

Также вне фичи:

- вывод `@tag_by_mod` из имён событий — явная карта защищает wire-тег от переименования модуля;
- перевод кода потребителей — они переводятся сами по CHANGELOG при обновлении.

## Further Notes

- Порядок: вывод нагрузки-struct и проверка фасада → удаление колбэков из контракта.
- Нагрузки, которые после перевода останутся у потребителей ручными, — материал для замера по расширениям из Out of
  Scope; после расширения они переходят из ручного плагина в `fields:`, кодек событий это уже не затрагивает.
