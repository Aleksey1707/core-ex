# Подписи событий: название, сведения и словарь ссылок в `Core.Labels`

Type: spec
Status: ready-for-agent

Решения и отвергнутые варианты — ADR-0063 (`docs/adr/0063-labels-subsystem.md`) и ADR-0064
(`docs/adr/0064-openapi-schemas-optional.md`); термины — `CONTEXT.md`, «Подписи».

## Problem Statement

Автор приложения на `Core.*`, у которого есть страница событий агрегата для человека, отдаёт клиенту
событие в машинной форме — тег и нагрузку. Чтобы показать событие человеку, клиент держит копию
знания обо всех событиях: название по тегу, подписи полей, подписи значений Enum, разбор вложенных
нагрузок, какое значение — ссылка на запись, а какое — дата. Копия расходится с доменом молча, при
каждом новом событии и поле.

Потребитель A решил это у себя: подсистема подписей (8 модулей, ≈1000 строк), ≈1300 строк тестов с
ратчетом полноты, презентер и OpenAPI-схема сведений (≈350 строк), нормы в пяти своих сводах. Его ADR
называл объявления в библиотеке чище и откладывал перенос только из-за цикла выпуска core-ex. Ещё
один потребитель отдаёт страницу событий без подписей: ему пришлось бы повторить механизм с нуля, а
wire сведений и его схему — переписать руками, как четыре потребителя сейчас пишут руками схему
обёртки ответа.

Один к одному реализация потребителя A в библиотеку не ложится:

- вид записи у ссылки объявлен camelCase-строкой — wire-формат в домене;
- ошибки сборки — `ArgumentError`, а у макросов библиотеки — `CompileError` через общую проверку
  опций;
- проверка текста и опций повторена в трёх модулях;
- сборщик словаря ссылок спускается в любой struct — дату, decimal, Prim без вида id — и на каждом
  значении проверяет загрузку модуля;
- построитель сведений перечисляет виды `type:` вручную, отдельно от списка типов проверки полей;
- документация говорит терминами предметной области потребителя.

## Solution

Подписи объявляются в домене приложения рядом с тем, что они называют, отдельными `use Core.Labels.*`
после основного `use` модуля:

- название события — у модуля события;
- подписи полей — у struct'а нагрузки и вложенного struct'а, подпись изменения — у нагрузки
  «было → стало»;
- подписи значений — у Enum;
- вид id в сведениях — у Prim-идентификатора: ссылка на запись, ссылка на учётную запись или только id;
- текст значения — у Prim, который человеку показывают текстом.

Сборка не проходит, пока решение не принято по каждому полю и значению. Из объявлений библиотека
строит сведения события — чистой функцией «событие → название и сведения», — собирает словарь ссылок
страницы событий пачкой по резолверам типов id и отдаёт оба на wire: модуль приложения с
`use Core.Web.Labels` порождает дамп сведений в JSON и OpenAPI-схему этого JSON, а свою часть — профиль
кодека и форму ссылки на учётную запись — приложение задаёт опциями. Схема порождается, только если у
приложения есть `open_api_spex`. Ратчет полноты подключается одним тест-модулем на приложение и сам
находит все кодеки событий.

Модуль без объявлений собирается как прежде: подписи подключаются по желанию.

## User Stories

### Название события

1. Как автор приложения, я хочу объявить название события одной опцией у модуля события, чтобы
   название жило рядом с событием, а не в карте «тег → название» на клиенте.
2. Как автор приложения, я хочу, чтобы `use Core.Labels.Event` вне модуля, объявленного
   `use Core.Es.Event`, ломал сборку, чтобы название не повисло на модуле, который событием не является.
3. Как автор приложения, я хочу, чтобы пустое или не строковое название ломало сборку, чтобы событие
   не ушло клиенту без названия.
4. Как автор приложения с нагрузкой-Prim, я хочу подписать саму нагрузку (`payload:`), чтобы
   единственное значение события вышло в сведения с подписью.
5. Как автор приложения, я хочу, чтобы нагрузка-Prim без `payload:` и `payload:` у нагрузки-struct'а
   ломали сборку, чтобы источник подписи нагрузки был один.

### Подписи полей

6. Как автор приложения, я хочу подписать каждое поле struct'а нагрузки или пометить его скрытым
   (`:hidden`), чтобы решение по каждому полю было записано в домене.
7. Как автор приложения, я хочу, чтобы поле без решения ломало сборку, чтобы новое поле нагрузки не
   ушло в сведения без подписи и не пропало из них молча.
8. Как автор приложения, я хочу, чтобы подпись поля, которого нет в struct'е, повтор поля и пустая
   подпись ломали сборку, чтобы опечатка не жила в объявлении.
9. Как автор приложения, я хочу подписать у map'ы с id в ключах ключ и значение
   (`[label:, key:, value:]`), чтобы map'а вышла в сведения списком групп «ключ — значение».
10. Как автор приложения, я хочу, чтобы вид поля брался из спеки полей нагрузки события
    (`Core.Es.Event.Payload`), чтобы не повторять спеку в объявлении подписей.
11. Как автор приложения со struct'ом без спеки полей — нагрузкой с ручным плагином кодека или
    вложенным struct'ом сведений, — я хочу объявить спеку видимых полей (`fields:`) на языке спеки
    плагина по полям, чтобы построитель знал вид каждого видимого поля.
12. Как автор приложения, я хочу, чтобы спека поля и у нагрузки события, и в `fields:` ломала сборку,
    чтобы у вида поля был один источник.
13. Как автор приложения, я хочу, чтобы видимое поле без спеки, спека скрытого поля и спека лишнего
    поля ломали сборку, чтобы спека и подписи не расходились.
14. Как автор приложения со значением без собственного модуля — полем, где лежит один из двух
    struct'ов, или списком открытых атомов, — я хочу задать у поля вид `text:` с функцией-захватом,
    чтобы значение вышло текстом.
15. Как автор приложения с нагрузкой «было → стало» (`Core.Es.ValueChanged`), я хочу объявить одну
    подпись изменения (`change:`), а вид значения брать из её `type:`, чтобы изменение вышло одним
    сведением «было → стало».
16. Как автор приложения с ручным struct'ом изменения (поля `old_value` / `new_value`), я хочу задать
    вид значения опцией `value:`, чтобы он вышел так же, как `Core.Es.ValueChanged`.
17. Как автор приложения, я хочу, чтобы `labels:` вместе с `change:` и изменение без вида значения
    ломали сборку, чтобы объявление было однозначным.

### Подписи значений Enum

18. Как автор приложения, я хочу объявить подписи значений у Enum (`labels:` после `use Core.Enum`) и
    получить `label/1` и `labels/0` в порядке `values/0`, чтобы человек видел «Активна», а не `:active`, и
    форма выбора строилась из того же списка.
19. Как автор приложения, я хочу, чтобы значение без подписи, подпись вне Enum, повтор и пустая
    подпись ломали сборку, чтобы новое значение Enum не ушло без подписи.
20. Как автор приложения, я хочу, чтобы `use Core.Labels.Values` без `use Core.Enum` ломал сборку,
    чтобы подписи не повисли на модуле, который перечислением не является.

### Вид id

21. Как автор приложения, я хочу объявить у Prim-идентификатора вид «ссылка на запись» с видом записи
    атомом и резолвером, чтобы id вышел в сведения ссылкой с текущим именем.
22. Как автор приложения, я хочу объявить вид «ссылка на учётную запись» с резолвером, чтобы автор
    события и учётные записи в нагрузке вышли одной формой.
23. Как автор приложения, я хочу объявить вид «только id», чтобы служебный id, которого человеку не
    называют по имени, вышел текстом без похода в резолвер.
24. Как автор приложения, я хочу, чтобы опция не своего вида (вид записи у учётной записи, резолвер у
    «только id»), отсутствие обязательной опции и `use Core.Labels.ID` без `use Core.Prim` ломали
    сборку, чтобы объявление вида было однозначным.
25. Как автор приложения, я хочу писать вид записи атомом, а camelCase получать на wire, чтобы
    wire-формат не жил в домене.

### Prim текстом

26. Как автор приложения, я хочу объявить у Prim функцию текста (`use Core.Labels.Text, with:`),
    чтобы код, который человек читает по имени, вышел в сведения именем.
27. Как автор приложения, я хочу, чтобы `with:` не захватом функции арности 1 и `use` без
    `use Core.Prim` ломали сборку, чтобы ошибка не всплыла на странице событий.

### Сведения события

28. Как автор приложения, я хочу получить из события название и сведения одной чистой функцией, чтобы
    страница событий не знала ни одного события в лицо.
29. Как автор приложения, я хочу, чтобы сведения были деревом из Prim-значений без дампа и без
    разыменования id, чтобы домен не знал ни JSON, ни чужих контекстов.
30. Как автор приложения, я хочу, чтобы у каждого сведения был вид — текст, число, дата, дата-время,
    учётная запись, ссылка на запись, группа, список, изменение, — чтобы клиент рисовал сведения одним
    рендером по виду.
31. Как автор приложения, я хочу, чтобы необязательное поле без значения выходило сведением с `nil` и
    своим видом, а нагрузка `nil` — пустыми сведениями, чтобы отсутствие значения было видно, а не
    терялось.
32. Как автор приложения, я хочу, чтобы скрытое поле в сведения не попадало, чтобы служебное не
    показывалось человеку.
33. Как автор приложения, я хочу, чтобы вложенный struct выходил группой, а список — элементами одного
    вида без подписи, чтобы структура нагрузки сохранялась.
34. Как автор приложения, я хочу, чтобы нагрузка-семейство (`union:`) выходила группой полей своего
    варианта, чтобы вариант был виден без знания тега.
35. Как автор приложения, я хочу, чтобы Prim-композит выходил видом своего базового Prim, чтобы
    обёртка роли не меняла отображение.
36. Как автор приложения, я хочу, чтобы `boolean` выходил текстом «Да» / «Нет», чтобы клиенту не
    пришлось переводить `true`.
37. Как автор приложения, я хочу, чтобы id без объявленного вида давал исключение с именем модуля,
    чтобы ошибка программиста не превратилась в молчаливый текст.

38. Как автор приложения, я хочу собрать словарь ссылок страницы событий одним вызовом от событий

40. Как автор приложения, я хочу, чтобы резолвер вызывался один раз на тип id пачкой всех id страницы,

41. Как автор приложения, я хочу, чтобы при отсутствии id с резолвером не читалось ничего, чтобы

## Implementation Decisions

### Модули домена (`Core.Labels.*`)

- **`Core.Labels.Event`** — `use` в модуле события после `use Core.Es.Event`. Обязательная `title:`,
  необязательная `payload:` (только у нагрузки-Prim, у неё — обязательная). Порождает интроспекцию
  названия и подписи нагрузки. Хост проверяется по интроспекции `Core.Es.Event`.
- **`Core.Labels.Fields`** — `use` в struct'е нагрузки, вложенном struct'е и варианте семейства.
  Необязательные `labels:`, `change:`, `fields:`, `value:`; ровно одна из `labels:` / `change:`.
  Решение по полю — подпись, `:hidden` или `[label:, key:, value:]` для map'ы. Язык спеки — виды
  `Core.Codec.Plugin.Fields` (`prim`, `enum`, `entity`, `union`, `list`, `type`) плюс `text:` с
  захватом функции арности 1. Полнота — на `@after_compile`: там уже есть struct и спека нагрузки.
  Публичное: спека видимых полей типа, вид значения изменения, подписи по типу (`paths/1`).
- **`Core.Labels.Values`** — `use` в Enum после `use Core.Enum`. Обязательная `labels:`. Порождает
  `label/1` и `labels/0` в порядке `values/0`; полнота — на `@after_compile`.
- **`Core.Labels.ID`** — `use` в Prim-идентификаторе после `use Core.Prim.*`. Обязательная `kind:`
  из `~w(ref user id)a`; `entity:` — атом, обязателен у `:ref` и запрещён у остальных; `resolver:` —
  обязателен у `:ref` и `:user`, запрещён у `:id`. Публичная интроспекция «объявление или `nil`» по
  модулю.
- **`Core.Labels.Text`** — `use` в Prim после `use Core.Prim.*`. Обязательная `with:` — захват функции
  арности 1. Публичная интроспекция «функция или `nil`».
- **`Core.Labels.Details`** — `build/1`: событие → `{название, сведения}`. Сведение —
  `%{label, kind, value}`, элемент списка и сторона изменения — без `label`, у ссылки на запись рядом
  `entity` (атом). Виды: `text`, `number`, `date`, `datetime`, `user`, `ref`, `group`, `list`,
  `change` (вместо `value` — `old` и `new`). Значения — Prim как есть: дампа и имён нет. Вид `type:`
  сопоставляется со списком типов проверки полей библиотеки, а не с отдельным перечнем. Id без
  `Core.Labels.ID` — документированное исключение с именем модуля.
- **`Core.Labels.Refs`** — `get/2`: значение (страница событий, список, событие) и контекст →
  `Result.t(%{id => имя | nil})`. Обходит struct'ы, map'ы (ключи и значения) и списки; не спускается в
  Prim без вида id, `DateTime`, `Date`, `Decimal`; проверка «модуль несёт вид id» кешируется по модулю
  в пределах вызова. Id группируются по резолверу, резолвер вызывается один раз на группу. Без id с
  резолвером — `{:ok, %{}}` без вызовов. Отказ резолвера — итог.
- **`Core.Labels.Resolver`** — behaviour с одним колбэком «список id, контекст →
  `Result.t(%{id => имя | nil})`».
- **`Core.Labels.CompletenessCase`** — case-модуль поверх `ExUnit.Case`. Обязательная `app:`,
  необязательная `async:`. Модули приложения перечисляет `:application.get_key/2`; кодеки — модули с
  интроспекцией кодека событий, семейства — плагины с интроспекцией семейства. Логика — публичные
  функции `check_*` над набором модулей (`:ok | {:error, пробелы}`), тест — `assert :ok = …`. Пустой
  обход — провал. Числовых нижних границ нет.
- Общая проверка текста подписи и keyword-списка без повторов — один helper подсистемы. Ошибки
  сборки — `CompileError`; опции `use` — через `Core.Helper.Opts.validate!` с разделением на
  обязательные и необязательные.

### Wire (`Core.Web.Labels`)

- `use Core.Web.Labels` в модуле приложения. Обязательные `codec:` (внешний профиль кодека
  приложения: им дампятся Prim-значения и id) и `user_ref:` — keyword со схемой ссылки на учётную
  запись (`schema:`) и захватом функции дампа (`dump:`, «дамп id, имя → map»).
- Порождает `to_wire/2`: событие и словарь ссылок → `%{title: String.t(), details: [map()]}`. Вид —
  строкой; число — строкой с десятичной точкой (integer — `Integer.to_string`, decimal — нормальная
  запись); текст, дата и дата-время — дампом кодека; ссылка на запись — `%{entity, id, name}`, вид
  записи — camelCase атома; ссылка на учётную запись — результат `dump:`; группа и список —
  рекурсивно; изменение — `%{label, kind: "change", old, new}`. Id без имени в словаре —
  исключение: словарь собирают с той же страницы.
- При `open_api_spex` у приложения тот же `use` делает модуль схемой семейства сведений
  (`oneOf` по видам, дискриминатор `kind`) и порождает вложенные модули схем видов. Названия схем —
  от последнего сегмента имени модуля приложения. Схема вида `user` ссылается на `schema:` из
  `user_ref:`. Проверка наличия `open_api_spex` — при раскрытии макроса; модули библиотеки на
  `OpenApiSpex` безусловно не ссылаются.
- Предпосылка — `open_api_spex` с `optional: true` в зависимостях библиотеки и норма о нём
  (ADR-0064). Их заводит фича схемы обёртки ответа, которая выпускается раньше. Если к началу
  wire-тикета её нет, тикет заводит зависимость и норму сам.
- Подмена строк-id в машинной нагрузке события и дамп самого события (`id`, `type`, `payload`, `at`,
  `by`) остаются у приложения.

### Совместимость и документы

- Wire `title` / `details` потребителя A после переезда не меняется: виды, порядок сведений, «Да» /
  «Нет», форма ссылок, числа строкой.
- Отличия объявлений от реализации потребителя A: префикс модулей, `ID` вместо `Id`, вид записи
  атомом вместо camelCase-строки, `CompileError` вместо `ArgumentError`; дамп и схема — через
  `use Core.Web.Labels`. Всё это — CHANGELOG, «Новое», с «было → стало» для переезда.
- Нормы:
  - механизм (что даёт каждый `use`, что ломает сборку) — `docs/rules/11-domain.md`, новый раздел
    «Подписи»;
  - использование — ярус потребителя с условием «приложение, отдающее сведения событий, MUST …»:
    `app/11-domain.md` (где объявляется, название без подстановок, ручные `label/1` / `labels/0` MUST
    NOT, `:hidden` — только служебное), `app/13-repos.md` (страница потока со словарём ссылок в
    usecase), `app/15-web-api.md` (дамп и схема через `Core.Web.Labels`), `app/19-testing.md`
    (ратчет).
  - Правка `app/**` — CHANGELOG тем же коммитом.
- `CONTEXT.md`, группа «Подписи», получает адрес нормы, когда появится раздел свода.
- moduledoc и примеры — `MyApp.*`, без терминов предметной области потребителей.

## Testing Decisions

Хороший тест проверяет поведение через публичный выход — сведения, словарь ссылок, подписи по типу,
JSON и его схему, отказ сборки, — а не служебную интроспекцию (`__label_*__`) и не внутренние
функции.

- **Домен на фикстурах.** Фикстуры событий, struct'ов, Enum и Prim с объявлениями — в `test/support`,
  резолверы — фикстурные, контекст — настоящий. Проверяются `Details.build/1` (каждый вид, группа,
  список групп map'ы с id в ключах, `:hidden`, `nil`-поле, `nil`-нагрузка, вариант семейства, Prim с
  `Core.Labels.Text`, Prim-композит, `boolean`, исключение у id без вида), `Refs.get/2` (глубина,
  один вызов резолвера на тип, пустой обход без вызовов, отказ резолвера, имя `nil`, автор события),
  `Fields.paths/1`, `label/1` / `labels/0`. Тесты потребителя A — образец сценариев, переносятся на
  фикстуры с обезличенными примерами.
- **Сборка объявления.** Компиляция модуля в тесте и `assert_raise CompileError` на каждый отказ из
  User Stories. Образец — тесты плагина по полям в `test/core/codec/`.
- **Wire.** Тестовый модуль приложения с `use Core.Web.Labels`; дамп сведений каждого вида
  сверяется со схемой, порождённой тем же `use` (`OpenApiSpex`), — требование ADR-0064. Число,
  camelCase вида записи, форма ссылки на учётную запись от `dump:`.
- **Ратчет.** Функции `check_*` на полном и сломанном наборе модулей (событие без названия, поле без
  решения, Enum без подписей, id без вида, вариант с расходящейся спекой, пустой обход); `use` — только
  опции. Образец — тест `Core.Es.EventCompatCase`.
- **Вывод типов и сборка без `open_api_spex`.** Фикстура-потребитель `fixtures/consumer` получает
  объявления всех видов и модуль с `use Core.Web.Labels`; у неё `open_api_spex` нет, поэтому она же
  проверяет ветку без схемы. Храповик — `make consumer-check` (ADR-0014).
- После каждого тикета — `make`.

## Out of Scope

- Схема и дамп события страницы событий целиком (`id`, `aggregateId`, `type`, `payload`, `at`, `by`).
  Их ведут руками три потребителя, различается только `by`. Следующий кандидат — отдельная фича
  `Core.Web.Event` с параметром `by:`, к которой подписи подключаются модулем приложения с
  `use Core.Web.Labels`.
- Схема обёртки ответа — отдельная фича, выпускается раньше этой.
- Локализация текстов и вид `boolean` без текста (ADR-0063).
- Разница «было → стало» вместо снимка нагрузки.
- Частичный ратчет — по части агрегатов приложения.
- Подмена строк-id в машинной нагрузке события ссылками на учётную запись.
- Переезд потребителя A — после выпуска, в его репозитории.

## Further Notes

- Выпуск — следующим после выпуска обёртки ответа; пункты — «Новое».
- После выпуска — handoff в репозиторий потребителя A: замена своих модулей подписей на
  `Core.Labels.*` и `Core.Web.Labels`, перенос общих норм на ярус библиотеки, свои частности
  остаются у него.
- Перед выпуском — проверка на потребителе A (`docs/agents/release-check.md`).
