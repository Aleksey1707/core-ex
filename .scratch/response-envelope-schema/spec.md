# OpenAPI-схема обёртки ответа: `Core.Web.Response.Schema`

Type: spec
Status: ready-for-agent

Решение и отвергнутые варианты — ADR-0065 (`docs/adr/0065-response-wrapper-schema-functions.md`),
механизм optional-зависимости — ADR-0064, форма обёртки — ADR-0062; термин — `CONTEXT.md`,
«Обёртка ответа».

## Problem Statement

Автор приложения на `Core.*` описывает ответы API в `operation/2` через OpenApiSpex, и схему
обёртки ответа пишет руками. Её пишут так все шесть потребителей, четырьмя разными способами, и все
шесть копий описывают форму до ADR-0062 (`{code, messages, data}`, страница `{count, items}`):
смена обёртки сделала их устаревшими ещё до выпуска. Схема расходится с тем, что пишет
`Core.Web.Response`, молча и у каждого потребителя отдельно; реальный ответ со схемой сверяет только
один из шести.

## Solution

Библиотека даёт схемы того, что пишет `Core.Web.Response`, функциями условного модуля
`Core.Web.Response.Schema` — он собирается, только если у приложения есть `open_api_spex`. Схема
данных эндпоинта — аргумент: `Response.Schema.success(Item)`, `page(Item)`; ошибка — общий модуль
`ErrorResponse`. Тест библиотеки сверяет со схемами каждую форму обёртки и каждую строку таблицы
`Core.Web.ErrorMapper`. Потребитель удаляет свой хелпер обёртки и переписывает вызовы.

## User Stories

1. Как автор приложения, я хочу описать успешный ответ эндпоинта одним вызовом
   `Response.Schema.success(Item)` в `operation/2`, чтобы схема обёртки не жила у меня копией.
2. Как автор приложения, я хочу описать успех без данных (`Response.Schema.success()`), чтобы
   ответ `data: {}` тоже был описан схемой библиотеки.
3. Как автор приложения, я хочу описать страницу одним вызовом `Response.Schema.page(Item)`, чтобы
   не заводить модуль страницы на каждый ресурс.
4. Как автор приложения, я хочу ссылаться на одну схему ошибки (`Response.Schema.error()`) у любого
   статуса ошибки, чтобы ошибка, не дошедшая до контроллера, и доменная описывались одинаково.
5. Как клиент API, я хочу видеть в схеме `status` перечислением (`ok` / `error`), чтобы различать
   исход по схеме, а не по соглашению.
6. Как клиент API, я хочу видеть в схеме ошибки `code` строкой, `message` и необязательный
   `data.errors` из `{code, message}`, чтобы разбирать множество ошибок по схеме.
7. Как клиент API, я хочу, чтобы новое поле обёртки не ломало мою валидацию ответа, чтобы
   расширение обёртки не было ломающим изменением.
8. Как читатель спецификации, я хочу видеть пример ошибки в `ErrorResponse`, чтобы форма ошибки
   была видна без запроса.
9. Как автор приложения без `open_api_spex`, я хочу собирать приложение без него, чтобы OpenAPI не
   стал условием `Core.Web.Response`.
10. Как сопровождающий библиотеки, я хочу, чтобы тест сверял со схемами `Response.*` и каждую
    строку `ErrorMapper.map/2`, чтобы схема не разошлась с дампом (ADR-0064).
11. Как автор приложения с хелпером обёртки, я хочу перейти на схемы библиотеки по списку
    «было → стало» в CHANGELOG, чтобы переезд был механическим.

## Implementation Decisions

- **Модуль.** `Core.Web.Response.Schema` под `if Code.ensure_loaded?(OpenApiSpex)`; модули
  библиотеки на него безусловно не ссылаются, а если сошлются — `no_warn_undefined` в `mix.exs`.
  Лист `Schema` занят `OpenApiSpex.Schema`, поэтому вызов — через родителя:
  `alias Core.Web.Response` → `Response.Schema.success(Item)`.
- **Функции:**
  - `success(data)` — `{status: enum ["ok"], data: <data>}`, обе обязательны;
  - `success()` — то же с `data` — объектом без свойств;
  - `page(item)` — `success` с `data: {items: [<item>], total: integer ≥ 0}`, обе обязательны;
  - `error()` — модуль `Core.Web.Response.Schema.Error`.
  Схемы успеха и страницы анонимные: без названия и без опции `title:`. `data` / `item` — модуль
  схемы, `%OpenApiSpex.Schema{}` или `%OpenApiSpex.Reference{}`.
- **`ErrorResponse`.** Модуль `Core.Web.Response.Schema.Error`, название `ErrorResponse`, одна
  схема на все статусы: `{status: enum ["error"], data: {errors?: [{code, message}]}, code: string,
  message: string}`, обязательны `status`, `data`, `code`, `message`; у элемента `errors` — `code`
  и `message`. `code` — строка без перечисления. Пример — ошибка домена с непустым `data.errors`.
  Модуль — не через макрос `OpenApiSpex.schema/2` (норма «OpenAPI-схемы wire»).
- Все объекты открытые: `additionalProperties: false` нет.
- Схемы описывают только то, что пишет `Core.Web.Response`: 202 `{id, version}`, `{id}`
  создания и курсорная страница остаются у приложения.
- Проверки `ensure_available!` нет: отсутствие модуля видно `UndefinedFunctionError` при сборке
  спеки. README — оговорка о пересборке `core` после добавления `open_api_spex`.
- **Нормы:**
  - `docs/rules/10-architecture.md`, «OpenAPI-схемы wire», — уточнение: параметр приложения,
    общий у схемы и дампа, — опция `use` в его модуле; схема данных места вызова — аргумент
    функции условного модуля библиотеки; таблица «Граница HTTP» — строка схемы обёртки;
  - `docs/rules/app/15-web-api.md`, «Schemas», — схема обёртки, страницы и ошибки —
    `Core.Web.Response.Schema`; своя — MUST NOT (вместо «собираются общими хелперами»). Норма
    «описывать каждый статус ошибки» не вводится.
- **CHANGELOG** — «Новое», было → стало по каждому способу потребителей:
  - хелпер, отдающий анонимную `%Schema{}` (`data_response(X)` / `info_response()` / `page(X)`) →
    `Response.Schema.success(X)` / `success()` / `page(X)`, модули страниц ресурсов удаляются;
  - хелпер с названием (`of(X, title)` / `empty(title)`, `of(page_of(X, title), title)`) → те же
    вызовы без названия: названия ответов уходят из components;
  - модуль ответа на операцию поверх хелпера → вызов по месту в `operation/2`, модуль удаляется;
  - `allOf` над своим компонентом обёртки → вызов по месту, компонент и модули ответов удаляются;
  - свой компонент ошибки → `Response.Schema.error()`, свой удаляется; его пример старой формы
    больше не проходит ратчет примеров.

## Testing Decisions

Хороший тест сверяет то, что пишет библиотека, со схемой, которую она же отдаёт, через
`OpenApiSpex` (`assert_schema` / `cast_value` на спеке с `add_schemas`), после круга через JSON.

- `success/0,1` и `page_data/2` под `success/1` — против `success()`, `success(Item)`, `page(Item)`
  на фикстурной схеме элемента.
- `error/2,3` и каждая строка `Core.Web.ErrorMapper.map/2` (412, 403, 401, 400, 500 прикладная и
  не-`%Error{}`, `Error.many` на доменной строке) — против `ErrorResponse`.
- Пример `ErrorResponse` проходит свою схему.
- Отказ: тело ошибки против схемы успеха, `status` не из перечисления, `code` числом, страница
  без `total`.
- Сборка без `open_api_spex` — `make compile-no-optional`.
- После каждого тикета — `make`.

## Out of Scope

- Курсорная страница, 202 `{id, version}`, `{id}` создания.
- Перечисление кодов ошибки по эндпоинту.
- Норма об описании каждого статуса ошибки в `operation/2`.
- Ошибки по полям `data.fields` (`.scratch/http-response-envelope/issues/01-error-fields.md`).
- Схема и дамп события страницы событий (`Core.Web.Event`).
- Переезд потребителей — после выпуска, в их репозиториях.

## Further Notes

- Выпуск — тем же выпуском, что смена обёртки (ADR-0062) и подписи (`.scratch/labels/`):
  потребитель переписывает схемы обёртки один раз, сразу на схемы библиотеки.
- `open_api_spex` (`optional: true`) и норма «OpenAPI-схемы wire» уже заведены тикетом
  `.scratch/labels/issues/09-openapi-schema.md`.
