# Один запрос и один план чтения event-sourced агрегата

Внутренний рефакторинг пути чтения после волны `es-read-engine`. Термины — `CONTEXT.md`,
«Состояние на версии», «Адрес версии», «Снапшот», «Поток событий», «Незаведённый агрегат»;
нормы — `docs/rules/13-repos.md`, «Состояние на версии», `docs/rules/21-observability.md`,
«Event sourcing»; решения — ADR-0094, ADR-0016, ADR-0019, ADR-0076.

## Problem Statement

Движок чтения `Core.Es.Aggregate.Load` уже владеет свёрткой и сверкой версии, но шов вокруг него
не закрыт, и понимание одного чтения требует держать в голове всю связку.

Внутренняя заявка на чтение — map, которую собирают восемь мест: пять живых точек входа
репозитория агрегата, две мёртвые (версионное чтение ушло в read-репозиторий по ADR-0094, а функции
остались) и две точки read-репозитория. Обязательные и необязательные ключи этой map (`states` против
`state`, флаг «можно писать снапшоты», `born?`, `many?`, `decide`) меняют ветвление движка, но
конструктора нет: каждая новая операция повторяет форму руками.

Read-репозиторий достаёт конфигурацию чтения из persisted-атрибута чужого макроса через
`module_info(:attributes)` и зовёт служебный `fetch/3` репозитория агрегата напрямую. То есть макрос
write-репозитория обязан держать и атрибут, и функцию, но этот контракт нигде не объявлен.

План снапшота разложен по трём модулям: маркер считается трижды за одно чтение (в SQL-запросе, при
сборке адресов расшифровки и при записи снапшота), «какой снапшот брать и какой хвост читать»
считает SQL-билдер, а «какой расшифрованный снапшот какому потоку принадлежит» — движок, который
режет общий список по позиции. Сдвиг порядка — тихая ошибка, а не падение.

Тестовый источник строк вынужден переписывать SQL-фильтр на Elixir: он повторяет границы снапшота,
потолок версии и выбор последнего снапшота. Расхождение дублёра с SQL видно только по редкому тесту.

## Solution

Заявка на чтение становится структурой с конструктором на операцию; план чтения — структурой, которая
считает маркер один раз и владеет границами потоков; источник строк — behaviour с двумя адаптерами
(SQL и тестовый). Read-репозиторий получает конфигурацию чтения функцией макроса, а не интроспекцией
атрибута; мёртвые версионные функции репозитория агрегата удаляются.

Телеметрия, исходы, коды ошибок, detail отказа и поведение снапшотов не меняются. Потребитель
обновление не замечает.

## User Stories

1. As мейнтейнер библиотеки, I want заявку на чтение задавать структурой, so that новая операция не повторяла форму map руками.
2. As мейнтейнер библиотеки, I want у каждой операции был конструктор, so that обязательные и необязательные ключи были видны в одном месте.
3. As мейнтейнер библиотеки, I want имена операций сохранились, so that телеметрия `[:es, :aggregate, :load]` и `[:es, :aggregate, :fold]` с меткой `op:` не разошлась с дашбордами.
4. As мейнтейнер библиотеки, I want флаг «можно писать снапшоты» назывался по смыслу, so that его не путали с «снапшоты включены».
5. As мейнтейнер библиотеки, I want read-репозиторий получал конфигурацию чтения функцией, so that контракт между макросами был объявлен, а не выковыривался из атрибутов.
6. As мейнтейнер библиотеки, I want мёртвые версионные функции репозитория агрегата удалены, so that у чтения на версии остался один вход.
7. As мейнтейнер библиотеки, I want маркер снапшота считался один раз за чтение, so that `module_info(:md5)` по всем модулям событий не повторялся на каждый шаг.
8. As мейнтейнер библиотеки, I want границы потоков и выбор снапшота считал план, so that SQL-билдер не был вторым владельцем политики чтения.
9. As мейнтейнер библиотеки, I want расшифрованный снапшот возвращался вместе со своим потоком, so that склейка по позиции не могла молча сдвинуться.
10. As мейнтейнер библиотеки, I want источник строк был behaviour, so that SQL и тестовый источник реализовывали один контракт.
11. As мейнтейнер библиотеки, I want тестовый источник не переписывал SQL-фильтр, so that расхождение дублёра с продакшеном ловилось сборкой, а не редким тестом.
12. As мейнтейнер библиотеки, I want свёртку и сверку версии проверять без Postgres, so that регрессия в нарезке версий и снапшотах ловилась быстро.
13. As разработчик приложения, I want `get` / `get_many` / `get_decision` / `refresh` не изменили исходы, so that usecase'ы не правились.
14. As разработчик приложения, I want чтение на версии через read-репозиторий не изменилось, so that `get_at` / `get_many_at` работали как раньше.
15. As разработчик приложения, I want коды ошибок и `source: :expected` / `:address` не изменились, so that повтор команды и разбор отказа остались прежними.
16. As разработчик приложения, I want снапшоты и расшифровка ПДн-значений не изменились, so that уничтоженный ключ субъекта по-прежнему давал уничтоженное значение.
17. As разработчик приложения, I want запись снапшота после чтения сохранилась, so that `snapshot: every:` продолжал работать.
18. As оператор приложения, I want метрики чтения и свёртки не изменились, so that алерты и дашборды не требовали правок.

## Implementation Decisions

- **`Core.Es.Aggregate.Load.Request` — структура заявки.** Поля: операция, опции вызова, источник
  строк, флаг «писать снапшоты», состояния потоков (`states` для головы и пачки, `state` для чтения
  на версии), пары для пачечного чтения на версии, версия, `born?`, `many?`, функция решения. Обязательны
  только операция и опции; остальные ставит конструктор операции.
- **Конструкторы — по именам операций**: `get`, `get_decision`, `get_many`, `refresh`, `get_at`,
  `get_many_at`. Они повторяют то, что сейчас делают точки входа, включая `born?`, `many?` и
  `decide`. Источник по умолчанию — SQL-адаптер.
- **Имена операций не меняются.** `op` остаётся `:get`, `:get_decision`, `:get_many`, `:refresh`,
  `:get_at`, `:get_many_at`: по ним размечена телеметрия и норма `21-observability.md`.
- **`write?` переименовывается в `write_snapshots?`.** Значение прежнее: «можно писать снапшоты после
  чтения», не «снапшоты включены».
- **`Core.Es.Aggregate.Load.Plan` — план чтения.** Содержит маркер снапшота (считается один раз),
  признак расшифровки, порог записи снапшотов, флаг записи и потоки. Поток плана — адрес
  (`aggregate_id`), нижняя граница (`after_version`), потолок (`to_version`), граница снапшота
  (`snapshot_to`) и признак «снапшот разрешён». Состояния агрегатов и их версии остаются в заявке и в
  движке: источник строк про них не знает.
- **`Core.Es.Aggregate.Load.Source` — behaviour.** Один колбэк: по конфигурации, плану и опциям
  вернуть для каждого потока его снапшот (если есть) и строки хвоста. Адаптеры: SQL в репозитории
  агрегата и тестовый источник строк. Замыкание в заявке заменяется модулем.
- **`Load` строит план и передаёт его источнику.** Свёртка, сверка версии, повторное чтение
  отвергнутых снапшотов, телеметрия и запись снапшотов остаются в движке; меняется только источник
  данных и владелец границ.
- **`Snapshot` принимает план вместо пересчёта маркера.** Расшифровка адресов, раскладка открытых
  снапшотов по потокам и запись используют маркер из плана. `marker/1` остаётся доступной для теста,
  который проверяет зависимость маркера от настройки расшифровки.
- **Расшифрованный снапшот возвращается вместе с потоком.** Список открытых исходов перестаёт быть
  общим и позиционным: источник и движок не режут его по индексу.
- **Read-репозиторий получает конфигурацию функцией.** Write-репозиторий объявляет
  `__es_read_cfg__/0` (служебную, вне публичного API); read-репозиторий проверяет её наличие на
  компиляции и зовёт её в рантайме. Интроспекция persisted-атрибута и общий `fetch/3` как публичная
  точка — уходят.
- **Мёртвые функции удаляются.** Версионное чтение у репозитория агрегата остаётся только внутренним:
  публичный шов — read-репозиторий (ADR-0094).
- **Порядок работ (тикеты).** 01 — `Request`, конструкторы во всех точках входа, `__es_read_cfg__/0`,
  удаление мёртвых функций. 02 — `Plan`, behaviour `Source`, маркер один раз, тестовый источник строк,
  раскладка расшифрованных снапшотов по потокам.
- **CHANGELOG не пополняется.** Все затронутые функции и модули — `@doc false`; публичные головы,
  исходы и телеметрия не меняются.

## Testing Decisions

- Хороший тест проверяет наблюдаемое поведение: состояние агрегата, исход (включая detail отказа),
  события телеметрии и записанный снапшот. Внутренние имена и форма SQL не проверяются.
- **Шов чтения — read-репозиторий на реальной базе.** `get_at` / `get_many_at` проверяются через
  свой behaviour; образец — общий контракт read-репозитория и тесты со снапшотами.
- **Шов записи и головы — репозиторий агрегата** через общий контракт репозитория: `get`, `get_many`,
  `get_decision`, `refresh` (включая незаведённый агрегат и сверку версии).
- **Шов движка без базы — `Source`.** Тестовый источник строк реализует behaviour и получает готовый
  план: проверяются границы версий, выбор снапшота, отвергнутый снапшот и повторное чтение, свёртка
  пакета версий. Это единственный новый шов; он заменяет нынешнюю копию SQL-фильтра, а не добавляется
  рядом с ней.
- **Шов снапшотов — реальная база**: запись после чтения по `every:`, расшифровка, уничтоженный ключ
  субъекта, зависимость маркера от настройки расшифровки.
- **Метрики** проверяются на событиях телеметрии: те же имена, измерения и метка `op:`; образец —
  тесты метрик event sourcing.

## Out of Scope

- Читатели брокера (следующая волна), подписи, проекции и кодек-поля.
- Раскладка `Load` внутри (сверка версии, свёртка пакета версий) — уже сделана волной `es-read-engine`.
- Алгоритм снапшота: `sealed`/`open`, AAD, уничтожение ключа субъекта.
- `Core.Es.Store` как хранилище строк: SQL-запрос остаётся в репозитории агрегата.
- Типизация конфигурации event-sourced репозитория (это отдельная тема, не карточка чтения).
- Публичный API `Core.Es.Aggregate.ReadRepo` — головы и исходы не меняются.

## Further Notes

- Мотивация: волна `es-read-engine` вынесла движок, но оставила вокруг него три источника истины —
  форму заявки, границы потоков и маркер. Спека закрывает шов, не пересматривая решения ADR-0094.
- Главный риск — раскладка расшифрованных снапшотов по потокам: сейчас порядок держится тремя
  модулями и ловится только личными тестами на ПДн. В 02 это должно стать свойством структуры
  «поток + его снапшот», а не соглашением о порядке.
- Второй риск — тестовый источник: если он останется копией SQL-фильтра, выигрыша нет. Поэтому план
  обязан нести готовые границы, а адаптер — только выбирать строки по ним.
- `snapshot_to` у отвергнутого снапшота приравнивается к нижней границе — это поведение движка и
  остаётся в нём; план получает уже посчитанное значение.
- Параллельно идёт отдельная маленькая спека `projection-fixtures`: она не пересекается с этим швом.
