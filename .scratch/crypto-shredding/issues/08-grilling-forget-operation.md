# Операция уничтожения ключа

Type: grilling
Status: resolved
Blocked by: 01, 06, 07
Map: [Crypto-shredding персональных данных в событиях :core](../map.md)

## Question

Как потребитель уничтожает ПДн субъекта:

- API: модуль, сигнатура (`…, context`), CQS — изменяющая; вызывается из usecase потребителя;
- транзакция: своя или внутри `Transact.run` потребителя; что ещё меняется в той же транзакции;
- один шаг или два: сразу ключ — или сначала событие уничтожения в потоке, затем ключ с задержкой (akka-gdpr);
- идемпотентность: повтор, уничтожение несуществующего ключа, уничтожение во время команды того же субъекта;
- запись ПДн субъекта после уничтожения его ключа (поздняя команда, повторное согласие): новый ключ или отказ
  записи; аргумент операции — идентификатор субъекта, UUID-Prim
  ([Единица ключа и субъект данных](04-grilling-key-unit.md));
- подтверждение для 152-ФЗ (акт и выгрузка из журнала, хранятся 3 года): библиотека даёт субъекта, категории,
  способ, причину и дату — где это лежит (событие, журнал, возврат вызывающему); журнал называет субъекта, то
  есть сам содержит ПДн и не шифруется уничтожаемым ключом;
- кого операция обязана известить: процессы агрегатов, проекции (контракт read-модели — в Not yet specified
  карты); кеша ключей на нодах нет ([Хранилище ключей](07-grilling-key-store.md));
- уникальный индекс по субъекту в таблице встроенного хранилища — по живым ключам или полный (следует из
  ответа о записи после уничтожения); идемпотентность, на которой стоит повтор уничтожения по актам после
  восстановления копии ([Хранилище ключей](07-grilling-key-store.md)).

## Answer

Решено в grilling 2026-10-18; ADR — [ADR-0076](../../../docs/adr/0076-subject-key-destruction-final.md), термин
«Уничтожение ключа субъекта» — `CONTEXT.md`, «Персональные данные».

- **Один шаг**: ключ уничтожен в момент commit, заявки и фоновой фазы нет. Задержку потребитель ставит своей
  очередью задач. Отвергнут akka-gdpr — событие, затем ключ с задержкой: ПДн читаемы весь срок, нужен воркер,
  дата в акте расходится с вызовом.
- **API** — функция фасада хранилища ключей `(subject_id, context)`, условно `Core.Es.Personal.destroy_key/2`
  (имя — в спеке); реализация — через `Core.Config`. `subject_id` — UUID-Prim (`Prim.UUID` / `Prim.Compose` над
  ним), строки UUID нет. Изменяющая, возврат `Result.unit()`; хранилище не ответило — `{:error, %Error{kind:
  :app}}`. Права проверяет usecase.
- **Транзакция** — вызывающего, если открыта (`Transact.run(DAO, …)`), иначе своя. Библиотека в ней меняет только
  строку ключа; потребитель кладёт рядом своё событие об уничтожении и чистку своих таблиц. Реализация порта мимо
  транзакции уничтожает необратимо — это в контракте порта. Отвергнут `ArgumentError` внутри транзакции.
- **Запись после уничтожения — отказ**: уникальный индекс по субъекту полный, строка-след держит субъекта
  навсегда. Повторное согласие — новый идентификатор субъекта; у субъекта `:aggregate_id` агрегат больше не
  пишет событий с непустым ПДн-значением. Отвергнут новый ключ (частичный индекс): поздняя команда, ретрай
  подписчика или устаревшее состояние процесса агрегата молча воскресили бы ПДн.
- **Ошибка отказа** — `%Error{kind: :domain}`, строит библиотека: фиксированный код (условно
  `:subject_destroyed`), `ns` хранилища ключей, константный текст, `detail` — идентификатор субъекта, без
  идентификатора ключа; строка в таблице «`ns`, которые ставит библиотека». `Es.Transact` не повторяет. `nil`
  необязательного ПДн-поля не шифруется и отказа не даёт. Отвергнут код из каталога `errors:`.
- **Субъект без ключа** — строка-след без ключа (`INSERT … ON CONFLICT (subject) DO UPDATE`): следующая запись
  ПДн получает отказ. **Повтор** — `:ok`, первая дата уничтожения не перезаписывается; на этом стоит повтор по
  актам после восстановления копии.
- **Гонка с командой того же субъекта** — встроенная реализация читает строку ключа при шифровании `FOR SHARE`,
  `UPDATE` уничтожения её ждёт: событие либо записано раньше и уничтожено, либо получает отказ. Контракт своей
  реализации — минимум: после уничтожения ни одно ПДн-значение субъекта не читается. Взаимная блокировка при
  уничтожении нескольких субъектов одной транзакцией вразнобой — Postgres обрывает одну.
- **Подтверждение** — журнала библиотеки нет. След — строка хранилища ключей (субъект, время создания и
  уничтожения), способ — описание встроенной реализации в своде. Причину, автора, категории, ИСПДн и ФИО
  потребитель пишет в свой акт, например событием в той же транзакции. Дата не возвращается.
- **Чтения «уничтожен ли»** нет: запись защищает отказ, команду потребитель отвергает по своему состоянию.
- **Извещение** — операция никого не извещает: связи «субъект → потоки» нет, кеша ключей нет. Третьих лиц
  (ст. 20 ч. 3) извещает потребитель. Сигнал, если его потребуют процессы или read-модель, добавится без смены
  сигнатуры.

Передано дальше:

- в [Снапшот и процесс агрегата после уничтожения ключа](11-grilling-state-caches.md) — операция процессы не
  извещает; устаревшее состояние процесса при записи ПДн получает отказ, но держит открытые ПДн в памяти до
  `idle_timeout`;
- в [Резерв ключа из ПДн](10-grilling-key-reservation.md) — уничтожение окончательно, операция резервы не
  трогает; транзакция вызывающего доступна для снятия резерва рядом;
- в [Контракт read-модели после уничтожения ключа](13-grilling-read-model-contract.md) — операция проекции не
  извещает; доменное событие потребителя в той же транзакции — кандидат сигнала;
- в туман «Раскладка сводов» — норма: акт пишет потребитель; повторное согласие — новый идентификатор субъекта;
  отображение отказа записи в usecase;
- в туман «Наблюдаемость» — лог и span операции, автор из `%Context{}`.

Уточнено в [Контракт read-модели после уничтожения ключа](13-grilling-read-model-contract.md) 2026-10-18
([ADR-0079](../../../docs/adr/0079-key-destruction-event-for-projections.md)):

- в транзакции уничтожения библиотека, кроме строки ключа, пишет событие уничтожения ключа в поток субъекта —
  проекциям; процессы, снапшоты и третьих лиц операция по-прежнему не извещает;
- «чистка своих таблиц» — строки state-stored агрегатов и таблицы не проекций; таблицы read-модели usecase
  уничтожения MUST NOT трогать, их чистит проекция по событию уничтожения ключа.

Уточнено при сведении в спеку 2026-10-18 (ADR-0076 и ADR-0079 поправлены): у `%Context{}` поля автора нет, а
`es_events.by_id` — `NOT NULL`. Сигнатура операции — `(subject_id, by, context)`: `by` — UUID-Prim актора, его
usecase берёт своим `CurrentUser` до транзакции, как `by` команды; `at` события уничтожения ключа — часы
библиотеки в момент вызова.
