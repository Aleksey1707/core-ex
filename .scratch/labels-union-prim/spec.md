# Labels: видимое семейство Prim-вариантов — лист в сведениях события

Type: spec
Status: ready-for-agent

Термины — `CONTEXT.md`, «Подписи»; решение области — ADR-0063 (подписи событий), ADR-0066 (wire сведений
события страницы событий). Новое решение фиксируется ADR-0098. Факты о потребителях — обезличенно
(`AGENTS.md`, «Потребители — обезличенно»).

## Problem Statement

Потребитель A хочет показать в сведениях события значение-семейство (`union:`), варианты которого — Prim
(например, способ связи: телефон / email / ссылка на запись). Сегодня видимое поле `union:` всегда выходит
группой: обход сведений раскрывает вариант через его объявление полей (`Core.Labels.Fields`), а у
Prim-варианта такого объявления нет — Prim не struct по полям. Результат — `UndefinedFunctionError` в
рантайме на странице событий. Единственный обходной путь — держать поле скрытым (`:hidden`), и человек
не видит значение вовсе.

Дополнительно ратчет полноты (`Core.Labels.CompletenessCase`) сегодня обходит варианты семейства как
struct'ы: Prim-вариант видимого поля попал бы в пробел «struct без решения по полям», даже если с видом
у него всё в порядке. Пробел области не виден ни сборке, ни ратчету — он всплывает только в рантайме.

## Solution

Видимое поле `union:` выводится по значению:

- значение — вариант-Prim → **лист**: вид и значение по варианту (`Core.Labels.Text` → текст функции,
  `Core.Labels.ID` → `id` / `user` / `ref`, без объявления — plain-вид Prim: `text` / `number` / `date` /
  `datetime`);
- значение — вариант-struct с `Core.Labels.Fields` → **группа**, как сегодня.

Эффективная спека листа — модуль варианта, не модуль семейства: объявления вида и текста применяются
к варианту. Словарь ссылок находит id Prim-варианта с резолвером без каких-либо правок своего обхода.
Уничтоженное ПДн-значение остаётся видом `destroyed` без значения; поле без значения — как сегодня.
Неподдерживаемый вариант (struct без `Core.Labels.Fields`, не Prim) даёт понятный `ArgumentError` с именем
модуля, а не `UndefinedFunctionError`. Ратчет полноты проверяет видимые `union:`-поля: каждый вариант —
либо Prim с известным видом, либо struct с объявлением полей; скрытое поле не проверяется.

Wire сведений не меняется: новых видов нет, значение листа — результат `Labels.Text` / `Labels.ID` или
Prim, дампнутый кодеком. Правка кода потребителя не требуется; скрытое поле-семейство можно сделать видимым.

## User Stories

1. Как разработчик приложения-потребителя, я хочу объявить видимым поле `union:` семейства с Prim-вариантами, чтобы человек видел значение в истории агрегата, а не скрытое поле.
2. Как человек, читающий историю агрегата, я хочу видеть значение-семейство с вариантом-Prim как подписанный лист, чтобы читать его так же, как обычное поле-Prim.
3. Как человек, читающий историю агрегата, я хочу видеть вариант с `Core.Labels.Text` текстом его функции, чтобы читать значение по-человечески, а не как дамп.
4. Как человек, читающий историю агрегата, я хочу видеть вариант-Prim без объявления вида его plain-видом (`text` / `number` / `date` / `datetime`), чтобы значение имело правильный вид без лишних объявлений.
5. Как человек, читающий историю агрегата, я хочу видеть вариант с `Core.Labels.ID kind: :ref` ссылкой на запись с видом записи, чтобы понимать, на какую запись ссылается значение.
6. Как человек, читающий историю агрегата, я хочу видеть вариант с `Core.Labels.ID kind: :user` ссылкой на учётную запись, чтобы видеть её имя из словаря ссылок.
7. Как человек, читающий историю агрегата, я хочу видеть вариант с `Core.Labels.ID kind: :id` текстом-id, чтобы id без резолвера не ломал сведения.
8. Как разработчик приложения-потребителя, я хочу, чтобы id Prim-варианта с резолвером попадал в словарь ссылок страницы событий, чтобы имя записи резолвилось пачкой вместе с остальными id.
9. Как разработчик приложения-потребителя, я хочу, чтобы объявления вида и текста действовали на вариант через цепочку композита (`Core.Prim.Compose`), чтобы вариант-композит над id или текстом работал как обычный Prim.
10. Как человек, читающий историю агрегата, я хочу видеть уничтоженное ПДн-значение варианта видом `destroyed` без значения, чтобы уничтоженное значение не показывалось и не ломало страницу.
11. Как человек, читающий историю агрегата, я хочу видеть поле-семейство без значения (`nil`, `optional:`) как сегодня — группа с `value: nil`, чтобы поведение пустого поля не менялось.
12. Как человек, читающий историю агрегата, я хочу видеть вариант-struct с объявлением полей группой его видимых полей, чтобы существующие семейства (например, фигуры) не изменили свой вид.
13. Как разработчик приложения-потребителя, я хочу, чтобы скрытые поля-семейства вели себя ровно как раньше, чтобы правка не трогала работающие скрытые поля.
14. Как разработчик приложения-потребителя, я хочу получать понятный `ArgumentError` с именем модуля варианта на неподдерживаемом варианте (struct без `Core.Labels.Fields`, не Prim), чтобы сразу видеть причину, а не `UndefinedFunctionError` в глубине обхода.
15. Как разработчик приложения-потребителя, я хочу, чтобы ратчет полноты ловил Prim-вариант без вида (`Kind.of/1` — `:unkinded`) на сборке тестов, чтобы пробел не всплывал в рантайме на странице событий.
16. Как разработчик приложения-потребителя, я хочу, чтобы ратчет полноты ловил Prim-вариант с custom-видом (`Kind.of/1` — `{:custom, _}`), чтобы значение без вида в сведениях не проходило проверку.
17. Как разработчик приложения-потребителя, я хочу, чтобы ратчет полноты ловил вариант-struct без `Core.Labels.Fields` пробелом «struct без решения по полям», чтобы неподдерживаемый вариант был виден до рантайма.
18. Как разработчик приложения-потребителя, я хочу, чтобы ратчет полноты не проверял скрытое поле-семейство, чтобы скрытые значения не требовали объявлений.
19. Как разработчик приложения-потребителя, я хочу, чтобы ратчет полноты не считал Prim-вариант «struct'ом без решения по полям», чтобы корректное семейство Prim-вариантов проходило проверку.
20. Как разработчик приложения-потребителя, я хочу, чтобы `Core.Labels.Fields.paths/1` для `union:` по-прежнему отдавал только подпись поля, чтобы подписи по типу не зависели от неизвестных вариантов.
21. Как разработчик приложения-потребителя, я хочу, чтобы wire сведений события страницы событий не получил новых видов и форм, чтобы контракт API моего приложения не изменился.
22. Как разработчик приложения-потребителя, я хочу, чтобы элементы списка, множества и значения словаря с вариантом-Prim выходили листом по варианту, чтобы контейнеры над семейством работали так же, как поле.
23. Как разработчик приложения-потребителя, я хочу, чтобы стороны изменения «было → стало» со значением-семейством выводились по тому же правилу, чтобы изменение на семейство не было особым случаем.
24. Как разработчик приложения-потребителя, я хочу, чтобы словарь ссылок не расширялся на id под `text:`-вариантом и на уничтоженное значение, чтобы словарь оставался не шире сведений.
25. Как разработчик библиотеки, я хочу, чтобы решение было зафиксировано ADR со ссылками на ADR-0063 и ADR-0066 и отклонёнными альтернативами, чтобы область не переоткрывалась.
26. Как разработчик приложения-потребителя, я хочу запись в CHANGELOG «Не выпущено» с пометкой «правка потребителя не требуется», чтобы понимать влияние выпуска на мой код.
27. Как разработчик приложения-потребителя, я хочу, чтобы проверка на приложении-потребителе прошла до выпуска (path-зависимость, полный `make`), чтобы выпуск не сломал потребителя.
28. Как мейнтейнер библиотеки, я хочу выпуск `0.19.0-rc.3` поверх двух незапушенных коммитов ветки, чтобы состав пререлиза соответствовал накопленным записям «Не выпущено».

## Implementation Decisions

- **Правка в обходе значений (`Core.Labels.Walk`), не в сведениях.** Узел видимого значения для спеки
  `union:` со struct-значением: вариант-Prim (`Core.Prim.prim?/1`) даёт лист со **спекой `prim:` модуля
  варианта** (подмена спеки семейства на спеку варианта); вариант-struct с объявлением полей — группу,
  как сегодня; прочий вариант — `ArgumentError` с именем модуля варианта. `nil` и уничтоженное значение
  отсекаются по значению раньше разбора варианта и сохраняют сегодняшнее поведение.
- **Сведения (`Core.Labels.Details`) и словарь ссылок (`Core.Labels.Refs`) функционально не меняются.**
  Подменённая спека `prim:` варианта подхватывается существующими клаузами вида и значения листа
  (`prim_shape`, `prim_value`) и словаря (`leaf` со спекой `prim:` → группировка по резолверу). Отклонённая
  альтернатива — особые клаузы `union:` в сведениях при спеке семейства: словарь ссылок молча терял бы id
  Prim-вариантов, так как его листовые клаузы спеку семейства не знают.
- **Обход объявлений (`Walk.declarations`) маршрутизирует Prim-варианты как места `prim`, варианты-struct —
  как места `struct`.** Это снимает ложный пробел «struct без решения по полям» для Prim-вариантов и отдаёт
  их под существующую проверку вида id. Новых генерируемых тестов ратчета не нужно: состав вариантов покрыт
  существующими проверками полей и id. Проверка спеки варианта против спеки плагина Prim-варианты уже
  пропускает (она только для декларативных вариантов).
- **Известный вид варианта — `Kind.of/1` не `:unkinded` и не `{:custom, _}`.** Предикат пробела вида в
  ратчете расширяется на `{:custom, _}` глобально: это закрывает и существующую дыру обычных `prim:`-полей
  с custom-видом. В сведениях клауза вида Prim для `{:custom, _}` даёт `ArgumentError` по образцу
  `:unkinded`, а не `FunctionClauseError`.
- **Проверка вариантов — ратчетом (тестом), не сборкой.** На сборке нагрузки варианты семейства могут быть
  ещё не собраны или жить в другом приложении-плагине; полнота держится тестом на всё дерево модулей
  приложения, как и остальные объявления подписей (ADR-0063).
- **Wire не меняется.** Видов сведений не прибавляется; значение листа — результат `Labels.Text` /
  `Labels.ID` или Prim как есть, дамп кодеком. Событие страницы событий и его OpenAPI-схемы не правятся.
- **Новых макросов и опций нет.** Объявление текста/вида на семействе (например, отдельный `use` для
  семейства) отклонено: вид берётся по варианту, объявления уже есть у Prim.
- **Фикстура семейства Prim-вариантов — на новых Prim-модулях, выделенных под семейство.** Вариант-Prim
  занимает свой модуль в фасаде; тот же Prim не может быть ещё и `prim:`-полем в том же фасаде — существующие
  фикстурные Prim не годятся. Состав вариантов: с `Core.Labels.Text`, plain без объявления, с
  `Core.Labels.ID kind: :ref` (вид записи + резолвер) и `kind: :user` (резолвер); резолверы — существующие
  фикстурные. Плагин семейства регистрируется в общем наборе плагинов кодек-фикстуры; новое событие с
  видимым `union:`-полем входит в полный набор ратчета полноты. Сломанная фикстура получает Prim-вариант
  без вида; вариант-struct без объявления полей в ней уже есть.
- **Документация:** таблица видов сведений — строка про `union:` (группа у struct-вариантов, лист по
  варианту у Prim-вариантов, спека листа — модуль варианта); раздел про `union:` в объявлении полей;
  moduledoc ратчета полноты (Prim-варианты проверяются как Prim). ADR-0098: контекст, решение, отклонённые
  альтернативы (явный текст на семействе, новый макрос, объявление на семействе), следствия; ссылки на
  ADR-0063 и ADR-0066.
- **CHANGELOG** в том же коммите: «Не выпущено» → «Новое» — поведение ранее падало, wire не меняется,
  правка потребителя не требуется; ратчет полноты стал строже к вариантам (и к custom-виду Prim).
- **Выпуск:** `make release VERSION=0.19.0-rc.3` (версия сейчас `0.19.0-rc.2`), коммит сведения, тег на
  коммит сведения; в пререлиз входят два незапушенных коммита ветки («view: build the field IR once»,
  «field: check kind completeness at compile time»). Push и тег — только по явному запросу пользователя.
  До выпуска — проверка на потребителе A по workflow release-check (path-зависимость, симлинк рабочей копии,
  полный `make`).

## Testing Decisions

- **Швы — только существующие публичные, новых нет** (подтверждено пользователем):
  1. `Core.Labels.Details.build/1` — основной шов поведения сведений;
  2. `Core.Labels.Refs.get/2` — словарь ссылок;
  3. `Core.Labels.CompletenessCase.check_*/1` — ратчет полноты;
  4. `Core.Labels.Fields.paths/1` — регрессия подписей по типу.
  Правка внутри обхода значений приватная и отдельно не тестируется.
- **Хороший тест** сверяет внешнее поведение: полную форму сведения (`label` / `kind` / `value`, у ссылки —
  `entity`), состав словаря ссылок и вызовы резолверов (фикстурные резолверы шлют сообщения процессу теста),
  точные кортежи пробелов ратчета `{владелец, поле, модуль}`. Внутренние узлы обхода и подмена спеки не
  ассертятся.
- **Кейсы сведений:** вариант с `Labels.Text` → лист `text` с текстом функции; вариант без объявления →
  лист plain-вида с Prim-значением; вариант `Labels.ID` → `ref` с видом записи / `user` / `text` для `id`;
  уничтоженное значение → `destroyed` без `value`; `nil` → группа с `value: nil`; вариант-struct → группа
  (регрессия существующего кейса семейства фигур); неподдерживаемый вариант → `ArgumentError` с именем
  модуля; вариант-композит — вид базы.
- **Кейсы словаря ссылок:** id варианта `ref`/`user` с резолвером резолвится пачкой; вариант под `text:` и
  уничтоженное значение в словарь не попадают; существующие кейсы скрытых полей не меняются.
- **Кейсы ратчета:** полный набор с новым семейством Prim-вариантов проходит все проверки; Prim-вариант без
  вида — пробел вида id с владельцем, полем и модулем; вариант-struct без объявления — пробел полей;
  скрытое поле-семейство пробела не даёт; семейство без плагина — существующий пробел неизвестного семейства.
- **Регрессия:** `paths/1` для `union:` — только подпись поля; таблица «вид × подписи × ссылки × полнота»
  расширена новым плагином/кодеком; существующие тесты сведений, словаря и ратчета не меняют ожиданий.
- **Prior art:** describe «вложенность» тестов сведений (группа варианта семейства фигур), таблица
  «вид × подписи» (сведения, словарь и полнота по каждому виду), тесты ратчета на сломанной фикстуре
  (точные пробелы), тесты словаря на скрытых полях и `text:`.
- **Проверка целиком:** `make` (boundary-check → rules-check → layout-check → spec-check → format-check →
  compile → compile-no-optional → consumer-check → deps-clean → xref → dialyzer → test → credo → audit).

## Out of Scope

- Wire событий, кодек, outbox, golden-фикстуры событий — не меняются.
- Поведение `Core.Labels.Fields.paths/1`, `Core.Labels.Values`, `Core.Labels.Refs` — не меняется.
- Новые макросы и опции объявления (`use Core.Labels.Union, text: …` и подобные) — отклонены.
- Поведение скрытых полей — не меняется.
- Правка кода приложения-потребителя — не требуется; обновление `tag:` у потребителя — после выпуска.
- Компиляционная проверка вариантов семейства на сборке нагрузки — невозможна (варианты могут жить в другом
  приложении), заменяется ратчетом.
- Push, тег и выпуск — только по явному запросу пользователя.

## Further Notes

- Ориентир задачи лежал вне репозитория; спека составлена по коду независимо. Ключевое отличие от ориентира:
  место правки — обход значений с подменой спеки листа на модуль варианта, а не особые клаузы в сведениях;
  иначе словарь ссылок терял бы id Prim-вариантов (ориентир требовал «Refs не меняется», но его путь это
  нарушал).
- Решение по `{:custom, _}` принято в спеке: пробел ратчета глобально и понятный `ArgumentError` в сведениях
  (ориентир определял известный вид только как «не `:unkinded`»).
- Риск: добавление Prim-варианта в семейство сломанной фикстуры может задеть другие её тесты — состав
  вариантов сверить при реализации; набор ратчета использует эту фикстуру только в проверках пробелов.
- Факт о потребителе A записан обезличенно; соответствие метки приложению — вне репозитория.
