# Один read-движок event-sourced агрегата

Внутренний рефакторинг read-пути ES после ADR-0094. Термины — `CONTEXT.md`, «Состояние на версии»,
«Адрес версии», «Снапшот»; норма — `docs/rules/13-repos.md`.

## Problem Statement

Чтение event-sourced агрегата в `Core.Es.Aggregate.Repo.Pg` выросло в шесть точек входа (`get`,
`get_many`, `get_decision`, `refresh`, `get_at`, `get_many_at`), и каждая собирает внутреннюю спеку
загрузки `%{state, upper, captures}` плюс флаг `write_snapshots?` своими руками. Дальше эта спека
разбирается в четырёх клаузах свёртки, версия сверяется пятью почти одинаковыми функциями, а строки и
спеки склеиваются по позиции через `Enum.zip_with` — тот молча обрезает по короткому списку. Понимание
одного чтения требует держать в голове весь этот разброс, а исправление свёртки или сверки версии
приходится повторять в нескольких местах.

Публичная поверхность при этом в порядке: `ReadRepo` уже даёт правильный шов (`get_at`/`get_many_at`),
контрактные тесты гоняются через базу. Проблема — в реализации за швом и в тестовом шве: чтобы проверить
свёртку, тесты вынуждены звать `@doc false`-функцию с вручную собранной спекой и поднимать Postgres.

## Solution

Внутри библиотеки появляется один read-движок `Core.Es.Aggregate.Load`. Наружу он не выходит: это
`@doc false`-модуль, единственный вход — `Repo.Pg`. Движок владеет политикой чтения (потолок версии,
выбор снапшота, свёртка, сверка версии, телеметрия), а SQL-запрос приходит к нему через узкий порт
«источник строк». Строки и мета потока ходят парой, поэтому позиционной склейки больше нет. Публичные
функции репозитория, их исходы, телеметрия, обработка ПДн и исключения не меняются — потребитель
обновление не замечает.

## User Stories

1. As мейнтейнер библиотеки, I want одну реализацию свёртки на все точки входа, so that исправление свёртки или выбора снапшота делалось один раз.
2. As мейнтейнер библиотеки, I want одну сверку версии с одним builder'ом detail, so that `source:` и форма ошибки не расходились между `get`, `get_at` и `get_many_at`.
3. As мейнтейнер библиотеки, I want строки и мету потока в одной структуре, so that `Enum.zip_with` не мог молча обрезать список.
4. As мейнтейнер библиотеки, I want источник строк за узким портом, so that SQL не переплетался со свёрткой и расшифровкой.
5. As мейнтейнер библиотеки, I want тесты свёртки без Postgres, so that регрессия в нарезке версий и снапшотах ловилась быстро и точно.
6. As мейнтейнер библиотеки, I want скрытые хуки write-репозитория убраны, so that у чтения остался один вход и макрос не генерировал лишних функций.
7. As мейнтейнер библиотеки, I want `load_at/6` перестал быть публичным, so that внутренняя спека загрузки не стала де-факто контрактом.
8. As разработчик приложения, I want поведение `get`, `get_many`, `get_decision` и `refresh` не изменилось, so that обновление библиотеки не потребовало правок в приложении.
9. As разработчик приложения, I want поведение `get_at` и `get_many_at` не изменилось, so that адрес версии и представление работали как описано в ADR-0094.
10. As разработчик приложения, I want те же коды ошибок и detail, so that каталог ошибок и обработка `:version_mismatch` остались прежними.
11. As разработчик приложения, I want те же события `[:es, :aggregate, :load]` и `[:es, :aggregate, :fold]` с теми же `op`, so that дашборды и алерты не требовали правок.
12. As разработчик приложения, I want снапшот выбирался по прежнему правилу (не выше наименьшей версии пакета), so that чтение на версии и обычное чтение давали то же состояние.
13. As разработчик приложения, I want чтение на версии по-прежнему не писало снапшоты, so that исторический прогон не затирал свежий снапшот.
14. As разработчик приложения, I want уничтоженные ПДн-значения остались уничтоженными, so that рефакторинг не открыл обход уничтожения ключа субъекта.
15. As разработчик приложения, I want поток каждого id в пакете читался один раз до наибольшей версии, so that число запросов не выросло.
16. As разработчик приложения, I want `:current` по-прежнему давал `FunctionClauseError`, so that голову потока читали через `get`.
17. As разработчик приложения, I want неразобранная строка по-прежнему поднимала `Core.Exc`, so that поведение ошибок хранилища не разъехалось между обычным чтением и чтением на версии.
18. As разработчик приложения, I want ни одной новой публичной функции, so that поверхность библиотеки не росла из-за внутреннего рефакторинга.
19. As оператор приложения, I want метрики загрузки и свёртки считались на тех же местах, so that длительность чтения не изменилась из-за лишних измерений.
20. As мейнтейнер библиотеки, I want в `13-repos.md` одну фразу о внутреннем движке, so that агент не пытался звать его из кода потребителя.
21. As мейнтейнер библиотеки, I want запись в CHANGELOG о снятых скрытых хуках, so that редкий потребитель, звавший их, узнал о причине поломки.

## Implementation Decisions

- **Новый внутренний модуль `Core.Es.Aggregate.Load`** (`@doc false`). Публичных функций три:
  `head/2`, `at/3`, `many_at/3`. Общий движок — приватный `run/3`. Форма возврата у каждой функции своя
  (`Result.t(state)` для головы, `Result.t(state)` для версии, `Result.t([state])` для пакета); ADT адреса
  остаётся внутри, публичных конструкторов нет.
- **Порт источника — карта функций, не behaviour.** `Load` получает `source` — функцию
  `fetch.(cfg, metas, opts)`, которую передаёт `Repo.Pg`. Возврат — `[{meta, snapshot_cipher, rows}]`.
  Второй реализации порта в библиотеке нет, поэтому behaviour и отдельный модуль-адаптер не заводятся.
- **Границы порта.** Источник делает только SQL: один запрос потоков с join'ом снапшота и хвоста (как
  сейчас). Политику `to_version`/`snapshot_to` считает `Load` из меты. Расшифровка снапшота и хвоста
  остаётся в `Load` и идёт одним `open` через `Core.Es.Store`/`Snapshot`; handshake `sealed`/`put_opened`
  не выходит за `Load`.
- **Пара «мета + строки».** `source` паррит мету со строками сам; наружу `index` не выходит. `Load`
  сворачивает каждую тройку отдельно, поэтому `Enum.zip_with` и проверки «длины совпадают» исчезают;
  инвариант держится формой данных.
- **Сверка версии.** Пять `verify_*` сводятся к одной приватной функции с одним builder'ом detail;
  различие — `source: :address` (адрес версии) против `source: :expected` (сверка ожидаемой версии).
  Коды `:version_mismatch`, форма detail и каталог ошибок write-репозитория не меняются.
- **Точки входа.** `get`, `get_many`, `get_decision`, `refresh`, `get_at`, `get_many_at` сохраняют
  сигнатуры, головы, исходы и `defoverridable`. Скрытые `__es_get_at__/4` и `__es_get_many_at__/3`,
  генерируемые write-репозиторием, удаляются; `ReadRepo.Pg` зовёт `Load` напрямую.
- **`write_snapshots?`** остаётся параметром движка: `get`-путь пишет снапшоты после загрузки, `at`-путь
  не пишет. Это точка входа, а не режим чтения, поэтому флаг переезжает в вызов `Load`, а не в мету потока.
- **Телеметрия.** Те же события и измерения; `op` — `:get | :get_many | :get_at | :get_many_at`.
  `[:es, :aggregate, :fold]` эмитится там же, где сейчас (после свёртки каждого потока).
- **Отказы.** `Load` возвращает `Result`; `Core.Exc` для неразобранной строки поднимается как сейчас и
  не заворачивается в `%Error{}`. Решение `Repo.Pg` об исключении не меняется.
- **ПДн.** Расшифровка, апкаст и уничтожение значения идут прежним путём; уничтоженный снапшот тоже
  остаётся уничтоженным, и снапшот такого потока не пишется.
- **Свод.** `docs/rules/13-repos.md`, «Состояние на версии»: абзац «свёртка до версии — один внутренний
  движок, наружу не выходит; звать его из кода потребителя MUST NOT». Норм не добавляет.
- **CHANGELOG.** «Изменения контракта макросов»: write-репозиторий больше не генерирует
  `__es_get_at__/__es_get_many_at__`; поведение write-репозитория не изменилось, потребителю править
  нечего. Внутренние перестановки без видимой поверхности в CHANGELOG не попадают.
- **Порядок работ (тикеты).** 01 — вынести `Load` + порт, поведение то же; 02 — убрать скрытые хуки и
  перевести тесты на `Load`; 03 — свести сверку версии и убрать позиционную склейку. Каждый шаг — зелёный
  `make`.

## Testing Decisions

- Хороший тест проверяет наблюдаемое поведение: исход и форму результата публичной функции, detail
  ошибки, телеметрию. Внутренние имена функций, число запросов и порядок клауз не проверяются.
- **Основной (высший) шов — существующий контракт read-репозитория через базу:**
  `Core.EsAggregateReadRepoContract` и тесты write-репозитория (`get`, `get_many`, `get_decision`,
  `refresh`, `get_at`, `get_many_at`). Они уже покрывают исходы, снапшоты, ПДн и телеметрию; после
  рефакторинга должны пройти без смысловых правок.
- **Новый внутренний шов — `Load` на строках.** Чтобы не гонять Postgres ради свёртки, добавляется
  тестовая поддержка `Core.Es.Store.Rows` (`test/support`): из списка `{type, aggregate_id, version,
  tag, payload}` строятся строки в форме, которую отдаёт источник. `Load` проверяется на этих строках:
  нарезка по `upper`/`captures`, снапшот ≤ границы, снапшот новее границы, отказ `source: :address`,
  свёртка без событий. Это шов ниже публичного, но оправдан: свёртку нельзя дёшево и точно проверить
  через базу.
- **Сборка.** Тесты, ожидающие `__es_get_at__`/`__es_get_many_at__` или `load_at/6`, переводятся на
  `Load`; тестов на наличие снятых хуков не заводим — их отсутствие видно компиляцией фикстур.
- **Телеметрия** — в контрактном наборе обработчиком `:telemetry`, по образцу существующего блока
  телеметрии read-репозитория.
- **Снапшоты** — существующие фикстуры со снапшотами (`Repo.Snapshotted`, `AtVersion.Snapshotted`);
  факт «читали от снапшота» проверяется телеметрией, как сейчас.

## Out of Scope

- Публичный API чтения и новые опции `ReadRepo`; поведение `get_at`/`get_many_at` не меняется.
- Lease, MQ, outbox и `Repo.Sc` — соседние волны, в этой спеке не трогаются.
- Спека поля (`Core.Codec.Field` / `Core.View`), подписи, `Core.Es.Events` — отдельные спеки.
- Пересборка снапшотов, история снапшотов, кеш состояния на версии (запрещён ADR-0094).
- Оптимизация числа запросов: SQL остаётся тем же, меняется только его место и форма возврата.

## Further Notes

- Спека продолжает ADR-0094: свёртка остаётся внутренней, behaviour write-репозитория не меняется.
- Мотивация по истории коммитов: читающая половина `Repo.Pg` — около 500 строк, добавленных и
  изменённых последней волной; рефакторинг дешевле сейчас, чем после следующей фичи read-пути.
- При сомнении «оставить в `Repo.Pg` или унести в `Load`»: в `Load` уходит всё, что не является SQL или
  сборкой Ecto-запроса; SQL остаётся у порта.
