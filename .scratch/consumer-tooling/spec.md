# Дашборды подсистем библиотеки и служебные инструменты потребителя

Status: ready-for-agent

Решение о поставке дашбордов: `docs/adr/0089-library-ships-subsystem-dashboards.md`. Термины:
`CONTEXT.md`, раздел «Наблюдаемость». Факты о потребителе A: `.scratch/consumer-tooling/research.md`.
Отложенное: `.scratch/consumer-tooling/deferred.md`.

## Problem Statement

Каждый потребитель собирает дашборды Grafana для подсистем библиотеки сам. У потребителя A дашборды
outbox, брокеров, event sourcing, кеша, процессов и внешних вызовов повторяют плагины
`Core.*.PromEx` один в один. Отличаются они только тем, что зашито под приложение: префикс метрик,
`title`, `uid`, datasource. Остальным потребителям остаётся копировать JSON руками. Имя метрики
меняется в библиотеке, копии лежат у каждого потребителя, и после обновления зависимости панель
молча пустеет в проде. Сверки имён метрик в дашбордах нет ни у кого.

Штатные дашборды PromEx A держит копиями и одну из них доработал руками. Повторный экспорт эту
доработку сотрёт. Форму панелей, которая не разваливается от растущей метки (`component`,
`projection`), A выработал у себя и проверяет своим тестом, хотя метки дают плагины библиотеки и
проблема общая для всех потребителей.

Oban Web и Tidewave A подключил, не опираясь на свод: свод о них молчит. У Oban Web при этом есть
неочевидные места:
- отдельный эндпоинт или маршрут в основном роутере;
- запуск сборщика метрик `Oban.Met`;
- `secret_key_base`, который у A генерируется случайно на каждом старте и сломается на нескольких
  нодах.

Сервер метрик и дашборд Oban устроены одинаково (свой порт, адрес по окружению, тумблер), но
шаблона «служебный эндпоинт» в своде нет. В примере `plugins/0` в `README.md` не хватает
`dlq_repo:`, без него DLQ-панели дашборда Kafka пусты.

## Solution

Дашборды подсистем библиотеки поставляет сама библиотека: шаблоны EEx в своём `priv`. Mix-задача
core рендерит их через `PromEx.DashboardRenderer` в каталог дашбордов приложения, приложение
коммитит выгрузку, provisioning файлами остаётся. Порядок тот же, что у штатных дашбордов PromEx:
экспорт без ручных правок. Пороги панелей приложение задаёт в `dashboard_assigns/0` своего модуля
PromEx.

Библиотека проверяет свои шаблоны тестом: каждое имя метрики объявлено плагином, форма панелей
соблюдена. Приложению библиотека даёт публичную проверку каталога дашбордов: форма панелей во всех
дашбордах и совпадение выгрузок с текущим рендером. Устаревшую после обновления core выгрузку
ловит тест приложения, а не пустая панель.

Свод потребителя получает нормы:
- обращение со штатными дашбордами и дашбордами подсистем библиотеки;
- «Форма панелей»;
- служебный эндпоинт;
- Oban Web;
- инструменты агента (Tidewave).

Граница ярусов сдвигается: доменные дашборды и пороги остаются в локальном своде приложения.

## User Stories

1. Как разработчик потребителя, я хочу получить дашборды outbox, брокеров, event sourcing, кеша,
   процессов и внешних вызовов одной командой, чтобы не собирать их JSON руками.
2. Как разработчик потребителя, я хочу, чтобы выгруженный дашборд уже нёс префикс метрик моего
   приложения, чтобы панели показывали данные сразу после provisioning.
3. Как разработчик потребителя, я хочу, чтобы `title` и `uid` выгрузки строились от моего
   приложения, чтобы дашборды разных приложений в одной Grafana не конфликтовали.
4. Как разработчик потребителя, я хочу задавать datasource параметром шаблона, как у штатных
   дашбордов PromEx, чтобы выгрузка подходила к моей Grafana.
5. Как разработчик потребителя без Kafka, я хочу, чтобы экспорт по умолчанию не создавал дашборд
   Kafka, чтобы в Grafana не было пустых дашбордов.
6. Как разработчик потребителя, я хочу, чтобы набор дашбордов по умолчанию определялся моим
   `plugins/0`, чтобы не перечислять дашборды отдельно от плагинов.
7. Как разработчик потребителя, я хочу явно выбрать дашборд флагом, чтобы перевыгрузить только
   один.
8. Как разработчик потребителя, я хочу указать каталог выгрузки флагом, а без флага получить
   принятый в своде каталог, чтобы не повторять путь при каждом экспорте.
9. Как разработчик потребителя, я хочу задать пороги панелей (очередь outbox, память контейнера) в
   `dashboard_assigns/0`, чтобы повторный экспорт их не терял.
10. Как разработчик потребителя, я хочу получить разумные пороги по умолчанию, чтобы не настраивать
    их до первого инцидента.
11. Как разработчик потребителя, я хочу, чтобы тест приложения падал, когда выгрузка дашборда
    подсистемы библиотеки разошлась с текущим рендером, чтобы после обновления core я не забыл
    перевыгрузить дашборды.
12. Как разработчик потребителя, я хочу, чтобы тот же тест падал на ручной правке выгрузки, чтобы
    правка не потерялась молча при следующем экспорте.
13. Как разработчик потребителя, я хочу проверять форму панелей во всех своих дашбордах, включая
    доменные, публичной функцией библиотеки, чтобы не держать свою копию этой проверки.
14. Как разработчик потребителя, я хочу получать нарушения формы с именем дашборда и заголовком
    панели, чтобы сразу найти, что править.
15. Как оператор, я хочу, чтобы сводка (stat / gauge / bargauge) отвечала, есть ли проблема, и не
    рассыпалась по растущей метке, чтобы читать дашборд при сотне процессов.
16. Как оператор, я хочу, чтобы панель с растущей меткой фильтровалась переменной дашборда и имела
    легенду-таблицу справа, чтобы найти, где проблема.
17. Как оператор, я хочу, чтобы состояние с растущей меткой рисовалось как «1 = проблема», а
    подсказка показывала только проблемные серии, чтобы не читать нули.
18. Как оператор, я хочу видеть сбои сбора метрик всех плагинов и память контейнера на дашборде
    процессов, чтобы отличить пустую панель от сломанного сбора.
19. Как оператор, я хочу видеть внешние вызовы по системам через переменную `system`, чтобы один
    дашборд подходил любому набору внешних систем.
20. Как оператор, я хочу видеть DLQ-панели дашборда Kafka заполненными, чтобы разбирать мёртвые
    письма, поэтому пример `plugins/0` в README показывает `dlq_repo:`.
21. Как сопровождающий библиотеки, я хочу, чтобы тест библиотеки падал, когда шаблон дашборда
    ссылается на метрику, которую не объявляет ни один плагин `Core.*.PromEx`, чтобы
    переименование метрики не гасило панели у потребителей.
22. Как сопровождающий библиотеки, я хочу, чтобы шаблоны библиотеки проходили ту же проверку формы,
    что и дашборды приложения, чтобы библиотека не поставляла то, что запрещает свод.
23. Как разработчик потребителя, я хочу, чтобы свод прямо говорил, что штатные дашборды и
    дашборды подсистем библиотеки — выгрузки без ручных правок, а доработка идёт отдельной
    панелью в доменном дашборде, чтобы не терять правки при экспорте.
24. Как разработчик потребителя, я хочу, чтобы свод разделял, что относится к ярусу потребителя
    (выгрузки и нормы обращения с ними), а что к локальному своду (доменные дашборды, пороги),
    чтобы знать, где записывать решение.
25. Как разработчик потребителя без аутентификации, я хочу норму подключения Oban Web на отдельном
    служебном эндпоинте с защитой сетью и прокси, чтобы дашборд, меняющий задачи, не оказался
    открытым.
26. Как разработчик потребителя с аутентификацией, я хочу норму подключения Oban Web маршрутом в
    основном роутере с проверкой доступа через `resolver:` и режимом только для чтения, чтобы не
    поднимать второй эндпоинт.
27. Как разработчик потребителя, я хочу, чтобы свод требовал запуска `Oban.Met` ребёнком корня
    дашборда, чтобы выключенный дашборд не опрашивал `oban_jobs`.
28. Как разработчик потребителя, я хочу, чтобы свод требовал `secret_key_base` эндпоинта дашборда
    из окружения, одинаковым на всех нодах, чтобы сессии LiveView не рвались за балансировщиком.
29. Как разработчик потребителя, я хочу общий шаблон служебного эндпоинта (свой порт, loopback
    вне prod, не публикуется на хост, корень с тумблером и `:ignore`, выключен в test), чтобы
    сервер метрик и дашборд Oban устраивались одинаково.
30. Как разработчик потребителя, я хочу норму подключения Tidewave (MAY; только `:dev`, только
    localhost, не в релизе), чтобы инструмент агента не попал в prod.
31. Как разработчик потребителя, я хочу видеть в CHANGELOG, что появилось и как перейти со своих
    копий дашбордов на выгрузку, чтобы обновить core без чтения кода.

## Implementation Decisions

- **Шаблоны.** Библиотека кладёт шаблоны EEx в свой `priv`, по одному на подсистему:
  - `outbox` — `Core.Outbox.PromEx`;
  - `mq` — RabbitMQ Stream и подписчики, `Core.Mq.PromEx`;
  - `kafka` — читатели Kafka и DLQ, `Core.Mq.PromEx`;
  - `es` — `Core.Es.PromEx`;
  - `cache` — `Core.Cache.PromEx`;
  - `external` — `Core.External.PromEx`, система переменной `system`, без литералов;
  - `workers` — `Core.Workers.PromEx`, сбои сбора всех плагинов (`Core.PromEx.Safe`) и память
    контейнера (`Core.Cgroup.PromEx`).

  Основа — дашборды потребителя A без доменных панелей. Всё, что у A было литералами под
  приложение (префикс, `title`, `uid`, `tags`, datasource, пороги, `system=`), становится
  параметрами шаблона.
- **Параметры шаблона** — те же, что даёт `PromEx.DashboardRenderer` штатным дашбордам (`otp_app`,
  префиксы, `datasource_id`, интервал), плюс параметры библиотеки: пороги со значениями по
  умолчанию. Приоритет по возрастанию: умолчания рендерера → умолчания библиотеки →
  `dashboard_assigns/0` модуля PromEx приложения. `title` и `uid` строятся от `otp_app` и имени
  дашборда.
- **Модуль `Core.PromEx.Dashboards`** — публичный, единственная точка рендера и проверок:
  - рендер одного дашборда подсистемы для модуля PromEx приложения → JSON;
  - набор дашбордов по умолчанию для модуля PromEx — по его `plugins/0`. Дашборд `kafka` входит,
    только если у `Core.Mq.PromEx` задана опция `kafka_readers:`, `mq` — только если задана
    `stream_readers:` или `readers:`;
  - проверка формы панелей над одним дашбордом или каталогом → список нарушений (дашборд, панель,
    правило). Пустой список — норма. Для теста приложения есть вариант, который падает с
    читаемым перечнем нарушений;
  - проверка свежести: каждая выгрузка дашборда подсистемы библиотеки в каталоге приложения
    совпадает с текущим рендером для его модуля PromEx. Расхождение — нарушение с именем файла.
- **Правила формы** переносятся из нормы потребителя A «Форма панелей». Закрытый список
  фиксированных меток (`result`, `outcome`, `status`, `error`, `op`, `operation`, `channel`, `kind`,
  `collector`, `reason`) задаёт библиотека, приложение MAY его расширить аргументом проверки. Метки
  экспортёров (`datname`, `mountpoint`) под проверку не попадают.
- **Mix-задача `mix core.dashboards.export`** — тонкая обёртка над рендером, ответ оператору через
  `Mix.shell()`. Флаги:
  - `--module` — модуль PromEx приложения, обязателен;
  - `--dashboard` — повторяемый, без него — набор по умолчанию;
  - `--out` — каталог, по умолчанию `deploy/monitoring/grafana/dashboards`.

  Файл выгрузки называется по имени дашборда.
- **Зависимость.** Публичный документированный `PromEx.DashboardRenderer`. `prom_ex` у библиотеки
  уже обязательная зависимость, новых нет.
- **Свод `docs/rules/app/00-index.md`.** Строка таблицы ярусов «дашборды» разделяется:
  - выгрузки штатных дашбордов и дашбордов подсистем библиотеки и нормы обращения с ними — ярус
    потребителя;
  - доменные дашборды и пороги — локальный свод.
- **Свод `docs/rules/app/21-observability.md`:**
  - раздел о служебном эндпоинте; «Сервер метрик» становится его частным случаем;
  - в «Дашборды и алерты» — выгрузки без ручных правок, переэкспорт после обновления core,
    доменные панели только в доменном дашборде, `dashboards/0` не регулируется;
  - норма «Форма панелей» в обезличенном виде (`my_app_prom_ex_…`), с строкой «Проверяется» на
    публичную проверку;
  - раздел «Oban Web»: развилка по аутентификации, `Oban.Met` под корнем, тумблер и `:ignore`,
    `secret_key_base` из окружения; дерево процессов — ссылкой на `app/17`.
- **Свод `docs/rules/app/20-agreements.md`.** Раздел «Инструменты агента»: Tidewave MAY, только
  `:dev`, плаг под `Code.ensure_loaded?/1` в эндпоинте, только localhost, не в релизе;
  `.mcp.json` и хуки агента — дело приложения.
- **`README.md`.** В примере `plugins/0` у `Core.Mq.PromEx` появляется `dlq_repo:`. Добавляется
  абзац об экспорте дашбордов.
- **`CHANGELOG.md`.** Раздел «Новое»: задача экспорта, шаблоны, публичная проверка. Отдельным
  пунктом — правки яруса `app/**` с переходом «своя копия → выгрузка». Пишется тем же коммитом,
  что и каждая правка.

## Testing Decisions

- Тесты проверяют внешнее поведение: отрендеренный JSON, список нарушений, файлы, которые создала
  задача. Внутреннее устройство рендера и шаблонов не проверяется.
- **`Core.PromEx.Dashboards`, самопроверка библиотеки:**
  - каждый шаблон рендерится для фиктивного модуля PromEx и даёт валидный JSON;
  - каждое имя метрики в запросах панелей и переменных, после снятия префикса, объявлено
    `event_metrics` или `polling_metrics` какого-либо плагина `Core.*.PromEx`, с учётом суффиксов
    distribution (`_bucket`, `_sum`, `_count`);
  - каждый шаблон проходит проверку формы;
  - в выгрузке нет литералов под приложение: префикс, `title` и `uid` строятся от `otp_app`.
- **`Core.PromEx.Dashboards`, проверка формы.** Фикстуры-дашборды: по одной на каждое правило
  нормы, нарушающей и соблюдающей. Отдельно — расширение списка фиксированных меток.
- **`Core.PromEx.Dashboards`, проверка свежести.** Совпадающая выгрузка проходит. Выгрузка с
  ручной правкой, со старым порогом или от другого `otp_app` даёт нарушение с именем файла. Файлы,
  которые не выгружены из библиотеки (доменные, штатные), проверка свежести не трогает.
- **Набор по умолчанию.** `Core.Mq.PromEx` без `kafka_readers:` не даёт дашборд `kafka`; без плагина подсистемы
  не даёт её дашборд.
- **Mix-задача.** Вызывается во временном каталоге с модулем PromEx из фикстуры; проверяются
  набор файлов по умолчанию, `--dashboard`, `--out`, отказ без `--module`. Образец —
  `test/mix/tasks/outbox_requeue_test.exs`.
- **Образец проверки формы** — тест потребителя A `dashboards_test.exs` (`research.md`, раздел 1),
  переносится в обезличенном виде.
- Свод проверяется `make rules-check`, всё целиком — `make`.

## Out of Scope

- Перевод потребителей на выгрузки, удаление их копий и тест у потребителя. Это задача их
  собственных трекеров.
- Счётчик потерь подписчика в `Core.Mq.PromEx` (`deferred.md`).
- Дашборд окружения (экспортёры Postgres, RabbitMQ, хоста): его не поставляют и не регулируют.
- Доменные дашборды и их содержимое.
- Выгрузка дашбордов через API Grafana.
- Код Oban Web и Tidewave в библиотеке: зависимостей от `oban` и `tidewave` у core нет, есть только
  нормы.
- Алерты: правила и их сверка остаются как есть.

## Further Notes

- Переменная Grafana в имени метрики не проверялась, механизм на ней не держится: префикс
  подставляет рендер.
- Смена API `PromEx.DashboardRenderer` ломает экспорт. Это цена из ADR-0089.
- Все факты о потребителе A в текстах — только обезличенно.
