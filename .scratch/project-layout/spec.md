# Раскладка приложения-потребителя: норма, линтер, read-модели и компоненты

Type: spec
Status: ready-for-agent

## Problem Statement

Раскладку приложения-потребителя (не umbrella) задаёт свод `docs/rules/app/*.md`, но задаёт её так, что
ни разработчик потребителя, ни агент не могут на неё опереться:

- таблица top-level namespaces, дерево файлов агрегата и раскладка web записаны без модальности, а по
  стандарту свода текст без `MUST` / `SHOULD` / `MAY` — пояснение, а не норма; при этом потребители
  записывают отступления от них в `DEBT.md`, как от нормы;
- один и тот же вопрос свод отвечает по-разному: View и репозиторий лежат то в `Common`, то в срезе
  роли; проекция — «одна на контекст» и одновременно «одна на read-модель»; примеры README называют
  модули иначе, чем ярус потребителя;
- на вопросы «куда класть X» свод во многом не отвечает: файл агрегата, кодек агрегата, каталог
  ошибок, usecases, воркеры, подписчики, модули уровня контекста, аксессор текущего пользователя,
  `config/`, mix-таски;
- направления зависимостей внутри контекста и между контекстами не нормированы, и потребитель уже
  зовёт срез из `Common` (у потребителя A проекция `Common` вызывает проектор среза `admin`);
- чтение event-sourced агрегата разнесено на три места (View и ReadRepo под агрегатом, проектор под
  ReadRepo, одна проекция на контекст), а read-модель через два агрегата вынужденно лежит под одним
  из них;
- у контекста нет точки входа: из чего он состоит, видно только по дереву каталогов;
- процессы одного компонента протекают в `Application`: кеш и его инвалидатор — разные дети,
  проверки старта компонента — в `start/2`, тумблеры компонентов повторно вычисляются в
  `watch_list/0`; дерево подписчика с DLQ копируется из супервизора в супервизор, хотя порядок его
  детей — `MUST`;
- механически держится почти ничего: `MUST` «событие и команда — по файлу» не проверяется, и
  фикстуры самой библиотеки его нарушают; в репозитории библиотеки нет ни одного живого образца
  раскладки bounded context / `Common` / срез.

Исследование с доказательствами — `.scratch/project-layout/research/01-layout-rules-inventory.md`.
Решения — ADR-0023 (раскладка — норма с линтером) и ADR-0024 (компонент владеет своим поддеревом).

## Solution

Раскладка потребителя становится нормой свода с модальностью, одним общим правилом вместо
перечисления и механической проверкой в уже существующем шаге пайплайна потребителя.

- Путь файла равен имени модуля; bounded context — это `Common` и срезы инициаторов; `Common` не
  зависит от своих срезов, чужой контекст виден только через его `Common`; у каждого контекста есть
  модуль-оглавление. Всё это проверяет `boundary_lint --consumer`, а сознательное отступление
  оформляется маркером у `defmodule` со ссылкой на строку `DEBT.md`.
- Read-модель — единица раскладки: View, ReadRepo и проекция лежат в одном каталоге, проекция пишет
  свои таблицы сама, отдельного проектора нет.
- Компонент — единица тумблера: процессы, которые включаются вместе, живут под одним
  `<Component>.Supervisor`, который сам владеет тумблером, опциями, проверками старта и
  `watch_list/0`; `Application` перечисляет корни компонентов плоско.
- Библиотека даёт готовое дерево подписчика с DLQ, чтобы обязательный порядок детей держался
  построением.
- `use Core.Es.Projection` отказывает сборке, если семейство событий не `<Aggregate>.Event`, вместо
  того чтобы молча не создать clause `await/3`.
- Свод библиотеки, README и фикстуры приводятся к ярусу потребителя; `fixtures/consumer` становится
  живым образцом раскладки, на котором проверяется линтер.

## User Stories

1. Как разработчик потребителя, я хочу, чтобы нормы раскладки были записаны с модальностью, чтобы

   своде место для каждого нового вида модуля.
3. Как разработчик потребителя, я хочу найти модуль по имени без поиска по содержимому файлов, чтобы

## Implementation Decisions

### Свод потребителя (`docs/rules/app/`)

- `app/10` получает раздел «Раскладка» с модальностью и строкой «Проверяется»:
  - путь файла от `lib/` равен имени модуля в snake_case (`MUST`); mix-таски — по конвенции Mix
    (`Mix.Tasks.Foo.Bar` в `lib/mix/tasks/foo.bar.ex`);
  - bounded context — `<BC>.Common` и срезы; срез — операции одного инициатора (роль или системный
    процесс), имя среза свободно, `system` — пример; модулей в корне контекста нет;
  - подсистема `MyApp.<Subsystem>` — top-level часть без агрегатов (`MAY`); агрегаты — только в
    `Domain.<BC>`;
  - `Common` `MUST NOT` зависеть от срезов своего контекста; контекст `MUST NOT` ссылаться на срезы
    чужого контекста — только на его `Common`;
  - модуль-оглавление `MyApp.Domain.<BC>` рядом с каталогом контекста: наличие `MUST`, содержание
    (назначение, агрегаты, срезы, read-модели, компоненты, ссылки на другие контексты) — `SHOULD`;
  - таблица top-level namespaces дополняется `StreamID`, `MetricsServer`, `Release`, `Mix.Tasks.*`;
  - таблица `config/`: `config.exs` — `compile_env` и DI-подмены; `runtime.exs` — env и тумблеры;
    `test.exs` — тестовый overlay; в `dev.exs` / `prod.exs` секреты и env `MUST NOT`;
  - явная строка: потребитель — один Mix-проект, один `otp_app`, один `DAO`; umbrella не
    поддерживается; `otp_app:` списком у `TagsCase` — частный случай, а не заявка на поддержку;
  - оформление отступления: маркер у `defmodule` со ссылкой на строку `DEBT.md`.
- Таблица «Actor / role slices» в `app/10` приводится к новому определению среза и к составу
  `Common` (агрегаты, значения, события, кодеки, outbox, репозитории записи, read-модели, компоненты
  без привязки к инициатору).
- Раздел «Usecases» в `app/10`: имя — `MyApp.Domain.<BC>.<Actor>.Usecases.<Scenario>`, по умолчанию
  имя агрегата.
- `app/11`: Prim вложен в агрегат-владелец по имени, файл отдельный или внутри — `MAY`; значение без
  владельца — `<BC>.Common.<Value>`; аксессор текущего пользователя — пример в `Common` контекста,
  владеющего учётной записью.
- `app/12`: путь каталога ошибок следует из правила «путь = имя»; ссылка на «путь» в своде
  библиотеки исправляется.
- `app/13`: дерево агрегата остаётся примером с модальностью и ссылкой на `app/10`; чтение выносится
  в раздел о read-модели — каталог `<scope>/<read_model>/` с View, ReadRepo и проекцией; правило
  «одна проекция на контекст в `common/projection.ex`» и `<Aggregate>.ReadRepo.Pg.Projector`
  заменяются на «одна проекция на read-модель, пишет свои таблицы сама»; кеш read-модели и его
  супервизор — в её каталоге.
- `app/15`: раскладка web — поверхность `MyAppWeb.<Api>` с `ApiSpec` и `<Version>.<Resource>`;
  общее для поверхностей (`FallbackController`, `ErrorMapper`, `Presenters`, `Plugs`, `Schemas`) — в
  корне `MyAppWeb`; вложенный ресурс — вложенный namespace.
- `app/17`: вводится «компонент» вместо «подсистемы» там, где речь о тумблере и поддереве; контракт
  корня `<Component>.Supervisor` (тумблер, опции, проверки старта, `watch_list/0`); `Application`
  держит `Core.Config.validate!()`, проверки разделяемой инфраструктуры, саму инфраструктуру и корни
  компонентов плоско; `watch_list/0` приложения — конкатенация списков компонентов; дерево
  подписчика — библиотечное; место компонента — срез инициатора, подсистема или каталог
  read-модели.
- `app/19`: тест модуля лежит по пути модуля (`SHOULD`, без линтера); архитектурный тест и ратчеты —
  в `test/my_app/`; `ConnCase` — в `test/support/`.
- Шаг `boundary-check` в таблице пайплайна `app/20` описывает новые проверки.

### Свод библиотеки, README, CONTEXT

- Примеры `MyApp.Domain.Orders.Order.Repo` и `<BC>.Common.Repo` приводятся к
  `MyApp.Domain.<BC>.Common.<Aggregate>.Repo`; `MyApp.Repo.Migrations.*` — к `MyApp.DAO.Migrations.*`.
- Примеры `<Actor>.<Aggregate>.View` / `.Repo` / `.ReadRepo` в сводах `11`, `13` и в `app/16`
  переводятся на `Common` по умолчанию с оговоркой о переезде в срез.

### Линтер `boundary_lint --consumer`

- Остаётся одним шагом пайплайна потребителя, разбирает AST без компиляции.
- Новые проверки (только для `lib/`; `test/` проверяется, как и сейчас, только на DI):
  - каждый верхнеуровневый `defmodule` файла совпадает с путём файла: сравнивается
    `Macro.underscore` имени модуля с путём от `lib/`, а не `camelize` пути — так корректно
    обрабатываются аббревиатуры (`AppA` ↔ `app_a`); несколько верхнеуровневых модулей в одном файле —
    нарушение; вложенные модули следуют за родителем; mix-таски сверяются по конвенции Mix;
  - ссылка из файла `Common` контекста на модуль среза того же контекста — нарушение;
  - ссылка из контекста A на модуль среза контекста B — нарушение; на `Common` B — разрешена;
  - каждый каталог `domain/<bc>/` имеет модуль-оглавление `MyApp.Domain.<BC>`.
- Ссылки разрешаются с учётом `alias` файла (в том числе многоимённого `alias A.{B, C}`),
  `__MODULE__` и полных имён; корень приложения берётся из имени модуля самого файла.
- Исключение: маркер-комментарий у `defmodule`, называющий правило и строку `DEBT.md`; маркер
  гасит нарушения только своего правила и только в своём модуле.
- Сообщение нарушения: `путь:строка: текст` и путь к норме свода — в той же форме, что у
  существующих проверок.
- Проверки включаются сразу ошибкой, без переходного режима.

### `use Core.Es.Projection`

- Если модуль события в `events:` не лежит в семействе `<Aggregate>.Event` (родитель модуля события
  не оканчивается на `Event`), сборка падает с `CompileError`, называющим событие и ожидаемую форму;
  сейчас в этом случае clause `await/3` для агрегата молча не создаётся.
- Комментарии кода и прошлые ссылки CHANGELOG на «раскладку `11-domain.md`» для кодека событий
  исправляются на фактическое место нормы.

### Дерево подписчика с DLQ в `Core.PubSub`

- Новый библиотечный супервизор над `Core.PubSub.MqSubscriberReliable`: дети строго в порядке — свой
  DLQ-writer (если задан), затем на каждый топик читатель и его подписчик; стратегия `:rest_for_one`.
- Принимает тумблер `enabled:` и при выключении отдаёт `:ignore` с `info`, как
  `Core.Es.Projection.Supervisor`.
- Отдаёт `watch_list/1` по тем же опциям, что и старт, — имена процессов не повторяются литералами.
- Подписчики стартуют с `subscribe: true`, bootstrap-процесс подписки не нужен.
- Библиотека не читает конфигурацию потребителя: опции собирает одна функция приложения.

## Testing Decisions

- Хороший тест проверяет внешнее поведение через самый высокий доступный шов: для линтера — вызов
  скрипта (код выхода и строки нарушений), для макроса — сборку модуля, для дерева — запущенный
  супервизор и его наблюдаемые эффекты; внутренние функции не тестируются.
- Линтер раскладки: ExUnit-тест пишет пробы во временный каталог-потребитель, вызывает скрипт через
  `System.cmd` и сверяет код выхода и строки. По тесту на правило: путь ≠ имя модуля, два
  верхнеуровневых модуля в файле, аббревиатура в корне (`AppA` в `lib/app_a`) без ложного нарушения,
  mix-таска по конвенции Mix, `Common` → свой срез, контекст → чужой срез, контекст → чужой `Common`
  без нарушения, ссылка через `alias` и многоимённый `alias`, контекст без модуля-оглавления, маркер
  гасит нарушение своего правила и не гасит чужое, существующая проверка DI не сломана. Образец
  формы проб — самопроверка `fixtures/consumer`.
- Живой прогон: `boundary_lint --consumer` над `fixtures/consumer` проходит без нарушений (шаг
  `consumer-check`).
- `use Core.Es.Projection`: новый случай в describe «use» теста проекции — событие вне семейства
  `<Aggregate>.Event` даёт `CompileError` с ожидаемым текстом; существующие случаи `CompileError`
  там же — образец.
- Дерево подписчика: тест поверх `MqFake`, как тест `MqSubscriberReliable` — порядок детей,
  отравленное сообщение уходит в DLQ, выключенное дерево отдаёт `:ignore`, `watch_list/1` совпадает с
  именами запущенных процессов. Образец для `watch_list` — тест `Core.Es.Projection.Supervisor`.
- Свод: `make rules-check` на оба яруса; фикстура: `make consumer-check`; полный `make`.

- Поддержка umbrella-проектов: приведение `DocsCase` / `ConstraintErrorsCase` к списку приложений,
