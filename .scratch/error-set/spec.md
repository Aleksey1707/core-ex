# Множество ошибок: несколько независимых отказов одной операции

Type: spec
Status: ready-for-agent

## Problem Statement

`%Error{}` описывает одну ошибку и, через `parent`, цепочку причин: отказ и то, что его вызвало.
Отношения «несколько независимых отказов сразу» у библиотеки нет, и каждое место, где оно
возникает, обрывается на первом:

- `Result.traverse/2` останавливает пачку на первом провале (`lib/core/result.ex:77`) — какие ещё
  элементы плохи, вызывающий не узнает;
- список валидаторов Prim обрывается так же (`lib/core/prim.ex:375`), загрузка списка сущностей
  кодеком — тоже (`lib/core/codec/helper.ex:63`);
- клиенту уходит ровно один `message`: `ErrorMapper.map/2` отдаёт один `String.t()`, и
  `Response.__error__/3` кладёт его в `messages` единственным элементом, хотя само поле конверта —
  список.

Итог: форма с пятью невалидными полями правится клиентом за пять запросов, а batch-сохранение
сообщает о первой сломанной строке из двадцати.

## Solution

Множество ошибок — поле `errors: [t()]` в существующем `%Error{}` (ADR-0021). Контейнер остаётся
обычной ошибкой: где про поле не знают, он ведёт себя как одна ошибка с текстом «в целом», где
знают — раскрывается в состав. Термины — `CONTEXT.md`, «Ошибки».

Существующие API формы `{:error, %Error{}}` не меняются: аккумуляция включается явно на call site.

### Тип и конструктор

- поле `errors: [t()]`, дефолт `[]`, вне `@enforce_keys`; независимо от `parent`;
- `Error.many/1,2` — макросы, симметрично `domain` / `app`, с compile-check литерального kwlist:
  обязательны `code:`, `ns:`, `message:`, `errors:`; опциональны `detail:`, `parent:`;
- `kind` не принимается, а выводится: хотя бы один элемент `:app` → контейнер `:app`;
- `ns` и `code` — из словаря потребителя, общего кода библиотека не вводит;
- пустой `errors:` — `ArgumentError`; один элемент — допустим; порядок входа сохраняется; дубли
  `{ns, code}` не схлопываются;
- элемент с непустым `errors` — `ArgumentError`: множество плоское;
- контейнер не бывает причиной: `wrap/2` вторым аргументом и `parent:` любого конструктора его не
  принимают — `ArgumentError` с текстом правила.

### Обход и печать

- `has?/2`, `find/2`, `chain/1`, `root/1`, `unwrap/1` и `Enumerable` читают **только** цепочку
  причин; состав читается из поля `errors`;
- `format_chain/1` печатает состав — `"outer (e1 | e2): root"`, рекурсивно по цепочке; у ошибки
  с пустым `errors` вывод прежний;
- `Error.messages/1` → `[String.t()]`: у контейнера — тексты элементов (`to_string/1` каждого),
  у обычной ошибки — `[to_string(error)]`;
- `Exc.message/1` у контейнера — `format_chain/1`; у обычной ошибки — прежний `to_string/1`.

### Комбинатор

`Result.traverse_all(list, fun)` → `{:ok, [b]} | {:error, [Error.t()]}`: проходит весь список,
собирает все провалы, порядок сохраняет. Голый список наружу не отдаётся — заворачивается в
`Error.many` в теле той же функции.

### Граница HTTP

`ErrorMapper.map/2` не меняется: контейнер уходит по строке `kind: :domain` — 400
`:domain_error` с outer `message`. Состав подставляет потребитель в fallback-контроллере через
`Error.messages/1`, и только там, где маппер вернул `:domain_error`: на 401 и 500 наружу идёт
константа. `Response.error/2,3` получает clause на `[String.t()]`.
