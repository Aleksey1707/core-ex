# 01: Создание отвечает `{id, version}` / `{id}` общими схемами корня

**Status:** done

**What to build:** норма яруса потребителя выделяет создание event-sourced агрегата из «команда
отвечает представлением из read-модели»: заведение ждёт проекцию, как любая команда, и отвечает
`{id, version}` записи одной схемой на 200 и на 202. Создание агрегата без событий отвечает `{id}`.
Обе формы — общие схемы корня `MyAppWeb.Schemas`, независимо от числа поверхностей. Норма —
`docs/rules/app/15-web-api.md`, «Раскладка», «Controller», «Ожидание проекции».

**Why:** ярус описывает ответ команды представлением, а создания event-sourced агрегата в нём нет
вовсе: пример в «Controller» — state-stored создание (`{:ok, id}`, `app/10-architecture.md`,
«Usecases»). Потребитель A отступил от нормы осознанно и держит отступление записью `DEBT.md`,
которая снимается только правкой яруса. Вторая запись там же — схема `{id}` в корне web при одной
поверхности: «Раскладка» поднимает в корень только схему, которую делят поверхности.

Довод потребителя A: создание пишет несколько событий, версию после него клиент не угадает, а без
неё не пошлёт следующий `If-Match`. При ответе `{id}` на 200 и `{id, version}` на 202 версия
приходила только тогда, когда представление не готово, и узнать её оставалось `GET` с
`If-Match: *`. Статус несёт готовность представления (200 — `GET` по `id` уже видит запись,
202 — ещё нет), тело — одно.

Считанные альтернативы (у потребителя A):

- **представление на 200, как у остальных команд** — ответ распадается на две формы по статусу,
  а представление клиент после 200 читает `GET` без риска отставшей проекции;
- **`{id, version}` без ожидания проекции** — 200 перестаёт гарантировать, что `GET` сразу видит
  запись: `:not_found` на свежем объекте;
- **две схемы одной формы на 200 и 202** — расходятся при первой правке.

- [x] ADR-0027: создание отвечает `{id, version}` / `{id}` общими схемами корня; альтернативы выше
- [x] «Ожидание проекции»: создание event-sourced агрегата выделено из «отвечает представлением»
- [x] `MyAppWeb.Accepted.written/4` рядом с `respond/4`; строка `MyAppWeb.Accepted` в «Раскладке»
- [x] `MyAppWeb.Schemas.Written` и `MyAppWeb.Schemas.Created` — в корне при любом числе поверхностей
- [x] пример `def create` в «Controller» помечен как state-stored и отвечает схемой `Created`;
      пример event-sourced создания — в «Ожидании проекции»
- [x] CHANGELOG «Не выпущено» тем же коммитом

Вне тикета — сторона потребителя A после выпуска: `mix deps.update core`, снять обе записи `DEBT.md`
(ответ создания и схема `{id}` в корне) и строку ратчета одной поверхности.

Решения мейнтейнера (триаж 29.09.2026):

- ADR в `core-ex` — да: норма меняет контракт всех потребителей, отвергнутые варианты записаны
  только у потребителя A.
- Имена закрепляются в ярусе: `MyAppWeb.Accepted.written/4`, `MyAppWeb.Schemas.Written`,
  `MyAppWeb.Schemas.Created` — одна форма ответа на приложение, иначе ревью не сверяет.
- Пример state-stored `def create` остаётся, event-sourced создание получает свой пример.
- Схема `Created` для создания без событий — общая, в корне: пара форм ответа создания, а не схема
  ресурса; вторая поверхность берёт её же, а не заводит копию.

Проверено по коду: норма «отвечает представлением» создание не выделяет; «Раскладка» описывает
`MyAppWeb.Accepted` только как ответ 202, а корневые `MyAppWeb.Schemas` — как общие для
поверхностей; usecase event-sourced создания уже отдаёт `{:ok, {ID, Version}}`
(`app/10-architecture.md`, «Usecases»). `boundary_lint --consumer` число поверхностей у схем корня
не считает — исключение для `Created` / `Written` линтер не затрагивает.

Реализация (29.09.2026):

Поправка к триажу: у state-stored агрегата версия есть (optimistic lock), `{id}` в ответе создания
держится тем, что usecase state-stored создания отдаёт только идентификатор, а проекции нет
(ADR-0027, альтернатива «`{id, version}` и у state-stored создания»). Схема 202 любой команды
названа в норме: `accepted:` — `MyAppWeb.Schemas.Written`.

## Agent Brief

**Category:** enhancement
**Summary:** ярус потребителя: создание event-sourced агрегата отвечает `{id, version}` после
ожидания проекции (схема `Written`), создание без событий — `{id}` (схема `Created`); обе схемы —
в корне web

**Current behavior:**
Свод потребителя (web API) говорит, что команда event-sourced агрегата отвечает представлением из
read-модели после ожидания проекции, а при `:projection_timeout` / `:projection_rebuilding` —
202 с `{id, version}` через хелпер `MyAppWeb.Accepted` (`respond/4`: conn, результат ожидания,
`{id, version}`, `render`). Создание отдельно не описано: единственный пример создания в разделе
контроллера — state-stored, отвечает `Response.success(%{id: …})` без ожидания и без названной
схемы. Таблица раскладки web описывает `MyAppWeb.Accepted` как «ответ 202», а корневые
`MyAppWeb.Schemas.*` — как схемы, общие для поверхностей (конверт, страница, ошибка); по лестнице
раскладки схема одной поверхности лежит в её namespace. Usecase создания event-sourced агрегата
уже отдаёт `{:ok, {ID, Version}}` (свод архитектуры потребителя, «Usecases»).

**Desired behavior:**

- Создание event-sourced агрегата ждёт проекцию, как любая команда (литеральный
  `Projection.await(Agg, id, timeout)` в экшене или его `defp`, ID сужен до `%Agg.ID{}`), и
  отвечает `{id, version}` записи: 200 — представление готово (`GET` по `id` видит запись),
  202 — ещё нет. Тело одно, схема `MyAppWeb.Schemas.Written`; операция создания объявляет её и в
  `ok:`, и в `accepted:`. Это выделено из нормы «команда отвечает представлением», остальные
  команды не меняются.
- `MyAppWeb.Accepted.written/4` — `(conn, результат ожидания, id, version)`: тот же исход, что у
  `respond/4`, с `render`, который отдаёт тело `{id, version}`. Строка `MyAppWeb.Accepted` в таблице
  раскладки описывает и ответ создания.
- Создание state-stored агрегата проекцию не ждёт и отвечает `{id}` схемой
  `MyAppWeb.Schemas.Created`: usecase отдаёт только идентификатор.
- `Written` (ответ 200 создания и 202 любой команды) и `Created` MUST лежать в корне
  `MyAppWeb.Schemas` при любом числе поверхностей: это формы ответа создания на всё приложение, и
  вторая поверхность берёт их же, а не заводит копию. Исключение записано рядом с правилом лестницы
  схем в «Раскладке» и в строке `MyAppWeb.Schemas.*` таблицы.
- Пример state-stored `def create` в разделе контроллера помечен как state-stored и отвечает схемой
  `Created`; в «Ожидании проекции» — пример event-sourced создания через `written/4`, в форме
  соседних примеров (`defp` с литеральным `await` и суженным ID).
- ADR-0027 в `docs/adr/` записывает решение и считанные альтернативы (раздел **Why** выше), без
  имени потребителя: «потребитель A».
- CHANGELOG «Не выпущено», раздел ломающих изменений контракта: что изменилось в норме, почему, и
  как правится экшен создания потребителя (было: `{id}` на 200 без ожидания или представление →
  стало: ожидание проекции и `Accepted.written/4`; схемы `Written` / `Created` в корне).

**Key interfaces:**

- `MyAppWeb.Accepted.written/4` — `(Plug.Conn.t(), Result.unit(), id, Version.t()) :: Plug.Conn.t()`
- `MyAppWeb.Schemas.Written` — `{id: string, version: integer}`, оба обязательны
- `MyAppWeb.Schemas.Created` — `{id: string}`, обязателен

**Acceptance criteria:**

- [x] раздел ожидания проекции выделяет создание event-sourced агрегата: `{id, version}` на 200 и
      202 одной схемой `Written`, объявленной в `ok:` и `accepted:`
- [x] `written/4` описан в своде и присутствует в строке `MyAppWeb.Accepted` таблицы раскладки
- [x] раскладка требует `Written` и `Created` в корне `MyAppWeb.Schemas` при любом числе
      поверхностей
- [x] state-stored пример создания помечен и отвечает `Created`; event-sourced пример создания есть
- [x] ADR-0027 заведён, в тексте нет имён потребителей
- [x] пункт CHANGELOG в «Не выпущено» с было → стало
- [x] `make rules-check` и `make` зелёные

**Out of scope:**

- код библиотеки: хелпер и схемы живут у потребителя, `Core.Web.*` не меняется
- ответ остальных команд (представление на 200) и поведение ожидания проекции
- правки в репозиториях потребителей, снятие их записей `DEBT.md`
- линтер на число поверхностей схем корня
