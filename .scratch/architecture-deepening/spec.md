# Углубление швов: заявка чтения, конфигурация, подписи, читатели MQ, wire страницы

Волна из шести углублений в недавно менявшихся местах библиотеки. Термины — `CONTEXT.md`,
«Состояние на версии», «Адрес версии», «Снапшот», «Поток событий», «Событие», «Сведения»,
«Словарь ссылок», «Читатель», «Подписчик»; нормы — `docs/rules/13-repos.md`, `docs/rules/11-domain.md`,
`docs/rules/21-observability.md`, `docs/rules/17-otp-concurrency.md`, `docs/rules/20-agreements.md`;
решения — ADR-0094, ADR-0016, ADR-0087, ADR-0063, ADR-0066, ADR-0064, ADR-0033.

## Problem Statement

Мейнтейнер библиотеки платит за трение в шести местах, которые чаще всего менялись в последних
волнах.

Путь чтения event-sourced агрегата описывает одну операцию двумя дискриминантами: заявка несёт `op`,
а движок ветвит по отдельной метке `kind`, которую собирают точки входа. Телеметрия пишет `op`,
сверка идёт по `kind` — расхождение не ловится ни сборкой, ни типами. Политика «писать ли снапшот
после чтения» живёт отдельным флагом, который тесты правят напрямую, потому что выразить «прочитать,
но не писать» через интерфейс репозитория нельзя. Конфигурация чтения ходит как map через пять
модулей и скрытую функцию чужого макроса: новое поле не даёт ошибки сборки ни в одном из них.
Тестовый источник строк вынужден повторять SQL-фильтр снапшота, и расхождение дублёра с
продакшеном видно только редким тестом.

Подписи обходят одну и ту же объявленную видимую форму трижды: сведения — по значениям, словарь
ссылок — по значениям со своим правилом видимости, ратчет полноты — по спекам кодеков. Правила
видимости (`hidden`, `text:`, `union`, `set`/`map`, `change`) продублированы, а `@moduledoc` словаря
обещает «те же поля, что сведения», хотя код берёт другую функцию. Новый вид поля меняет один обход
и не меняет два других.

Страница событий для человека собирается тремя вызовами в usecase: страница потока, словарь ссылок,
wire. Словарь — обязательный неявный параметр: забыли собрать его с той же страницы — падение
происходит на последнем шаге, в `Details.name!/3`, а не в точке сборки.

Читатели MQ по-разному сообщают о себе: `metrics/1` объявлен в контракте, но реализован только у
DLQ-читателя; stream и Kafka отдают `info/1`, которого в контракте нет, а PromEx пробует оба и
разбирает четыре формы одного значения. Новый адаптер молча выпадает из метрик. При этом заявка на
готовность `notify_when_ready/2` реализована у двух из трёх читателей, но `get/2` передаёт в общий
цикл ожидания `nil` и опрашивает вхолостую.

## Solution

Шесть углублений, упорядоченных так, чтобы каждое следующее не переписывало те же строки.

1. **Конфигурация чтения — типизированная структура.** Write-репозиторий собирает её один раз и
   отдаёт read-репозиторию и движку; резолв зависимостей — в одной точке.
2. **Заявка чтения — один дискриминант.** Операция задаёт и способ сверки, и политику снапшота;
   политика записи — свойство операции плюс возможность источника. Тестовая модель выбора снапшота
   удаляется, контракт источника закрепляется тестом.
3. **Заявка на готовность используется.** `get/2` читателей stream и Kafka ждёт `{:mq_ready, ref}`,
   а не опрашивает вхолостую.
4. **Страница событий → wire одним шагом.** Генерируемая функция модуля события владеет словарём
   ссылок и порядком вызовов.
5. **Один обход подписей.** Видимость объявленной формы решается в одном модуле; сведения, словарь и
   ратчет — разные выходы одного обхода.
6. **Снимок состояния читателя.** Одна типизированная форма для метрик вместо duck typing четырёх
   форм; `metrics/1` и `info/1` уходят в deprecated, а не удаляются.

Публичное поведение репозиториев, коды ошибок, detail отказов, телеметрия чтения, формат wire и
метрики не меняются. Потребитель замечает только новую генерируемую `to_wire_page/2` и пометки
deprecated у метрик читателей.

## Implementation Decisions

### 01. Типизированная конфигурация event-sourced репозитория

- Новый модуль конфигурации write-репозитория: структура с `@enforce_keys`, поля — поведение, агрегат,
  модуль id, кодек событий, тип, каталог ошибок, настройка снапшота, резервы ключей, `dao`, `codec`,
  источник строк.
- Настройка снапшота — вложенная структура (`every`, `version`, `sealed`), а не map. `nil` означает
  «снапшоты выключены».
- На компиляции собирается базовая структура без `dao`/`codec`/источника; вызов конфигурации делает
  struct update и резолвит зависимости через `Core.Config` в одной точке. `Map.merge` на каждый вызов
  уходит.
- `Snapshot.marker/1`, `Snapshot.sealed/4`, `Snapshot.opts!`, `Plan.new/3`, движок чтения и
  read-репозиторий читают поля структуры.
- Имя служебной функции read-репозитория сохраняется, меняется только возвращаемый тип. На компиляции
  read-репозитория она не вызывается: проверка — наличие экспорта, как сейчас. Это сохраняет главный
  инвариант: компиляция библиотеки не требует конфигурации потребителя.
- Поведение, исходы и телеметрия не меняются; CHANGELOG не пополняется — всё внутреннее.

### 02. Заявка чтения: один дискриминант и политика снапшота у источника

- В заявке остаётся одна метка операции со прежними именами (`get`, `get_decision`, `get_many`,
  `refresh`, `get_at`, `get_many_at`): по ней размечена телеметрия. Отдельная метка `kind` в адресе
  движка удаляется, ветвление идёт по операции.
- Конструкторы операции строят адреса потоков сами (состояния головы, состояние и версия, пары
  версий). Точки входа репозиториев зовут один вход движка `run/2`; внутренние `head/at/many_at`
  удаляются.
- Политика записи снапшота выводится из операции: `get`, `get_decision`, `get_many`, `refresh`
  пишут, чтение на версии — нет. Флаг в заявке удаляется.
- `Core.Es.Aggregate.Load.Source` получает обязательный колбэк «источник умеет писать снапшоты»:
  SQL-адаптер — да, тестовый источник строк — нет. Это единственная причина, по которой тесты
  раньше правили заявку.
- Тестовая модель выбора снапшота (`Plan.snapshot/2`, `Plan.tail_from/2`) удаляется: в продакшене
  на поток ровно одна строка снапшота (первичный ключ таблицы), и выбор «последнего из многих» —
  сценарий, которого нет. Тестовый источник повторяет два сравнения SQL явно.
- Добавляется контрактный тест источника строк: SQL-адаптер и тестовый адаптер на одних граничных
  случаях дают одинаковые тройки «поток, снапшот, строки хвоста». Случаи: снапшот не выше адреса,
  выше потолка версии, отсутствует, отвергнут.
- Тест «признак не писать снапшоты» переписывается в правило «чтение на версии не пишет снапшот»;
  тесты головы с тестовым источником перестают править заявку.
- CHANGELOG не пополняется — всё внутреннее.

### 03. Заявка на готовность в `get/2` читателей

- stream-читатель и Kafka-читатель передают в общий цикл ожидания заявку `notify_when_ready/2` на
  процесс вызывающего; DLQ-читатель передаёт `nil` и продолжает опрос.
- Ложная заявка (`:empty` после `{:mq_ready, ref}`) продолжает ожидание, отказ заявки переходит на
  опрос с интервалом — поведение общего цикла не меняется.
- Исходы `get/2` прежние: `{:ok, message}`, `:empty`, `{:error, error}`. Интерфейс и телеметрия не
  меняются; CHANGELOG не пополняется.

### 04. Страница событий → wire

- `use Core.Web.Event` порождает `to_wire_page/2`: страница (`%Core.Pagination.Result{}`) и контекст →
  `Core.Result` со страницей wire-элементов.
- Функция собирает словарь ссылок `Core.Labels.Refs.get/2` один раз со всей страницы, затем применяет
  свою `to_wire/2` к элементам, сохраняя `total` через `Core.Pagination.Result.map/2`.
- Работает для обоих профилей: без подписей и с `labels: true` (включая требование `user_ref:`).
  Отказ резолвера возвращается как итог функции.
- Имя фиксировано: `to_wire_page/2`. Это аддитивное публичное API — пункт «Новое» в CHANGELOG.
- Схема страницы для `open_api_spex` остаётся делом приложения.

### 05. Один обход подписей

- Новый внутренний модуль `Core.Labels.Walk` с двумя входами:
  - обход значений — для сведений и словаря ссылок;
  - обход объявлений — для ратчета полноты.
- В `Walk` переезжают правила видимости: видимые поля, скрытые, `text:`, `change:`, спуск в struct,
  `set`/`map`/`union`. `Core.Labels.Kind` остаётся правилом вида Prim и не меняется.
- `Details` и `Refs` переводятся на обход значений; их собственные `collect`/`classify`/`visible_fields`
  и дубль `text?` удаляются. `CompletenessCase` переводится на обход объявлений и перестаёт держать
  свой `walk`/`visit`/`descend`.
- `@moduledoc` словаря ссылок приводится к коду: обещание «те же поля, что сведения» должно быть
  верным.
- JSON и `Core.Web` в `Core.Labels` не попадают; выходы `Details`, `Refs` и ратчета не меняются.
  CHANGELOG не пополняется — всё внутреннее.

### 06. Снимок состояния читателя

- В `Core.Mq.ReaderReliable` добавляется необязательный колбэк `snapshot/1` и тип снимка: топик,
  длина буфера, остаток чанка, признак сообщения в работе, возраст сообщения в работе в секундах,
  признак подписки/аренды и `details` для адаптерных подробностей.
- Снимок реализуют stream-читатель (буфер и подписка), Kafka-читатель (аренда и партиции) и
  DLQ-читатель (сообщение в работе). Возраст считается в читателе, PromEx больше не разбирает
  timestamp.
- `Core.Mq.PromEx` для общих gauge'ей читает только `snapshot/1`: четыре формы (`pending`/`pending?`,
  `pending_ts`/`pending_age_seconds`, `subscribed`/`subscribed?`) и попытка `metrics/1` → `info/1`
  уходят. Kafka-ветка аренды и лагов остаётся отдельной и продолжает читать `info/1` своей формы.
- `metrics/1` и `info/1` помечаются deprecated для метрик, но не удаляются: удаление — отдельное
  ломающее изменение следующего выпуска. CHANGELOG: «Новое» (снимок) и пометка deprecated.

### Порядок и зависимости

- 01 → 02: заявка и план сразу переносят типизированную конфигурацию, а не map.
- 03 → 06: оба трогают контракт читателя; снимок идёт после заявки на готовность.
- 04 и 05 независимы и могут идти параллельно.
- 02 включает свёрнутый кандидат «границы снапшота»: отдельного тикета нет.

## Testing Decisions

Хороший тест проверяет наблюдаемое поведение через существующий шов: состояние агрегата, исход и
detail отказа, события телеметрии, записанный снапшот, wire-map, значения gauge'ей. Внутренние имена,
форма SQL и устройство `Walk` не проверяются.

- **Репозиторий агрегата и read-репозиторий** — общие контракты
  (`test/support/es_aggregate_repo_contract.ex`, `test/support/es_aggregate_read_repo_contract.ex`).
  Тикеты 01 и 02 не меняют их ожиданий; тесты конфигурации правятся по полям структуры.
- **Движок без Postgres — `Load.run/2` и тестовый источник строк.** Проверяются режимы заявки,
  нарезка версий, снапшот, отвергнутый снапшот и повторное чтение. Образец — текущие тесты движка.
- **Контракт источника строк** — новый тест: SQL-адаптер и тестовый адаптер на одних граничных
  случаях. Образец — контракты репозиториев и читателей. Это единственный новый шов в тикете 02.
- **Запись и чтение снапшотов** — реальная база: `every:`, расшифровка, уничтоженный ключ субъекта,
  зависимость маркера от настройки. Образец — тесты со снапшотами.
- **Читатели MQ** — контракт `test/support/mq_reader_contract.ex` плюс юнит общего цикла ожидания.
  Заявка на готовность проверяется через `get/2`; ложная заявка и отказ заявки — на тестовом
  читателе. Живые брокеры — только под тегами `:rabbit_stream` / `:kafka`.
- **PromEx читателей** — события телеметрии с фейковым читателем
  (`test/support/prom_ex_fixture.ex`, `test/core/mq/prom_ex_test.exs`): те же имена метрик, метки,
  измерения и правила агрегации по нодам.
- **Wire страницы** — генерируемый модуль `test/support/web_event_fixture.ex`: оба профиля подписей,
  пустая страница, сохранение `total` и порядка, отказ резолвера, отсутствующий id.
- **Подписи** — публичные `Labels.Details.build/1`, `Labels.Refs.get/2` и проверки
  `CompletenessCase`; фикстура с `hidden`, `text:`, `union`, `set`/`map` и `change`. Образцы —
  текущие тесты подписей.
- **Регрессия расхождений** — тест, где одно поле скрыто, а `Refs` не должен его резолвить; и тест,
  где `text:` не порождает ссылку. Сейчас такие правила держатся только фикстурами.

## Out of Scope

- Сужение публичного API `Core.Es.Events`: удаление функций — ломающее изменение и запрещено нулём
  вызовов внутри библиотеки (`docs/rules/11-domain.md`).
- Слияние `get` / `get_decision` / `refresh` в один вход: ADR-0016 и ADR-0087.
- Общая машина состояний для трёх читателей и унификация транспортов: ADR-0033 и ограничения
  lease-волны.
- Разложение `Core.Es.Store` на write/read-модули.
- Перенос лагов Kafka в `details` снимка читателя.
- Удаление `metrics/1` и `info/1` — отдельное ломающее изменение следующего выпуска.
- Схема страницы для `open_api_spex` и правки приложений-потребителей, кроме CHANGELOG.
- Новые публичные швы, кроме `to_wire_page/2` и колбэка `snapshot/1`.
