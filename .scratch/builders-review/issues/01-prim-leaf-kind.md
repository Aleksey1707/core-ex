# 01: Prim сам отдаёт leaf и kind

**Status:** ready-for-agent

**Blocked by:** None (can start immediately)

**Сила:** Strong. Правка небольшая, и, вероятно, закрывает баг.

**Файлы:**
- `lib/core/codec.ex` — `prim_chain` (~360);
- `lib/core/codec/plugin/fields.ex` — `leaf` (~168);
- `lib/core/labels/details.ex` — `plain_kind` (~169);
- `lib/core/labels/refs.ex` — `prim_role`;
- `lib/core/labels/completeness_case.ex` — `unkinded?` (~312);
- `lib/core/view/opts.ex` — `prim_kind!` (~233).

**Проблема.** В `Core.Prim` нет функции «leaf-модуль композита и его действующий kind». Есть только `unwrap/1` по значению. Поэтому пять вызывающих сами спускаются по `__domain_base__`.

`View.Opts.prim_kind!` композит не разворачивает: берёт `mod.__domain_kind__()` и получает `:composite`, которого нет в приводимых kind'ах. Судя по коду, `prim:` с композитом во View даёт `CompileError`, хотя `Codec.coercible?/1` и Redump композит разворачивают. Тестом это не проверено — первый шаг проработки.

**Что изменилось бы.** `Core.Prim` сам отвечает на вопрос «leaf и kind». Вызывающие перестают знать про `Prim.Compose`.

**Выигрыш.** Locality: знание о композите в одном module. Расхождение View закрывается. Leverage на пяти местах.

**ADR:** конфликта нет.

## Agent Brief

**Category:** bug
**Summary:** `Core.Prim` отдаёт цепочку композита и её leaf; View типизирует `prim:`-композит по kind leaf-примитива.

**Current behavior:**
Поле View `prim:` с `Prim.Compose` падает на сборке: `CompileError` «у <Mod> kind :composite —
типизировать нечем; объявите поле через type:». Воспроизведено на `Core.PrimFixture.SubjectRef`
(композит над `UserID`). При этом `Core.Codec.coercible?/1` для того же модуля возвращает `true`, и
Redump композит принимает: они спускаются до leaf, а разбор опций View берёт `__domain_kind__/0`
самого композита. Функции, которая по модулю отдавала бы цепочку или leaf, в `Core.Prim` нет:
`unwrap/1` работает по значению. Поэтому Codec (цепочка для `coercible?` / `coerce`), Es.Event.Payload
(leaf для проверки «Prim субъекта») и Labels.Details (`plain_kind`) спускаются по `__domain_base__/0` сами.

**Desired behavior:**
- В `Core.Prim` две публичные функции по модулю:
  - `chain(module) :: [module()]`: `[Mod, Base, …, Leaf]` для Prim, `[]` — не Prim;
  - `leaf(module)`: последний элемент цепочки. Форму результата для не-Prim выбрать по
    `docs/rules/20-agreements.md` («find / get / get!»).
- Обе с `@doc` / `@spec`. Знание о `__domain_base__/0` вне `Core.Prim` и `Core.Prim.Compose`
  остаётся только в Labels (см. «Out of scope»).
- `coercible?/1` и `coerce/2` у Codec работают через `Prim.chain/1`. Сейчас `coerce/2` зовётся на
  каждое поле каждой строки и намеренно не проверяет `prim?/1` повторно на каждом звене; новая
  `chain/1` не должна дать лишних проверок на звено.
- Спуск до leaf в Payload и в `plain_kind` Labels.Details идёт через `Prim.leaf/1`.
- View: kind поля `prim:` — kind leaf-примитива. Композит над приводимой базой собирается, а typespec
  поля совпадает с typespec поля прямо по базе. Композит с кастомным `kind:` над приводимой базой
  ведёт себя так же, как в `Codec.coercible?/1` (решает kind leaf). Композит над базой
  неприводимого kind по-прежнему даёт `CompileError`.

**Key interfaces:**
- `Core.Prim.chain/1`, `Core.Prim.leaf/1`: новые.
- `Core.Codec.coercible?/1`, `Core.Codec.coerce/2`: поведение не меняется.
- Разбор опций `use Core.View` (`fields:` → `{:prim, mod, kind}`): `kind` берётся у leaf.

**Out of scope:**
