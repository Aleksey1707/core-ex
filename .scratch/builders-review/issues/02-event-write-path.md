# 02: Запись событий агрегата — один module

**Status:** ready-for-agent

**Blocked by:** None (can start immediately)

**Сила:** Strong.

**Файлы:**
- `lib/core/es/aggregate/repo/pg.ex` — `write/4` (~668–679), `page_stream` (~252–270), `behaviour!` (~319);
- `lib/core/repo/pg/state_stored.ex` — `flush_events` / `do_flush_events` внутри `quote` (~205–233), `page_stream` (~276–298), `behaviour!` (~300);
- `test/core/es/operation_test.exs` — describe «event-sourced агрегат» (~28) и «state-stored агрегат с событиями» (~111).

**Проблема.** Конвейер `Es.Operation.stamp` → `outbox.from_events` → `Es.Store.append` → `Personal.Wire.seal_records` → `Config.outbox_repo().append` написан дважды. В event-sourced пути это обычная функция, где между шагами вставлен `KeyReservation.append`. В state-stored пути — код внутри `quote` у потребителя: вызвать или протестировать его как функцию нельзя, поэтому одно и то же свойство проверяют два теста. Тело `page_stream` совпадает дословно, `behaviour!` тоже написан дважды.

**Что изменилось бы.** Порядок «события → резервы → outbox» принадлежит одному module библиотеки, и оба репозитория зовут его. В `quote` остаётся только сужение результата по ADR-0014.

**Выигрыш.** Locality: штамп операции и шифрование ПДн правятся в одном месте. Свойство пути проверяет один тест. `quote` у `StateStored` становится меньше.

**ADR:** конфликта нет. Сужение результата по ADR-0014 сохраняется.

## Agent Brief

**Category:** enhancement
**Summary:** конвейер записи событий агрегата («события → резервы → outbox») — одна функция библиотеки,
её зовут оба write-репозитория.

**Current behavior:**
Конвейер `Es.Operation.stamp` → `outbox.from_events` → `Es.Store.append` → `Es.Personal.Wire.seal_records`
→ `Config.outbox_repo().append` написан дважды:
- `Core.Es.Aggregate.Repo.Pg` — приватная `write/4` (раздел «запись»), между `Store.append` и
  `seal_records` вставлен `Es.KeyReservation.append`, `Store.append` с `continuous?: true`;
  транзакцию открывает `append/4` сам;
- `Core.Repo.Pg.StateStored` — `defp do_flush_events/3` внутри `quote`, у потребителя: без резервов,
  без `continuous?:`, вызывается внутри уже открытого `Transact.run` вместе с записью строки агрегата.

Код в `quote` нельзя вызвать или протестировать как функцию, поэтому штамп операции проверяют два
describe в `test/core/es/operation_test.exs` («event-sourced агрегат», «state-stored агрегат с
событиями»).

**Desired behavior:**
- Новый module `Core.Es.Store.Write` (`@moduledoc false` или `@doc false` — как у соседних
  внутренних функций билдеров) с одной публичной функцией записи пачки событий. Транзакцию она не
  открывает: её открывает вызывающий.
- Различия путей — данными, не развилкой по билдеру: кодек событий, outbox, построитель ошибки
  отказа (`mismatch`), опция непрерывности версий, объявления резервов ключей (пустой список — шаг
  резервов ничего не делает) и построитель ошибки занятого ключа. Порядок шагов — как сейчас в
  `write/4`: stamp → from_events → Store.append → KeyReservation.append → seal_records → outbox append.
- `Core.Es.Aggregate.Repo.Pg.write/4` сводится к вызову новой функции внутри своего `Transact.run`.
- `do_flush_events/3` в `quote` `StateStored` сводится к вызову новой функции. Пустая пачка
  по-прежнему отсекается до вызова (`flush_events/3`). `continuous?:` у state-stored не появляется.
- Поведение обоих путей не меняется: коды и ns ошибок, исход `{:error, _}` из транзакции, порядок
  записей.
- `docs/rules/13-repos.md`, правило «`Core.Es.Store.append` MUST NOT вызываться вне write-builder'ов…»:
  добавить `Core.Es.Store.Write` в перечень. Таблицу `continuous?:` (там же) поправить, если в ней
  останется ссылка на место вызова.
- Moduledoc обоих билдеров, где описан конвейер, ссылаются на новый module вместо перечисления шагов,
  если перечисление дублирует его `@doc`.

**Key interfaces:**
- `Core.Es.Store.Write` — новая функция записи пачки (имя и порядок аргументов — по
  `20-agreements.md`: context последний из данных, затем колбэк, затем `opts`).
- `Core.Es.Aggregate.Repo.Pg.append/4`, сгенерированные `insert/update/save` у `StateStored` —
  контракт не меняется.

**Acceptance criteria:**
- [ ] `Es.Operation.stamp`, `seal_records` и `outbox_repo().append` в write-путях агрегатов
      встречаются только в `Core.Es.Store.Write` (`grep` по `lib/core/es/aggregate/repo/pg.ex` и
      `lib/core/repo/pg/state_stored.ex` пуст).
- [ ] Тест новой функции: операция и сеанс контекста попадают в события потока и записи outbox; без
      резервов шаг резервов пропускается; ошибка отказа строится переданным `mismatch`.
- [ ] Из `test/core/es/operation_test.exs` describe «state-stored агрегат с событиями» удалён либо
      сокращён до проверки проводки, если иначе state-stored путь нигде не проверяет запись записи outbox.
      Describe «event-sourced агрегат» остаётся: он проверяет транзакцию на два агрегата и повтор.
- [ ] Существующие тесты `test/core/repo/pg/state_stored_test.exs`, `state_stored_race_test.exs`,
      `test/core/es/aggregate/repo/pg_test.exs`, `test/core/es/personal/events_test.exs`,
      `test/core/es/key_reservation*` зелёные без правок ожиданий.
- [ ] `make` зелёный, включая `consumer-check` (`quote` `StateStored` уменьшился, предупреждений
      фикстуры-потребителя нет).
- [ ] CHANGELOG не правится: изменение внутреннее.

**Out of scope:**
- `behaviour!` двух билдеров: проверки разные (пары `{name, arity}` против имён `insert/update/save`).
- `page_stream`: у ES-репозитория `@impl true` без `@spec`, у `StateStored` — `@spec` без `@impl`;
  общий AST дал бы развилку ради ~10 строк.
- `Core.Es.Personal.destroy_key/3`: пишет событие без outbox, под конвейер не подходит.
- Связи агрегата и опции `use` (тикеты 07, 08), полнота `reservation/1` (тикет 10).
