# 03: Чтение подписей — одна классификация

**Status:** ready-for-agent

**Blocked by:** 01 — Prim сам отдаёт leaf и kind (`.scratch/codec-field/` — resolved)

**Сила:** Strong.

**Файлы:**
- `lib/core/labels/details.ex` — `prim_shape`, `plain_kind`, `declaration`, `change_detail` (~140–218);
- `lib/core/labels/refs.ex` — `classify`, `prim_role`, `visible_fields` (~95–134);
- `lib/core/labels/completeness_case.ex` — `walk`, `visit`, `unkinded?`, `specs` (~250–340);
- `lib/core/labels/fields.ex` — `specs`, `paths` (~400–440);
- `lib/core/labels/event.ex` (~137).

**Проблема.**
- Правило «как Prim выходит в сведения» записано трижды: в `Details.declaration` / `plain_kind`, `Refs.prim_role` и `CompletenessCase.unkinded?`. Оно состоит из `Text.find` + `ID.find`, спуска к `__domain_base__`, проверки `__domain_kind__` и пробела для `:uuid`.
- Дерево нагрузки обходится четырьмя способами: по спеке и значению, по значению, по типам с раскрытием семейств и по спеке.
- Подстановка «change → `[old_value, new_value]`» повторена трижды.
- Предикат «модуль подписан» реализован пять раз, и модуль в нём загружается по-разному: `ensure_compiled`, `ensure_loaded` или голый `function_exported?`.
- `__label_fields__` читается в обход interface `Labels.Fields` в шести местах.

**Что изменилось бы.** На вопросы «вид значения в сведениях» и «видимые поля struct» отвечает один module. Details, Refs и CompletenessCase спрашивают его, а не собирают ответ сами.

**Выигрыш.** Ситуация «сведения показали значение, а словарь ссылок его не собрал» становится невозможной. Классификацию можно тестировать без построения событий. Locality: правило `text:` / `change:` правится в одном месте.

**ADR:** конфликта нет. ADR-0063 фиксирует объявления подписей, а не модули, которые их читают.

## Agent Brief

**Category:** enhancement
**Summary:** классификацию Prim в сведениях, видимые поля struct'а и предикат «struct подписан» отвечают по одному
месту; Details, Refs и CompletenessCase спрашивают их, а не собирают ответ сами.

**Current behavior:**
- Правило «как Prim выходит в сведения» записано трижды — в построении сведений (`Core.Labels.Details`), словаре
  ссылок (`Core.Labels.Refs`) и ратчете полноты (`Core.Labels.CompletenessCase`, проверка «id без вида»). Каждая
  копия сама зовёт `Labels.Text.find/1` и `Labels.ID.find/1` в своём порядке, сама спускается по цепочке
  композита до звена с объявлением и сама решает, что Prim `kind: :uuid` без объявления — пробел. Расхождений
  сейчас нет (Text и ID в одном Prim запрещает сборка), но держит их только дисциплина.
- Подстановка «struct изменения → поля `old_value` / `new_value` со спекой значения» повторена трижды: сведения,
  словарь ссылок (видимые поля), обход ратчета.
- Предикат «struct подписан» (`__label_fields__/0` экспортирован) реализован в четырёх местах с разной загрузкой
  модуля: `Code.ensure_loaded?`, `Code.ensure_compiled` (проверка при сборке в `Labels.Fields`) и голый
  `function_exported?` в `@after_compile` `Labels.Event`. Голый вызов работает только потому, что прямо перед
  ним `Core.Prim.prim?/1` компилирует модуль нагрузки побочным эффектом.
- `__label_fields__/0` читается в обход `Labels.Fields` в семи местах (Details, Refs, Event, четыре в
  CompletenessCase).

**Desired behavior:**
- Один публичный модуль Labels (имя на выбор, например `Core.Labels.Kind`) отвечает на вопрос «как Prim-модуль
  выходит в сведения». Ответ — данные, а не исключение:
  - объявление вида значения (`Labels.Text` или `Labels.ID`) и Prim-владелец объявления — первое звено цепочки
    `Core.Prim.chain/1` (тикет 01), у которого объявление есть;
  - без объявления — вид leaf-Prim (`:text` / `:number` / `:date` / `:datetime`);
  - без объявления над leaf `kind: :uuid` — отдельный исход «id без вида».
- Details, Refs и CompletenessCase классифицируют Prim только через этот модуль. Details по-прежнему поднимает
  `ArgumentError` с именем модуля на «id без вида»; CompletenessCase по тому же исходу пишет пробел `unkinded`;
  Refs по объявлению `Labels.ID` с резолвером собирает id владельца, по остальным исходам не спускается.
- `Labels.Fields` получает публичные `@doc` / `@spec`-функции:
  - «struct подписан» — одна стратегия загрузки, верная и при сборке (`@after_compile`, проверка `entity:`), и в
    рантайме (форма как у `Core.Prim.prim?/1`: загружен или `Code.ensure_compiled`);
  - «видимые поля struct'а» — `[{имя, спека}]` в порядке спеки, без `:hidden`; у struct'а изменения —
    `old_value` / `new_value` со спекой значения `change:`;
  - доступ к решению по полю (подпись / `:hidden`), если он нужен вызывающим после двух функций выше.
- Details, Refs, Event и CompletenessCase не читают `__label_fields__/0` / `__label_specs__/0` /
  `__label_change__/0` сами и не проверяют их экспорт сами.
- Четыре обхода (сведения по спеке и значению, словарь по значению, ратчет по типам с раскрытием семейств, пути
  `Fields.paths/1`) остаются раздельными: у них разные входы. Сводятся только вопросы, которые они задают.
- Поведение сведений, словаря ссылок и ратчета не меняется.

**Key interfaces:**
- Новый модуль классификации Prim в сведениях: функция `module() → исход` (три формы исхода выше); тип исхода — с
  `@type`.
- `Core.Labels.Fields`: функция «подписан» и функция «видимые поля» (с подстановкой изменения); `specs/1`,
  `change/1`, `paths/1` — контракт сохраняется.
- `Core.Prim.chain/1` из тикета 01 — единственный способ пройти цепочку композита в Labels.

**Acceptance criteria:**
- [ ] Тесты классификатора без построения событий: leaf-Prim каждого приводимого kind; Prim с `Labels.Text`;
      `Labels.ID` `kind: :id` / `:user` / `:ref`; композит без своего объявления над базой с объявлением (владелец
      — база); вложенный композит; композит со своим объявлением; `kind: :uuid` без объявления и композит над
      ним — «id без вида».
- [ ] Тесты функций `Labels.Fields`: «подписан» для подписанного struct'а, неподписанного struct'а, не-struct'а;
      «видимые поля» для struct'а с `:hidden` и для struct'а изменения (`Core.Es.ValueChanged` и ручной с
      `value:`).
- [ ] Вне `Core.Labels.Fields` никто не вызывает `__label_fields__`, `__label_specs__`, `__label_change__`
      (поиск по `lib/`).
- [ ] В `Core.Labels.*` нет `__domain_base__` и своих спусков по композиту: цепочку даёт `Core.Prim.chain/1`.
- [ ] Details, Refs и CompletenessCase не вызывают `Labels.Text.find/1` / `Labels.ID.find/1` для классификации
      значения нагрузки (проверка автора события в ратчете MAY остаться на `ID.find/1`).
- [ ] Проверка нагрузки в `@after_compile` `Labels.Event` не зависит от того, что модуль нагрузки скомпилирован
      побочным эффектом другой проверки.
- [ ] Существующие тесты Labels (Details, Refs, Fields, Event, CompletenessCase) и `Core.Web.Event` зелёные без
      правок ожиданий.
- [ ] Пункт в `CHANGELOG.md`, «Новое»: новые публичные функции `Labels.Fields` и модуль классификации.
- [ ] `make` зелёный.

**Out of scope:**
- Слияние четырёх обходов в один обобщённый обход.
- `Core.Prim.chain/1` / `leaf/1` и правка View (тикет 01).
- Протокол Prim-обёрток (тикет 04).
- Чтение чужих атрибутов (`:enum_values`, `:es_payload_fields`, `:es_value_changed`), `Check.prim!` и шаблон
  `declare!` / `required_keys` (тикет 06).
- Изменение семантики объявлений подписей (ADR-0063).
