## Triage Notes

**Established:**

- В библиотеке нет ни контракта резерва, ни таблицы: `Core.Es.Migration.up/0` создаёт только `es_events`,
  `es_snapshots`, `es_checkpoints` и вышел в v0.2.0. Норма `app/13-repos.md`, «Уникальность без индекса состояния»,
  покрывает только неизменяемый ключ (id потока — UUIDv5); альтернатива в своде — state-stored агрегат ради
  уникальных индексов.
- Решение qc (ветка `core-rc`, коммит b62c2b0) почти не специфично для приложения: behaviour
  (`reserve` / `rename` / `release` / `find`, отказ `{:error, :taken}`), Pg-реализация (`ON CONFLICT DO NOTHING` со
  сверкой числа строк, идемпотентность по `aggregate_id`, `rename` = резерв нового + снятие старого), таблица
  `unique_keys (scope text, key text)` PK → `aggregate_id`, тест гонки через `unboxed_run`, нормы в своде и
  ADR-0005 qc. Специфично только отображение событий агрегата на резерв (`*Key.sync/3`) и коды ошибок каталога.
- qc: резерв у трёх агрегатов — `User` (`user.login`), `Role` (`role.name`), `Perm` (`perm.name`); `sync` зовётся в
  пяти usecase (admin трёх агрегатов, два `quick_start`) после `get` и до `append`; процесс агрегата не используется,
  повтор — своя обёртка `QC.Transact`. `find` зовут только `quick_start` и `seed_demo` («найти или создать»).
  Нормализации ключа нет (только `trim` Prim). Состояние `sync` нужно только ради `Deleted` без нагрузки;
  `Created` и `LoginChanged` / `NameChanged` несут ключ.
- Дефект qc при переносе: `release` удаляет по `(scope, key)` без проверки владельца.
- `sync` нужно состояние после команды, а колбэк `Process.execute` получает только события — агрегат с таким
  ключом через процесс агрегата не пишется.
- Резерв (INSERT) до чтения потока назначает xid и делает ложные отказы стража `append` достижимыми
  (ADR-0008, «Цена»).
- `append` event-sourced репозитория (`Core.Es.Aggregate.Repo.Pg`, `write/4`) уже отображает события в записи outbox
  той же транзакцией (`outbox:` → `from_events/1`, сборка сверяет семейство событий) — образец встраивания.
- С тикетом 08 кодовой зависимости нет (изменяемый ключ не может быть id потока); общий только раздел `app/13`.

## Grilling (18.09.2026)

**Decided:**

- Объём — норма, код и DDL в библиотеке; перевод qc — вне объёма.
- Один ключ области на агрегат: unique `(scope, aggregate_id)`, занятие нового ключа снимает прежний, снятие — по
  владельцу. Набор ключей одной области — агрегат на элемент с идентификатором из ключа.
- Сопоставление только по событиям; событие, занимающее ключ, MUST нести ключ в нагрузке. Колбэк
  `Process.execute` не расширяется.
- Встраивание — опция репозитория `key_reservations:`, а не явный вызов: `append` пишет события → резервы → outbox.
- Ключ сравнивается побайтно; каноническую форму даёт `to_key/1` модуля ключа, её зовёт библиотека на записи и в
  `find`. Составной ключ — список строк, колонка `text[]`.
- Отказ — код из `code:` модуля ключа через `errors:` репозитория, `detail` — `%{scope}` без значения ключа (ПДн).
- Полнота `reservation/1` проверяется сборкой через `Core.Es.Check`, catch-all MUST NOT.
- `find(value, context) :: Agg.ID.t() | nil` генерируется.
- DDL — отдельный модуль `Core.Es.KeyReservation.Migration`, таблица `es_key_reservations`.
- Заполнение резервов существующих потоков — норма; функция библиотеки — отдельный тикет при втором потребителе.
- Имена: `Core.Es.KeyReservation`, `key_reservations:`, `<Aggregate>.<Name>Key`, `reservation/1` →
  `{:reserve, value} | :release | :keep`, `to_key/1`, `find/2`.
- `CONTEXT.md`: термин «Резерв ключа», «Область ключа» расширена на резерв. ADR-0018.

## Agent Brief

**Category:** enhancement
**Summary:** event-sourced агрегат объявляет изменяемые уникальные ключи в репозитории; `append` держит их резервы в
таблице библиотеки той же транзакцией, что и события.

**Current behavior:**
Уникальность изменяемого ключа (логин, имя) у event-sourced агрегата библиотека не даёт: индекса по состоянию нет,
read-модель пишет асинхронная проекция. Потребитель пишет свою таблицу, behaviour и вызов в каждом usecase.

**Desired behavior:**

- Модуль ключа потребителя:
  ```elixir
  defmodule MyApp.Domain.Users.Common.User.LoginKey do
    use Core.Es.KeyReservation,
      scope: "user.login",
      event: User.Event,
      id: User.ID,
      code: :already_exists

    def reservation(%Event.Created{payload: %{login: nil}}), do: :keep
    def reservation(%Event.Created{payload: p}), do: {:reserve, p.login}
    def reservation(%Event.LoginChanged{payload: p}), do: {:reserve, p.new_value}
    def reservation(%Event.Deleted{}), do: :release
    def reservation(%Event.Blocked{}), do: :keep

    def to_key(%User.Login{} = login), do: User.login_to_wire(login)
  end
  ```
  - колбэки: `reservation/1` → `{:reserve, value} | :release | :keep`; `to_key/1` → `String.t() | [String.t(), ...]`,
    строка равна списку из одной части;
  - генерируется `find(value, context) :: Agg.ID.t() | nil` — ключ через `to_key/1`, id через `id:`; голова и
    сужение результата — `20-agreements.md`, «Генерируемые функции» (ADR-0014);
  - опции: `scope:` — непустая строка; `event:` — семейство событий агрегата; `id:` — Prim идентификатора; `code:` —
    атом. Проверка опций при сборке, как у `use Core.Es.Outbox`.
- `use Core.Es.Aggregate.Repo.Pg, ..., key_reservations: [User.LoginKey]` (опционально):
  - `append`: `Es.Store.append` → резервы по каждому событию пачки в порядке пачки → outbox, одна транзакция;
    `{:reserve, value}` занимает `to_key(value)` за `aggregate_id` события и снимает прежний ключ этого агрегата в
    области; `:release` снимает ключ агрегата в области; `:keep` — ничего;
  - повторный резерв тем же владельцем — успех; ключ другого владельца — `{:error, errors.domain(behaviour, code,
    %{scope: scope})}`, транзакция не в aborted (вызывающий откатывает её по `{:error, _}`);
  - сборка: clause `code:` в `errors:` (`domain(_, code, nil)`); clause `reservation/1` на каждое событие кодека
    через `Core.Es.Check` (предупреждение на строке `use`); `event:` модуля ключа — семейство кодека; `id:` — `id:`
    репозитория; области в списке не повторяются.
- `Core.Es.KeyReservation.Migration` (`up/0` / `down/0` под `defdelegate`): `es_key_reservations` — `scope text`,
  `key text[]`, `aggregate_id uuid NOT NULL`; PK `(scope, key)`, unique `(scope, aggregate_id)`; колонки, ключ и
  состав индексов — контракт, имена индексов — нет. Тестовая база библиотеки — новая миграция в
  `priv/repo/migrations`, делегирующая сюда.
- Новых метрик и span нет — резерв внутри телеметрии `append`.

**Key interfaces:**

- `Core.Es.KeyReservation` — `__using__/1`, `@callback reservation/1`, `@callback to_key/1`, генерируемый `find/2`,
  интроспекция `@doc false`
- `Core.Es.Aggregate.Repo.Pg` — опция `key_reservations:`, moduledoc (опции, сборка, порядок записи)
- `Core.Es.KeyReservation.Migration` — `up/0`, `down/0`

**Acceptance criteria:**

- [x] гонка через `unboxed_run` (`async: false`, уборка `on_exit`): две транзакции за один ключ — одна успешна,
      вторая получает ошибку `code:`, транзакция не в aborted
- [x] резерв: повтор тем же владельцем — успех; перенос — прежний ключ свободен для другого агрегата; `:release` —
      ключ свободен; два агрегата разных видов в общей области конфликтуют
- [x] пачка одного потока `Created` + `LoginChanged` — в таблице только последний ключ
- [x] две конкурентные команды одного потока с разными ключами — вторая `:version_mismatch`, а не unique violation
- [x] составной ключ: `["x:y", "z"]` ≠ `["x", "y:z"]`; `to_key` строкой и списком из одной части — один резерв
- [x] `find` — `%Agg.ID{}` занятого ключа, `nil` свободного
- [x] путь `Agg.Process.execute` (`enabled: false` и процесс на id) пишет резервы без колбэка
- [x] сборка: `CompileError` на опции `use Core.Es.KeyReservation` и на повтор области / чужое семейство / чужой `id:`
      / нет clause `code:`; предупреждение — событие кодека без clause `reservation/1`
- [x] `fixtures/consumer`: модуль ключа и `find` без предупреждений в корректной части, маркеры `# expect:` при нужде
- [x] нормы:
  - `docs/rules/13-repos.md` — «Write event-sourced агрегата» (`key_reservations:`, порядок записи, отказ),
    «Процесс агрегата» (резерв без колбэка);
  - `docs/rules/app/13-repos.md`, «Уникальность без индекса состояния» — изменяемый ключ: модуль
    `<Aggregate>.<Name>Key` (`common/<aggregate>/<name>_key.ex`), событие, занимающее ключ, MUST нести ключ,
    catch-all в `reservation/1` MUST NOT, каноническая форма в `to_key/1`, составной ключ списком, заполнение
    резервов существующих потоков до первой записи нового кода; ссылка на ADR-0018;
  - `docs/rules/12-errors.md`, «Каталог агрегата» — строка `use Core.Es.Aggregate.Repo.Pg`: `:version_mismatch` и
    `code:` каждого модуля `key_reservations:`;
  - `docs/rules/19-testing.md` — если нужна норма теста модуля ключа
- [x] `CHANGELOG.md`, «Не выпущено»: «Новое» — `Core.Es.KeyReservation` и миграция; «Изменения контракта
      макросов» — `key_reservations:`; перевод потребителя было → стало (`unique_keys` + `*Key.sync` в usecase →

- [x] `make` проходит

**Out of scope:**

- перевод quality-control-back (`QC.UniqueKeys`, три `*Key`, вызовы `sync`, таблица `unique_keys`, нормы и ADR-0005
  qc) — в репозитории потребителя

- несколько ключей одной области у агрегата
- резерв у state-stored агрегата (там уникальный индекс)
