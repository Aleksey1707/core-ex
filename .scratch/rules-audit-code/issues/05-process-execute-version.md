## Agent Brief

**Category:** enhancement
**Summary:** `<Aggregate>.Process.execute` возвращает версию агрегата после commit — `{:ok, Version.t() | nil}`
вместо `:ok`. Ломающее изменение подтверждено мейнтейнером.

**Current behavior:**
`execute` возвращает `:ok | {:error, Error.t()}`. Состояние после записи внутри исполнения команды есть, но
вызывающему не отдаётся ни в inline-режиме (`enabled: false`), ни через процесс: сервер кэширует состояние у себя
и отвечает без него. Свод записывает это исключением — `docs/rules/app/10-architecture.md`, «Usecases»: «версии
после записи у этого пути нет». Поэтому ответ 202 с версией (`docs/rules/app/15-web-api.md`, «Ожидание проекции»)
на процессе агрегата не собрать: потребитель на процессе отвечает 202 без версии. Процесс агрегата уже вышел
в теге v0.2.0.

**Desired behavior:**
- успех — `{:ok, version}`: версия состояния после commit, `%Version{}`; `nil` — только когда команда на пустом
  потоке не дала событий (`decide` → `{:ok, []}`, состояние остаётся `version: nil`). Ошибки — без изменений;
- одинаково в inline-режиме, через процесс и после повторов на `:version_mismatch`;
- наружу — только версия, не состояние (CQS, `docs/rules/20-agreements.md`);
- сгенерированный `execute` сужает результат паттерном (`{:ok, %Version{}}` / `{:ok, nil}`) по
  `20-agreements.md`, «Генерируемые функции»: у потребителя компилятор видит узкий тип, а не `dynamic()`;
- telemetry и span команды: значение результата в метаданных прежнее.

**Key interfaces:**
- `<Aggregate>.Process.execute` (генерирует `use Core.Es.Aggregate.Process`) — спецификация
  `{:ok, Version.t() | nil} | {:error, Error.t()}` вместо `:ok | {:error, Error.t()}`
- ответ сервера процесса вызывающему несёт версию

## Реализация

Коммит «process execute version» (отдельная сессия; полный pre-commit прошёл):

- `Execution.result/1` отдаёт `{:ok, state.version}` (тип `Execution.result()`), ответ `Server` вызывающему —
  через неё же: один путь на inline, процесс на id и повторы. Сервер по-прежнему кэширует всё состояние.
- Сгенерированный `execute` сужает результат клаузами `{:ok, %Core.Version{}}` / `{:ok, nil}` / `{:error, _}`;
  `@spec` — в `Process`, `Server.reply()` и `Otel.Es.execute/4`. Тег `result: :ok` telemetry и span — прежние.
- Тесты `process_test.exs` — конкретные версии: inline и через процесс (1 → 3 у двухсобытийного `close`), после
  записи в обход процесса (3), после повторов inline и в процессе (2), пять конкурентных команд — 2..6.
  `{:ok, nil}` — тест «команда без событий — версия прежняя, на пустом потоке `{:ok, nil}`». Готовой команды без
  событий на пустом потоке у `Core.EsFixture.Account` не было (`Rename` / `Freeze` / `Close` при `version: nil` —
  `:not_found`): добавлены `Cmd.Check` (`decide` → `{:ok, []}` в любом состоянии) и хелпер `check/0`
  `Core.EsAggregateRepoContract`; решения существующих команд не менялись.
- `fixtures/consumer`: F5 — clause `:ok` по результату, новый F5b — `{:ok, %Account{}}`; оба — предупреждение.
  `Usecase.process/3` матчит `{:ok, %Version{}}` / `{:ok, nil}`.
- Свод: `13-repos.md` «Процесс агрегата» (контракт, пункт о версии и `nil`, пример «плохо»),

Замечено, не сделано:

- `{:ok, nil}` через процесс на id отдельным тестом не проверен — ответ сервера идёт той же `Execution.result/1`.
  Следующая команда после такого ответа дочитывает `refresh` от закэшированного состояния с `version: nil` —
  поведение прежнее, тестом не закрыто.
- Exit вызывающему после commit: `in_time` проверяется до commit, а `GenServer.call` ждёт до того же дедлайна —
  commit, закончившийся после дедлайна, даёт вызывающему exit при применённой записи, и версии у него нет. Поведение
  прежнее; для ответа 202 это ложный отказ — кандидат в отдельный тикет.
