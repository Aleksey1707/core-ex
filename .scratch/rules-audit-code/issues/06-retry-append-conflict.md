# 06: Повтор по источнику отказа записи

**Status:** done

**What to build:** `:version_mismatch` несёт источник отказа (`source: :expected | :storage` в detail), а повтор
решается по нему, а не по ожидаемой версии. Публичный `Core.Es.Transact` — цикл повтора с транзакцией,
пределом и логами; процесс агрегата переезжает на него.

**Why:** сейчас повтор только при `:current`, поэтому корректный `If-Match` получает 412 от конкурента по
соседнему потоку; каждый потребитель пишет обвязку повтора у себя (`QC.Transact`). Снаружи отказ сверки версии
и отказ хранилища неразличимы: detail у обоих одной формы.

- [x] `source:` в detail всех точек; `Core.Es.Transact`; перевод `Execution`; ADR-0019; `CONTEXT.md`; свод; CHANGELOG

## Agent Brief

**Category:** enhancement
**Summary:** повтор команды после `:version_mismatch` решается источником отказа, а не ожидаемой версией.
Ломающее изменение формы detail и наблюдаемого поведения `Agg.Process.execute`. Подтверждено мейнтейнером.

**Термины (заводятся в `CONTEXT.md`):**

- **сверка ожидаемой версии** — вызывающий назвал `%Version{}`, действительная другая. Повтор не помогает: 412.
- **отказ хранилища (отказ записи событий)** — `Es.Store.append` не принял пачку: занятая версия потока, страж
  `xid` или разрыв непрерывности. Не означает, что вызывающий видел устаревшее состояние: голова потока может
  быть ровно там, где он её видел (ADR-0008, «Цена»). Снимается повтором новой транзакцией.

**Current behavior:**
`Execution.tag_conflict/2` помечает конфликтом только результат `cfg.repo.append` и только при `version:
:current`; источник отказа различён **местом вызова**, а не данными ошибки. Снаружи он не различим вовсе:
detail сверки и detail отказа хранилища — одной формы (`%{aggregate_id, expected, actual}`), у state-stored
сверка строки даёт `%{id, expected, actual: :stale}`. Поэтому `:version_mismatch` из колбэка процесса или из
соседнего потока в теле usecase повтора не даёт, а обёртка потребителя (`QC.Transact.run(version, fun)`)
повторяет по единственному аргументу `version` и об отказавшем потоке не знает. Свод сам себе противоречит:
`13-repos.md:596` — «реакция одна — повтор usecase», `app/13-repos.md` «Повтор при `:current`» и
`app/10-architecture.md:146` — «по явной `%Version{}` — нет».

**Desired behavior:**

- detail `:version_mismatch` симметрично несёт `source: :expected | :storage`;
- повторяется отказ хранилища при **любой** ожидаемой версии; сверка не повторяется никогда. Ожидаемая версия
  в решении о повторе не участвует вовсе: сверка при `:current` невозможна, значит любая сверка — уже явная
  версия. Обоснование: если чтение по `V` прошло, вызывающий видел актуальное состояние, и отказ записи — не
  его вина; при настоящем конфликте повтор даст 412 от сверки одной транзакцией позже;
- `Core.Es.Transact` — `run/2` (результат) и `run_counted/2` (`{result, retries}` для своей telemetry). Сам
  открывает `Transact.run(Config.dao(), fun)`, `retries:` по умолчанию 3, паузы между попытками нет, вызов
  внутри открытой транзакции — `ArgumentError`, логи — `debug` на повтор и `warning` на исчерпание, контекст
  сообщения «транзакция команды»;
- `Execution` переезжает на `run_counted/2`: `tag_conflict/2` исчезает, дедлайн и перечитывание кэша остаются
  в теле. Следствие — `:version_mismatch` из колбэка `fun.(events)` теперь повторяется (колбэк обязан быть
  идемпотентным), и повтор идёт при явной `%Version{}`;
- классификатор: detail-список (`get_many`) — сверка, повтора нет; detail без `source:` — не повторять (ошибку
  собрал не write-путь библиотеки); `{:error, reason}` с не-`%Error{}` (в т.ч. служебное `:expired`
  `Execution`) — как есть.

**Key interfaces:**

- `Core.Es.Store.mismatch_detail/0` — `+ source: :storage`, ставится один раз в `append/5` (покрывает
  event-sourced и state-stored write-пути)
- `Core.Es.Aggregate.Repo.Pg.mismatch_detail/3` — `source: :expected` (питает `verify_version`,
