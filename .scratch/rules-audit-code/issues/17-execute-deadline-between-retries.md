# 17: Повтор команды процесса агрегата не смотрит на дедлайн

**Status:** done

**What to build:** дедлайн команды проверяется **между** попытками цикла повтора, а не только
последним шагом внутри попытки.

**Why:** вызывающий уже вышел по `GenServer.call` timeout, а сервер продолжает попытки: держит
`handle_call`, соединение пула и очередь команд этого id. Команды из очереди успевают просрочиться
и отбрасываются.

- [x] триаж: дедлайн — контракт `Execution`, проверка первым шагом попытки (вариант «а»)

## Triage Notes

**Что установлено:**

- `Execution.run/4` (`lib/core/es/aggregate/process/execution.ex:44`) отдаёт цикл повтора
  `Es.Transact.run_counted(fn -> attempt(...) end, retries: target.limit)`; `target.deadline`
  в цикл не передаётся вовсе.
- `in_time(target.deadline)` — **последний** шаг `attempt/4` (`:57`), то есть проверяется уже
  после `append` и колбэка, ради отката до commit. Перед следующей попыткой дедлайн не смотрят.
- `deadline` ставится только в режиме `:process`: `System.monotonic_time(:millisecond) + timeout`
  (`lib/core/es/aggregate/process.ex:314`); у `:inline` он `nil` и не проверяется.
- Сценарий: `timeout: 5_000`, `retries: 3`, попытка ~2 c. Вызывающий отваливается на 5-й секунде,
  сервер прогоняет попытки 3 и 4 ещё ~4 c.
- Данные не теряются: `in_time` откатывает транзакцию, коммита после дедлайна нет. Это
  деградация под нагрузкой, не потеря.
- Путь стал достижимее в этой же ветке: ADR-0019 расширил повтор на **любую** ожидаемую версию
  и на отказ из колбэка, так что попыток стало больше, чем было при `version: :current`.

**Что нужно от вас:**

- Где проверять: (а) `in_time` первым шагом `attempt/4` в дополнение к последнему — попытка после
  дедлайна отваливается сразу, `Es.Transact` не трогаем; (б) опция дедлайна у
  `Es.Transact.run_counted/2` — тогда это контракт публичного цикла повтора, и им сможет
  пользоваться usecase; (в) не чинить, записать в `DEBT.md`.
- Если (а): дедлайн-ошибка из первого шага не должна выглядеть как ошибка команды — нужен ли
  отдельный код, или хватает того, что отдаёт `in_time` сейчас.
- Нужен ли тест без процесса (чистая функция следующего шага), или достаточно теста через
  `Agg.Process.execute` с `enabled: false`.

**Решение (18.09.2026):** вариант (а) — проверка в `Execution`, `Es.Transact` не трогаем; отдельного
кода ошибки не нужно; тест — через `Agg.Process.execute` в процессе на id (`enabled: true`): при
`enabled: false` дедлайна нет вовсе. Спецификация — `## Agent Brief` ниже.

## Agent Brief

> *This was generated by AI during triage.*

**Категория:** bug
**Кратко:** попытка команды, начатая после дедлайна, обрывается до чтения и записи — цикл повтора
после дедлайна не выполняет полных попыток.

**Текущее поведение:**

`Core.Es.Aggregate.Process.Execution.run/4` отдаёт цикл повтора `Core.Es.Transact.run_counted/2`,
передавая только предел повторов; дедлайн команды в цикл не уходит. `in_time/1` — последний шаг
`with` в теле попытки, поэтому при отказе записи (`:version_mismatch`, `source: :storage`) `with`
прерывается на `append` и до проверки дедлайна не доходит. `Es.Transact` решает о повторе только по
источнику отказа и времени не видит. Итог: вызывающий уже вышел по таймауту `GenServer.call`, а
процесс агрегата прогоняет оставшиеся попытки целиком — держит `handle_call`, соединение пула и
очередь команд этого id; команды из очереди успевают просрочиться и отбрасываются. Данные не
теряются: `in_time` откатывает транзакцию, коммита после дедлайна нет.

**Желаемое поведение:**

Дедлайн проверяется **первым** шагом попытки в дополнение к последнему. Попытка, начатая после
дедлайна, отваливается до `get_decision` / `refresh` и `append`; её ошибка отказом хранилища не
является, значит цикл повтора обрывается на ней — после дедлайна открывается не более одной пустой
транзакции вместо оставшихся полных попыток. Исход вызывающему не меняется: он уже получил exit по
таймауту, процесс пишет warning о просроченной команде и не отвечает. Проверка последним шагом
остаётся: дедлайн может истечь между колбэком и commit.

Режим в вызывающем процессе (`enabled: false`) не затронут: дедлайна там нет (`nil`), проверка —
no-op.

**Ключевые контракты:**

- `Execution`, тело попытки: `in_time(target.deadline)` стоит и первым, и последним шагом `with`.
- Метка истёкшего дедлайна и сведение её к исходу `:expired` не меняются — нового кода ошибки не
  заводить: служебная метка с именем модуля уже отличает дедлайн от `{:error, _}` колбэка, а
  `Server` сводит `:expired` к отбрасыванию команды с warning.
- `Core.Es.Transact` не трогать: опции и классификация отказа те же.
- `@moduledoc Core.Es.Aggregate.Process`, описание `timeout:` — дописать третий случай: попытка,
  начатая после дедлайна, не идёт. `@moduledoc` `Execution` — уточнить, что дедлайн проверяется на
  границах попытки.

**Критерии приёмки:**

- [x] Тест в `test/core/es/aggregate/process_test.exs`, describe «повтор после отказа записи»:
      команда в процессе на id с отказом записи и попыткой длиннее `timeout:` — после истечения
      дедлайна новая полная попытка не стартует (число событий `{:load, %{op: :get_decision}}` не
      растёт), в логе — warning о просроченной команде, колбэк не звался, в потоке нет событий
      команды. Рычаг задержки — telemetry-хендлер на событии загрузки агрегата
      (`[:es, :aggregate, :load]`, эмитится в процессе агрегата) со `sleep`; гонка записи —
      `Core.EsFixture.Account.RacyRepo.Pg.race/2`.
- [x] Существующие тесты дедлайна («команда, простоявшая в очереди до дедлайна…», «дедлайн истёк
      посреди команды…») и тесты повтора проходят без правок.
- [x] `enabled: false` — поведение неизменно.
- [x] `make` зелёный.

**Вне области:**

- Опция дедлайна у `Core.Es.Transact.run_counted/2` — отклонена в триаже: контракт публичного цикла
  повтора ради одного потребителя.
- Пауза между попытками, изменение значений `retries:` / `timeout:` по умолчанию.
- Проверка дедлайна в режиме `enabled: false`.
- Отдельный код ошибки дедлайна и изменение исхода вызывающему (exit по таймауту — как был).
- CHANGELOG: правка внутренняя, публичный контракт не меняется.
