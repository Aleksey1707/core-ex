# Одна конфигурация и одна точка переопределения write-пути репозитория

Внутренний рефакторинг `Core.Repo.Pg`, `Core.Repo.Pg.StateStored` и `Core.Es.Store.Write`. Термины —
`CONTEXT.md`, «Repo (репозиторий записи)», «Repo.Pg», «State-stored агрегат», «Хранилище событий»,
«Запись outbox»; нормы — `docs/rules/13-repos.md`, «Generic `use Core.Repo.Pg`», «State-stored»,
`docs/rules/14-events-outbox.md`; решения — ADR-0001, ADR-0006, ADR-0019.

## Problem Statement

Write-путь репозитория держится на трёх неявных контрактах, которые нигде не выражены типом.

Конфигурация репозитория — map из тринадцати ключей, который макрос кладёт в модуль-потребитель, а
`StateStored` читает как свой: форма и порядок раскрытия `use` стали обязательными, но не проверяются.
Точка переопределения записи разрезана: `save` вызывает `insert`/`update` макроса, а не модуля, поэтому
`StateStored` переопределяет `save` целиком и держит вторую копию решения «строка уже есть или её ещё
нет». Правило «модуль, переопределивший `insert`/`update`, обязан переопределить `save`» записано в
документации как обход собственного дизайна, а забытое переопределение пишет строку без детей и без
событий — молча.

Данные записи пачки событий — map с необязательными ключами: объявления модулей ключа и ошибка занятого
ключа связаны по смыслу, но не по типу, а отсутствие ключа неотличимо от опечатки — резервы ключа в этом
случае не ставятся, и `{:ok, _}` возвращается без них.

## Solution

Конфигурация становится структурой `Core.Repo.Pg.Config`, единственной формой `@pg` для обоих
builder'ов и для кастомных методов репозитория. Появляется одна точка переопределения записи:
`persist` в модуле-потребителе решает «insert или update» по факту строки и вызывает **модульные**
`insert`/`update`; `StateStored` переопределяет только её, оборачивая выбор транзакцией. Решение
«вставка требует `insert` и `update`» проверяется на компиляции. Данные записи пачки событий становятся
структурой `Core.Es.Store.Write.Plan`, где резервы ключа и ошибка занятого ключа задаются вместе.

Поведение записи, схема таблиц, публичные головы behaviour `Core.Repo`, обработка ошибок и телеметрия не
меняются; потребитель обновление не замечает, если не трогал `@pg` через `Map.put`/`Map.merge`.

## User Stories

1. As мейнтейнер библиотеки, I want форму конфигурации репозитория задавать структурой, so that правка ключа не требовала помнить о двух макросах.
2. As мейнтейнер библиотеки, I want `StateStored` получать тот же тип конфигурации, что и `Repo.Pg`, so that чтение `@pg.errors`/`@pg.module` не было угадыванием.
3. As мейнтейнер библиотеки, I want решение «insert или update» в одном месте, so that его правка не повторялась в двух копиях.
4. As мейнтейнер библиотеки, I want `save` вызывать переопределённые в модуле `insert`/`update`, so that забытое переопределение не писало строку без детей и событий.
5. As мейнтейнер библиотеки, I want `StateStored` переопределять только `persist`, so that его тело не повторяло выбор ветки.
6. As мейнтейнер библиотеки, I want транзакцию вокруг выбора ветки сохранить, so that конкурентное создание или удаление строки не уводило `save` не в ту ветку.
7. As мейнтейнер библиотеки, I want `save` без `insert`/`update` ломать сборку, so that невозможная конфигурация не доживала до первого вызова.
8. As мейнтейнер библиотеки, I want `save` остаться переопределяемым, so that модуль, переопределивший его по старой документации, не сломался.
9. As мейнтейнер библиотеки, I want внешний вызов `Repo.Pg.save/4` сохранил прежнюю семантику, so that вызовы вне макроса не изменились.
10. As мейнтейнер библиотеки, I want данные записи пачки событий задавать структурой, so that опечатка в ключе была ошибкой сборки, а не тихим пропуском резервов ключа.
11. As мейнтейнер библиотеки, I want резервы ключа и ошибку занятого ключа задавать вместе, so that недостижимое состояние не описывалось типом.
12. As мейнтейнер библиотеки, I want оба write-builder'а собирали план одинаково, so that отличия остались только данными.
13. As разработчик приложения, I want сгенерированные `get` / `insert` / `update` / `save` / `delete` не изменили головы и исходы, so that usecase'ы не правились.
14. As разработчик приложения, I want кастомные методы репозитория, получающие `@pg`, продолжали работать, so that `get_by_*` и `page_by_*` не переписывались.
15. As разработчик приложения, I want `shadow_copy?` и эталон в `Repo.Sc` не изменились, so that load → mutate → save работал как раньше.
16. As разработчик приложения, I want ошибки записи и `source: :expected` / `:storage` не изменились, so that `Core.Es.Transact` повторял по тем же правилам.
17. As разработчик приложения, I want запись событий и outbox в одной транзакции сохранилась, so that откат команды оставался целым.
18. As разработчик приложения, I want схему таблиц и миграции не менять, so that выкладка не требовала шага с базой.

## Implementation Decisions

- **`Core.Repo.Pg.Config` — публичная структура.** Поля: `dao`, `module` (behaviour), `schema`,
  `query`, `default_filters`, `to_entity`, `to_model`, `to_id`, `version_field`, `shadow_copy?`,
  `errors`, `constraint_errors`. Все обязательные; структура собирается тем же `quote`-литералом, что и
  прежний map, поэтому значения-выражения остаются на этапе компиляции модуля-потребителя.
- **`@pg` остаётся именем атрибута, меняется значение.** Головы функций `Repo.Pg` продолжают матчить
  конфигурацию по ключам, а не по `%Config{}` — поэтому `Repo.Pg.get_by(@pg, …)` и
  `Repo.Pg.page_by(@pg, …)` в коде потребителя работают без правок.
- **Спеки `Repo.Pg` — `Config.t()` вместо `map()`.** Это единственное место, где структура видна
  снаружи; тестовые фикстуры, строившие конфигурацию руками, переводятся на структуру.
- **`persist` — точка переопределения.** В модуле-потребителе генерируются `save/2,3` и `persist/2,3`;
  `save` делегирует в `persist`, `persist` по умолчанию зовёт политику `Repo.Pg.persist/5` с модулем
  реализации (`__MODULE__`). Политика: эталон в `Repo.Sc` есть → `update`, иначе `exists?(id, :current)`
  → `insert`. Обе функции `defoverridable`.
- **`Repo.Pg.persist/5` и `Repo.Pg.exists_for_write?/4` публичны с `@doc false`.** Они — интерфейс
  между макросом и сгенерированным кодом, а не API приложения; `exists_for_write?/4` остаётся
  единственной копией решения «строка уже есть».
- **`StateStored` переопределяет `persist`, а не `save`.** Тело: `Transact.run(dao, fn -> Repo.Pg.persist(@pg, __MODULE__, entity, context, opts) end, opts)`.
  Своя копия решения о существовании удаляется. `insert`/`update` остаются переопределёнными: строка →
  дети → события и outbox в одной транзакции, возврат входного агрегата с очищенными событиями.
- **Компиляционная проверка.** `use Core.Repo.Pg` с `save` в `only:` требует `insert` и `update`
  в том же наборе: `save` выбирает между ними, и без одной из веток вызов не определено чем закончить.
  Нарушение — отказ сборки с текстом про `only:`; это изменение контракта макросов.
- **`Repo.Pg.save/4` (внешний) сохраняет прежнюю семантику.** Он по-прежнему выбирает между
  generic `insert/4` и `update/4`, потому что у вызывающего вне макроса нет модуля реализации.
  Ловушка снимается для сгенерированного `save/2,3`, а не для этой функции.
- **`Core.Es.Store.Write.Plan` — структура.** Обязательные: `event_codec`, `outbox`, `mismatch`;
  остальные — `continuous?` (по умолчанию `false`), `key_reservations` (по умолчанию `[]`), `taken`
  (по умолчанию `nil`). Публичный тип заменяет прежний `t:path/0`.
- **`reserve/3` теряет клаузу «ключа нет в map».** Остаются два случая: пустые объявления → `:ok`;
  непустые → `KeyReservation.append/4`. `taken` без объявлений больше не описывается: builder ставит
  оба поля вместе, а структура с неизвестным ключом — ошибка компиляции.
- **Три места сборки плана:** оба write-builder'а и тестовая фикстура. `continuous?: true` остаётся
  свойством только event-sourced builder'а; у `StateStored` резервов ключа и непрерывности нет.
- **CHANGELOG (теми же коммитами).** Ломающие изменения контракта: `@pg` — структура (правка:
  `Map.put(@pg, …)` → `%{@pg | …}`); `Store.Write.append/4` принимает `Plan`. Изменения контракта
  макросов: `save` в `only:` требует `insert` и `update`. Новое: `Core.Repo.Pg.Config`,
  `Core.Es.Store.Write.Plan`.
- **Порядок работ (тикеты).** 01 — `Config`: структура, `@pg`, спеки, фикстуры. 02 — `persist`:
  политика, генерируемые функции, `StateStored`, компиляционная проверка, свод. 03 — `Plan`:
  структура, `reserve/3`, три места сборки, тестовая фикстура.

## Testing Decisions

- Хороший тест проверяет наблюдаемое поведение репозитория: исход операции, записанную строку, детей,
  события, записи outbox. Приватные имена и форма запросов не проверяются.
- **Шов записи — сгенерированный репозиторий через свой behaviour.** Тесты `insert`/`update`/`save`
  идут через функции модуля-фикстуры на `Core.DataCase`, а не через `Repo.Pg.*` напрямую. Образец —
  `repo/pg_test.exs`, `repo/pg/state_stored_test.exs`, `repo/pg/state_stored_race_test.exs`.
- **Шов компиляции — `Code.eval_quoted` + `assert_raise CompileError`.** Так уже проверяются опции
  `use Core.Repo.Pg`; тот же приём ловит `save` без `insert`/`update` и неизвестный ключ структуры
  конфигурации.
- **Шов записи пачки событий — `Core.Es.Store.Write.append/4`** в транзакции тестового репозитория:
  проверяется эффект (строки `es_events`, записи outbox, резервы ключа, отказ по `continuous?`), не
  форма плана. Образец — `store/write_test.exs`, `es/aggregate/repo/pg_test.exs`,
  `es/key_reservation_test.exs`.
- **Регресс ловушки `save`.** Новый тест: модуль-фикстура переопределяет только `insert`/`update`;
  `save` обязан пройти через них. Сейчас такое переопределение пишет строку мимо детей и событий.
- **Регресс `persist`.** `StateStored` с `save` не переопределённым вручную: вставка и обновление идут
  одной транзакцией, `Repo.Sc`-эталон кладётся после commit, возвращается входной агрегат.
- **Совместимость `@pg`.** Тест кастомного метода, получающего `@pg` и вызывающего `Repo.Pg.get_by/6`,
  продолжает проходить без правок — это проверка «правка не требует обновления потребителя».
- **Полный прогон** после третьего тикета: `make` (в частности `consumer-check`, `spec-check`,
  `dialyzer`), плюс `mix test test/core/repo test/core/es/store test/core/es/aggregate`.

## Out of Scope

- Единый модуль записи state-stored (строка → дети → события одним владельцем) и query-builder для
  `read_scope`/`write_scope` — следующий заход, меняет раскладку сгенерированного кода.
- Контрактный набор тестов `Core.Repo` по образцу `Core.EsAggregateRepoContract`.
- `insert_many/4`, `chunk_size:` и длинный `quote` — остаются в `DEBT.md` как есть.
- `read_scope`/`baseline`/`put_baseline` как часть публичного интерфейса: имена и поведение не
  меняются, вопрос «остаются ли они на поверхности» не решается.
- `Repo.Sc`, `shadow_copy?`, `Helper.AfterCommit`, маппинг constraint-ошибок, `page_stream/4`.
- Event-sourced read-путь (`Load`, `Snapshot`, `ReadRepo`) и читатели брокера.
- Схема БД, миграции, телеметрия, метрики.

## Further Notes

- Мотивация: самый горячий файл библиотеки (`Repo.Pg` — 24 правки за 200 коммитов) и волна
  `repo-sc-clock` уже показали, что конфигурация и write-путь — место постоянных изменений. Спека
  делает владельца формы конфигурации и точки переопределения явным, не меняя поведения.
- Главный риск — `persist` как занятое имя в модуле-потребителе. Решение принято: имя `persist`,
  макрос документирует занятые имена; альтернатива `save_or_update` отвергнута как более длинная.
- Второй риск — компиляционная проверка `save` без `insert`/`update`: набор `only: [:get, :save]`
  собирался раньше. В библиотеке таких конфигураций нет (кроме тестов, которые дополняются), но
  потребитель мог так объявить: изменение идёт в CHANGELOG как контракт макросов.
- `Repo.Pg.save/4` намеренно сохраняет старую семантику: если её перевести на `persist` с неизвестным
  модулем реализации, внешние вызовы получат другое поведение.
- ADR-0001 (возврат входного агрегата), ADR-0006 (реализация по конвенции), ADR-0019 (`source:` отказа)
  не пересматриваются: голова behaviour, `dao:` и коды ошибок остаются прежними.
