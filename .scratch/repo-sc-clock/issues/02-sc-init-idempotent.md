# 02: `Repo.Sc.init/1` идемпотентен в своём процессе

**What to build:** повторный `init/1` на контексте, который уже держит живую таблицу **этого же
процесса**, возвращает контекст как есть: прежняя таблица и её эталоны сохраняются, новая не
создаётся. Сегодня `init/1` безусловно кладёт новую таблицу поверх ключа, и прежняя сиротеет до
смерти процесса — в долгоживущем процессе это утечка. `init/1` в чужом процессе над контекстом с
живой таблицей по-прежнему создаёт свою (кейс `with_shadow_copy` процесса агрегата) и чужую не
трогает.

**Blocked by:** None (can start immediately) — но правит тот же `lib/core/repo/sc.ex`, что и
тикет 01: по `docs/agents/parallel-implement.md` оба отдаются одному агенту последовательно; при
раздельных worktree тикет 02 перестраивается на хелпер резолва таблицы из 01.

**Status:** resolved

- [ ] `init/1`: ключ в контексте → таблица жива и `:ets.info(tid, :owner) == self()` → контекст
      без изменений; иначе (нет ключа, таблица мертва, таблица чужая) — `:ets.new` поверх ключа.
      Мёртвую/чужую таблицу не удалять: своя мёртвая исчезнет сама, чужую убивать нельзя.
- [ ] Moduledoc: `init/1` идемпотентен в процессе-владельце.
- [ ] Тесты `test/core/repo/sc_test.exs`: два `init` подряд в одном процессе — один `tid`,
      эталон, положенный между ними, читается; `init` в чужом процессе над контекстом с живой
      таблицей — новая таблица своя, прежняя жива и доступна владельцу.
- [ ] Тест окружения процесса агрегата («Repo.Sc — таблица процесса, таблица вызывающего цела»)
      зеленый: `with_shadow_copy` стартует с контекста вызывающего, чья таблица ему чужая, —
      ветка создания новой сохранена.

## CHANGELOG

Внутреннее изменение (публичное поведение `init/1` на свежем контексте не меняется) — пункт
волны не требуется, если в 01 не всплывёт видимая потребителю разница.

## Answer

Сделано в `repo-sc: make init/1 idempotent in the owner process` (ветка `repo-sc-clock`). `init/1`
переиспользует живую свою таблицу (эталоны сохраняются), чужую не трогает и создаёт свою, мёртвую
заменяет. Moduledoc и `@doc init/1` дополнены. Тесты: два `init` подряд — тот же `tid`, эталон
читается; `init` в чужом процессе — своя таблица, прежняя жива; `init` поверх мёртвой своей —
новая. Видимая потребителю разница (повторный `init` не сбрасывает кэш) отражена в пункте
`Repo.Sc` раздела «Не выпущено».

## Приёмка

`make` целиком (минимум: `mix test test/core/repo test/core/es/aggregate/process_test.exs`,
`format-check`, `credo --strict`).
