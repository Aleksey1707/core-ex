# 01: `Repo.Sc`: деградация на чужой таблице вместо `ArgumentError`

**What to build:** write-репозиторий с `shadow_copy?: true`, получивший контекст, чья таблица
`Repo.Sc` создана другим процессом (контекст уехал в `Task`, подписчик передал контекст процессу
агрегата), больше не падает `ArgumentError`: `put/2` и `find/3` деградируют в no-op / `nil` — как
сегодня при выключенном кэше. Кэш — оптимизация write-пути: отсутствие эталона штатно уводит
`Children.sync` на широкий diff, корректность записи от этого не страдает. Правило «таблица
принадлежит создавшему процессу» задокументировано в moduledoc и своде репозиториев; ложное
предупреждение про расхождение эталона после отката транзакции снято (штатный путь регистрирует
эталон после commit — `Helper.AfterCommit`).

**Blocked by:** None (can start immediately). Параллельно с тикетом 02 — общий файл
`lib/core/repo/sc.ex`: по `docs/agents/parallel-implement.md` тикеты, правящие один файл,
отдаются одному агенту последовательно (или 02 вливается после 01 с перестройкой).

**Status:** resolved

- [ ] Единый приватный хелпер резолва таблицы: `tid` из `Context.find` → `is_reference` →
      `:ets.info(tid, :owner) == self()` → иначе `nil`; `put/find` идут через него и по `nil`
      сохраняют текущую no-op-семантику. Проверено на OTP: для чужой `:private`-таблицы
      `:ets.info/1` возвращает метаданные, а `lookup`/`insert` падают — текущий `alive?/1`
      не защищает.
- [ ] `delete/1` / `clear/1` на чужой живой таблице не удаляют её (владелец — другой процесс);
      ключ с контекста снимают только для своей или мёртвой таблицы — поведение согласовать с
      `with_shadow_copy` процесса агрегата (таблица вызывающего обязана пережить команду).
- [ ] Moduledoc: правило владения таблицей и деградация в no-op в чужом процессе; абзац
      «После отката транзакции эталон в ETS расходится с БД» заменён точным: расхождение возможно
      только при прямом `put_baseline/3` внутри транзакции, штатная запись регистрирует эталон
      после commit.
- [ ] `docs/rules/13-repos.md`, семантики `Repo.Sc`: то же правило владения; `make rules-check`.
- [ ] Тесты `test/core/repo/sc_test.exs`: `put/find` из чужого процесса (`spawn` / `Task`) над
      контекстом с живой таблицей — no-op и `nil`, без `ArgumentError`; таблица владельца цела;
      существующие тесты (stale-контекст, `clear`, `delete`) зелены без изменений.
- [ ] Тест окружения процесса агрегата (`test/core/es/aggregate/process_test.exs`, «Repo.Sc —
      таблица процесса») зеленый как был: пересоздание таблицы в `with_shadow_copy` не сломано.

## CHANGELOG

Текст пункта волны (в `CHANGELOG.md` вносит сводный тикет/слияние):

- **`Repo.Sc` в чужом процессе деградирует вместо падения.** `put/2` / `find/3` на контексте, чья
  таблица создана другим процессом, раньше падали `ArgumentError` (приватная ETS доступна только
  владельцу, а проверка живости таблицы её не отсекала): было — исключение в репозитории, которому
  передали контекст из другого процесса; стало — no-op и `nil`, как при выключенном кэше, запись
  идёт широким diff дочерних строк. Правка потребителя не требуется; код, ловивший это исключение,
  упрощается.

## Answer

Сделано в `repo-sc: degrade on a foreign shadow-copy table` (интеграционная ветка `repo-sc-clock`,
`lib/core/repo/sc.ex`). Единый `own_table/1` (`Context.find` → `is_reference` → `:ets.info(:owner) ==
self()`) отсекает чужую таблицу: `put` — no-op, `find` — `nil`, `delete`/`clear` чужую живую
таблицу не трогают и ключ снимают только для своей/мёртвой. Правило записано в moduledoc и
`docs/rules/13-repos.md`; абзац про откат транзакции заменён на `put_baseline/3` внутри транзакции
и регистрацию после commit. Тесты — `test/core/repo/sc_test.exs`; тест окружения процесса агрегата
зелёный.
