# Состояние на версии через read-репозиторий

Решение — ADR-0094; термины — `CONTEXT.md`, «Состояние на версии», «Адрес версии».

## Problem Statement

Потребителю нужно показать event-sourced агрегат таким, каким он был на известной версии: условия на момент
события, «как было» в документе, который на агрегат опирается. Библиотека этого не даёт — `get` с `%Version{}`
только сверяет голову потока и отказывает `:version_mismatch`, если она ушла дальше. Поэтому потребитель
хранит копию агрегата или его полей рядом с документом: копия дублирует хранение и расходится с потоком
событий, который и так помнит каждое состояние. Собрать префикс руками (`page_stream` → отбор → `Agg.fold/2`)
можно, но тогда в коде потребителя оказывается доменное состояние, от которого легко принять решение: такая
команда упрётся в отказ хранилища и будет бесполезно повторена `Es.Transact`.

## Solution

Потребитель хранит адрес версии `{id агрегата, версия}` вместо копии и читает по нему представление.
Библиотека даёт пару модулей read-пути: behaviour `use Core.Es.Aggregate.ReadRepo` и реализацию
`use Core.Es.Aggregate.ReadRepo.Pg`. Они отдают `get_at` (один адрес версии) и `get_many_at` (список адресов
версий одним запросом). Состояние на версии сворачивается внутри библиотеки и переводится в View функцией
потребителя `to_view:`; наружу уходит только `%View{}`, поэтому принять решение от прошлого состояния
сборка не даст. Write-репозиторий агрегата и его behaviour не меняются.

## User Stories

1. As a разработчик приложения, I want хранить адрес версии вместо копии агрегата, so that не дублировать данные потока событий.
2. As a разработчик приложения, I want получить представление агрегата на версии `N` одним вызовом, so that показать «как было» без ручной свёртки.
3. As a разработчик приложения, I want получить представления по списку адресов версий одним запросом, so that список документов не делал запрос на каждую строку.
4. As a разработчик приложения, I want в одном пакете указывать один агрегат на разных версиях, so that документы, опирающиеся на разные версии одного агрегата, читались вместе.
5. As a разработчик приложения, I want допускать повтор одной и той же пары в пакете, so that не убирать дубли перед вызовом.
6. As a разработчик приложения, I want получать результаты пакета в порядке пар, so that сопоставлять результат с входом по позиции.
7. As a разработчик приложения, I want получать отказ, если адрес версии указывает за голову потока, so that рассинхрон адреса и потока не маскировался головным состоянием.
8. As a разработчик приложения, I want получать отказ на пустом потоке, so that адрес на незаведённый агрегат не давал пустого представления.
9. As a разработчик приложения, I want чтобы этот отказ отличался от сверки ожидаемой версии и от отказа хранилища по `source:`, so that реагировать на него отдельно и не попадать под повтор `Es.Transact`.
10. As a разработчик приложения, I want чтобы все расхождения пакета пришли одной ошибкой со списком detail в порядке пар, so that показать все битые адреса разом.
11. As a разработчик приложения, I want чтобы отказ строился моим каталогом ошибок write-репозитория, so that не заводить новый код и не править каталог.
12. As a разработчик приложения, I want задавать перевод состояния агрегата в View своей функцией, so that wire-форма не повторяла поля агрегата и не ломалась при их переименовании.
13. As a разработчик приложения, I want чтобы результат был сужен до `%View{}`, so that компилятор предупреждал о неверной clause и опечатке в поле у вызывающего.
14. As a разработчик приложения, I want не видеть состояние агрегата на версии вне `to_view`, so that случайно не исполнить от него команду.
15. As a разработчик приложения, I want подменять read-репозиторий дублёром behaviour в тестах usecase, so that тестировать usecase без базы.
16. As a разработчик приложения, I want чтобы write-репозиторий и его реализация брались по `repo:` и конвенции DI, so that не дублировать агрегат, кодек, снапшоты и каталог ошибок в опциях.
17. As a разработчик приложения, I want получать `CompileError`, если `repo:` — не репозиторий event-sourced агрегата, so that state-stored агрегат не получил свёртку, которая не воспроизводит его строку.
18. As a разработчик приложения, I want получать `CompileError` на неверную форму `behaviour:`, `view:` и `to_view:`, so that ошибка объявления ловилась при сборке.
19. As a разработчик приложения, I want получать `FunctionClauseError` на `:current` вместо версии, so that голову потока читали через `get`, а не через чтение по версии.
20. As a разработчик приложения, I want чтобы свёртка начиналась со снапшота, если его версия не выше `N`, so that близкая к голове версия читалась быстро.
21. As a разработчик приложения, I want чтобы снапшот новее `N` пропускался, а свёртка шла с начала потока, so that состояние на версии было верным.
22. As a разработчик приложения, I want чтобы чтение по версии снапшоты не писало, so that исторический прогон не затёр свежий снапшот старым.
23. As a разработчик приложения, I want чтобы поток каждого агрегата в пакете читался один раз до наибольшей версии, so that несколько адресов одного агрегата не умножали чтение.
24. As a разработчик приложения, I want чтобы уничтоженные ПДн-значения оставались уничтоженными и в состоянии на версии, so that историческое чтение не обходило уничтожение ключа субъекта.
25. As a разработчик приложения, I want явный запрет кешировать состояние на версии, so that кеш не отдавал ПДн после уничтожения ключа.
26. As a разработчик приложения, I want чтобы read-репозиторий не проверял доступ и не отдавал `:not_found`, как `page_stream`, so that права по `Context` решал читающий usecase в одном месте.
27. As a разработчик приложения, I want вызывать чтение вне транзакции с опциями запроса, so that оно не втягивалось в транзакцию команды и её повторы.
28. As a разработчик приложения, I want именовать read-модель по назначению в каталоге агрегата, so that она не конфликтовала с проецируемой `<Aggregate>.ReadRepo` / `<Aggregate>.View`.
29. As a оператор приложения, I want видеть загрузку и длину свёртки чтения по версии в тех же метриках `[:es, :aggregate, :load]` и `[:es, :aggregate, :fold]`, so that оценить цену далёких версий без новых дашбордов.
30. As a оператор приложения, I want различать чтение по версии меткой `op: :get_at | :get_many_at`, so that отделить его от `get` / `get_many` в метриках.
31. As a мейнтейнер библиотеки, I want держать свёртку до версии внутренней функцией (`@doc false`), so that не расширять behaviour write-репозитория и не ломать дублёров потребителей.
32. As a мейнтейнер библиотеки, I want описать нормы в `13-repos.md`, «Состояние на версии», so that агенты и разработчики потребителя видели запреты и исходы в своде.
33. As a мейнтейнер библиотеки, I want запись в CHANGELOG в разделе «Новое», so that потребители узнали о способе заменить копию агрегата.

## Implementation Decisions

- **Новые модули.** `Core.Es.Aggregate.ReadRepo` — макрос behaviour: опции `repo:` (behaviour write-репозитория event-sourced агрегата, `use Core.Es.Aggregate.Repo`) и `view:` (модуль `use Core.View`). Генерирует колбэки `get_at/3,4` и `get_many_at/2,3`, результат которых сужен до `%View{}` / списка. `Core.Es.Aggregate.ReadRepo.Pg` — макрос реализации: опции `behaviour:` (модуль `use Core.Es.Aggregate.ReadRepo`) и `to_view:` (захват функции арности 1 `%Agg{} → %View{}`). Связь называет один владелец, как у write-репозитория (ADR-0084): `repo:` и `view:` объявляет behaviour, реализация берёт их у behaviour.
- **Резолв write-репозитория.** Реализация write-репозитория — `<Behaviour>.Pg` по конвенции DI; агрегат, кодек событий, снапшоты, `errors:` и `ns` берутся из её конфигурации.
- **Сигнатуры.** `get_at(%Agg.ID{}, %Version{}, %Context{}, opts \\ [])` → `{:ok, %View{}} | {:error, %Error{}}`; `get_many_at([{%Agg.ID{}, %Version{}}], %Context{}, opts \\ [])` → `{:ok, [%View{}]} | {:error, %Error{}}`. Головы закрыты на `%Agg.ID{}`; `:current` — `FunctionClauseError`. Функции `defoverridable` с сохранением закрытой головы и сужения.
- **Внутренняя свёртка до версии.** Функция модуля write-репозитория (`@doc false`), не колбэк behaviour: начальное состояние — снапшот с версией ≤ `N` или незаведённый агрегат; хвост читается событиями с версиями до `N` включительно; свёртка — `fold/2` агрегата. Снапшоты не пишутся. Для пакета поток каждого уникального id читается один раз до наибольшей `N` его пар, а состояние снимается на каждой запрошенной версии.
- **Отказ «версии нет».** Адрес версии за головой потока или пустой поток — `errors.domain(behaviour write-репозитория, :version_mismatch, detail)` с detail `%{aggregate_id, expected: N, actual: голова | nil, source: :address}`. У `get_many_at` — одна ошибка со списком detail в порядке пар. `Es.Transact` повторяет только `source: :storage`, поэтому новый `source:` повтора не вызывает. Новое значение `source:` — дополнение контракта detail, в CHANGELOG.
- **Пакет.** Уникальна пара `{id, N}`, а не id; одинаковые пары разрешены, результат — в порядке пар; `[]` — `{:ok, []}` без запросов.
- **Сборка (`CompileError`).** `repo:` — не behaviour event-sourced агрегата (в том числе state-stored `Repo.Pg.StateStored`); `view:` — не `use Core.View`; `behaviour:` — не `use Core.Es.Aggregate.ReadRepo`; `to_view:` — не захват функции арности 1; неизвестные опции.
- **ПДн.** События грузятся тем же путём, что у `get`: расшифровка до апкаста, уничтоженное значение остаётся уничтоженным; снапшот с ПДн расшифровывается так же, как у `get`.
- **Транзакция и опции.** Чтение вне `Transact.run`; `opts` — опции запроса, транзакционных нет.
- **Телеметрия.** Те же события `[:es, :aggregate, :load]` и `[:es, :aggregate, :fold]`, метаданные `op: :get_at | :get_many_at`; span нет, как у `get`.
- **Свод.** `docs/rules/13-repos.md` — новый раздел «Состояние на версии»: объявление пары модулей, таблица функций с исходами, запреты MUST NOT (кешировать состояние на версии; звать чтение внутри `Es.Transact.run` / `Transact.run`; отдавать наружу что-либо кроме View), SHOULD на имя по назначению `<Aggregate>.<Purpose>.ReadRepo` / `.View` в каталоге агрегата, доступ — читающим usecase до чтения. Ссылки из `app/13-repos.md` («Read-модель») и `21-observability.md` (новые значения `op`). Форма раздела — по стандарту `00-index.md` (`make rules-check`).
- **CHANGELOG.** «Новое»: пара модулей, функции и как заменить копию агрегата адресом версии (было → стало); новое значение `source: :address` в detail `:version_mismatch`. Ломающих изменений нет.

## Testing Decisions

- Хороший тест проверяет внешнее поведение через публичные функции read-репозитория: исходы, форму результата, телеметрию. Внутреннюю свёртку до версии, запросы и порядок чтения не проверяет.
- **Основной шов — контрактный набор `get_at` / `get_many_at` через базу.** Набор подключается по образцу `Core.EsAggregateRepoContract` и гоняется на двух read-репозиториях-фикстурах: над обычным `Core.EsFixture.Account.Repo.Pg` и над вариантом со снапшотами. Это покрывает снапшот ≤ `N`, снапшот новее `N` и отсутствие записи снапшота. Фикстуры — read-модель по назначению над `Core.EsFixture.Account` со своим View и `to_view`, в `test/support`.
- Сценарии набора: версия 1, промежуточная и голова; версия за головой и пустой поток — отказ `source: :address` с detail; пакет с разными версиями одного id, с повтором пары, с несколькими расхождениями (одна ошибка, detail в порядке пар), пустой пакет; `:current` — `FunctionClauseError`; ПДн — уничтоженное значение после уничтожения ключа субъекта остаётся уничтоженным на любой версии (образец — тесты ПДн `get` в `Core.EsAggregateRepoContract` и `Core.Es.Personal`).
- **Телеметрия** — в том же наборе обработчиком `:telemetry`, по образцу блока `telemetry` тестов write-репозитория: `op:` и `events` свёртки.
- **Сборка** — блок «компиляция» по образцу тестов write-репозитория: каждая причина `CompileError` из решений выше.
- **Сужение результата** — фикстура-потребитель с маркерами `# expect:` (`make consumer-check`, ADR-0014): опечатка в поле View и невозможная clause по результату `get_at` / `get_many_at` дают предупреждение.
- Кейсы — `Core.DataCase`.

## Out of Scope

- State-stored агрегаты: источник истины — строка, свёртки нет; копию они оставляют.
- Граница по времени (`at`) вместо версии; перевод «момент → версия» — дело потребителя.
- Решение (команда) от состояния на версии, ветвление потока.
- История снапшотов и ускорение свёртки далёких версий; решается отдельно по метрике `es_aggregate_fold_events`.
- Read-модель без таблицы над головой потока (`get` с `:current`) через тот же макрос.
- Проверка, что сохранённый у потребителя адрес версии существовал на момент записи адреса.
- Diff двух версий.
